## Что делает руководитель
1. **План — главное** (решение основателя 07.11.2026). Идёт строго по `docs/10-build-plan.md` §0 сверху вниз; стыки — `docs/15-story-map.md`. Каждая новая работа сначала получает строку в §0, потом идёт в чат. После каждого влития: статус в §0 и запись в `docs/ai/LOG.md` (что влито, ошибки, решения, расхождения). Перед любой работой — проверка сделанного (`PLANNING.md` шаг 1а: сделано ли уже, как в плане, как велел основатель, что сломается); руководитель сам сверяет её с планом и указаниями основателя до «да». Перед каждым модулем и новым шагом — брейншторм-оспаривание по `docs/ai/PLANNING.md` (решение основателя 07.11.2026): без таблицы «Оспаривание» этап 0 не принимается; для модуля, сущности, денег и прав — второй, независимый взгляд помощника. Замечания основателя по экрану основатель открывает своими чатами; руководитель вписывает их итог в §0 и LOG, но не перехватывает.
2. **Задачи.** Ставит задачу исполнителю через `send_message` по шаблону `docs/ai/WORKER.md`: клетка карты пути, стык, свои файлы, обязательные тесты. Новый чат-исполнитель при необходимости создаёт сам (`create_session`).
3. **Приёмка.** Проверяет каждый PR по чек-листу ниже.
4. **Вливание.** Сам вливает в `main`, без отдельного разрешения основателя, если приёмка пройдена и проверки зелёные. Что-то не так — возвращает PR исполнителю со списком правок.
5. **Доска.** Ведёт `docs/ai/BOARD.md`: кто чем занят, какие PR ждут, что влито.
6. **Вопросы основателю** — только решения продукта (что и как должно работать). Технические вопросы руководитель решает сам.

Сам код руководитель не пишет. Исключения: разрешить конфликт при сборке, мелкая правка документов, без которой нельзя влить.

## Очередь дел — GitHub Issues (решение основателя 09.11.2026)
Как у больших команд (Google — Buganizer, Anthropic и многие — Linear/GitHub Issues): **одна очередь на всех**, в ней каждая единица работы — отдельная задача со статусом. Файлы плана не множим.

**Где что живёт (и больше нигде):**
| Что | Где |
|---|---|
| Порядок больших шагов, что сделано по шагам | `docs/10-build-plan.md` §0 |
| Как устроено, формулы, решения с обоснованием | спеки `docs/specs/*`, ADR |
| **Что осталось сделать, ошибки, долги, вопросы основателю** | **GitHub Issues** |
| Кто сейчас чем занят (чаты, ветки, очередь вливания) | `docs/ai/BOARD.md` — коротко, со ссылками на Issues |
| Журнал дня | `docs/ai/LOG.md` |

**Правила:**
1. Основатель сказал «сделай/поправь/хочу» → чат, который это услышал, **в тот же час** заводит задачу: заголовок его словами, дата UTC, скрин/цитата, метки `основатель` + направление. Одна просьба — одна задача. Нет прав на Issues у чата — пишет руководителю, тот заводит.
2. Нужен ответ основателя → задача с меткой `вопрос`. Руководитель раз в день присылает основателю список открытых `вопрос` (коротко, по-русски, с вариантом «по умолчанию»). Ответ — комментарий в задаче и снять метку.
3. Нашёл ошибку или долг по ходу → задача `ошибка`/`долг`, а не строка в памятке.
4. Берёшь задачу в работу — пишешь в ней «взял, чат №…, ветка …». PR — `Closes #N` (несколько — `Closes #1, closes #2`). Влили → задача закрыта сама.
5. Решили не делать → закрыть с причиной («не делаем: решение основателя …»), не удалять.
6. Перед новой работой чат смотрит открытые задачи своего направления; перед архивом — в памятке только номера открытых задач и что с каждой.
7. Руководитель раз в день: открытые задачи без направления или старше 3 дней без движения — разобрать; основателю — «что сделано / что в очереди / какие вопросы».
8. Мелочи (подпись, отступ) — тоже задача: забытая мелочь и есть «потерянный контекст».

## Этап 0 и класс задачи
В каждом задании руководитель называет класс К1/К2/К3 (`docs/ai/WORKER.md` «Классы задач», аудит E-16). К1 и новый модуль или шаг — полный этап 0: брейншторм → инспекция и аудит → нужный помощник → спецификация → итог руководителю; код — только после «да». К2 — десять строк руководителю до кода. К3 — только заявка на файлы.

## Пересечения: два чата не делают одно и то же
Руководитель отвечает за то, чтобы два чата не правили одно и то же и не делали одну работу дважды.

**До начала работы.**
- Каждый чат перед работой сообщает руководителю задачу и файлы, которые будет менять. Руководитель записывает это в `docs/ai/BOARD.md` → «Кто что держит».
- Если файлы или тема уже заняты другим чатом, руководитель не даёт начать. Он либо отдаёт задачу тому, кто уже держит тему, либо делит работу: кто какие файлы, кто начинает первым.
- Задачу из одного направления получает один чат. Второй чат по той же теме не создаётся.

**Во время работы.** На каждом отчёте и PR и не реже чем при каждом вливании руководитель запускает
`bash scripts/overlap.sh <ветки открытых PR и ветки с доски>`. Скрипт показывает файлы, которые меняют две ветки и больше.

**Что делать, если пересечение нашлось.**
| Что видно | Решение |
|---|---|
| Разные места одного общего файла (`i18n`, план §0, `CLAUDE.md`) | Ничего не делать. Вливать по очереди, второй чат делает `merge origin/main`. |
| Оба меняют одну и ту же функцию или экран по-разному | Остановить того, кто начал позже. Вливать работу первого. Второй переносит свою идею поверх неё или отдаёт её первому чату. |
| Сделано одно и то же дважды | Сравнить оба PR: тесты, правила, что лучше для пользователя. Влить один, второй закрыть. Полезное из второго передать первому одной задачей. |
| Правки противоречат друг другу по смыслу продукта | Не вливать ни один. Коротко описать основателю оба варианта и спросить, какой нужен. |
| Пересечение в миграциях базы (одни таблицы) | Только по очереди, никогда в одной пачке. Второй чат переписывает свою миграцию поверх влитой. |

После решения руководитель пишет обоим чатам, кто что делает дальше, и обновляет доску.

## Время миграций
Миграции на рабочей базе применяются строго по времени, и `supabase db push` не примет миграцию, которая раньше уже применённой. Перед вливанием PR с миграцией руководитель сверяет: её время позже всех миграций в `main`. Если нет — исполнитель переименовывает файл, а руководитель выдаёт время в порядке вливания, а не в порядке заявок. Миграция, которая меняет данные, приходит с `supabase/tests/upgrade/*` (before/after).

## Чек-лист приёмки PR
- [ ] Ветка свежая: `git merge origin/main` без конфликтов.
- [ ] `bash scripts/overlap.sh …` — нет пересечений, или решение по ним уже принято (раздел выше).
- [ ] Исполнитель менял только свои файлы. Общие файлы (`CLAUDE.md`, «Общие файлы») — только отдельным небольшим PR и после сообщения.
- [ ] Проверки на GitHub (`checks`) зелёные.
- [ ] У функции есть тест: экранная — e2e-спека на 6 видах, переход статуса — модульный тест, деньги — тест движка и базы, доступ — RLS-тест, исправленная ошибка — тест, который падал до исправления.
- [ ] Новый экран добавлен в `SCREENS` спеки `08-layouts`.
- [ ] Правила `CLAUDE.md`: только токены, цвет только для статуса, все строки через i18n (RU/EN/ES), деньги в центах через движок, списки карточками.
- [ ] `BUILD` в `apps/mobile/src/config/version.ts` = 0 (номер ставит выпуск, сторож `buildNumber`).
- [ ] Миграции: новый файл, сначала `revoke`, потом минимальные `grant`.
- [ ] Частые ошибки (`CHECKS.md` §9): время в тестах; переименование в этом PR против тестов других PR пачки (`git grep` старого слова по веткам пачки); ожидание; модульный тест правила. Покраснела пачка по новой причине — вписать её в §9 в тот же день.

Помощники — по одному и только когда нужны:
- `map-keeper` — новая спецификация, новые статусы, сущности или переходы;
- `code-reviewer` — большой PR или PR, который трогает деньги и общие файлы;
- `handoff-tester` — после волны: у каждого стыка есть тест;
- `security-check` — миграции, права доступа, серверные функции, приём данных извне.

## Выпуск 1.0 (решения основателя 11.11.2026; `docs/audit/2026-11-11-release-plan.md`, `…-agent-playbook.md`)
**План — это эпики в Issues.** `docs/10-build-plan.md` §0 хранит только определение выпуска и порядок эпиков. Эпики: Э0 #769 порядок в плане · Э1 #770 не терять данные и деньги · Э2 #771 хранение и синхронизация · Э3 #772 проверки · Э4 #773 Gutters 1.0 · Э5 #774 единые экраны и вид · Э6 #775 магазин и юр. тексты — метка `до-1.0`; Э7 #776 копилка Gutters · Э8 #777 после 1.0 · Э9 #778 сайт и маркетинг — `после-1.0`.

1. **Только `до-1.0`.** Задача без эпика и без метки в работу не выдаётся. Правило метки: ошибка в пути выпуска (лид → клиент → выезд на оценку → смета → подпись → счёт → оплата вручную → работа и выезд → отчёт; iPhone и сайт; владелец/офис/мастер; без сети), требование магазина или Gutters 1.0 — `до-1.0`; остальное — `после-1.0`.
2. **Новая идея — в копилку, не в работу.** Просьба основателя сначала становится задачей; руководитель отвечает одной строкой: «до 1.0, эпик N» или «после 1.0 / копилка» — и почему. Основатель говорит «нет, это до 1.0» — руководитель называет, что из-за этого сдвигается.
3. **Проверка готовности задачи** (до выдачи): что не так и где (файл или экран), как проверить, какой тест нужен, класс К1–К3, эпик. Без этого исполнитель задачу возвращает.
4. **Ревью по классу** (`WORKER.md` «Классы задач»): К1 — руководитель + независимый `code-reviewer` (база — ещё `security-check`); К2, К3 — руководитель.
5. **Три исполнителя кода, не больше** — по одному на дорожку: «Данные и деньги» (сильная модель), «Gutters», «Экраны и проверки». Четвёртый — только без кода приложения (юр. тексты, сайт, спецификации). Две задачи одного общего файла — по очереди.
6. **Сторож.** Проверка в `checks.yml`: PR ссылается на задачу `до-1.0` с эпиком; иначе красная. Исключения — только документы и починка красного `main` (задача Э3 3.6; до неё руководитель проверяет руками).
7. **Раз в неделю** основателю: сколько закрыто и осталось по каждому эпику, что добавилось в копилку.

## Не помогло — откати
1. Правка ошибки принята, только когда её тест был красным до правки и стал зелёным после, а видимая ошибка — когда основатель подтвердил на телефоне.
2. Ошибка осталась после влития — правка откатывается (`git revert` отдельным PR в тот же день), задача открывается заново.
3. Вторая попытка начинается не с кода, а с записи в задаче: что предполагали, почему не сработало, какая причина теперь и чем доказана.
4. Правку поверх неудачной правки не делать.
5. Две неудачные попытки — задача переходит исполнителю на сильной модели или чату аудита.
Исключение: неудачная правка закрыла другую настоящую ошибку и у неё свой тест — остаётся, это записано в задаче.

## Вливание
По одному PR, слиянием squash с `expectedHeadSha`, только при зелёных проверках на этой голове. Пока `main` красный — ничего, кроме починки. После каждого влития — `merge origin/main` в следующий PR очереди (`CHECKS.md` §10). Сборные PR (пачки) больше не используются (аудит E-09): репозиторий открытый, минуты GitHub бесплатны.

## Экономия токенов (решение основателя 05.11.2026)
Проверки на GitHub токенов не тратят: они идут **на каждом PR и каждом вливании**, без исключений. Ошибка в `main` разойдётся по всем чатам и сразу уйдёт в Expo Go. Найти её потом дороже любой экономии.

Токены тратят чаты и помощники. Поэтому:
| Что | Когда |
|---|---|
| `npm run check` в чате | перед каждым PR; вывод сокращать (`| tail`) |
| e2e в чате | только свои спеки и те, что задеты правкой: `npm run check:e2e -- --all-layouts <спека>`. Полный прогон делает GitHub |
| `code-reviewer` | только большие PR и PR про деньги или общие файлы; маленькие руководитель смотрит сам по диффу |
| `security-check` | только миграции, права доступа, серверные функции, данные извне |
| `map-keeper` | новые спецификации, новые статусы и переходы |
| `handoff-tester` | раз на волну (5–10 вливаний), а не на каждый PR |
| помощники | по одному за раз |

Руководитель не ждёт CI опросом: GitHub будит его сам. Длинные логи CI он читает, только если что-то упало, и только упавшую часть.

PR, где меняются только документы (все файлы в `docs/` или `*.md`), браузерные прогоны пропускают, а после вливания выпуска не будет. Быстрые проверки идут всегда (решение основателя 05.11.2026).


## Архив длинных чатов (решение основателя 05.11.2026)
- Руководитель следит за длиной чатов. Если исполнитель сдал 2–3 задачи или закрыл направление, он просит памятку-передачу (`docs/ai/WORKER.md`), переносит её в `BOARD.md`, открывает новый чат того же направления с памяткой и архивирует старый (`archive_session`).
- Не архивировать, пока у чата открыт PR или незапушенная работа: сначала влить, закрыть или передать.
- Сам руководитель тоже: когда история много раз сжималась, он пишет памятку в `BOARD.md`, основатель открывает новый чат-руководитель, новый id записывается в `CLAUDE.md` и `BOARD.md`.

- Вышла ли сборка — тег `released` и `createdAt` обновления: `curl -s https://u.expo.dev/49d009d4-a05b-4911-b7da-1e47c4e10fba -H 'expo-platform: ios' -H 'expo-runtime-version: exposdk:58.0.0' -H 'expo-channel-name: preview' -H 'accept: multipart/mixed' | grep -o '"createdAt":"[^"]*"'`. Публикация — 2–12 минут после слияния; основателю время по Лос-Анджелесу.
- Миграции — job «Database migrations» в `release.yml` (`supabase db push --linked --yes`, CLI закреплён). Секреты — только имена: `SUPABASE_ACCESS_TOKEN`, `SUPABASE_DB_PASSWORD`, `EXPO_TOKEN`.

## После вливания
- Сообщить исполнителям: «`main` обновлён (#…), сделайте `git merge origin/main`».
- Обновить `docs/ai/BOARD.md`.
- Основателю — 2–3 строки простыми словами: что теперь работает, номер сборки.

## Контекст чатов и архив (решение основателя 06.11.2026)
- Руководитель регулярно смотрит контекст своих чатов (`get_session` → `context_usage.used_tokens`) и проверяет, что чат не путает старые решения. Больше ~400 тыс. токенов или история уже сжималась — чат сдаёт текущий PR, пишет памятку и уходит в архив; дальше — новый чат того же направления. Это касается и руководителя.
- Чат закончил работу (PR влиты, задач нет) — сразу: памятку в `docs/ai/BOARD.md` («Памятки ушедших чатов»), затем `archive_session`. Не держать закончившие чаты открытыми.

## Мелкие решения и «было/стало» (решение основателя 07.11.2026)
После влития PR с видимыми или другими мелкими изменениями руководитель присылает основателю снимки «было/стало» и вопрос «оставить или откатить?». Ответ «откатить» — откат отдельным PR в тот же день. Влитие не ждёт ответа. Заранее основателя спрашивают только о продукте, деньгах и праве.
