# Исполнитель OCTODEX

Руководитель проекта один — см. `CLAUDE.md` и `docs/ai/DIRECTOR.md`. Он ставит задачи, принимает PR и вливает их в `main`.

## Правила исполнителя
1. В начале чата прочитать `CLAUDE.md` и `docs/ai/BOARD.md`. **До первой правки** сообщить руководителю (`send_message`; id руководителя — первая строка `docs/ai/BOARD.md`, больше нигде не копируется): задачу, ветку и файлы, которые будешь менять. Если тема или файлы уже у другого чата (доска, «Кто что держит»), не начинать: ждать ответа руководителя.
1а. Если по ходу работы нужен файл, которого не было в списке, сначала сообщить руководителю.
2. Работать в своей ветке и только в файлах своего направления (таблица в `CLAUDE.md`). Чужой или общий файл — сначала сообщение руководителю.
3. В `main` не пушить и PR не вливать. Это делает руководитель.
4. Перед PR: `git merge origin/main`, `npm run check` (вывод сокращать) и e2e только своих спек: `npm run check:e2e -- --all-layouts <спека> …`. Полный прогон делает GitHub. `BUILD` не трогать (всегда 0, номер ставит выпуск). Какие ещё проверки нужны по содержанию PR (база, зависимости, схема в два шага) — `docs/ai/CHECKS.md` §1–§2. И сверка с частыми ошибками — `CHECKS.md` §9 (правило 19 `CLAUDE.md`): время, старые надписи в чужих тестах, ожидание, модульный тест правила.
5. После PR — отчёт руководителю (шаблон ниже). Вопросы о продукте можно задавать основателю напрямую; технические — руководителю.
6. Правки от руководителя — в ту же ветку, затем снова отчёт.

6а. **Очередь дел — GitHub Issues** (`docs/ai/DIRECTOR.md` «Очередь дел»): просьба основателя, ошибка, долг, вопрос — задача в тот же час; PR пишет `Closes #N`; памятка при архиве — номера открытых задач.

6б. **Убрать перед выпуском** (решение основателя 16.11.2026). Заметил что-то, что нужно убрать или спрятать перед выпуском, — допиши строку комментарием в задачу #1790 «Перед выпуском: закрыть репозиторий и убрать лишнее», не в памятку.

6в. **Пока репозиторий публичный:** подробности находок безопасности, ключи, имя и почта основателя — никогда в репозиторий, задачи и описания PR.

6г. **Шаги проверки для основателя автор PR сначала проходит сам** — на вебе или в сборке — и только потом отправляет руководителю: что открыть, что нажать, что видно глазами (16.11: шаги #1650 обещали цвет, которого на холсте нет; основатель: «коричневым ничего не стало, и я не понял, почему должно было стать коричневым»).

6д. **Ветка живёт не дольше 2 дней** от первого коммита до сдачи PR (принято аудитом 16.11; trunkbaseddevelopment.com/short-lived-feature-branches). Не успеваешь — разрежь задачу на PR поменьше (данные отдельно от экранов, `docs/audit/2026-11-15-plan-stages.md` А3 К17) и сообщи руководителю до конца второго дня.

## Архив длинных чатов (решение основателя 05.11.2026)
Чат с длинной историей теряет контекст (старое сжимается в пересказ) и тратит токены: каждый ход заново читает всю историю. Поэтому:
- один чат — 2–3 задачи или одно направление; сдал — в архив;
- признаки, что пора: история уже сжималась, чат путает старые решения, задача закрыта, а впереди новая большая;
- перед архивом — **памятка-передача** руководителю (`send_message`), 10–20 строк: что влито (номера PR), что открыто и в каком состоянии, ветки, какие файлы держит, что дальше по очереди, нерешённые вопросы;
- незапушенной работы перед архивом не оставлять: всё в ветке и в PR или явно в памятке;
- руководитель переносит памятку в `docs/ai/BOARD.md`, открывает новый чат того же направления и даёт ему памятку первым сообщением. Архивирует руководитель или основатель.

## Классы задач (решение основателя 11.11.2026, аудит E-16)
Класс называет руководитель в задании; он же стоит меткой `К1`/`К2`/`К3` на задаче.
| Класс | Что это | До кода | Кто смотрит PR |
|---|---|---|---|
| **К1. Данные, деньги, права** | `src/data/**`, `src/cloud/**`, `supabase/**`, платежи, роли, новая сущность или статус; новый модуль или шаг | полный этап 0 (ниже) + короткая спецификация + «да» руководителя | руководитель + `code-reviewer`; база — ещё `security-check` |
| **К2. Обычная задача** | экран, правило, компонент, находка аудита размера M | десять строк руководителю: что есть сейчас, что меняю, какие тесты, какие файлы | `code-reviewer` (дешёвая модель, вывод 5–10 строк) → руководитель по выводу; К2 с общими файлами из `CLAUDE.md` — как К1 |
| **К3. Мелкая правка** | одна ошибка, до ~30 строк, без новых сущностей | только заявка на файлы | руководитель по диффу; без миграций и общих файлов — автослияние |

**Дизайн-решения — через независимого design-reviewer** (решение основателя 16.11.2026: «Те правила, которые ты принимаешь касательно дизайна, я хочу, чтобы ты обсуждал с ревьюером, дизайнером, а не сам решал»). Для любого правила вида и поведения (DS) и любого дизайн-решения по экрану: (1) предложение делает дизайнер или автор экрана; (2) независимый `design-reviewer` (не тот, что помогал автору) даёт заключение по DS, iOS HIG и образцам; (3) руководитель и аудит вид не выбирают, а сверяют только слова основателя, противоречия с другими правилами, деньги/данные/право; если дизайнер и ревьюер расходятся, оба мнения идут основателю; (4) в `DESIGN-SYSTEM.md` правило попадает со строкой «предложил / проверил». Без заключения design-reviewer в PR руководитель дизайн-PR не принимает.

**Экранная задача К2** (экран, компонент, вид; решение основателя 13.11.2026) — до сдачи PR `design-reviewer` смотрит снимки «было/стало» (390 / 820 / 1280 × две темы) без выводов автора; блокирующее исправить, его вывод (3–10 строк) — в отчёт руководителю. **Любая экранная правка К2/К3 вида — в описании PR пара снимков «было» и «стало» на 390 в светлой теме** (решение аудита 16.11.2026; `CHECKS.md` §10 п.8а): без неё PR не вливается.

Порядок для любого класса: прочитать (`CLAUDE.md`, верх `BOARD.md`, задачу, находку аудита, спеку шага) → заявить файлы и дождаться ответа → **воспроизвести** (для ошибки — тест, который падает; не падает — сообщить руководителю, не чинить вслепую) → исправить наименьшей правкой, без рефакторинга «заодно» → проверить (`CHECKS.md` §10) → сдать одним пушем; в отчёте строка «тест падал до правки: да, <имя теста>». Задача берётся только с меткой `до-1.0` и эпиком; найденную по ходу другую ошибку — отдельной задачей, не в свой PR.

## Зоны файлов (согласовано чатом аудита 11.11.2026)
В каждой зоне одновременно работает **один** исполнитель: (а) `src/data/**` + `src/cloud/**`; (б) `supabase/**`; (в) `src/modules/gutters/**` и gutter-часть движка; (г) экраны и `src/ui/**`. Правка клиента и миграция по одной сущности или операции — одна задача одного чата К1. Чат «Проверки» (`e2e/**`, `.github/**`, сторожа в `apps/mobile/test/**`) в потолок трёх исполнителей кода не входит, пока не трогает `src/**` и `supabase/**`. Зона занята — заявка ждёт ответа руководителя.

## Этап 0 — до кода (для К1 и нового модуля или шага; решение основателя 05.11.2026)
Задача класса К1 начинается так. Код пишется только после этапа 0 и «да» руководителя.
Порядок и шаблоны — `docs/ai/PLANNING.md` (решение основателя 07.11.2026).
1. **Брейншторм.** Что нужно пользователю (подрядчику с телефона), 2–3 варианта, плюсы и минусы, рекомендация.
1а. **Оспаривание (обязательно).** Каждое утверждение из PRD, спеки, ADR, карты пути и плана, на которое опирается задача, — подтвердить, опровергнуть или оспорить, с доказательством. Таблица «Оспаривание» в спеке (`PLANNING.md` §3, шаг 3). Опровергнутое правится в своём документе в том же PR.
0. **Проверить, что уже сделано** (решение основателя 07.11.2026): сделано ли уже, так ли как в плане, так ли как велел основатель, что сломается — таблица `PLANNING.md` шаг 1а. Мелкие решения (кроме вида, см. «Дизайн-решения» ниже) принимать самому после брейншторма и сравнения вариантов, к PR — снимки «было/стало»; основатель решает после влития «оставить или откатить» (CLAUDE.md «Решения», 07.11.2026). Заранее спрашивать его только о продукте, деньгах и праве.
2. **Инспекция и аудит.** Прочитать, что уже есть в коде и в спецификациях, найти, что сломается, что дублируется, какие стыки затронуты (`docs/15-story-map.md`).
3. **Нужный помощник** — по одному за раз, по смыслу задачи:
   - экран и вид — `design:design-critique`, `design:accessibility-review`, `design:design-system`;
   - устройство кода — агент `Plan` (архитектор);
   - статусы, сущности, переходы — `map-keeper`;
   - база, права, приём данных извне — `security-check`;
   - большой или денежный код — `code-reviewer`.
4. **Спецификация.** Раздел в `docs/specs/*` или `docs/14-*`: что делаем, варианты, решение, стыки, тесты. Шаблон — `docs/15-story-map.md` §7. Приёмка — сценариями «ДАНО / КОГДА / ТОГДА» с номерами С1, С2…, у теста тот же номер (§7 п.9; решение основателя 17.11.2026).
4а. **«Чем лучше образца»** (решение основателя 15.11.2026: «там, где мы хуже, сделать не так, как у тех, кого хвалят, а лучше»; шаблон — `docs/audit/2026-11-15-research/README.md` §11). Если у функции есть сильный образец у конкурентов, этот раздел в спеке обязателен. Он для К1 и К2 (новые функции, экраны, переделки) и этапа 0; для К3 (мелкая правка, исправление ошибки) не требуется. Раздел один и покрывает правило 28 «самое современное» (решение основателя 16.11.2026): как делают лучшие сегодня (Apple HIG, лидеры рынка и лучшие приложения вообще, не только FSM/CRM) + чем мы лучше измеримо. В нём:
   - шаги и число нажатий у лучшего образца, с цитатой;
   - жалобы на образец, с цитатой;
   - наш вариант с измеримым отличием;
   - чем это проверим;
   - что самое современное из доступного в стабильном виде и почему выбрано (вход: код, Face ID, Apple/Google, passkey, а не пароль).
   Границы: «современное» не повод расширять задачу — путь больше задачи предлагается руководителю отдельной задачей; для хранения, синхронизации и платежей проверенное важнее нового (этап 1); бета не идёт в продакшн; новая зависимость — правило 17. В PR класса К1/К2 — строка «Современно: что выбрали и почему лучше»; в К3 её нет.
   «Сделали как у Jobber» приёмкой не считается. Задача в работу не уходит, пока этот раздел не принят.
5. **Итог руководителю** (10–15 строк): сколько утверждений подтверждено, опровергнуто, оспорено; выводы, план PR, файлы, вопросы основателю. Потом проектирование и реализация.

6. **План реализации и его вторая проверка** (решение основателя 15.11: «пересматривал код, логику, обдумывал и потом делал; проверял сам себя»; README исследований §13.6). Для К1 и К2 после этапа 0 (К2 — после десяти строк) исполнитель пишет план реализации по коду: какие файлы и функции, в каком порядке, что может сломаться, какие тесты. План проверяет **не автор** — помощник-ревьюер (`code-reviewer` или `Plan`) получает план и код без рассуждений автора; его вывод — руководителю вместе с планом. Код — после «да» руководителя на проверенный план. **К1 и новое правило DS — не меньше двух независимых проверок** (решение основателя 16.11.2026: «всё обдумывать хорошо, дважды советоваться с ревьюерами… должны проверять сильные специалисты»): два разных ревьюера (для DS — два `design-reviewer`, для К1 — `code-reviewer`/`security-check` и второй агент), второй не видит выводов первого; оба вывода — в PR. **Чужой код — только смотреть**, если репозиторий под AGPL/GPL (решение аудита 16.11.2026): идею брать можно, код не копировать; лицензию образца проверять до чтения кода (правило 17 — про зависимости, это — про копирование).

Для К2 и К3 полный этап 0 не нужен (таблица «Классы задач» выше); шаг 1а `PLANNING.md` (проверить, что уже сделано) — по-прежнему для любой правки.
