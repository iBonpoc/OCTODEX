## 4. Статусы и переходы (сверка с картой §5)

Приложение `unscheduled · scheduled · in_progress · done` ↔ база `draft · scheduled · in_progress · completed` (`statusMap.ts`).

| Переход | Кто | Когда | Сейчас | Стало |
|---|---|---|---|---|
| `unscheduled → scheduled` | офис | первый выезд (S9) | ✅ | без изменений |
| `scheduled → in_progress` | авто | первый выезд работы «На месте» | нигде (сервер — только внутри оплаты) | стор + сервер на `visit.step on_site` |
| `in_progress → done` | **только** owner/admin/office | «Да, выполнена» или «Завершить работу» | авто при оплате (стор и сервер) | одна функция: стор `completeJob` + база `public.complete_job(job_id)` → `completed` |
| `scheduled → done` | owner/admin/office | «Завершить работу» вручную (работа без выездов «на месте») | — | та же функция; сервер идёт `scheduled → in_progress → completed`; прямой `update` статуса проверяется тем же правилом (страж `t31`); на закрытую работу новый выезд не ставится |
| оплата выезда | мастер | шаг «Оплата» | ставит `done` | статус работы не меняет; выезд работы закрывается (`completed`) оплатой — это его последний шаг; при $0 тоже (раньше оставался открытым на сервере) |
| `scheduled → unscheduled` | офис | отмена последнего выезда | `cancel_visit` | без изменений; записать в карту S17/S9a |

Вычисляемое «Работа выполнена?» = работа `in_progress` и нет открытого выезда (все `done` или отменены) и хотя бы один `done`. Видят owner/admin/office (очередь дел и шторка на работе). Мастеру ничего не спрашиваем.
`done` = база `completed` (не `closed`): у `completed` мастер уже не видит код ворот — так и нужно.

Сейчас при оплате $0 операция на сервер не уходит, и стор с сервером расходятся — исчезает вместе с переходом на `complete_job`.

## 5. Как приходит / как уходит
- Работа приходит: из сметы (как сейчас), из формы «Новая работа» (S17), из «＋ Работа» на клиенте, объекте, Плане и Главной (`fab`, держит «Каркас»; маршрут `/job/new?customerId=&propertyId=` — мой).
- «В пути» с работы и выезда: SMS телефона с текстом на языке клиента (`tFor(docLanguageFor(...))`), событие в ленту (`visit.step en_route` уже пишет). До своего номера — только SMS телефона.
- «Да, выполнена» → если остаток > 0 — «Создать счёт на остаток» (существующий `issueInvoice`, сумма — движок).

## 7. Экраны

### 7.1 Работа `job/[id]`
Шапка «Работа JOB-0001» (`Job.number`, без номера — «Новая работа»), подзаголовок — название. Блок «Связано»: Клиент › · Объект (адрес) › · Лид › (через смету) · Смета ›. Вкладки (`Segmented`): **Детали · Деньги · История**.
- **Детали:** ряд действий **Начать · В пути · Оплата · Заметка · Файл** (по ближайшему открытому выезду; без выезда «Начать»/«В пути»/«Оплата» скрыты); название и описание; статус значком и словом + «Завершить работу» (офис, владелец; не для `done`); клиент: позвонить, SMS, маршрут; доступ/код ворот по правам (из объекта); расписание: выезды карточками, «Запланировать» / «Ещё выезд»; тип работы; направление; команда (люди выездов); заметки. Карта и «расстояние от меня» — после `Property.geo` в данных демо, иначе строка адреса с «Маршрут».
- **Деньги:** то, что есть (выписка по договору, расходы и прибыль по праву `canSeeProfit`), «Создать счёт» (этап / остаток), место под «Позиции» (П-2a). Мастер видит только «К оплате» своей работы.
- **История:** фильтры Всё · Действия · Заметки · Звонки, лента событий работы и её выездов (отменённые — с причиной), внизу «Добавить заметку».
- Шторка «Работа выполнена?»: «Да, выполнена» · «Нужен ещё выезд» (→ `/job/schedule`).
- 390 — один столбец; 820/1280 — та же разметка, ширина по `Screen`.

### 7.2 Выезд `visit/[id]`
- Сверху «Связано»: Работа JOB-… › (у осмотра — Лид LEA-… ›), Клиент ›, Объект ›. Мастер тоже (свои).
- Ряд действий как у работы (В пути · Оплата · Заметка · Файл). «Этажей: N» убираем из ядра (13 §3.3).
- Шаги работы: Еду → На месте → Работа → Подпись → Оплата → Готово. Осмотр: Еду → На месте → Готово; после «Готово» главная кнопка **«Сделать смету»** (лид и объект подставлены). Кнопка «Смета» в ряду у работы убирается (смета делается с осмотра или лида).
- Офис и владелец: «Перенести» (форма выезда) и «…» → «Отменить выезд» (шторка `CancelVisitSheet` уже есть).

### 7.3 Новая работа `job/new`
Одна форма (13 §3.5): клиент (поиск или новый — имя, телефон, адрес; новый `active`) → адрес (объект клиента или новый) → название, тип (`job_types`), направление, описание → «Дата и время» или «Назначить позже» (с датой — `VisitFormFields`, команда, «Накладка», затем «Сообщить клиенту?») → «Создать работу». Продажи: только «Назначить позже» (блок даты скрыт). Без сети — в очередь, в шапке «Новая работа» до номера. Клиентов `do_not_service` в выборе нет — через `canServe(db, customerId)` из `features/clients.ts` (PR 4b «Лиды и клиенты»); до неё — место в фильтре.

### 7.4 Форма выезда (перенос)
В `VisitFormFields` добавить: «Весь день», «Сдвинуть − / +», быстрые даты «Позже сегодня (18:00) · Завтра утром (9:00) · В понедельник (9:00)» по поясу компании (`todayKey`/`atMinute`). Остальное — как в 03 §7.1.

## 8. Права, офлайн, уведомления
- Права: «Связано» не даёт ссылок на деньги мастеру и продажам там, где их нет в 15-flows §2 (М); мастер видит только свои выезды и их работу.
- «Завершить работу», перенос, отмена — owner/admin/office (в приложении `director`, `dispatcher`; `canPlan`). Сервер проверяет сам (`complete_job`, `cancel_visit`).
- S17: создавать могут owner, admin, office, sales; **sales — только без даты** (база: в `create_job` с датой — отказ для sales; `jobs_insert` уже пускает sales).
- Офлайн: всё через `mutate` и очередь; новая работа — временный id, номер после синхронизации.
- Уведомлений новых нет; «Работа выполнена?» — пункт очереди дел, не пуш.

### 12.1 Работы создаются только сервером
**Сейчас.** `authenticated` имеет `select, insert, update` на `public.jobs` (core.sql), политики `jobs_insert` (owner/admin/office/sales), `jobs_update` (staff); правила новой строки держит триггер t14 (`20261106046000`). Приложение вставляет jobs само в трёх операциях `cloud/ops.ts`: `lead.book`, `lead.visit` (стор их больше не ставит — только старые очереди; работа «Estimate visit») и `estimate.deposit` (ставит до сих пор). UPDATE — только `status` (advanceJob), `description, job_type_id, tax_enabled, tax_rate_bps` (job.update), `service_category_id` (job.category); других колонок старые версии ops.ts не писали (git log). Серверные пути (create_job, execute_estimate, portal_accept, cancel_visit, complete_job, t90) — security definer, права `authenticated` им не нужны.

**Риск.** `INSERT … ON CONFLICT DO NOTHING` без права INSERT падает 42501 и на уже существующей строке; `run()` считает 42* постоянной ошибкой, `flush` выбрасывает операцию. Для `estimate.deposit` это потеря задатка (счёт и платёж идут после работы); уже сегодня — если на сервере ещё нет работы этой сметы (t14 отклоняет строку с `estimate_id`). Минимальной версии приложения нет — старые сборки живут неопределённо.

| Что | Варианты | Решение |
|---|---|---|
| Когда отзывать INSERT | а) сейчас; б) два шага правила 16 | б: шаг 1 — приложение больше не вставляет jobs; шаг 2 — отдельным PR `revoke insert` + `drop policy jobs_insert`. **Условие шага 2** (руководитель 07.11): есть «минимальная версия приложения» (сервер отдаёт min build, старая сборка просит обновиться — задача «Каркаса»), и min build ≥ сборки PR 6-1. По дате не делаем |
| `lead.book` / `lead.visit` из старых очередей | а) звать `create_job`; б) осмотр без работы, как `visit.inspection` (с 20261105280000) | б: выезд `kind=inspection` с `lead_id`, `property_id`, без `job_id` |
| `estimate.deposit` | а) новая RPC «задаток»; б) без работы — временная ошибка | а + б: `public.record_estimate_deposit(estimate, payment id, method)` security definer, owner/admin/office/sales. Работу и счёт задатка делает подпись (execute_estimate); функция пишет только платёж на остаток этого счёта по данным сервера (не сумму телефона). Нет работы → P0001, отказ (не «позже»: очередь идёт строго по порядку, значит подпись так и не дошла или смета одобрена старым путём — ожидание работу не создаст; временная ошибка никогда не выбрасывается и держала бы очередь вечно, отказ считается до MAX_TRIES и выбрасывается). После отказа телефон перечитывает данные, и на смете снова «Задаток к оплате» — тост «получен» не остаётся неправдой; нет счёта задатка → 22023; задаток уже оплачен → второго платежа нет; повтор того же id → тот же платёж. revoke/grant по правилу 18. Долг «Сметам»: стор `payDeposit` по-прежнему ставит локальную работу и счёт до перечитывания |
| UPDATE | а) колоночный grant сейчас; б) с шагом 2 | а: `revoke update` + `grant update (status, title, description, job_type_id, tax_enabled, tax_rate_bps, service_category_id)`; старые сборки ничего другого не пишут; `title` — простой текст, ни один сторож от него не зависит (переименование работы — следующий экран); `contract_total_cents` не даём (t14 и так отбрасывает) |

**Тесты.** T72 — create_job / execute_estimate / portal_accept создают работу; update разрешённых колонок проходит; запрещённые (`customer_id, property_id, estimate_id, number, deleted_at, completed_at, contract_total_cents, company_id`) — 42501. T73 — `record_estimate_deposit`: owner/admin/office/sales — да (как `payments_insert_staff`), tech/чужая компания/anon — нет, повтор не двоит платёж, сумма с сервера. Подготовку данных в `core_rls.sql` (~100 строк пишут jobs под `as_owner_a/as_office_a`) перевести на `as_super` там, где ломается колоночный grant. Правка свойства адреса работы (`property_id`) — сейчас приложение её не шлёт; если понадобится — отдельной RPC.

**Ревью security-check 07.11.** (1) У приложения больше нет права на `customer_id, property_id, completed_at, contract_total_cents …`, поэтому ветки UPDATE в t14 / t31 / t18 для этих колонок недостижимы: t14 работает только для `authenticated`, серверные функции его обходят. Теперь сторож — колоночное право. Тесты T41/T44/T47 проверяют отказ 42501, триггеры остаются запасной защитой. (2) Платёж пишется на клиента и компанию счёта. (3) Повтор засчитывается только по платежу этой компании на счёте задатка этой сметы; любой другой занятый id → 22023 с одним и тем же текстом, своё это или чужое — не видно. (4) Задаток уже оплачен → `already_paid: true`; локальный платёж операции остаётся на телефоне до перечитывания — долг «Сметам» (стор `payDeposit`).

**Ревью руководителя 07.11 (#247).** Узкие риски, записаны. (а) Старая очередь (до 05.11, сборки ≤ ~143) с операциями на `jobId` из `lead.book` — `photo.add`, `expense.add`, `visit.pay` — теперь получит 23503: внешний ключ `(company_id, job_id) → jobs`, а работы нет. Операция выбрасывается, данные пропадают. Нужен телефон, который больше двух дней держит неотправленную очередь и уже обновился — не чиним. (б) Два телефона одновременно повторяют один id: второй может получить `already_paid` вместо `repeat`. Деньги не двигаются.
