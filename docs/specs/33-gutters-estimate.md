## П23.1 Брейншторм
**Что нужно подрядчику.** Нарисовал на крыше → «Смета» → готовые строки по разделам из его прайса, работа отдельными строками (О4), правит руками как любую смету, отправляет. Перерисовал — «Обновить смету»: пересчитались только строки замера; его ручные цены, количества и свои строки остались.

**Где хранить «эта строка — из замера».**
| Вариант | Плюсы | Минусы |
|---|---|---|
| А. Колонки `estimate_line_items` (C4a: `source`, `source_key`, `section_key`) + приложение пишет (C4b) | видно в базе, отчёты по строкам | миграция + два шага (правило 16); строки переписываются из `calc_inputs` при каждом сохранении — колонки лишь копия; ядро смет менять в двух местах |
| **Б. Поля строки в документе** (`CustomLine.source = { module, key, section, calcQty }`, `CustomLine.override`), они уже доходят до базы в `calc_inputs` | без миграции; одна правда (документ); старые версии приложения просто не знают поле (терпят — строка как ручная) | в `estimate_line_items` метки нет (отчёты по модулям — позже, тогда C4a как копия) |
**Выбор: Б** (C4a/C4b переносятся «когда понадобится отчёт по строкам модуля»).

**Как обновлять.** Ключ строки = `matchKey` детали (то же, что ищет позицию прайса). «Обновить смету»: строка с ключом — новое количество (`calcQty`), если её `quantity` не правили руками (`override` нет); цена — из прайса, если не правили; строка, которой больше нет в замере, — убирается, если не тронута, иначе остаётся с пометкой «нет в замере»; свои строки не трогаются; новые — в конец своего раздела.

**Разделы.** Ядро не знает разделов; строки идут в порядке разделов движка (`section`: gutter, corners_caps, fasteners, downspouts, adapters, ds_bottom, guards, consumables, labor) — работа последней; имя раздела — в описании строки не пишем (решение основателя по виду — «было/стало»).

**Цена не найдена.** Строка с ценой 0 и пометкой «нет цены» (не $0 молча) — отправить нельзя, пока не поставили (C5: проверка перед отправкой — общий механизм ядра «чего не хватает», модуль даёт свои причины).
