> v1, 17.11.2026, чат «Вход». Задачи: #1822 (Apple + Google, до-1.0), #1821 (Face ID, до-1.0), предпосылки #1675
> (runtime `fingerprint`), #1787 (аккаунты только сервером). Дополнение к спеке 52 (вход по коду).
> Решения основателя 16.11: Apple и Google — до 1.0, оба вместе; Face ID — до 1.0; «во всём самое современное» (#1824).
> Этап 0 (К1): план → проверка безопасности ×2 и осуществимости (17.11) → аудит «принято как документ» (17.11).
> Проверяющий Apple — §9. Ручные шаги основателя — `docs/guides/apple-google-setup.md`.
> Подробности атак здесь не описываются — только что закрываем (руководитель 16.11).

## 1. Как будет у человека
- **Первый вход:** «Продолжить с Apple» и «Продолжить с Google» (Apple первой на iOS, Google — на Android и вебе;
  кнопки по HIG и правилам бренда Google) над почтой; ниже «или по почте» → код (спека 52). Галочка согласия (7а-1)
  нужна и для Apple/Google: без неё нажатие подсвечивает галочку. Отмена системного окна — без сообщения.
- **Каждый следующий раз:** открыл GoRix → Face ID → внутри (если замок включён).
- **Новое устройство:** Apple/Google одним касанием или код.
- **Без сети:** Face ID работает (только устройство); Apple, Google, код — «Нужна сеть, чтобы войти».

**Чем лучше (WORKER п.4а):** Jobber/HCP — почта + пароль (≥ 2 поля и запоминание); у нас — 1 касание + Face ID на
iPhone, повторные входы — только Face ID.

## 2. Как устроено
| Часть | Решение |
|---|---|
| Apple на iPhone | `expo-apple-authentication` → `identityToken` с nonce (sha256 сырого nonce — в запрос Apple, сырой — в Supabase; 32+ случайных байта `expo-crypto`, одноразовый, не хранится и не пишется в журнал) → `supabase.auth.signInWithIdToken({ provider: "apple", token, nonce })` |
| Google (iPhone, Android, веб) и Apple (Android, веб) | `signInWithOAuth({ provider, options: { redirectTo: "gorix://auth/callback", skipBrowserRedirect: true } })` → системное окно `expo-web-browser` `openAuthSessionAsync` → `exchangeCodeForSession` (PKCE, `flowType: "pkce"`). Нативный SDK Google не берём: бесплатный `@react-native-google-signin` 17 не передаёт nonce, на Android — устаревший Legacy SDK. Платная «Universal Sign In» — после 1.0, отдельным решением (правило 17) |
| Имя от Apple | приходит один раз: сохранить на устройстве сразу, записать в `public.users` операцией #1606, стереть после записи. Вопрос имени — только с «Позже» (App Review 4.0/4.8) |
| `locale` провайдера | триггер `app.tg_handle_new_auth_user` (`core.sql:1198`) пишет `locale` в `public.users` с check `en/es/ru`; провайдер даёт `en-US`, `pt-BR` → создание аккаунта упадёт. Миграция (правило 16 — только тело функции): первая часть ∈ {en, es, ru}, иначе `en`; длина `full_name` ограничена. Тест базы T332 |
| app.json / EAS | `ios.usesAppleSignIn` + плагин `expo-apple-authentication`; `expo-local-authentication` с `faceIDPermission` и `NSFaceIDUsageDescription` (RU/EN/ES в `locales`); `expo-secure-store` с `configureAndroidBackup`; `expo-web-browser`; Supabase Redirect URLs `gorix://**`, `https://gorix.expo.app/**`; `ITSAppUsesNonExemptEncryption: false` (AES только для своих данных — освобождённая категория) |
| Новые зависимости | `expo-apple-authentication`, `expo-local-authentication`, `expo-secure-store`, `expo-web-browser` — `npx expo install`, проверка по `docs/ai/CHECKS.md` §4. `expo-crypto` 58 уже стоит (AES-GCM в нём есть) |
| Старые сборки | нативные модули → новая сборка; JS по воздуху до старых сборок не дойдёт после #1675 (`fingerprint`). Страховка: модули загружаются только ленивым `require` в `try` / `requireOptionalNativeModule`; нет модуля — кнопок Apple/Google и замка нет, вход по коду как прежде |

## 3. Новые аккаунты: хук «Before User Created» (одна дверь для #1787 и #1822)
Хук не видит пароль (в GoTrue он не передаётся), поэтому «почту по коду» и «почту с паролем» по данным хука не
отличить. Решение:
- Регистрация в Supabase **остаётся включённой** (`DisableSignup` проверяется до хука).
- Хук пропускает:
  - `apple` и `google` — **только если почта подтверждена у провайдера** (`email_verified = true`);
  - `email` — **только по разрешающему токену** от функции `request-code` (#1787): токен **одноразовый**, **привязан к
    почте** (хранится хэш почты), **живёт около 10 минут**, таблица доступна **только `service_role`**; хук гасит токен
    при использовании.
- Всё остальное — отказ: анонимные, телефон, SSO, прочие провайдеры, Google/Apple без подтверждённой почты, `email` без
  токена. Исключений по полям, которые задаёт клиент (`user_metadata`), нет. Сбой хука — отказ, не пропуск.
- Postgres-хук: `security definer`, `search_path = ''`, `revoke all … from public, anon, authenticated`,
  `grant execute … to supabase_auth_admin` (правила 16, 18), T52.
- **Тесты** (база, с T333): чужая почта с токеном другой почты → отказ; повтор того же токена → отказ; истёкший токен →
  отказ; без токена → отказ; Google/Apple с `email_verified = false` → отказ; Apple/Google с подтверждённой почтой →
  пропуск; хук отказывает при ошибке. Облачный тест: вызывается ли хук для admin `createUser` и `/invite` (демо-учётка §9).
- **Доступность:** документация хуков (supabase.com/docs/guides/auth/auth-hooks, прочитано 17.11.2026) — «Before User
  Created … Free, Pro»; на странице цен в строке «Auth Hooks» для Free/Pro он не назван. Проверить в панели проекта до
  кода. Если хука на нашем плане нет — запасной путь: только функция `request-code` (#1787) создаёт аккаунты admin API,
  а Apple/Google — через серверную проверку id-токена (JWKS, aud, iss, exp, nonce).

## 4. Связывание учёток
- Вход через Google или Apple с почтой, которая уже есть у аккаунта по коду, **не создаёт вторую учётку и не захватывает
  чужую**: Supabase связывает identities по почте **только когда почта подтверждена у провайдера** (`email_verified`) и
  у существующего аккаунта. Неподтверждённого аккаунта с паролем на чужую почту не бывает — хук (§3).
- В панели: ручное связывание (Manual linking) — **выкл.**; «Secure email change» — **вкл.**
- **Apple «Скрыть e-mail»** → адрес-прокладка `…@privaterelay.appleid.com` → **отдельная учётка** (почта не совпадает).
  Как человек связывает: войти обычным способом (код на настоящую почту) → «Профиль и аккаунт» → «Способы входа» →
  «Добавить Apple» (`linkIdentity`) — это после 1.0 (задача); до него — честно в подсказке «Скрыли почту в Apple? Это
  отдельный аккаунт. Войдите по коду на свою почту».
- Приглашения (S21): проверка почты в `accept_invitation` **остаётся** (`legal_acceptance.sql:218, 221`). Прокладка с
  приглашением на настоящую почту → экран «Это приглашение для <почта>» → «Войти по коду на эту почту». db-тест:
  прокладка с чужим токеном приглашения → отказ.
- Облачные тесты: (1) аккаунт по коду + Apple с той же подтверждённой почтой → один аккаунт; (2) Google с неподтверждённой
  почтой → отказ хука.

## 5. Face ID и защищённое хранилище
**Что где лежит:**
| Где | Что | Сколько живёт |
|---|---|---|
| Keychain (`expo-secure-store`, `AFTER_FIRST_UNLOCK_THIS_DEVICE_ONLY`, без `requireAuthentication`) | только ключ AES-256 (32 случайных байта) | до выхода / удаления аккаунта; не уходит в резервные копии и на другой телефон |
| AsyncStorage | сессия Supabase, зашифрованная AES-256-GCM (`expo-crypto`, новый IV на запись, AAD = имя записи) | access-токен — 1 ч; refresh-токен — до выхода (см. §8 про срок) |
| AsyncStorage | флажок «Блокировать по Face ID», тайм-аут, метка ухода в фон | до выключения или выхода |
| Веб | localStorage, как сейчас (без шифрования) — честно | |

- **Перенос старой сессии** (правило 16): прочитать → записать новое → прочитать и сверить → стереть старое; обрыв на любом
  шаге — старое остаётся. Ошибка Keychain или расшифровки ≠ «нет сессии» (не стирать, не запускать `signOutWipe`;
  повторить позже) и ≠ откат к открытому тексту. Явный выход — только если после восстановления Android из копии ключа нет.
- **Отзыв:**
  - выход: `signOut` (обычный — `scope: "local"`; «Выйти на всех устройствах» — `"global"`), стереть ключ, флажок замка,
    согласие; Google — отзыв токена провайдера;
  - удаление аккаунта: то же + отзыв Apple/Google (§6);
  - смена устройства: ключ `THIS_DEVICE_ONLY` на новый телефон не переносится → там вход заново; «Выйти на всех
    устройствах» гасит refresh-токены остальных (облачный тест);
  - iOS хранит Keychain после удаления приложения → при первом запуске после установки (нет отметки в AsyncStorage) свои
    ключи SecureStore стираются.
- **Замок:** ворота над навигатором (глубокие ссылки и нажатия на пуш — после разблокировки); смотрит только `background`
  (системные листы дают `inactive`); при `inactive` — заглушка от снимка в переключателе; «N минут» — метка времени
  (варианты: сразу, 1, 5, 15). Включение переключателя сразу вызывает проверку. Название по типу: Face ID / Touch ID /
  «Биометрия». Пока замок включён — пуши без подробностей клиента.
- **Отказ биометрии → обычный вход:** `user_cancel` / `system_cancel` / `app_cancel` → экран замка («Разблокировать»,
  без автоповтора); `lockout` → код-пароль телефона (решает система); `not_enrolled` / `passcode_not_set` /
  `not_available` → замок выключается с объяснением; «Войти заново» на экране замка = обычный выход без потери очереди
  (`signOutWipe` без стирания черновиков) → экран входа (код / Apple / Google).
- Честно: замок защищает интерфейс, не данные на диске; смену набора лиц не замечает.

## 6. Удаление аккаунта (5.1.1(v), S22)
- Apple-аккаунт: свежий вход через Apple → `authorizationCode` (живёт ~5 минут, одноразовый) передаётся в
  `delete-account` новым **необязательным** полем (старые сборки удаляют как прежде, правило 16). Функция **в том же
  запросе, до `closeSignIn`**: обмен кода (`client_id` = `com.gorix.app` для iPhone или Services ID для веба/Android,
  `client_secret` — JWT, подписанный ключом .p8 из секретов функции) → сверка `sub` с Apple-идентичностью `uid` →
  `revoke`; повторы внутри запроса; не вышло — удаление всё равно идёт, в журнал только факт (без кода и токена).
  Refresh-токен Apple не храним.
- Google: отзыв токена провайдера на клиенте (`oauth2.googleapis.com/revoke`).
- `CLEARED_METADATA` дополнить полями Apple/Google; облачный тест — после удаления в `auth.identities.identity_data` нет
  имени и почты.
- `app.signed_in_recently` принимает вход по id-токену (отбрасывает только `token_refresh`) — облачный тест.
- **Тест (на подделках):** обмен → revoke → удаление; revoke упал → удаление прошло, журнал без кода; `sub` не совпал → не
  отзываем чужое; поле отсутствует → прежнее поведение.

## 10. Тесты
unit: nonce (в запрос — sha256 hex, в Supabase — сырой); перенос сессии и все обрывы; «модуль есть, но бросает → открытым
текстом не пишем»; «модуля нет» (импорт); таймер замка и коды `authenticateAsync`; разбор отказов провайдеров (своими

приглашение с прокладкой. Облачные: связывание (§4), «Выйти на всех устройствах», `signed_in_recently`,
`identity_data` после удаления, хук для admin/`/invite`.
