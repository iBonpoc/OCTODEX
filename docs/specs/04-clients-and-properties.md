# 04. Клиенты и объекты — спецификация OCTODEX

> Черновик v1, 04.11.2026. Шаг хребта «Клиенты и объекты» (`docs/15-story-map.md` §6: после «Лиды» и «Осмотр и План», до «Сметы»).
> Источники: `docs/03-prd/03-customers-properties.md` (PRD 03), `docs/04-domain-model.md`, код сборки 39 (`app/client/*`, `(tabs)/clients.tsx`), база (`customers`, `contacts`, `properties`, `tasks`, `activities`, `notes`), решения основателя 03.11 и 04.11.
> Ядро не знает ниши: поля «тип крыши», «fire zone», «этажность» есть в базе, но показываются только модулями (Gutters, Roofing). В ядре — адрес, доступ, люди, история, документы.

## 1. Стыки

| Стык | Что приходит / уходит | Как у клиента |
|---|---|---|
| **S3** лид → потенциальный клиент | Из лида при записи на оценку или первой смете: люди (с телефонами и email), адрес → объект, источник, метки лида, заметки | Создаётся `Customer(status=prospect)` + люди + `Property`. Повтор не создаёт дубля (одна функция `lead_to_client`, владелец — шаг «Лиды»). Если найден существующий клиент по телефону/email — лид привязывается к нему, новый не создаётся |
| **S5** клиент → смета | «Новая смета» из клиента или объекта | Смета получает `customerId` + `propertyId` (объект выбирается явно, по умолчанию последний) |
| **S8 / S8a** подпись или ручная победа | лид `won` | Клиент `prospect → active` |
| Клиент → работа, визит | «Записать», «Запланировать» | Работа на конкретном объекте |
| Клиент → счёт, оплата | счета работ | Баланс и «Оплатил всего» (LTV) на карточке |
| Клиент → новый лид | повторная заявка того же человека | Новый лид привязан к клиенту, бейдж «Уже клиент» (шаг «Лиды») |
| Всё → история клиента | события лида, смет, работ, визитов, счетов, оплат, заметки, задачи | Лента «История» в карточке клиента и объекта |

## 2. Сравнение и решения

| Тема | У нас сейчас | Jobber / HCP / ServiceTitan | Решение |
|---|---|---|---|
| Клиент: человек или компания | только имя | все три: person / company | `kind` (уже в базе): человек или компания (управляющая компания, HOA, бизнес); у компании — имя компании + контактные люди |
| Люди у клиента | один телефон и email | несколько контактов с ролями | Блок «Контакты», как у лида: люди (основной, супруг(а), арендатор, управляющий, бухгалтер…), у каждого несколько телефонов и email, звёздочка = основной, язык EN/ES |
| Объекты | список адресов | Jobber: несколько properties; ST: locations | Несколько объектов **только внутри клиента** (и лида): вкладка «Объекты» + карточка объекта. Отдельного раздела «Объекты» в меню нет (решение основателя 04.11) |
| Метки | нет | теги в Jobber/HCP | Список меток компании (как источники: + новая, правка, скрыть); нейтральные плашки; на клиенте; лид клиента показывает метки клиента |
| Статус клиента | prospect / active | lead / active / archived | Хранится: `prospect`, `active`, `archived`, `do_not_service`. Показывается вычисляемый ярлык (§4) |
| История | только списки | лента активности | Одна лента клиента: все события его лидов, смет, работ, визитов, счетов, оплат, заметок, задач |
| Деньги на карточке | баланс | баланс + lifetime value | «Должен» (открытые счета) и «Оплатил всего» (оплаты − возвраты); только офис/директор |
| Задачи | у лида | у клиента | Общая сущность `Task` (уже есть), у клиента и объекта своя вкладка |
| Файлы | нет | фото, документы | Вкладка «Файлы»: фото с визитов, файлы от клиента, PDF смет и счетов |
| Доступ на объект | нет | gate code, заметки | Заметки доступа (собака, калитка, парковка) и код ворот; мастер видит код только в день визита и накануне |
| Дубли | предупреждение в лиде | слияние | Предупреждение при создании; «Возможный дубль» и «Слить» — шаг 17 C3, §13 |
| Импорт | нет | CSV | CSV с предпросмотром и отменой — отдельная волна (C3) |

Не делаем в ядре: тип крыши, fire zone, этажность на экранах ядра (это модули); «оценку» клиента; цветные метки (цвет только для статусов).

## 3. Сущности и поля

### 3.1 `Customer` (✚ — новое в приложении; в базе почти всё есть)
| Группа | Поля |
|---|---|
| Кто | `kind` (person/business), `name` (display_name), ✚`companyName` |
| Люди | ✚`people[]` → `Contact` (см. 3.2); один основной |
| Адрес для счетов | ✚`billingAddress` (если отличается от объекта) |
| Источник | `sourceId` (первый источник, ставится при S3; меняет только директор) |
| Метки | ✚`tagIds[]` |
| Статус | `status`: prospect / active / archived / do_not_service (+ причина) |
| Деньги (вычисляется) | ✚`balanceCents` (открытые счета), ✚`lifetimeCents` (оплаты − возвраты) |
| Служебное | ✚`number` CLT-0001 (нумерация компании), `createdAt`, `lastActivityAt` |

### 3.2 `Contact` (человек) — та же форма, что у лида (шаг «Лиды» использует её же)
`name`, `role` (main / spouse / tenant / property_manager / assistant / accountant / other), `language` (en/es), `preferredContact` (call/sms/email), ✚`phones[]` {`number`, `label` mobile/home/work/other, `isPrimary`}, ✚`emails[]` {`address`, `isPrimary`}, `smsConsent` (позже, для автоматических SMS), `isActive`.
В базе: `contacts` (есть) + ✚`contact_phones`, ✚`contact_emails`.

### 3.3 `Property` (объект)
`label` (Дом, Сдаётся, Офис…), `kind` (single_family / multi_family / commercial / hoa_common), адрес (`line1`, ✚`unit`, `city`, `state`, `zip`), ✚`accessNotes`, ✚`gateCode` (отдельно, с ограниченным доступом), ✚`contacts` объекта (арендатор, управляющий — ссылки на `Contact`), `attributes` (поля модулей; ядро не читает).

### 3.4 Остальное
| Сущность | Что |
|---|---|
| ✚`Tag` | `id`, `name`, `isActive`, `position` — список компании |
| `Task` | уже есть; `subjectType` = customer / property добавляется |
| `Note` | уже есть (команда / только я, закрепление) |
| `File` | фото и документы; ✚`customerId`, `propertyId` |
| `Activity` | уже есть; лента собирает события из всех таблиц |

Не заводим: отдельную «историю клиента» как таблицу — лента собирается из событий; «оценку» клиента.

## 4. Статусы

Хранится (как в `docs/15-story-map.md` §5): `prospect`, `active`, `archived`, `do_not_service`.

| Переход | Как |
|---|---|
| — → `prospect` | авто S3 (лид → клиент при оценке или смете) |
| `prospect` → `active` | авто S8 (подпись / депозит), S8a (ручная победа), или первая оплата |
| ручное создание клиента | сразу `active` (сборка 28) |
| `active` → `archived` | вручную директор; нельзя при открытом балансе («должен $850») |
| любой → `do_not_service` | вручную директор, обязательная причина; новые лиды с тем же телефоном получают красный бейдж |

**Ярлык в списке (вычисляется, не хранится):**
| Ярлык | Когда | Цвет (токены статусов) |
|---|---|---|
| Новый | `prospect`, есть открытый лид / смета не подписана | info |
| Отказался | `prospect`, все его лиды `lost` | neutral |
| Мы отказались | `prospect`, все его лиды `declined` | neutral |
| В работе | `active` + есть открытая работа, визит или смета | info |
| Должен | открытый баланс > 0 | warn (bad, если есть просроченный счёт) |
| Клиент | `active`, ничего открытого | ok |
| Архив / Не обслуживаем | по статусу | neutral / bad |

## 5. Как приходит / уходит

Приходит: из лида (S3), вручную «+ Клиент» (сборка 28), импорт CSV (волна C3).
Уходит: в смету, работу, визит, счёт (через кнопки карточки); в новый лид (повторная заявка); в архив.

## 7. Экраны

### 7.1 Список «Клиенты»
- Каждый клиент — карточка: имя (или компания), ярлык статуса, метки, основной телефон, первый объект, «Должен $…» если есть.
- Поиск: имя, любой телефон любого человека, email, адрес любого объекта, номер CLT-/LEA-/EST-/INV-/JOB-/RCT-.
- Фильтры: ярлык статуса, метки (несколько), источник, «Должен». Сортировка: недавние / имя / оплатил всего.
- «+ Клиент» (как сейчас) + предупреждение о дубле по телефону/email.

### 7.2 Карточка клиента
Шапка (как у лида): `‹ Клиенты`, имя, номер CLT-0012 · источник · с какого числа, ярлык статуса (нажатием — шторка статуса: в архив, не обслуживаем), метки (нажать — выбор), кнопки связи иконками (позвонить, SMS, email, маршрут к основному объекту), «⋯» (изменить, архив); «Возможный дубль» и «Слить» — карточкой на «Обзоре» (§13).
Для директора/офиса: «Должен» и «Оплатил всего».

Вкладки (строка вкладок прилипает при прокрутке; меняется только содержимое под ней):
| Вкладка | Содержимое | Пустое состояние |
|---|---|---|
| **Обзор** | закреплённые заметки, ближайшее (визит, задача, неоплаченный счёт), контакты (люди с телефонами), объекты кратко, последние 3 события | — |
| **Объекты** | карточка на каждый объект: адрес, ярлык, открытые сметы и работы, следующий визит; «+ Объект» | «Объектов нет — + Объект» |
| **История** | лента: лиды, сметы (отправлена / открыл / подписал), работы, визиты, счета, оплаты, заметки, задачи, смены статуса; фильтр «Всё / Общение / Документы / Деньги» | «Пока ничего не было» |
| **Документы** | сметы, счета, квитанции карточками со статусами | «Смет и счетов нет — + Смета» |
| **Задачи** | открытые и выполненные; «Напомнить» с быстрыми сроками | «Задач нет — Напомнить» |
| **Файлы** | фото с визитов и от клиента, PDF; «+ Фото / файл» (камера, галерея, файлы) | «Файлов нет — + Фото / файл» |

Все правки — шторками iOS (смахивание, вопрос «Сохранить изменения?»).

### 7.3 Объекты клиента и карточка объекта
- Где: только внутри клиента (вкладка «Объекты») и лида. Отдельного раздела в меню нет. Найти объект по адресу — общий поиск клиентов (ищет по адресам всех объектов).
- Список: адрес, клиент, ярлык, открытые сметы/работы, следующий визит; поиск по адресу.
- Карточка объекта: `‹ <Клиент>`, адрес, ярлык, тип, кнопки маршрут/позвонить контакту объекта; «Сейчас на объекте» (все открытые сметы и работы); доступ (заметки, код ворот — по правам); люди объекта (арендатор, управляющий); вкладки История · Документы · Файлы · Задачи.

### 7.4 Ширины и темы
390: одна колонка, вкладки сверху. 820: шапка + вкладки, объекты в 2 колонки. 1280: слева шапка и контакты, справа вкладки. Обе темы, только токены «Наряда».

## 8. Права, офлайн, уведомления

| Кто | Видит |
|---|---|
| Директор | всё |
| Диспетчер / офис | всё, кроме изменения источника клиента |
| Мастер | только клиентов и объекты своих визитов (сегодня, будущие, последние 14 дней по календарю компании; не считаются отменённые визиты, неявки, визиты отменённой или закрытой работы; визит без даты считается по последнему дню гибкой недели, а без неё — по дню создания); заметки — свои и командные заметки того, что он видит (свой лид, объект, работа, клиент, смета); без денег («Должен», «Оплатил всего»), без источника; код ворот — только в день визита и накануне |
| Субподрядчик | только адрес, заметки доступа и контакт объекта по своему наряду |

Код ворот и пароли — только в поле «Доступ» объекта (мастер видит его в день визита и накануне). Заметки объекта мастер видит при любом визите в окне, поэтому в форме заметки объекта, работы и клиента стоит подсказка: «Код ворот и пароли пишите в поле „Доступ“ — мастер увидит их только в день визита». Отдельного типа заметки нет (решение руководителя 05.11).

Офлайн: просмотр, поиск, правка клиента/людей/объектов/меток, заметки, задачи — в очередь. Слияние, архив с проверкой баланса, импорт — только онлайн.
Уведомления: срок задачи → пуш исполнителю и в «Сегодня».

## 10. Волны и вопросы основателю

| Волна | Что |
|---|---|
| **C1** | Люди у клиента (несколько телефонов/email), метки, ярлык статуса, номер CLT-, новая шапка, вкладки Обзор · История · Документы · Задачи · Файлы с пустыми состояниями, «Должен / Оплатил всего», права мастера |
| **C2** | Вкладка «Объекты» у клиента и лида, карточка объекта, доступ и код ворот, люди объекта, «Сейчас на объекте». ✅ у клиента (e2e 27, T20); вкладки объекта «История · Документы · Файлы · Задачи» — следующим шагом; у лида объект один (адрес) и переходит клиенту при S3 |

**C2 — проверка безопасности (#62).** Сделано: мастер не меняет время, работу, лид и удаление визита (`app.tg_visit_tech_guard`). Отменённая или закрытая работа, а также завершённый визит и «клиент не пришёл» кода не открывают. В приложении код ворот хранится только в памяти и на телефон не записывается. Правило в приложении берёт часовой пояс компании. Роль sales входит в офис (`app.is_staff`) и видит код, как диспетчер.
**Потом:** проверять триггером, что `contact_ids` ссылаются на людей этого клиента; проверять, что `companies.timezone` — настоящий часовой пояс.
| **C3** | Импорт клиентов CSV (предпросмотр, дубли, отмена), слияние дублей, архив / не обслуживаем |

Ответы основателя (04.11.2026):
1. Отдельного меню «Объекты» нет — объекты живут только внутри клиента и лида.
2. Метки по умолчанию: VIP, Постоянный, Избранный, «Не звонить после 18:00» — да.
3. Код ворот мастеру — только в день визита и накануне (по умолчанию, основатель не возражал).
4. «Принёс всего» → **«Оплатил всего»**; видят директор и офис, мастер — нет.
5. Номер клиента — да, 3 буквы: **CLT-0001** (как LEA, EST, INV, RCT, JOB). Миграция пересоздаёт ограничение `doc_type` со всеми значениями (estimate, job, invoice, receipt, purchase_order, change_order, lead, customer) — общий файл, согласуется с чатом лидов.

## 11. Волна 4 «Клиент и объект» (06.11.2026, «Лиды и клиенты» №5)

Источник: `docs/specs/13-app-structure.md` §3.3, §3.16, §5, §8 (волна 4); сценарии `docs/specs/15-flows.md` §1.13, §1.14. Этап 0 принят руководителем 06.11.

### 11.1 Что делаем и почему
| Что | Варианты | Решение |
|---|---|---|
| Карточка клиента | вкладки (как было, §7.2) · строки со счётчиками (Jobber, Workiz) | **строки** (решение 13 §3.3). Шапка не меняется: имя, номер · статус · метки, звонок / SMS / email / маршрут, деньги (офис). Ниже — контакты главного человека, «Следующее», затем строки: Объекты · Адрес для счетов · Люди · Работы · Лиды · Сметы · Счета и квитанции · Задачи · Заметки · Файлы · История |
| Где открывается список строки | новый маршрут на каждую строку · один экран `/client/<id>?s=<строка>` | **один адрес с `?s=`**: новых экранов в `src/app` нет, «вверх» — к клиенту (`nav/hierarchy.ts`, согласовано) |

## 12. Волна 4b «Не обслуживаем» и импорт CSV (06.11.2026, «Лиды и клиенты» №6) — этап 0 принят руководителем 06.11

### 12.1 Что нужно подрядчику
Пометил клиента «Не обслуживаем» — и больше случайно не поставит ему работу, смету или выезд: ни с телефона, ни из очереди без сети, ни со второго телефона. Новый лид с тем же телефоном сразу видно — красная метка «Не обслуживаем».

### 12.2 Варианты и решения
| Что | Варианты | Решение (рекомендация) |
|---|---|---|
| Где запрет | только экран · только база · оба | **оба**: экран прячет кнопки (`canServe`), база отказывает триггером (очередь без сети, старая сборка, второй телефон) |

### 13.2 Что нужно подрядчику
После импорта CSV, заявок с сайта и звонков у одного человека появляются две карточки: история и деньги делятся, SMS уходят дважды. Нужно: (1) увидеть «возможный дубль» без поиска; (2) за 3 нажатия с телефона слить две карточки в одну, ничего не потеряв; (3) сказать «это не дубль», чтобы метка не висела вечно (арендатор и хозяин по одному адресу).

### 13.3 Варианты
| | Вариант | Плюсы | Минусы |
|---|---|---|---|
| А | Экран «две колонки» с выбором каждого поля (PRD CUST-US-12) | полный контроль | на телефоне 390 две колонки не помещаются; 10+ нажатий; редко нужно |
| **Б (рекомендую)** | Шторка «Слить»: какая карточка остаётся (переключатель), что переходит (люди, объекты, лиды, сметы, работы, счета, оплаты — числа), «Слить» → подтверждение → тост «Отменить» | 3 нажатия; понятно, что будет | значения полей не выбираются: остаются у основной, пустые заполняются из второй |
| В | Автослияние при совпадении телефона | ноль нажатий | ошибка необратима, деньги переезжают молча — нет |

### 13.4 Решение
**Признаки дубля** (чистая функция `clientDuplicates`, только в приложении, работает без сети): любой телефон любого человека (последние 10 цифр, `fullPhoneKey`), любой email (без регистра), адрес любого объекта (строка улицы + квартира + zip, без регистра и знаков, сокращения St/Ave/Rd/Dr/Ln/Ct/Blvd/N/S/E/W). Не считаются: архив, слитые, пары «не дубль». Слабый признак — только адрес: подпись «тот же адрес», а не «тот же телефон».
**Где видно:** в списке «Клиенты» у карточки значок `warn` + «Возможный дубль»; на карточке клиента (вкладка «Обзор», сверху) — `Card` с каждым кандидатом: имя, номер, причина, «Слить» и «Не дубль».
**Слияние:** шторка Б. По умолчанию остаётся старшая карточка (раньше создана — у неё номер CLT меньше, ссылки в письмах старые). После «Слить» — подтверждение («Карточку <B> нельзя будет вернуть из приложения»), затем стор сливает сразу (люди — правилом `mergePeople`, объекты, лиды, документы, задачи, заметки → основной; метки — объединение; пустые поля основной — из второй; «не обслуживаем» у любой → у итоговой, с причиной), тост «Отменить» 5 с (операция ждёт в очереди, `SEND_AFTER_MS`). Вторая карточка: `status = archived`, `merged_into_customer_id = основная`; в списках не показывается; старая ссылка `/client/<B>` показывает «Слито с <A>» и кнопку «Открыть».
**«Не дубль»:** новая колонка `customers.not_duplicate_ids uuid[]` (правило 16: только добавление); пишет функция `public.mark_not_duplicate(p_id, p_other)` — добавляет один id (два телефона не перетирают друг друга), owner / admin / office. Пара не показывается, если id есть у любой из двух. Телефон или почта, общие для больше чем 5 карточек (офис управляющей компании), дублем не считаются (`CROWD`).
**Сервер:** одна функция `public.merge_customers(p_keep uuid, p_drop uuid)` (security definer, одна транзакция). Кто: только owner / admin своей компании (`app.has_role`). Повтор без вреда: вторая уже слита в эту же — ничего не делает и возвращает основную; слита в другую или удалена — отказ. Обе карточки одной компании, разные, основная не слита. Переносит `customer_id` у `contacts` (люди с тем же телефоном / email сливаются в одного, как `app.move_lead_people`: недостающие телефоны и email переходят, лишний человек — `deleted_at`, его `activities.contact_id` → оставшийся), `properties`, `leads` (+ `referred_by_customer_id`), `estimates`, `jobs`, `invoices`, `payments`, `payment_attempts`, `expenses`, `files`, `lead_sources.customer_id`; `customer_tags` — объединение; `activities`, `notes`, `tasks` с `subject = customer B` → A (`status_events` — только дописываемая история самой B, остаются); `custom_field_values` B — только где у A нет значения. Номера документов и суммы не меняются. Защиты счетов, оплат, подписанных смет и «не обслуживаем» пропускают только эту замену: функция пишет одноразовую строку в закрытую `app.customer_merge_runs` и ставит её id во флаг транзакции `app.merging_customer`; `app.merging_customer(old, new)` верна лишь для пары B → A этой транзакции; в защитах без security definer — ещё `current_user ≠ authenticated/anon`. Флаг без строки ничего не даёт (T134). Любое другое поле по-прежнему под защитой. Деньги в пути (попытка оплаты open/processing, платёж pending, возврат pending у второй) — отказ `merge_payment_in_flight`. Гард оплат (`tg_payment_guard`) правит «Деньги» №5 в миграции 20261109050000 — исключение для этой пары вписано там. В `audit_log` — строка `customer / merge` с id перенесённых строк по таблицам (для отката через поддержку, А16). Старый телефон, который не знает о слиянии и пришлёт новую строку на B: триггеры `t01_follow_merged_customer` (`contacts, properties, leads, estimates, jobs, invoices, payments, payment_attempts, expenses, files`) и `t01_follow_merged_subject` (`activities, notes, tasks`) меняют B на A при вставке (правило 16). Строка истории, которую пишет сама функция про B (снятие «не обслуживаем» при архиве), остаётся у B. `merged_into_customer_id` пишет только функция (`t02_customer_merge_guard`); статус слитой карточки не меняется. Правки самой карточки B со старого телефона после слияния: люди и метки (`save_customer_people`, `set_customer_tags` — целым списком) сервер отклоняет с подсказкой `customer_merged`, приложение показывает «Изменение клиента не сохранено» и ведёт на основную карточку (целый список B не должен заменить людей и метки A); поля карточки (`customer.update`) и свои поля (`custom_field_values` с `entity_id = B`) ложатся на архивную B — известное ограничение, видно поддержке. «Ничего не теряется» относится к новым строкам и документам.
**Люди и деньги при слиянии (проверка руководителя 08.11):** у совпавшего человека отказ от SMS (`opted_out` важнее всего), даты отказов (раннее) и язык (если у основной пуст) берутся строгой стороной — то же исправлено в `app.move_lead_people` (лид → клиент), TCPA / CAN-SPAM, правило 7. «Без налога» остаётся, если было у любой карточки, с её пометкой; шторка говорит об этом, когда у карточек разное. Триггеры следования не ждут на чужой компании (`is_member`); service_role меняет клиента черновика, как раньше.
**Офлайн:** операция `customer.merge` в очереди; сервер переносит всё, что есть у B в момент выполнения, плюс триггер следования. Отказ сервера (деньги в пути, уже слита, нет прав) не пропадает молча: карточка «Клиенты не слиты на сервере» с причиной (`outboxRejected`, подсказки `merge_payment_in_flight`, `merge_already_merged`). Попытка оплаты, брошенная на странице `/p/` больше суток, слиянию не мешает. PRD §9 («только онлайн») опровергаем — правлю в этом PR.
**Приложение:** `Customer.mergedIntoId` (из `merged_into_customer_id`), `Customer.notDuplicateIds`; мутации стора `mergeCustomers(keepId, dropId)` и `markNotDuplicate(aId, bId)` возвращают `undo` (повтор — двойное нажатие — ничего не ставит в очередь); op `customer.merge` → `merge_customers`, `customer.notDup` → `mark_not_duplicate`. Значок и блок дубля видят owner / admin / office (`canSeeClientDups`); «Слить» — только owner / admin (`canMergeClients`); «Не дубль» — офис (`canMarkNotDuplicate`). Шторка предупреждает: «не обслуживаем» перейдёт на основную, её открытые ссылки на сметы перестанут открываться.

| **Б (рекомендую)** | **rpc пакетами**: телефон разбирает файл (как сейчас), создаёт `import_job`, шлёт строки пакетами по 250 в `public.import_customers(p_job, p_rows)`; каждый пакет — одна транзакция; сервер сам проверяет каждую строку и ищет дубли | права и RLS в SQL, тесты в `core_rls.sql` (T), без нового деплоя; обрыв сети теряет не больше одного пакета, повтор пакета без вреда (ключ строки); прогресс «1 250 из 5 000» | телефон должен быть на связи до конца (≈ 20 пакетов по < 2 с); при закрытом приложении импорт ждёт «Продолжить» |
| В | Файл в Storage + фоновая обработка (pg_cron / очередь) | телефон можно закрыть | новая инфраструктура (воркер, опрос статуса, уведомление), сложнее отчёт до «Применить»; для 5 000 строк не нужно |

### 14.4 Решение
**Путь:** вариант Б. Разбор и предпросмотр остаются на телефоне (`parseCsv`, `guessMapping`, `rowsOf`, `planImport`) — это «Проверка» до кнопки; запись и окончательная проверка — на сервере. Окончательный отчёт — серверный (пока телефон смотрел, другой сотрудник мог добавить клиента). В демо-режиме (без облака) тот же экран ходит в локальную «функцию» `localImportBatch` с тем же правилом (`classifyImportRow`) — e2e на 6 видах проверяет весь путь, облачная e2e — настоящий сервер.

**Лимиты:** строк в импорте — до **5,000** (решение основателя; больше — «Разделите файл»: разбираем 5,001 строку и останавливаемся); файл — до **10 МБ**; ячейка — до 200 символов (как сейчас); пакет — **250 строк** (одна транзакция ≲ 2 с при лимите запроса Supabase 8 с; замер — в PR); сервер отклоняет пакет > 250 строк, импорт > 5,000 строк, строку длиннее лимитов (`import_too_big`); у компании одновременно один открытый импорт (`import_busy`), он закрывается сам через 24 часа без пакетов.

**Таблицы (правило 16 — только добавление):** `public.import_jobs` (`id` — с телефона, `company_id`, `target` = `customers` (check, на будущее — каталог), `source_kind` = `csv`, `file_name`, `file_sha256`, `total_rows`, `lead_source_id`, `status` `applying | applied | undone`, `counts jsonb` {added, dup_added, skipped по причинам}, `created_by`, `applied_at`, `undone_at`, `undo_until` = +30 дней); `public.import_rows` (`job_id`, `line`, `row_key`, `result` `added | dup_added | skipped`, `reason`, `customer_id` — новый или совпавший; ключ `(job_id, line)`). RLS: читать — owner/admin/office своей компании; писать напрямую — никто (`revoke all`, только функции). Это `ImportJob` / `ImportRow` домена.

**Функции (правило 18: `revoke all … from public, anon`, `grant execute … to authenticated`):**
- `public.import_customers_start(p_job uuid, p_file_name text, p_sha256 text, p_total int, p_source uuid) → jsonb` — owner/admin/office (`app.has_role`); в приложении пункт «Импорт из CSV» сейчас видят все, кроме мастера (`clients.tsx:39`, `office = role !== "tech"`) — sales его больше не видит (`canImportClients`): массовое создание и отмена, снимающая карточки, — дело офиса, как «Не обслуживаем» (§12.8); тот же `p_job` — вернуть его состояние (повтор). Тот же `file_sha256` у прошлого применённого импорта — ответ `same_file` с датой (экран: «Этот файл уже загружали 08.11 — всё равно продолжить?»; дубли всё равно отсеются).
- `public.import_customers(p_job uuid, p_rows jsonb) → jsonb` — пакет. Строка: `{line, name, first_name, last_name, company, phone, email, address, city}`. **Ключ строки** `row_key` = md5 нормализованных полей; `(job, line)` уже есть с тем же ключом — вернуть сохранённый итог (обрыв сети после записи), с другим — `row_changed`. Для каждой новой строки — то же правило, что `planImport` (`classifyImportRow`, общий порядок причин): `noName` → `badPhone` → `badEmail` → `noContact` → `dupClient` (телефон или email любого человека любой не слитой и не удалённой карточки — с её статусом: архив / «не обслуживаем») → `dupFile` (повтор более ранней строки этого импорта) → иначе **добавить**. Добавление = те же строки, что `createCustomer` в `cloud/ops.ts` (customers `active` с источником, основной человек, объект) плюс имя/фамилия/компания — одной транзакцией пакета.
- `public.import_customers_finish(p_job) → jsonb` — `applied`, `counts`, одна строка `audit_log` (`import_job / apply`, без личных данных).
- `public.undo_customer_import(p_job) → jsonb` — owner/admin/office, ≤ 30 дней: снимает (`deleted_at`) карточки импорта с их людьми и объектами, **если** к карточке ничего не прибавилось (лид, смета, работа, счёт, оплата, заметка, задача, звонок, слияние); остальные остаются, ответ `{undone, kept}`. Повтор — без изменений. `audit_log` `import_job / undo`.
- **Серверный ключ дубля** (одно правило с `clientDuplicates.ts`): `app.phone_key` (есть), новые `app.email_key(text)` = `lower(trim)`, `app.address_key(street, unit, city, zip)` — тот же разбор, что `addressKey` (буквы и цифры, сокращения Street→st … West→w, без apt/suite/unit, zip 5 цифр, иначе город; без цифры в улице — пусто), и `app.customer_keys(p_company) → (customer_id, kind, key)` по людям и объектам карточек компании. Колонку `customers.match_key` не пишем: у карточки много людей и объектов, один ключ на карточку не подходит (оспаривание №3); колонка остаётся пустой (правило 16 — не удалять).

**«Возможный дубль» при импорте:** не сливаем никогда. Совпал телефон или email — строка пропускается «Уже есть клиент <имя>» (как сейчас; повторная загрузка того же файла не даёт дублей). Совпал **только адрес** объекта живой карточки (слабый признак §13.4) — карточка **добавляется**, итог `dup_added`, в отчёте «Добавлен — возможный дубль <имя>», а после импорта она сама получает значок «Возможный дубль» в списке (правило `clientDuplicates`, отдельной пометки в базе не нужно) — решают «Слить» / «Не дубль» (§13). Адрес, общий для > 5 карточек (`CROWD`), дублем не считается — как в списке.

**Экран `/client/import`** (тот же, шаги те же): «Проверка» — три группы карточек: «Добавим N», «Добавим, возможный дубль K» (с именем совпавшего), «Пропустим M» (строка, причина — первые 50 каждой группы, «Показать все» на 1280/820 нет — только счётчик; полный отчёт по строкам — кнопка «Скачать отчёт CSV» после импорта: номер строки, итог, причина; формулы экранированы — долг §12.5 (в)). «Импортировать (N)» → подтверждение не нужно (обратимо 30 дней) → полоса «Загружено 1 250 из 5 000» (по пакетам) → экран остаётся открытым: итог по ответам сервера «Готово: добавлено N, возможных дублей K, пропущено M», карточки строк, которые не просто «добавлены» (первые 50), «Скачать отчёт» (CSV: строка, имя, итог, причина, кто; формулы — текстом), «К клиентам»; тост «Отменить» 5 с (зовёт `undo_customer_import`; правило 5). Перевод строки внутри ячейки — пробел (и на телефоне, и на сервере). Обрыв сети или ошибка пакета — «Импорт остановлен на строке 1 251» и «Продолжить» (тот же `job`, тот же файл в памяти экрана); закрыли экран — при выборе того же файла (`sha256`) открытый импорт продолжается с первой неотправленной строки. Без сети кнопка выключена (как сейчас). Отмена позже 5 с (до 30 дней) и «Продолжить» после закрытого экрана — экран «Импорты» в «Ещё действия» (`/client/imports`: карточка на импорт — дата, файл, итог, статус; «Продолжить» у открытого, «Отменить импорт» у применённого ≤ 30 дней с подтверждением и ответом «снято N, осталось K — у них уже есть документы») — **PR 3 этого шага** (решение руководителя 08.11).

**Офлайн (правило 6):** импорт — не правка одной записи, а перенос базы; он и сейчас только при сети. В очередь не кладём: 5,000 строк в очереди держат все остальные правки телефона. После итога телефон перечитывает компанию (`refresh`), новые карточки появляются в списке.

### 14.9 Проверка безопасности проекта (security-check, 08.11, до кода) — всё вписано в решение
1. **Компания импорта** — `import_customers_start(p_company, p_job, …)`: роль по `app.has_role(p_company, owner/admin/office)`; job вставляется `on conflict do nothing`, затем сверяются компания и автор; `p_job` чужой компании или чужого автора — отказ `not allowed` (как `merge_customers`), состояние не возвращается. Остальные функции берут компанию только из строки job и проверяют роль сами. `lead_source_id` — составной FK `(company_id, lead_source_id)`.
2. **`app.customer_keys`** — `revoke all … from public, anon, authenticated`; зовётся только изнутри definer-функций с компанией job; ключи компании считаются один раз на пакет (временная таблица `on commit drop`).
3. **Отмена** снимает только строки `result in (added, dup_added)` с `created = true` (никогда — совпавшую карточку). Карточка остаётся, если у неё есть: лид, смета, работа, счёт, оплата, попытка оплаты, расход, файл, заметка, задача, звонок/сообщение, метка, новый человек или объект, правка карточки (`row_version` > исходного), смена статуса, заявка приёма, слияние (цель или источник). Карточка берётся `for update`.
4. **Гонки** — частичный уникальный индекс `import_jobs (company_id) where status = 'applying'`; `import_customers` берёт job `for update`, принимает пакеты только в `applying`; ключ `(job_id, line)`.
5. **Застрявший импорт** закрывается лениво внутри `start` (нет пакетов 24 ч → `applied` с тем, что есть); owner/admin может закрыть чужой открытый импорт.
6. **Лимиты считает сервер**: принятые строки ≤ 5,000, `line` в 1..`total_rows`, `jsonb_array_length` ≤ 250 до разбора, `file_name` ≤ 200, `sha256` — 64 hex; не больше 10 импортов на компанию в сутки (`import_daily_limit`).
7. **RLS**: у `import_rows` своя `company_id`, составной FK `(company_id, job_id)`, `t11_company_id_immutable`; чтение — `app.has_role(company_id, owner/admin/office)` без join; `created_by`, `status`, `undo_until` ставит только сервер.
8. **Данные из файла**: при приёме убираются управляющие и bidi-символы; отчёт CSV экранирует `= + - @ \t \r` в начале ячейки (то же правило — для будущих выгрузок клиентов); ответы — только коды (`import_too_big`, `row_changed`, `import_busy`), без текста SQL.
9. **`dupClient`** отдаёт только имя и статус карточки (office и так видит всех клиентов по RLS); слитые и удалённые не участвуют.
10. **`audit_log`** — только `job_id`, `total`, `counts`; без имени файла и причин по строкам.
11. **Старые версии приложения** (правило 16) импортируют построчно через `createCustomer`; запрет для sales там только в интерфейсе — принятый риск (обычные права sales на создание клиента те же), записан в долги.
