## 1. Пояс компании (`companies.timezone`)

### 1.1 Инспекция
- Колонка `text not null default 'America/Los_Angeles'` (`20261104000000_core.sql:82`), проверки нет.
- Сервер считает «день компании» через `now() at time zone tz` в функциях: депозитный счёт при подписи клиента (`20261104070000:115`, `20261104020000:222`, `20261105240000:353`), срок сметы (`20261105240000:177, 186, 202`), письма (`20261105350000:171`), видимость визитов мастеру (`20261105200000:27`, `20261105160000`, `20261105170000`, `20261105280000` — там `coalesce(nullif(tz, ''), LA)` спасает только от пустой строки). Неверное имя → `time zone "X" not recognized` → падает вся функция. Пример худшего: **клиент не может подписать смету на `/p/`**, мастер не видит выезды.
- Проверено на PG16: `at time zone` принимает больше, чем точные имена — 'PST', 'UTC+3', 'XYZ+5' (POSIX-строки), 'america/chicago' (регистр не важен). `pg_timezone_names` — только точные имена IANA (+ 'EST5EDT', 'UTC', 'Etc/…'), запрос ~7 мс. Пустая строка, 'Bad/Zone' — ошибка.
- Приложение: `zone.ts setZone` и `scheduleSettings.companyTz` при неверном поясе молча берут LA. Экран «Расписание» (`company/schedule.tsx`) предлагает 7 поясов США чипами — сам неверного не создаёт; создание компании (`cloud/auth.tsx:228`) пишет только имя (пояс по умолчанию). Неверный пояс может прийти только из данных (SQL, импорт, старые версии, будущий API).
- Очередь: ошибка `22*` — постоянная (`ops.ts:229`) → `company.save` целиком выбрасывается, стор перечитывается. Если в `companyToDb` уйдёт плохой пояс, пропадут и остальные правки этого сохранения.

### 1.2 Варианты
| | Плюсы | Минусы |
|---|---|---|
| **А. Триггер `before insert or update of timezone` + список `pg_timezone_names`** (рекомендую) | ловит любой путь записи; понятная ошибка `22023`; данные чинятся в той же миграции | 7 мс на смену пояса (редко) |
| Б. CHECK с immutable-функцией по каталогу | ограничение видно в схеме | функция на самом деле не immutable (tzdata), риск при restore; подзапрос в CHECK запрещён |
| В. Безопасная обёртка `app.company_tz(id)` во всех функциях | сервер не падает | переписать ~10 функций чужих направлений; плохие данные остаются |

### 1.3 Решение (А, с поправками security-check 07.11)
Миграция `20261107050000_company_timezone_check.sql` (данные, потом триггер, одна транзакция):
1. **Допустимый пояс** — `app.zone_name(text) returns text` (null = неизвестный). Сначала явная карта сокращений (ниже; первой — иначе `US/Eastern` прошёл бы как точное имя), затем точное имя из `pg_catalog.pg_timezone_names`, подходящее под `^(UTC|[A-Z][A-Za-z_]+(/[A-Za-z0-9_+-]+)+)$` и не `posix/`, `right/`, `Etc/`, `SystemV/`. Иначе — то же без учёта регистра (`america/chicago` → `America/Chicago`, `order by name`). Карта: EST/EDT/EST5EDT → America/New_York, CST/CDT/CST6CDT → America/Chicago, **MST → America/Phoenix** (в Postgres это UTC−7 без летнего времени), MDT/MST7MDT → America/Denver, PST/PDT/PST8PDT → America/Los_Angeles, HST → Pacific/Honolulu, US/Eastern|Central|Mountain|Pacific|Alaska|Hawaii → их America/… (чтобы итог не зависел от tzdata сборки). 'EST', 'MST' и т. п. сохраняются как America/… (сами по себе — без летнего времени, день сдвинулся бы на час); 'Factory', 'posix/…' — отказ. Синонимы вне списка (`US/Michigan`, `Canada/Eastern`) на сборке с ними пройдут как точные имена — риск низкий.
2. **Данные**: `timezone = coalesce(app.zone_name(timezone), 'America/Los_Angeles')` там, где они отличаются; `raise notice` «id: было → стало» (для основателя). Триггеры на update не мешают (t06 смотрит только `closed_at`, t10 поднимет `row_version`).
3. **Триггер** `t89_company_timezone before insert or update` (после всех before-триггеров — проверяется итоговое значение; `distinct from old` внутри): известное, но неточное имя **приводится** к точному (`new.timezone := app.zone_name(…)`), неизвестное → `unknown time zone` (`22023`, без значения в тексте). Так очередь старой версии с `'america/chicago'` не теряет `company.save` (правило 16). Функции — `set search_path = ''`, `revoke all … from public, anon, authenticated` (правило 18).
4. Серверные функции чужих направлений не трогаю. Защита внутри функций на одну строку (`app.safe_tz` в подписи/депозите, письмах) — отдельная задача «Сметам» (довод: смена tzdata Supabase может убрать имя у уже записанной строки). В RLS видимости визитов — нельзя (7 мс на строку), там опора на триггер.
5. **До PR руководителю**: посчитать на боевой базе `select timezone, count(*) from public.companies where timezone not in (select name from pg_timezone_names) group by 1` — если 0, риска для старых версий нет совсем; запишу итог в спеку.

Приложение:
- `cloud/ops.ts` (общий, одна строка) читает `timezone` вместе с `COMPANY_STORED_COLUMNS`; `companyToDb` шлёт пояс, только если он **отличается от серверного** и телефон его знает (не через Intl — у Hermes/ICU на старом Android свой список). Остальное сохранение доходит всегда. Известный остаток (было и до правки): долго офлайн-телефон со старым поясом при любом сохранении затрёт смену пояса другим админом; точное «только выбранный на «Расписании»» — флаг в op (`store.tsx`, общий), отдельно.
- `company/schedule.tsx`: сохранённый пояс не из 7 чипов (например `America/Puerto_Rico`) — отдельным чипом (сейчас не выбран ни один); пояс, которого не знает телефон (`validZone` = false), — строка `warn` «Телефон не знает пояс «X», время показано по Los Angeles».
- `zone.ts` не трогаю (держит «Каркас» №6): только импорт `validZone`.

### 1.4 Тесты

## 2. «Требует внимания»: записи ушедшего участника

### 2.1 Инспекция
- После 7а-2b визит только с ушедшим (`Member.pending` + `deleted` или `disabled`) — «Не назначено» (`liveAssignees`, e2e 98). Лиды (`assigneeId`) и задачи (`assigneeId`) ушедшего показываются с «Удалённый пользователь», но в «Требует внимания» ничего не говорит офису «передайте».
- Лид уже может быть в списке по «чей ход» (ответить, напомнить, без шага). Правило карты: один объект — одна карточка; лид без клиента — всегда своя карточка.
- Переназначить: лид — шторка «Ответственный» на экране лида (`LeadParts.tsx:383`); задача — `TaskSheet` на лиде, клиенте, объекте и в «Задачах».
- «Требует внимания» у офиса (director, dispatcher); мастеру — только свои.

### 2.2 Варианты
| | Плюсы | Минусы |
|---|---|---|
| **А. Своя карточка на объект** (рекомендую): лид — «Ответственный ушёл: <имя лида>», заменяет карточку «чей ход» этого лида (одна карточка на лид, срочность не ниже прежней); задача — «Задача без исполнителя: <название>» | правило 12; ведёт прямо к объекту | у удалённого с 30 задачами — 30 карточек |
| Б. Одна сводная карточка на человека «N лидов, M задач» | мало шума | нужен экран «передать всё разом» (нет), противоречит правилу 12 |
| В. Ничего не добавлять, только подпись на карточке лида | 0 работы | задачи не видны совсем |

### 2.3 Решение (А, с поправками map-keeper 07.11)
- **«Не работает»** = `isGone(m)` в `features/team.ts` (новый хелпер, свой тест): `m.deleted || m.disabled` (оба всегда вместе с `pending`; приглашённый, не вошедший, — не «не работает»). Id, которого нет в `members`, — не считается (старые данные). Слово на экране — «не работает», не «ушёл»: отключённого можно включить снова.
- **Кто видит:** офис = director, dispatcher, **sales** (sales открывает «Сегодня» и «Требует внимания», ведёт лиды и по базе переназначает, `is_staff`). Мастеру эти экраны закрыты маршрутом.
- **Лид:** открытый (`isOpenLead`), не в архиве, **не отложенный** (`isSnoozed` — правило «скрыт до даты»), ответственный `isGone` → `kind: "leadOrphan"`, `warn`, chip «Без ответственного», «Ответственный не работает — передайте лид», `/lead/<id>`, кнопка triage «Передать» → экран лида. Заменяет карточки хода `leadIdle`, `leadNoStep`, `leadBack`; **кроме «Ответить»** (`kind: "lead"`): новому лиду может ответить любой в офисе, кнопка «Ответить» и минуты ожидания остаются, а «без ответственного» идёт параметром/второй строкой. Одна карточка на лид всегда. Отсечение архива — только для `leadOrphan` (нынешнее поведение прочих карточек не меняю).
- **Задача** (не выполнена): `kind: "taskOrphan"`, `id: torph-<taskId>`, **`refId` = id предмета** (лид / клиент / объект / работа / смета), свой `case` в `attentionHref` через `taskSubject().href` — никогда не общий список (`figures.test.ts`). Так на «Сегодня» (`attentionPeople.subjectOf`) задача становится причиной в карточке клиента/лида, а не отдельной карточкой. Для предмета `property` → клиент: правка `attentionPeople.ts` (файл «Карточек списков») — согласую с ними. Кнопка triage «Открыть», не «Напомнить». `score` 860 (просрочена — 865).
- **`TaskSheet`** (файл «Лидов»): сейчас выбран невидимый ушедший — сохранение без выбора оставит его. Прошу «Лиды» (или разрешение): при `isGone` исполнителя чип не выбран, «Сохранить» требует выбора. Без этого стык неполный.
- Счётчик причин на «Сегодня» (`today.tsx:126`) — у человека с 30 задачами будет «· 30+»: считаю как есть, не меняю (одна карточка на предмет уже группирует).
- Строки i18n — блок `fr7.*` (RU/EN/ES).

### 2.4 Тесты
- unit `attentionOrphans.test.ts`: лид удалённого и отключённого → `leadOrphan` вместо `leadIdle/leadNoStep/leadBack`; новый лид → `lead` с отметкой «без ответственного»; лид приглашённого, отложенный, в архиве, id не из `members` → без `leadOrphan`; «Включить снова» (снят `disabled`) → карточки нет; задача удалённого → `taskOrphan`, `refId` = предмет, `attentionHref` для всех 5 видов предмета; выполненная — нет; sales видит; мастер — нет. unit `isGone`.
- e2e **112** (6 видов): как в e2e 98, сажает `m-gone` в демо (localStorage), лид и задачу на него → обе карточки в «Требует внимания»; лид → «Ответственный» → Иван → карточка пропала; задача → её предмет → `TaskSheet` → исполнитель Иван → карточка пропала.
