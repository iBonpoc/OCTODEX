## 1. PR-1 «Честные тесты прав» (пункты 5 + 4)
**Варианты.** а) только тест — красный main; б) тест + миграция в одном PR (рек.); в) убрать default privileges только в заглушке — ложь.
**Решение (б).**
- `auth_stub.sql`: 3 строки `alter default privileges in schema public grant all on tables / functions / sequences to anon, authenticated, service_role` — до миграций, как в Supabase.
- Миграция `…_api_grants.sql`: `revoke all` на 6 таблиц от anon, authenticated; минимальные grant: `catalog_items` s/i/u, `notifications` select + update(read_at), `company_secrets` s/i/u, `company_licenses` s/i/u, `company_contacts` s/i/u, `notes` s/i/u (DELETE нигде не нужен — удаление мягкое). `alter default privileges for role postgres in schema public revoke all on tables, functions, sequences from anon, authenticated` — новые объекты без явного grant закрыты. EXECUTE для PUBLIC на новые функции — общая настройка Postgres, по схеме её не снять (а глобальный revoke сломал бы функции-помощники тестов и RLS-функции, которым забыли grant); поэтому новый `public`-функционал, доступный anon, ловит T52 по белому списку.
- Тест T52 «права API»: (1) anon не имеет ни одного права на таблицы `public`; (2) у authenticated нигде нет TRUNCATE/REFERENCES/TRIGGER и DELETE только там, где он задуман (список); (3) anon исполняет в `public` только `portal_estimate`, `portal_accept`, `portal_pay_simulated` (+ `uuid_generate_v7`); (4) новая таблица после миграции не получает прав anon/authenticated (default privileges сняты).
- Падало до исправления: T2 «anon reads catalog» и T52 на базе со строками Supabase.

## 2. PR-2 «Суммы счёта» (пункт 1)
**Варианты.** а) пересчёт сервером из строк — строк счёта нет, это E3/«Деньги» (позже); б) заморозка сумм не в draft + CHECK (рек.); в) суммы только через RPC — ломает офлайн-insert старых версий.
**Решение (б).**
- `tg_invoice_guard` (новой миграцией `create or replace`): на UPDATE при `old.status <> 'draft'`, кроме пересчёта оплат (локальный флаг `set_config('app.invoice_recalc', …)` внутри `recalc_invoice_payment`, а не `pg_trigger_depth()` — иначе любой будущий триггер обойдёт заморозку), `subtotal_cents`, `discount_cents`, `tax_cents`, `total_cents`, `tax_*`, `currency`, `customer_id`, `job_id`, `kind`, `source_estimate_version_id`, `revision`, `sent_at` (после отправки) не меняются — ошибка `42501` (а не молча: приложение их и не шлёт).
- CHECK `subtotal_cents >= 0`, `total_cents >= 0` — `not valid`, затем `validate`; upgrade-тест со старыми строками. `total_cents >= paid_cents` **не** CHECK: `t05_not_above_balance` срабатывает только на insert платежа, два pending → succeeded уронили бы пересчёт (будущий вебхук Stripe). Вместо этого — запрет уменьшать total ниже paid в черновике в `tg_invoice_guard` и тот же контроль баланса при переходе платежа в succeeded (тест). Серверные функции, создающие счета (`20261104070000:116`, `20261105240000:354`, `20261105350000:172`), — тест против новых CHECK.
- Совместимость: insert с телефона (старые версии) не меняется; переходы sent→void и пересчёт оплат (`recalc_invoice_payment`, глубина > 1) работают.
- Долг (позже, не в этом PR): счёт вставляется сразу sent с любой суммой и без проверки total = subtotal − discount + tax → выдача счёта только через RPC (с «Деньгами», вместе с серверными строками счёта).
- Тест: sales/office UPDATE total=-100 и total<paid на sent — падает; insert total=-100 — падает; draft — меняется; оплаты и void как раньше.

### 7.1 `company_id` неизменен (PR-5, миграция `20261106160000`, T59)
**Инспекция.** `public.expenses` триггер `t11_company_id_immutable` **имеет** (`20261104010000_app_fields.sql:93`, `attach_standard_triggers`): сообщение security-check из 7а-2 — ложная тревога. Сейчас достижим только последний случай; остальные — защита на будущее (новый grant или функция не должны открыть перенос).
**Варианты.** а) `t11` только на `company_secrets` — следующая таблица снова забудет; б) `t11` на все 11 + тест-сторож по каталогу (рек.); в) общий event trigger на `create table` — магия, не видна в миграциях.
**Решение (б)** (с находками security-check 06.11). `create or replace app.tg_company_id_immutable` — текст ошибки через `to_jsonb(old) ->> 'id'` (у `company_secrets`, `customer_tags`, `job_tags` нет `id`); `t11` вешаем прямым `drop trigger if exists … ; create trigger …`, **не** через `attach_standard_triggers` (та добавит `t10` таблицам без `updated_at`/`row_version` — миграция упадёт). Плюс `member_signatures_update`: `with check (user_id = auth.uid() and app.is_member(company_id))` — сейчас бывший участник проходит политику (дальше его держит только `t10`). Серверных функций, законно меняющих `company_id`, в миграциях нет (`users.last_active_company_id` — другая колонка). Новых функций нет.
**T59.** (1) сторож по `pg_trigger`/`pg_attribute`: у каждой таблицы (`relkind r/p`) **всех несистемных схем** с колонкой `company_id` есть включённый (`tgenabled <> 'D'`) BEFORE UPDATE ROW триггер на `app.tg_company_id_immutable`; исключения списком с причиной: `app.company_numbering`, `app.company_flags` (вне API, пишут только функции) — новая таблица в `app` уронит тест, пока её не впишут сознательно; (2) admin двух компаний переносит `company_secrets` — `fails_like '%company_id is immutable%'` (падало до исправления: строка переезжала); (3) участник переносит свою `member_signatures` / бывший участник её правит — отказ; (4) для таблиц без UPDATE у authenticated (`notifications`, `customer_tags`, `job_tags`, `email_outbox`, …) — перенос суперпользователем, проверка **текста** `company_id is immutable` (код 42501 дал бы и отказ в праве — тест ничего бы не доказал).
**В том же PR (руководитель, 06.11).** `storage.objects`: `using` и `with check` политики UPDATE (`20261106100000:83`) проверяют старое и новое имя по отдельности — сотрудник двух компаний «переименованием» переносит файл из A в B. Триггер на `storage.objects` повесить нельзя (владелец `supabase_storage_admin`); закрыто в политике `files_bucket_update`: `with check` добавляет `app.file_object_kept(id, bucket_id, name)` — объект с этим `id` в снимке оператора уже лежит под тем же bucket и именем (переименование и перенос — отказ; повторная загрузка upsert под тем же именем — работает). Тест T59 (5). Следствия (security-check): `move` Storage API теперь всегда отказ (приложение его не зовёт); `copy` — это insert, сотрудник двух компаний копирует файл из A в B (как и скачать-загрузить, риск низкий); функция должна остаться `stable` и безопасна, только пока у ролей приложения нет DELETE-политики на `storage.objects` (T59 проверяет); при двух одновременных upsert одного ключа второй может получить ошибку RLS — безопасно, `ops.ts uploadPhoto` стоит повторять загрузку («Работы»/«Каркас»).

### 7.2 Себестоимость не уходит клиенту (аудит п.8) — PR-6, миграция `20261106180000`
**Инспекция.** `app.portal_estimate_base` (`20261105260000:96`) отдаёт anon `'doc' = estimate_versions.calc_inputs` целиком. Себестоимость вырезает только приложение (`clientDoc`, `estimateDoc.ts:134`; `store.tsx:962`), сама она лежит в `estimate_line_costs`. Старая версия приложения, ошибка будущего модуля (Gutters) или прямой UPDATE через API — и `unitCostCents` уйдёт клиенту.
**Варианты.** а) только фильтр при выдаче в `/p/` — старые и любые будущие данные закрыты, хранимое не меняется (хэш подписи `calc_inputs::text` в `20261105240000:298/495` не трогаем); б) только триггер на запись — не чистит старые строки, а у подписанных версий (`t40_version_lock`) менять нельзя; в) а + запрет записи — офлайн-очередь старой версии встанет навсегда.
**Решение (а)** (с находками security-check). Фильтр по подстроке имени ключа отвергнут: пропускает `purchaseTaxBps`, `catalogItemId`, строки Gutters с `clientVisible: false` (`gutterEstimate.ts:66`) и молча режет будущие нужные ключи. Вместо него `app.client_doc(jsonb)` — **белый список** ключей документа, опции, строки и настроек (по `EstimateDoc`/`CustomOption`/`CustomLine`/`CustomSettings` в `types.ts`), строки с `clientVisible = false` выбрасываются целиком; без рекурсии (фиксированная форма — нет переполнения стека от данных authenticated). `immutable`, `search_path = ''`, `revoke all … from public, anon, authenticated` (T52). Цена: новое поле документа не появится в `/p/`, пока его не внесут в список, — тест T60 перечисляет список, правка видна в PR.
Где вырезать (решение руководителя 06.11): в `app.portal_estimate_base` (`'doc', app.client_doc(v.calc_inputs)`) — тело функции скопировано из `20261105260000` с одной этой строкой (сверено `diff`); обёртка `public.portal_estimate` и `portal_accept`/`portal_pay_simulated` получают уже чистый документ. Помощник `app.jsonb_scalars(jsonb, text[])`: только перечисленные ключи со скалярными значениями — под разрешённым именем ничего не спрятать. Строка выбрасывается целиком, если `clientVisible` — `false`/«false»/0 или если `name`, `group`, `quantity`, `unitPriceCents` не того типа (страница упала бы). Остаток (security-check): мастер прямым select `estimate_versions` прочтёт себестоимость, если её записала старая версия, — тот же класс, что `marginPct` (§6, «Сметам»); `document_hash` считается от полного `calc_inputs::text`, а клиент видит урезанную копию — в П1b хэшировать `app.client_doc(calc_inputs)`, двумя шагами.
Вырезание при записи — не делаем в этом PR: запертые версии (`t40_version_lock`, `core.sql:748`) чистить UPDATE нельзя, у них `document_hash` посчитан от текста с себестоимостью (формулу не меняем); их закрывает только вырезание при чтении.
Требование на будущее: письмо/PDF по `email_outbox` на сервере (П1b) собирает документ только через `app.client_doc`.
**Отдельная находка (руководителю).** `estimate_versions.totals.marginPct` (`ops.ts:852`) читает монтажник (`can_read_estimate`), хотя себестоимость закрыта `can_view_costs` (`core.sql:1692`): мастер видит маржу. Anon её не получает. Закрыть: убрать `marginPct` из `totals` двумя шагами (правило 16) или выдавать через функцию с `can_view_costs` — направление «Сметы».
**Тест (T60).** Версия с `unitCostCents`, `costCents`, `marginPct`, `vendorTaxBps`, `markupBps`, `purchaseTaxBps`, `catalogItemId`, неизвестным ключом и строкой `clientVisible: false` → `/p/` (anon) отдаёт только ключи белого списка, скрытой строки нет, цены на месте; T19 и прочие тесты портала без изменений. Падало до исправления.

### 9.1 Правка мастером не стирает себестоимость и маржу офиса — миграция `20261108180000`, T106
Все версии приложения сохраняют черновик так: удалить строки версии, вставить их заново (те же id). Каскад удалял `estimate_line_costs`, а мастер (нет `can_view_costs`) записать их обратно не может. Его приложение шлёт `totals.marginPct = null` — t45 затирал маржу офиса.
- Варианты: (а) приложение сохраняет «по разнице» (upsert по id) — старые телефоны всё равно стирают; (б) RPC сохранения целиком — велико; (в) **выбрано**: сервер. Строку удаляет тот, кто не видит себестоимость, — её себестоимость откладывается в `estimate_line_costs_kept` (без политик и грантов, пишут только два триггера security definer); вставка строки с тем же id (сразу же или при повторе операции) возвращает её. - Маржа: `tg_version_margin_move` пишет `margin_pct`, только если сохраняет тот, кто видит себестоимость (или миграция); ключ из `totals` вынимается всегда. T100 поправлен: маржа, присланная мастером, не хранится.
