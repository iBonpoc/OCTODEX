# Gutters — ключ цены без цвета (#1913, К1, этап 0)

> Статус: этап 0, только документ, кода нет. Автор — Gutters №21, 16.11.2026. План проверяет не автор (§8).
> Код — зона (в) и зона (а) по очереди руководителя; эта спека код не начинает.
> Связано: #1914 (экран «Цены и прайс», спека 57 — опирается на этот ключ), `33-gutters-settings.md` П22.10, `33-gutters-module.md` П16 (C3), `33-gutters-estimate.md` П23.

## 1. Слова основателя и задача

16.11.2026, сборка 1910, экран «Цены и прайс» (через чат аудита): «Цвет не влияет на стоимость… Цвет не должен влиять на стоимость».

Сейчас позиция прайса держит цвет в свойствах и в названии: «Желоб · Белый · Окрашенный · .027 · Алюминий · K · 5″». Белый и коричневый желоб — две позиции, две цены, и каждый новый цвет — «нет цены».

Нужно: цена детали ищется **без цвета**. Цвет остаётся свойством замера, заказа поставщику и строки сметы — клиент и поставщик по-прежнему видят «белый».

## 2. Как устроено сейчас (разбор кода, только чтение)

| Где | Что делает | Цвет |
|---|---|---|
| движок `gutterParts.ts` | пишет у детали `attrs` (profile, size, material, gauge, finish, color…); `stockAttrs`, `dsAttrs`, сложение по `key` | `color` в `attrs` и в `key` (`gutter.k.5.aluminum.027.white`) |
| `prices.ts` `matchAttrs` | свойства, по которым ищется позиция: все `attrs`, кроме `side` | **входит** |
| `prices.ts` `matchKey` | `unit` + отсортированные `matchAttrs` | **входит** |
| `prices.ts` `findItem` → `catalogMatch` | позиция подходит, если у неё есть **все** искомые свойства с теми же значениями; лишние свойства не мешают, ближайшая — с наименьшим числом лишних | искомое содержит `color` |
| `prices.ts` `missingItems` | «Создать позиции сразу»: позиция с `attributes = matchAttrs`, id = `stableItemId(company, matchKey)`, имя из `partName` | цвет в свойствах, в id и в имени |
| `estimate.ts` `linesFromParts` | **одна строка сметы на `matchKey`**; `source.key = matchKey`; имя строки = имя позиции | белый и коричневый — разные строки |
| `estimate.ts` `resyncLines` | «Обновить смету» находит старые строки модуля по `source.key` | старые сметы хранят ключ с цветом |
| база `catalog_items.attributes` | плоская карта `имя → текст`, сервер по ней **не ищет** (поиск только в приложении) | хранится как есть |

Вывод: цвет в цене держат **две** вещи — `matchAttrs` (поиск позиции) и `matchKey` (он же ключ строки сметы). Их нужно **разделить**: ключ цены без цвета, ключ строки — как сейчас.

Ловушка, найденная при разборе: у старых замеров отделки (`finish`) может не быть — движок тогда считает «есть цвет → окрашенный» (`painted()` в `gutterParts.ts`). Если просто выбросить цвет, окрашенный желоб без `finish` станет «mill» и возьмёт цену неокрашенного. Значит, ключ цены **выводит** отделку из цвета, когда её нет (§3, ось «отделка»).

## 3. Оси ключа цены — список для сверки с прайсом основателя

Ключ цены детали = **часть** + оси ниже, которые движок пишет этой детали. Цвет — не ось. Единица (`unit`) — часть ключа, как сейчас (ft и ea — разные позиции).

| Ось | Свойство | Значения сейчас | У каких деталей |
|---|---|---|---|
| Часть | `part` | gutter, downspout, end_cap, miter, slip_joint, outlet, end_outlet, elbow, offset, reducer, hanger, guard, … (`PART_WORDS`) | все |
| Форма желоба | `profile` | k, half_round, fascia, box, euro (`canvas/attrs.ts` `PROFILES`) | желоб, углы, заглушки, соединители, выпуски, крюки, guards, wedge, splash guard |
| Размер желоба | `size` (у выпуска — `gutterSize`) | k 5/6/7, half_round 5/6, fascia 6/7, box 6/7/8 … (`SIZES_BY_PROFILE`) | то же |
| Форма водостока | `shape` | rect, round | водосток и всё на нём |
| Размер водостока | `size` (у водостока) | rect 2x3/3x4/4x5, round 3/4 (`DS_SIZES`) | водосток и всё на нём |
| Вид водостока | `dsStyle` | plain, corrugated | водосток, колена, офсеты |
| Материал | `material` | aluminum, steel, galvalume, copper, zinc (`MATERIALS`) | листовые детали |
| Толщина | `gauge` | aluminum .027/.032, steel и galvalume 26ga/24ga, copper 16oz/20oz … (`GAUGES_BY_MATERIAL`) | листовые детали, где задана |
| Отделка | `finish` | painted, mill (copper и zinc — только mill, `MILL_ONLY`) | листовые детали; **нет `finish` → painted, если есть цвет, иначе mill** |
| Подтип детали | `style` (колено A/B/угол), `lengthIn` (офсет, секция, guard), `to` (переходник), `corner` (in/out), `hanger`, `guard` (тип), `eaveBox`, `pipe`, `buy` (coil/section), `blankIn`, `stickIn`, `rivet`, `screw`, `custom` | как в движке | по детали |
| Работа | `work`, `story` | install, downspout, corner_cut, … ; этаж 1–4 | только работа (labor) — без изменений |

**Не входят в ключ цены:** `color` (решение основателя 16.11), `side` (левая и правая заглушка — одна позиция, как и было).

Цвет-зависимые расходники: герметик (`sealant`) и краска (`touch_up_paint`) сейчас — позиция на цвет. По словам основателя цена от цвета не зависит → **одна позиция** «Sealant» и одна «Touch-up paint»; цвет остаётся в заказе поставщику и в строке (сколько тюбиков какого цвета купить). **Вопрос аудиту к сверке:** так ли в прайсе основателя (одна цена герметика на все цвета)?

> Сверку осей с прайсом основателя делает чат аудита: прайс в репозиторий и в чаты исполнителей не попадает (правило 9). Если в прайсе ось лишняя (например, толщина не меняет цену) или не хватает оси — правка этой таблицы до кода.

## 4. Что меняется (модель)

1. **`priceAttrs(p)`** — новое: свойства для поиска позиции. Это `matchAttrs` без `color`, с выведенным `finish` (§3). `findItem`, `missingItems` (`attributes`), `bindItem`, `starterWant` и экран «Цены и прайс» (`materialRows`) берут его.
2. **`priceKey(p)`** — `unit` + отсортированные `priceAttrs`. По нему: одна строка прайса на позицию (`materialRows`), id новой позиции (`stableItemId(company, priceKey)`).
3. **`matchKey` (ключ строки сметы) не меняется** — с цветом. Белый и коричневый желоб одной сметы остаются **двумя строками** с одной ценой: клиент видит, какой цвет где, и «Обновить смету» находит старые строки по старому ключу. Строки уже выданных смет не трогаем — это снимок.
4. **Имя строки сметы.** Сейчас имя = имя позиции. У позиции без цвета в имени цвета нет, поэтому строка сметы получает имя позиции **плюс цвет детали** («5″ K-Style Gutter · White») на языке клиента (правило 7). Деталь без цвета — имя позиции как есть.
5. **Имя новой позиции** (`missingItems`) — без цвета: «5″ K-Style Gutter · Painted · .027 · Aluminum».
6. **Поиск, порядок** (`findItem`), чтобы ни одна текущая цена не изменилась на шаге 1:
   1. позиция **без цвета** с теми же осями — она главная;
   2. нет её — старая позиция **с цветом этой детали** (цена компании как была);
   3. нет и её — старая позиция **другого цвета** с теми же осями (решение основателя: цвет на цену не влияет). Если таких несколько и цены разные — берётся та, что изменена последней (`updatedAt`), а экран «Цены и прайс» показывает «Цены по цветам расходятся: N» (§5 шаг 2);
   4. ничего — «нет цены», как сейчас.
7. **Сервер не меняется:** поиск по свойствам — только в приложении; `catalog_items.attributes` остаётся картой текста, ограничение `catalog_items_attributes_check` не трогаем.

## 5. Перенос позиций — правило 16, два шага

Почему два шага: на телефонах живут старые версии. Старая версия ищет позицию **с цветом** (`catalogMatch` требует `color`); позицию без цвета она не найдёт и покажет «нет цены». Поэтому старые позиции с цветом нельзя убрать сразу.

**Шаг 1 (код, один PR зоны (в)):**
- `priceAttrs` / `priceKey` / порядок поиска §4.6 / имя строки §4.4.
- Старые позиции с цветом **не меняются и не архивируются** — старые телефоны находят их как раньше.
- Новая позиция без цвета появляется, только когда её создают: «Создать позиции сразу» (тестовая цена, правило 9) или кнопка «Свести цвета» (ниже). Пока её нет — работает §4.6 п.2–3, цена та же, что сейчас.
- **«Свести цвета»** на экране «Цены и прайс» (видна, когда есть позиции, отличающиеся только цветом): для каждой группы
  - цены одинаковые → создаётся одна позиция без цвета с этой ценой (id = `stableItemId(company, priceKey)` — два телефона создадут одну и ту же, `catalog.save onlyNew`);
  - цены разные → человек выбирает цену из списка (меню, DS); без выбора группа не сводится;
  - старые позиции с цветом **остаются** до шага 2. Действие — с тостом «Отменить» 5 секунд (правило 5): отмена удаляет только что созданную позицию без цвета (её ещё не использует ни одна смета).
- Тексты — RU/EN/ES (правило 7), блок `mod.gutters.price.*`.

**Шаг 2 (отдельный PR, позже):** когда минимальная версия приложения ≥ версии шага 1 (старые телефоны не ищут по цвету) — позиции с цветом, у которых есть сведённая позиция без цвета, уходят в **корзину** — мягкое удаление `catalog_items.deleted_at` (`catalog.remove`, корзина `20261111030000_trash.sql`), не стираются: на них ссылаются строки старых смет (`catalogItemId`), а строка хранит свой снимок цены и имени. Своего поля «архив» у позиции нет (`CatalogItem` в `types.ts`) — новое не заводим. Пометка в PR: `rule16: step 2 (позиции с цветом, после PR шага 1)`. Если шаг 2 делается миграцией базы — новым файлом, `revoke` / минимальные `grant` по CLAUDE.md.

**Не трогаем никогда:** строки уже созданных смет и счетов (снимок цены, имени, `catalogItemId`).

## 6. Тесты (функция без тестов не готова, правило 15)

Модульные (`apps/mobile/test`, зона (в)):
1. `priceAttrs` не содержит `color` ни у одной детали `materialRows` и `sampleJob` с белым и коричневым запасом.
2. `priceAttrs` выводит `finish`: деталь с цветом и без `finish` → `painted`; без цвета и без `finish` → `mill`; явный `finish` не меняется. Тест, который **падает без** вывода (окрашенный желоб без `finish` берёт цену mill).
3. `findItem` порядок §4.6: есть без цвета → она; нет — с цветом детали; нет — другого цвета; два цвета с разной ценой → последняя по `updatedAt`; ничего → `undefined`.
4. Сегодняшняя компания (позиции с цветом, без сведённых): цена каждой строки сметы после шага 1 **та же**, что до (снимок «было» через старый `matchAttrs`).
5. `linesFromParts`: белый и коричневый желоб — две строки, одна цена, имена с цветом; `source.key` = старый `matchKey` (с цветом); `resyncLines` старой сметы не помечает строки `gone`.
6. `materialRows`: одна строка прайса на ось без цвета (белый и коричневый запас — одна строка).
7. «Свести цвета»: одинаковые цены → одна позиция с этой ценой и стабильным id (второй вызов — ничего нового); разные цены без выбора → не сводится; отмена удаляет созданную.
8. Имя новой позиции без цвета; имя строки — на языке клиента (`tFor`).

Движок: не меняется (цвет в `attrs` нужен заказу поставщику). Тест движка — что `attrs.color` у листовых деталей **остаётся** (сторож, чтобы никто не убрал цвет из движка ради цены).

База: схема не меняется → новых RLS-тестов нет; если шаг 2 — миграция, тест в `supabase/tests` (в корзину — только позиции с цветом при наличии сведённой; чужая компания не задета).

E2E: «Цены и прайс» с двумя цветами одной оси → одна строка, «Свести цвета», смета с двумя цветами → две строки одной цены. На всех 6 видах (`h.layout`).

## 7. Стыки и карта пути

- Стык «замер → смета» (`docs/15-story-map.md` §4, M8): цена строки ищется по ключу без цвета; ключ строки прежний. Новых статусов нет (§5 карты не меняется).

- Спека 57 (#1914) строит экран «Цены и прайс» на `priceKey`: «нет цены: N» считается по осям без цвета.
