# Gutters — цена детали без цвета (#1913, К1, этап 0)

> Статус: этап 0, только документ, кода нет. Автор — Gutters №21, 16.11.2026. План проверяет не автор (§8).
> Код — зона (в) и зона (а) по очереди руководителя; эта спека код не начинает.
> Связано: #1914 (экран «Цены и прайс», спека 57 — опирается на группы цены §4), `33-gutters-settings.md` П22.10, `33-gutters-module.md` П16 (C3), `33-gutters-estimate.md` П23.

## 1. Слова основателя и задача

16.11.2026, сборка 1910, экран «Цены и прайс» (через чат аудита): «Цвет не влияет на стоимость… Цвет не должен влиять на стоимость».

Сейчас позиция прайса держит цвет в свойствах и в названии: «Желоб · Белый · Окрашенный · .027 · Алюминий · K · 5″». Белый и коричневый желоб — две позиции, две цены, и каждый новый цвет — «нет цены».

Нужно: цена детали **не зависит от цвета** — одна на все цвета. Цвет остаётся свойством замера, заказа поставщику и строки сметы — клиент и поставщик по-прежнему видят «белый».

## 2. Как устроено сейчас (разбор кода, только чтение)

| Где | Что делает | Цвет |
|---|---|---|
| движок `gutterParts.ts` | пишет у детали `attrs` (profile, size, material, gauge, finish, color…); `stockAttrs`, `dsAttrs`, сложение по `key` | `color` в `attrs` и в `key` (`gutter.k.5.aluminum.027.white`) |
| `prices.ts` `matchAttrs` | свойства, по которым ищется позиция: все `attrs`, кроме `side` | **входит** |
| `prices.ts` `matchKey` | `unit` + отсортированные `matchAttrs` | **входит** |
| `prices.ts` `findItem` → `catalogMatch` | позиция подходит, если у неё есть **все** искомые свойства с теми же значениями; лишние свойства не мешают, ближайшая — с наименьшим числом лишних | искомое содержит `color` |
| `prices.ts` `missingItems` | «Создать позиции сразу»: позиция с `attributes = matchAttrs`, id = `stableItemId(company, matchKey)`, имя из `partName` | цвет в свойствах, в id и в имени |
| `estimate.ts` `linesFromParts` | **одна строка сметы на `matchKey`**; `source.key = matchKey`; имя строки = имя позиции | белый и коричневый — разные строки |
| `estimate.ts` `resyncLines` | «Обновить смету» находит старые строки модуля по `source.key` | старые сметы хранят ключ с цветом |
| база `catalog_items.attributes` | плоская карта `имя → текст`, сервер по ней **не ищет** (поиск только в приложении) | хранится как есть |

Вывод: цвет участвует в цене через `matchAttrs` / `matchKey`. Но убрать цвет из позиции нельзя — проверка плана (§9, Б4–Б6) показала, что от позиции с цветом зависят ещё три вещи:
- **заказ поставщику** (`features/purchaseOrders.ts` `jobMaterialNeeds`) суммирует строки сметы по `catalogItemId`: одна позиция без цвета склеила бы белый и коричневый в одну строку заказа без цвета;
- **«своя строка»** сметы (`estimate.ts` `resyncLines`) узнаёт позицию по id: одна позиция на два цвета даёт двойной счёт или пропажу цвета;
- **начальные сметы** (`estimateTemplate.ts` `starterLookup`) требуют одну лучшую позицию: без цвета в поиске белая и коричневая — «several», $0.

Поэтому решение — не «позиция без цвета», а **одна цена на группу цветов**.

## 3. Оси цены — список для сверки с прайсом основателя

Цена детали задаётся по **части** и осям ниже, которые движок пишет этой детали. Цвет — не ось цены. Единица (`unit`) — тоже ось, как сейчас (ft и ea — разные позиции). Набор осей без цвета = **ключ группы цены** (§4.1).

| Ось | Свойство | Значения сейчас | У каких деталей |
|---|---|---|---|
| Часть | `part` | gutter, downspout, end_cap, miter, slip_joint, outlet, end_outlet, elbow, offset, reducer, hanger, guard, … (`PART_WORDS`) | все |
| Форма желоба | `profile` | k, half_round, fascia, box, euro (`canvas/attrs.ts` `PROFILES`) | желоб, углы, заглушки, соединители, выпуски, крюки, guards, wedge, splash guard |
| Размер желоба | `size` (у выпуска — `gutterSize`) | k 5/6/7, half_round 5/6, fascia 6/7, box 6/7/8 … (`SIZES_BY_PROFILE`) | то же |
| Форма водостока | `shape` | rect, round | водосток и всё на нём |
| Размер водостока | `size` (у водостока) | rect 2x3/3x4/4x5, round 3/4 (`DS_SIZES`) | водосток и всё на нём |
| Вид водостока | `dsStyle` | plain, corrugated | водосток, колена, офсеты |
| Материал | `material` | aluminum, steel, galvalume, copper, zinc (`MATERIALS`) | листовые детали |
| Толщина | `gauge` | aluminum .027/.032, steel и galvalume 26ga/24ga, copper 16oz/20oz … (`GAUGES_BY_MATERIAL`) | листовые детали, где задана |
| Отделка | `finish` | painted, mill (copper и zinc — только mill, `MILL_ONLY`) | листовые детали; у позиции **с цветом** и без `finish` отделка читается как painted (§4.1) |
| Подтип детали | `style` (колено A/B/угол), `lengthIn` (офсет, секция, guard), `to` (переходник), `corner` (in/out), `hanger`, `guard` (тип), `eaveBox`, `pipe`, `buy` (coil/section), `blankIn`, `stickIn`, `rivet`, `screw`, `custom` | как в движке | по детали |
| Работа | `work`, `story` | install, downspout, corner_cut, … ; этаж 1–4 | только работа (labor) — без изменений |

**Не оси цены:** `color` (решение основателя 16.11), `side` (левая и правая заглушка — одна позиция, как и было).

Цвет-зависимые расходники: герметик (`sealant`) и краска (`touch_up_paint`) сейчас — позиция на цвет. Позиции по цвету остаются (поставщик продаёт белый и коричневый тюбик отдельно), но цена у них общая — как у всех деталей (§4). Краска и заклёпки — только заказ поставщику (`use: purchase`), в смету не идут, на цену сметы не влияют. Аудит 16.11: в прайсе основателя у герметика одна цена на все цвета — подтверждено.

> Сверка с прайсом основателя (чат аудита, 16.11): оси совпадают; толщина, отделка, вид downspout, материал и единица — все нужны (медь — «call for pricing»). Единицы прайса: lb, pc (= 10 ft), each, bag (100 pc), box; если у детали есть цена «за штуку» и «за коробку», берётся штучная, коробка — справочно. Цвет в названии guard («GALV Black») — вид guard (подтип), не цвет замера: у guard это ось `guard`, в группу по цвету не входит. Прайс в репозиторий и в чаты исполнителей не попадает (правило 9).

## 4. Решение: позиции по цвету остаются, цена у них одна

Поставщик продаёт белый и коричневый желоб как разные товары (свой код, свой заказ), а цена компании у них одна (слово основателя). Значит:
- позиция прайса **остаётся по цвету** — как сейчас; поиск позиции для строки сметы (`findItem`, `matchAttrs`, `matchKey`), «своя строка», начальные сметы, заказ поставщику, имена строк — **не меняются**;
- меняется **цена**: она задаётся один раз на **группу** — позиции одной детали с одинаковыми осями (§3), отличающиеся только цветом, — и одинакова у всех цветов группы;
- новый цвет без своей позиции **получает цену группы** вместо «нет цены».

### 4.1. Группа цены
- **Группа детали** (для строки сметы и цены под чертежом): цветные позиции, которые `catalogMatch` находит по свойствам детали **без `color`** — `matchAttrs(part)` без `color` (поиск по подмножеству, как `findItem`; лишнее свойство у позиции, например старое `custom`, группу не рвёт). Позиции без `color` в группу не входят (§9 Б2: белое колено-удлинитель не берёт цену бетонного блока). У детали с цветом без `finish` в искомое дописывается `finish=painted` (старые замеры: «есть цвет → окрашенный», `painted()` в `gutterParts.ts`), и позиция с цветом без `finish` считается painted.
- **Строки экрана** (§4.3): ключ строки — свойства детали без цвета + `unit`. Строки = детали пробного замера `materialRows` (цвет компании, без цвета в ключе) **плюс** цветные позиции каталога, свойства которых без цвета не совпали ни с одной из них (детали, которых нет в пробном замере, — их цвета тоже собираются в строку по своим свойствам без цвета).
- `LEGACY_ROUND_ELBOW` (круглое колено 45° находит старую позицию «A», `prices.ts`) применяется и при поиске группы.

### 4.2. Что такое «одна цена»
Цена материала — не одно число: `catalogUnitPrice` = себестоимость × налог поставщика × наценка. «Одна цена» у позиций группы = равны **`priceCents`** и **`placeholder`** (`catalog_items`) и **`unit_cost_cents`, `vendor_tax_bps`, `markup_bps`** (`catalog_item_costs`, видны не всем ролям — `20261108130000_tech_no_costs.sql`). Поставщик, код поставщика, единица закупки и упаковка (`supplierId`, `supplierSku`, `purchaseUnit`, `packSize`) — свои у каждого цвета и не трогаются.

### 4.3. Где живёт группа — ядро не знает про цвет (решение руководителя 16.11)
В других trade цвет **влияет** на цену (электрика: изолента, провод). Поэтому «цвет без цены» — правило **модуля Gutters**, не ядра.
- **Ядро и база знают только общее понятие «группа цены»:** свойство позиции `attributes.priceGroup` (текст). Позиции одной компании с одинаковым `priceGroup` имеют **одну цену** (§4.2) — это держит база (§4.6). Ядро не знает, **почему** позиции в одной группе; слов «цвет», «gutter» в ядре и базе нет. Позиция без `priceGroup` (любой другой trade, любая ручная позиция) живёт как сейчас — цена своя.
- **Членство решает модуль Gutters:** он пишет `priceGroup = "gutters:" + priceGroupKey` (§4.1 — свойства без `color`, с выводом `finish`, + `unit`) у **цветных** позиций, которые создаёт или переводит (§4.4). Только модуль знает, что ключ построен без цвета.
- **Общий распознаватель прайса** (импорт, спека 53 §12а) про цвет ничего не знает: он пишет цену в найденную позицию как обычно, а база разносит её по группе (§4.6). Так импорт пишет цену на группу без своих правил.
- Ключ `priceGroup` проходит ограничение `catalog_items_attributes_check` (имя `^[a-zA-Z]…`, значение ≤ 120 символов: ключ группы длиннее — модуль пишет его хеш `gutters:<sha1 16 символов>`).

### 4.4. Экран «Цены и прайс» и переход (база для спеки 57, #1914) — условия аудита 16.11
1. **Цена задаётся только на группу.** На экране цен — и везде, где модуль показывает цену детали, — группа одна строка **без цвета**: «5″ K-Style Gutter · Painted · .027 · Aluminum», цвета — только счётчиком «3 цвета» (раскрытие — список названий, без цен). Задать цену одного цвета нельзя нигде: в общем каталоге ядра цена позиции с `priceGroup` правится так же, но база тут же пишет её во все позиции группы, а карточка ядра говорит общими словами «Цена общая для 3 позиций» (без слова «цвет»).
2. **«Расходятся» — не состояние, а разовый переход.** При первом открытии экрана цен после обновления (персонал с себестоимостью) модуль находит цветные позиции без `priceGroup`, собирает их в группы (§4.1) и показывает **один экран перехода**:
   - группы с одинаковой ценой — списком «будут одной ценой: 18 групп» (подтверждение одной кнопкой);
   - группы с разными ценами — по одной строке «было → станет»: «White $8 · Brown $9 → $8 ⌄» (меню — какую цену взять; по умолчанию — позиция, изменённая последней: `updatedAt`, затем меньший `id` по коду символов);
   - «Перевести» пишет `priceGroup` и цену во все позиции группы (запись по полям `fields`, чтобы устаревший кэш не затёр `supplierSku` / `packSize`); после этого база держит равенство (§4.6) и «расходятся» больше не возникает.
   - Роль без себестоимости (sales) и монтажник переход не делают (экран говорит «Переход цен делает владелец или офис»); до перехода цены работают как сейчас (§4.5 п.2).
3. **Импорт прайса** (53 §12а) — §4.3: цена на группу через базу.
- Правка цены строки после перехода: одна запись в любую позицию группы — база разносит. Тост «Отменить» 5 секунд (правило 5) возвращает прежнюю цену той же записью (база разнесёт и её); ушло на сервер — «поздно», как везде.
- У группы, где для цвета замера нет позиции, — «Нет позиции цвета: Black» и кнопка «Создать»: позиция этого цвета с `priceGroup` группы; цену ставит база (§4.6, вставка).
- «Нет цены: N» (#1914) — строки (§4.1), у которых нет ни одной позиции.
- Права: правит персонал с себестоимостью (owner, admin, office); монтажник — только чтение (RLS `catalog_items_insert` = `app.is_staff`); модуль выключен — экрана нет.

### 4.5. Цена для строки сметы и под чертежом
1. Деталь с цветом, у которого **есть** позиция: `findItem` как сейчас — позиция своя, цена её (после перехода она равна цене группы).
2. **До перехода** (позиции без `priceGroup`): ничего не меняется — цена своей позиции; так ни одна текущая цена не сдвигается, пока компания сама не перевела (§9 Б1).
3. Цвет **без своей позиции**, группа есть (после перехода — позиции с тем же `priceGroup`; до перехода — цветные позиции по §4.1): строка сметы получает цену группы и **не получает `catalogItemId`**; в `source` — своё поле `groupPrice: <id позиции-источника>` (не `testPrice`): строка RU/EN/ES «Нет позиции цвета Black — цена группы», проверка перед отправкой (C5) **предупреждает, но не держит**. `listPreview` берёт ту же цену. Из сметы в каталог **ничего не пишется** (монтажнику каталог закрыт; чистая функция; удалённую позицию не воскрешаем) — позицию создаёт персонал на экране цен, после чего «Обновить смету» привязывает строку с той же ценой. Строка без позиции в заказ поставщику не попадает — пометку видно в смете и на экране цен.
4. Группы нет (первый цвет детали) — «нет цены», как сейчас.
5. `LEGACY_ROUND_ELBOW` (круглое колено 45° → старая позиция «A») — и при поиске группы.

### 4.6. База держит одну цену группы (условие аудита 2)
Новая миграция (новый файл, `revoke all … from anon, authenticated`, правило 18 для функций):
- **после изменения** `catalog_items.price_cents` / `placeholder` у позиции с `attributes ? 'priceGroup'` — те же значения пишутся во все позиции **той же компании** с тем же `priceGroup` и `deleted_at is null`, где они отличаются;
- **после изменения** `catalog_item_costs` (`unit_cost_cents`, `vendor_tax_bps`, `markup_bps`) позиции с `priceGroup` — так же в `catalog_item_costs` позиций группы (строка создаётся, если её нет);
- **перед вставкой** позиции с `priceGroup`, у которого в компании уже есть позиции, — цена и себестоимость берутся из группы (вставка с тестовой ценой со старого телефона или «Создать» не создаёт расхождения);
- изменение `attributes.priceGroup` (вход позиции в группу) — то же, что вставка: позиция получает цену группы, если группа есть;
- защита от повтора: разнесение не запускает само себя (`pg_trigger_depth()`); функция `security definer` с `set search_path`, действует только в компании изменённой строки и только если вызвавший — персонал (`app.is_staff`), иначе ничего не разносит; `revoke all on function … from public, anon`, исполнения приложению не нужно (только триггер);
- схема (колонки, ограничения) не меняется; старые телефоны пишут позиции как раньше — база сама держит группу (правило 16: шаг один, ничего не удаляется и не переименовывается).

### 4.7. Чего не меняем
- `matchAttrs`, `matchKey`, `findItem`, `catalogMatch`, `resyncLines`, `starterLookup`, `jobMaterialNeeds`, имена позиций и строк. `linesFromParts` и `listPreview` меняются только в одном: деталь без своей позиции ищет цену группы (§4.5 п.3).
- Движок: цвет в `attrs` нужен заказу поставщику — остаётся.
- Строки отправленных смет и счетов — снимок. Черновик после перехода обновится через «Обновить смету», как при любой смене цены прайса (правленные руками строки не трогаются — `handChanges`).

## 5. Правило 16 и старые телефоны

Колонки и таблицы не меняются, ничего не удаляется; новое — свойство `priceGroup` в существующей карте `attributes` и триггеры базы. Второго шага нет.
- Старый телефон ищет позицию по цвету, как раньше, и находит те же позиции — с ценой группы.
- Старый телефон правит цену одной позиции — база разносит её по группе (одна цена сохраняется).
- Старый телефон создаёт позицию нового цвета («Создать позиции сразу») — без `priceGroup`, с тестовой ценой; новый телефон при открытии экрана цен предложит включить её в группу тем же экраном перехода (§4.4 п.2), и база поставит ей цену группы.
- Старый телефон, сохраняя позицию целиком, может прислать `attributes` без `priceGroup` (если его кэш старше перехода) — позиция выпадет из группы; экран цен нового телефона увидит её как «не в группе» и вернёт тем же переходом. Тест 15.

## 6. Тесты (правило 15)

Модульные (`apps/mobile/test`, зона (в)); у каждого — сценарий, который падает без правки:
1. `priceGroupKey`: белая и коричневая позиции одной детали — одна группа; позиция без цвета — не в группе (белый extension и бетонный splash block / extension без цвета не склеиваются); цветная без `finish` = цветная с `finish=painted`; mill и painted — разные группы; разная единица — разные группы.
2. Компания сегодня (белый $8, коричневый $9, перехода не было): **цена каждой строки сметы та же**, что старым кодом (`findItem` целиком, снимок «было»); экран цен показывает экран перехода с «White $8 · Brown $9 → $8».
3. Переход: «Перевести» → у всех позиций группы `priceGroup` и те же `priceCents`, `placeholder`, себестоимость, налог, наценка; `supplierId`, `supplierSku`, `purchaseUnit`, `packSize` — свои; запись по полям. После перехода экран не показывает «расходятся» ни в одном состоянии.
4. Правка цены строки после перехода — одна запись; монтажник и sales — только чтение, переход не предлагается.
5. Новый цвет (Black, позиции нет, группа White+Brown с одной ценой): строка сметы с ценой группы, без `catalogItemId`, `source.groupPrice` = id источника; `listPreview` — та же цена; каталог не изменился (ни `linesFromParts`, ни `makeEstimate` не пишут в каталог — и у монтажника тоже); после «Создать» на экране цен «Обновить смету» привязывает строку к позиции Black, цена та же.
6. Новый цвет в расходящейся группе: цена — позиции с последним `updatedAt`, при равенстве / без поля — меньший `id` (по коду символов).
10. Группа по подмножеству: белая позиция с лишним свойством (`custom`) и коричневая без него — одна группа для детали; позиция без цвета — не в группе.
11. Роль без себестоимости: экран перехода не показывается, цены до перехода — как сейчас.
12. Переход сохраняет позиции по полям (только `priceGroup`, ценовые и `placeholder`) — `supplierSku`, `packSize` из более свежей серверной строки не затираются.
14. `priceGroup` не длиннее 120 символов (хеш), проходит `catalog_items_attributes_check`; позиция без цвета и позиции других trade `priceGroup` не получают.
15. Позиция, выпавшая из группы (сохранена старым телефоном без `priceGroup`), — экран цен снова предлагает её в группу.
13. Удалённая компанией позиция Black (корзина): строка чёрного желоба — цена группы без позиции, позиция не создаётся заново.
7. Без правки остаются прежними (сторожа): смета с белым и коричневым — две строки, две позиции; заказ поставщику (`jobMaterialNeeds`) — две строки по цвету; начальная смета (`starterLookup`) находит позицию цвета компании, не «several»; «своя строка» с белой позицией не задваивает и не выбрасывает коричневую.
8. `LEGACY_ROUND_ELBOW`: колено 45° без своей позиции, но со старой «A» белой — находит; группа «A» белая+коричневая — новый цвет 45° получает её цену.
9. `sealantByColor` вкл: тюбики по цветам — одна группа, одна цена; выкл: один «Sealant» без цвета — вне групп.

Движок: не меняется; сторож — `attrs.color` у листовых деталей остаётся.
База (`supabase/tests/core_rls.sql`, номер — следующий свободный; миграция на чистой и текущей базе):
- правка `price_cents` / `placeholder` одной позиции группы → у всех позиций группы той же компании то же; позиции без `priceGroup`, другой группы, удалённые (`deleted_at`) и **другой компании с тем же `priceGroup`** — не тронуты;
- правка себестоимости (`catalog_item_costs`) → то же; строки себестоимости у позиций группы без неё создаются;
- вставка позиции с `priceGroup` существующей группы с тестовой ценой → цена и себестоимость группы;
- вход позиции в группу (изменение `attributes.priceGroup`) → цена группы;
- разнесение не зацикливается (одна правка — одно разнесение);
- монтажник (не персонал) не может разнести цену через триггер: его правка не проходит RLS, разнесения нет;
- функции триггера не исполняются `anon` / `authenticated` напрямую (T52, правило 18).
E2E (6 видов, `h.layout`): прайс с белым $8 и коричневым $9 → экран перехода «White $8 · Brown $9 → $8» → «Перевести» → одна строка «3 цвета», «расходятся» нигде нет → правка цены строки на $10 → смета с белым и коричневым — две строки по $10; замер с чёрным → строка $10 с пометкой «Нет позиции цвета» → «Создать» → «Обновить смету» — строка привязана к Black, $10.

## 7. Стыки и карта пути

- Стык «замер → смета» (`docs/15-story-map.md` §4, S5g): цена строки для нового цвета — из группы; ключ строки и позиция — прежние. Новых статусов нет (§5 карты не меняется).
- Стык «смета → заказ поставщику» (спека 37, `jobMaterialNeeds`): позиции по цвету остаются — заказ по цветам как был.
- Спека 57 (#1914) строит экран «Цены и прайс» на группах §4.3: «нет цены: N» считает группы без цены.
