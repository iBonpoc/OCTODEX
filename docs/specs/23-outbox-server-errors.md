# 23. Очередь: сервер отвечает ошибкой (ревью #244, «Лиды и клиенты» №9, задачи 2–5)

Владелец: «Лиды и клиенты» (store.tsx, persist.ts, офлайн-очередь). Правило 6 — офлайн с первого дня: изменение не теряется молча.

## 1. Что нужно подрядчику
Он сохранил изменение на телефоне. Если оно не ушло, он должен видеть, **почему** и **что сделать**:
- «Без сети» — ждать сеть, ничего не делать;
- «Сервер недоступен» — сеть есть, отвечает сервер ошибкой «не сейчас» (5xx, 429, база перезапускается); ждать;
- «Не отправлено: сервер отвечает ошибкой» — одно конкретное изменение снова и снова получает 500 / таймаут, остальные уходят. Действия: «Повторить сейчас», «Отменить изменение…» (подтверждение; уходят и зависящие от него).

Сейчас (#244): временная ошибка без предела держит голову очереди навсегда, остальные операции владельца стоят, а в шапке «без сети» — неправда.

## 2. Варианты
| | Плюсы | Минусы |
|---|---|---|
| А. Строгий порядок, потолок → видимое «застряло» | просто, порядок не нарушается | одно плохое изменение держит все остальные |
| **Б. Строгий порядок для связанных, пропуск независимых** (рекомендация) | остальное уходит, связанное ждёт | нужна проверка связи по id |
| В. Очередь на каждую сущность | максимум параллельности | переписывать очередь, сложнее офлайн и «Отменить» |

## 3. Решение (вариант Б, проверено архитектором `Plan`)
**Классы ошибок** (`outboxRetry.ts`, чистые функции):
- `network` — пауза всей очереди, без пропусков (как в #244); шапка «Без сети».
- `transient` делится на:
  - «сервер целиком» — PGRST000–003, 08xxx, 57P0x, 53xxx, 503, 429, 401: пауза всей очереди, шапка «Сервер недоступен»;
  - «может быть только эта операция» — 500/XX000, 57014, 40001/40P01: операция ждёт своей паузы, очередь идёт дальше к **независимым** операциям; если и следующая получает не-отказ — «сервер целиком».
- `refusal` — как сейчас (`tries`, после `MAX_TRIES` выбрасывается). Временные ошибки `tries` не трогают.

**Связь операций (переделано по ревью #259, Б1–Б2):** зависимость на сервере не всегда видна в операции (шаг выезда и «работа выполнена», строка работы и её счёт, два контакта, из которых один становится основным). Поэтому **за задержанной операцией ждут все**, кроме видов `SELF_KINDS` — операций, которые только добавляют своё (новый лид, новый клиент, заметка, звонок, сообщение, задача, событие). Но и они ждут, если их id объекта **или справочный id** совпадает с id объекта задержанной или ждущей операции. Id объекта — UUID в операции вне справочных полей; справочные (`REF_KEYS`: источник, метки, люди, направление, тип работы, позиция каталога, те же колонки лида `source_id`, `service_category_id`, `service_item_id`, `assigned_to`) хранятся отдельно (ревью #259, Б1-бис): два лида с одним источником не связаны, но новый лид ждёт задержанного `source.save` своего нового источника (иначе FK `leads.source_id` / `customers.lead_source_id` → 23503 → отказ ×5 → лид выброшен). То же с новым направлением, типом работы, позицией каталога. Окно «Отменить» останавливает всё после себя. Чужие операции (другой владелец) мою не держат — как до изменения: они уходят только от своего владельца.

**Потолок:** у операции `failSince` (первая временная ошибка) и `fails`. «Застряла» — `now − failSince ≥ 10 мин` **и** `fails ≥ 3` (одна попытка спящего телефона — не застряла). Сетевая ошибка или отказ обрывают серию: счёт начинается заново. Застрявшая не выбрасывается; повторяется раз в 5 мин и по «Повторить сейчас». «Повторить сейчас» снимает только паузу: признак «застряла» и карточка остаются до ответа сервера «принято». Две ошибки «может быть одной операции» подряд — сервер целиком; ответ сервера между ними обнуляет подсчёт. Ошибка уже застрявшей операции не говорит о сервере ничего нового (после перезапуска).

**Данные:** необязательные поля в `OwnedItem` (`failSince?`, `fails?`, `stuck?`) под тем же ключом `octo.outbox.v1`; старые версии их не читают и сохраняют (`...item`). Порядок массива не меняется. Пауза по операции — только в памяти.

**`refresh()`:** сейчас ждёт, пока очередь пуста, — с застрявшей операцией данные устарели бы навсегда. Новое условие: ждёт, пока у человека есть хоть одна **незастрявшая** операция (и ждущая за застрявшей — её правка есть только на телефоне, перезагрузка стёрла бы её с экранов, ревью #259 №4). Остались только застрявшие — данные сервера заменяют локальный вид, сами операции остаются в очереди и видны в списке.

**Стор:** `link: "ok" | "offline" | "server"`; `online` прежний (false и для offline, и для server — ничего в приложении не меняется); `stuckOps` (id, что за изменение, с какого времени, `waiting` — сколько операций ждут её сейчас, `leaving` — сколько уйдёт при отмене, `sending` — отправляется сейчас), `retryOp(id)`, `discardOp(id)` → `false`, если операция или зависящая от неё сейчас в пути (дойдёт до сервера); иначе удаляет её и зависящие; потом `refresh`.

**Зависящие при отмене (ревью #259, п.1–п.2):** `CREATES` в `outboxDeps.ts` — для **каждого** вида операции (TypeScript требует запись на каждый вид), какие объекты она создаёт на сервере: upsert с `isNew` — только когда новый; upsert без флага (`UNSURE_KINDS`: `source.save`, `tag.save`, `catalog.save`, `contact.save`, `license.save`, `property.save`, `task.save`, `lead.contactSave`, `customer.people`, `lead.people`, `estimate.save`) при постановке в очередь получает `made` — только те id, которых не было на телефоне до изменения (ревью #259 круг 3): правка метки, старого контакта клиента, контакта или лицензии компании — ничего. **Исключение — смета (ревью #259 круг 4, Б1):** `estimate.save` всегда «создаёт» id сметы (`ALWAYS_MADE`), даже когда правит существующую: отправка, подпись клиента (`estimate.approve` с вариантом новой версии и счётом задатка), подпись компании и задаток несут id сметы и относятся к содержанию этой правки. Поэтому при отмене застрявшей правки они уходят вместе с ней, а подтверждение показывает значок «Деньги». Иначе подпись получила бы 22023 «option does not belong to the sent version» и пропала бы через MAX_TRIES, а у черновика легла бы на старую версию со старыми суммами.

**Известные ограничения (ревью #259 круг 4):**
- `madeOnQueue` ищет id на телефоне до 4 уровней вложенности. Строки вариантов сметы (`doc.options[].lines[]`) глубже, но строки на сервере существуют только внутри своей сметы, а она, по правилу выше, уходит вместе с отменённой правкой. Отдельных операций по строкам сметы нет.
- Редкий случай: новый объект (например, источник S) отклонён сервером и выброшен после MAX_TRIES, а перезагрузку телефон пропустил (сеть пропала), и S остался на телефоне. Тогда следующая правка S получит `made = []`, и `lead.add` с этим S пройдёт мимо застрявшей правки и тоже будет отклонён (23503). Риск низкий: после выброса операции `flush` перезагружает данные сервера (`dropped → refresh`), и S исчезает с телефона при первой удачной загрузке. Чинить — отдельной задачей, если появится в журнале. У старых элементов очереди без `made` — по виду (осторожно: создаёт всё, что пишет). Справочный id ждёт задержанную операцию, только если она этот объект создаёт (переименование направления новый лид не держит). Зависящие — поздние операции человека, которые о созданном объекте или ссылаются на него (свой или справочный id), и по цепочке — на объекты, созданные ими. Операция, которая только меняет (`customer.update`), ничего не создаёт: при её отмене никто не уходит, работы, счета и оплаты этого клиента остаются и уходят. «Ждут» ≠ «уйдут»: за застрявшей ждут все несамостоятельные, уходят только нуждающиеся в созданном.

**Отказ и сеть снимают «застряла» (ревью #259, п.4):** отказ сервера — это уже попытка (`tries`), после `MAX_TRIES` операция выбрасывается, поэтому карточка «Не отправлено: сервер отвечает ошибкой» снимается; сетевая ошибка — тоже (ждём сеть, шапка «Без сети»).

**Экран:** `SyncBadge` — «Без сети · в очереди: n» (warn, wifiOff) / «Сервер недоступен · в очереди: n» (warn, alert) / «Не отправлено: n» (bad, alert; нажимается → «Профиль и аккаунт», `/settings/profile`, спека 26). В «Профиле и аккаунте» (под строкой синхронизации аккаунта; до спеки 26 — в «Мои настройки») — карточка на каждое застрявшее изменение: вид изменения и значок со словом «Не отправлено» (`StatusChip`, правило 2), с какого времени, «ждут его: n · уйдут при отмене: m», своё пояснение («Ошибка на сервере, не в телефоне. Повторяем сами каждые 5 минут.»; английский текст сервера не выводится), «Повторить сейчас» и «Отменить изменение…» (второй шаг называет, что уйдёт вместе с ним, по видам и числу: «Работа: 1, Счёт или оплата: 3»; если среди уходящих или в самой операции есть деньги — `payment.record`, `visit.pay`, `estimate.deposit`, `invoice.issue`, `invoice.pay`, `expense.add` и любая операция, создающая счёт или оплату (`estimate.approve`, `estimate.countersign` с `invoiceId`), — (у `expense.add` вид «Расход», не «Счёт или оплата») значок «Деньги» и предупреждение словом; правило 5, решение руководителя 07.11); пока изменение отправляется — «Отправляется», кнопки неактивны; если отмена всё же не прошла (`discardOp` → `false`) — «Изменение сейчас отправляется. Дождитесь ответа сервера и попробуйте снова.». Карточки с действиями — `Card` со `StatusChip` (у `ItemCard` нет места для кнопок). Строки RU/EN/ES, префикс `sync.` (задача 3).

**Отказ сервера после `MAX_TRIES` (решение руководителя 07.11):** сейчас операция выбрасывается молча. Денежная операция (`estimate.deposit`, `invoice.issue`, `invoice.pay`, `visit.pay`, `expense.add`; в т. ч. `P0001` «задаток не записан» из #247 «Работ») не исчезает молча: она переходит в постоянный список `rejected` (ключ `octo.outbox.rejected.v1`, по владельцу, как очередь) с текстом отказа и видна (а) карточкой «Не отправлено: сервер отказал» в той же группе в «Настройках» и (б) пунктом «Требует внимания» (`attention.ts`, общий файл — отдельным сообщением руководителю и «Каркасу») с действием «Открыть» (смета / счёт / работа) и «Понятно» (убрать из списка). Повтор отказа нет смысла (сервер сказал «нет»): данные с сервера заменяют локальный вид, пункт объясняет, что не записалось. Немонетные отказы — только строка в «Настройках» (как сейчас — `syncError`).

## 4. Задача 4: гонка `adoptLegacy` / `forgetOnLoad`
Только тест (miniReact): стирание пришло до загрузки очереди → при загрузке сначала убираются операции удалённого человека и старые без владельца, и только потом `adoptLegacy` отдаёт оставшиеся старые вошедшему; удалённый человек, ещё вошедший в этот момент, ничего не «усыновляет». Если тест найдёт ошибку — исправление в том же PR.

## 5. Задача 5: S26 — «кто» в задаче мастера
Сейчас не-офис (мастер, субподрядчик) вставляет задачу с любым `assignee_id`; автор-мастер при правке меняет исполнителя на любого; `done_by` пишет приложение (`ops.ts task.save`: userId текущего, даже если отметил другой).
Решение — одна миграция (время даёт руководитель), правило 16 — только добавляет:
- триггер `t04_task_who` (`before insert or update`, до `t05_task_guard`; `revoke all … from public, anon, authenticated`): для не-офиса чужой исполнитель **заменяется, а не отклоняется** — при вставке на него самого, при смене автором на прежнего, не-автор исполнителя не меняет. Почему не `42501`: старые версии предлагали в «Кто» всех, а «выполнено» уходит в том же upsert — отказ выбросил бы из очереди всю операцию вместе с отметкой (правила 6, 16; security-check 07.11, M1). Не «исправлять» обратно на отказ. Для всех `done_by` ставит сервер: отметили выполненной → `auth.uid()`, вернули → `null`, иначе `old.done_by` (без вошедшего — сервер может менять);
- приложение: в `TaskSheet` у мастера в «Кто» только он; задача уже на другого — только этот человек; `task.save` перестаёт писать `done_by`.
- Решение руководителя 07.11 (L3, L2 security-check): старые задачи, которые мастера уже назначили на других, не исправляем — данных мало, офис их видит и может переназначить; телефон старой версии видит своё значение исполнителя до следующей загрузки — допустимо.
Тесты базы: **T78** — мастер не вставляет задачу на другого, не меняет исполнителя на другого, вставляет на себя; **T79** — `done_by` = тот, кто отметил (подделка перезаписывается), «Вернуть» очищает. e2e **115** — у мастера в шторке задачи «Кто» только он.
