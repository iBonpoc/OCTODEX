# 40. Смета: «Notes» и «Terms & conditions» — данные (#1304, часть д) переноса #1307)

Класс К1: данные компании, юридически значимый текст, права. Этап 0 — эта спецификация. Экран — чат «Экраны»
(#1307 д), данные, база и сервер — «Данные и деньги».

Слова основателя (13.11.2026, чат «Прототип сметы»): два поля сметы, у каждого «Вставить из шаблона» — шаблоны Notes и
Terms под разные услуги. Решение руководителя (#1304): до 1.0 — два поля и текст по умолчанию у компании; несколько
именованных шаблонов и «Вставить из шаблона» — после 1.0 (правило 22). Решение аудита (комментарий в #1304): у Terms текст по
умолчанию отдельно для каждого языка клиента — en обязателен, es и ru необязательны; нет нужного — en; у Notes умолчания нет.

## 2. Брейншторм-оспаривание

1. **Хранить Terms сметы в смете или ссылкой на компанию?** В смете (снимок). Подписанный документ не должен меняться, когда
   компания потом правит свои условия. Ссылка — это сегодняшняя беда из §1. → Terms — часть версии сметы, как строки.
2. **Новое поле или переименовать `note`?** `note` остаётся (правило 16: на телефонах старые версии), на экране зовётся
   «Notes». Новое — только `terms`.
3. **Отличать «нет поля» от «пусто».** `terms` отсутствует — смета сделана до #1304: клиент видит умолчание компании на своём
   языке (как сегодня, без регресса). `terms: ""` — подрядчик сознательно стёр: клиент не видит блок вовсе.
   Альтернатива «заполнить всем старым сметам» отвергнута: менять `calc_inputs` подписанных версий нельзя.
4. **Подставлять при создании или при отправке?** При создании (так в просьбе: «подставляется в новую смету»), чтобы подрядчик
   видел и мог править текст до отправки. Плюс страховка в сторе: если смета сохраняется впервые без `terms` (модуль,
   шаблон, старый путь экрана) — стор подставит сам. Так модулям (Gutters «Сделать смету») ничего делать не надо.
5. **Сменили клиента/язык в черновике.** Если текст Terms не трогали (равен умолчанию прежнего языка) — заменяется на
   умолчание нового языка. Если правили — остаётся, ничего не теряем. Функция чистая, тест.
6. **«en обязателен» — значит запрещать сохранять компанию без en?** Нет: это сломает онбординг и всех, у кого условий ещё нет.
   «Обязателен» = en — всегда последний запасной язык, и поле en показывается всегда; es и ru — по желанию. Пустой en и нет
   своего языка → Terms новой сметы пустые. Если руководитель понимает иначе — В1 в §9.
7. **Шаблоны смет (`EstimateTemplate`) несут Terms?** До 1.0 — нет: Terms приходят из компании. Шаблон несёт `note` как сейчас.
   Именованные шаблоны Terms — после 1.0 (копилка).
8. **Новая версия после отправки** (`ops.ts:1250–1255`, `docForSave`) и пересохранение (`EstimateCard.tsx:351`) берут `doc`
   целиком — `terms` копируются, умолчание заново не подставляется. Дубля сметы и change order в коде ещё нет (S8c, этап 4) —
   правило для них то же, тест появится с ними.
9. **Estixa** — не смотрели, идея не оттуда.
10. **Юридическое (CA, B&P §7159).** Поле Terms — это «свои условия» (warranty, уборка, доступ, PRD 05). Оно **не заменяет**
    статутные блоки и Notice of Cancellation (`est.rescission` остаётся отдельной строкой, как сейчас). Поэтому:
    - Terms на `/p/` — **выше** блока подписи; в PDF — до подписей (уже так);
    - в PDF Terms — основным шрифтом документа, не `.mut` 8 pt;
    - предупреждение про арбитраж (B&P §7191, PRD 05) — после 1.0, отдельная задача (В3).

## 3. Модель данных

### 3.1 Смета
```ts
interface EstimateDoc {
  note?: string;   // Notes — как было, ≤ 5000 символов
  terms?: string;  // НОВОЕ. Terms & conditions; отсутствует = смета до #1304; "" = стёрто. ≤ 10000 символов
}
```
- `normalizeDoc`: строка, управляющие символы кроме `\n`/`\t` — прочь, обрезка по 10000. Не строка → поле выкидывается (то
  есть «старая смета»). (`note` сейчас `normalizeDoc` не режет — 5000 только у шаблона, `estimateTemplate.ts:63,92`; это не меняем.)
- Шаблон сметы: `terms` в шаблон не пишется и из шаблона не читается. Сервер это уже держит: `valid_estimate_template_doc`
  (`20261112210000_tax_rate_ppm.sql:305`) пропускает только options/settings/note — записываем как защиту, тест.
- Сервер: `calc_inputs.terms` + копия в `estimate_versions.terms_text` (существующая колонка). Копию пишет триггер
  `t08_terms_text` из `calc_inputs` при каждой записи документа — так её не обойдёт ни `save_estimate_version`, ни запасной
  путь без функции (PGRST202), ни старый телефон; приложение `terms_text` не шлёт.
  Длина: `check (terms_text is null or char_length(terms_text) <= 10000) not valid` — без проверки старых строк, без
  блокировки (правило 16, малое).
- **Черновик хранит умолчание, полученное при создании**: последующая смена умолчания компании его не меняет (подрядчик видит и правит именно этот текст).
- **Черновик без ключа (сделан до #1304) замораживается при отправке или подписи** (ревью #1328): триггер `t06_terms_on_lock` (сервер, до t40) и `withFrozenTerms` (телефон: `sendEstimate`, `approveEstimate`) вписывают умолчание на языке клиента. Без своего текста остаются только версии, заблокированные до #1304.
- **Замораживает отправка, не подпись**: `locked_at` ставится при отправке (PRD 05:110). С этого момента `terms_text` и `calc_inputs` версии не меняются — уже держит триггер `app.tg_estimate_version_lock` (core.sql:738: изменение заблокированной версии — 42501); тест.

### 3.2 Компания
```ts
estimate: { validDays; depositBps; terms?: string /* старое, правило 16 шаг 1 */; termsByLang?: { en?: string; es?: string; ru?: string } }
```
- База: `estimate_settings.terms_by_lang = {"en": …, "es": …, "ru": …}` — только эти ключи, строки ≤ 10000.
- **Правило 16, шаг 1** (этот PR):
  - миграция переносит `terms` → `terms_by_lang.en`, где `terms_by_lang` нет;
  - новые телефоны пишут оба: `terms_by_lang` и `terms = terms_by_lang.en` (старые телефоны и старые сборки читают `terms`);
  - старый телефон, сохраняя компанию, перезаписывает только `terms` (`companyToDb` раскладывает сохранённое), а `terms_by_lang`
    не трогает → триггер `before update on companies` сводит их: изменился `terms`, а `terms_by_lang.en` нет → `en := terms`;
    изменился `terms_by_lang.en` → `terms := en`. Так и старый, и новый телефон видят одно и то же en;
  - оба изменились и не совпадают (новый телефон правит en, а старый пишет свою копию `terms`) — побеждает `terms_by_lang.en`
    (запись нового телефона), `terms := en`. Окно гонки малое: `company.save` перечитывает строку компании с сервера прямо
    перед записью (`ops.ts:881`), так что старый телефон затирает es/ru не своим кэшем, а только в эти миллисекунды — как и
    любые другие ключи `estimate_settings` сегодня;
  - триггер `before insert or update` (онбординг тоже): на вставке несогласованные ключи сводятся тем же правилом;
  - тот же триггер проверяет форму `terms_by_lang` (лишний ключ, не строка, длиннее 10000 — отказ).
- **Шаг 2** (отдельный PR после 1.0, задача `долг`): когда ни одна поддерживаемая сборка не читает `terms` — убрать ключ и
  триггер (`-- rule16: step 2 (estimate_settings.terms, после PR #1304-данные)`).
- Права: `companies_update` уже пускает только owner и admin — новых политик нет, нужен тест (§7).

## 4. Правила (чистые функции, `src/features/estimateTerms.ts`, новый файл зоны (а)/(г) по договорённости)

- `termsDefault(co, lang): string` — `termsByLang[lang]` (непустой) → `termsByLang.en` → старое `terms` → `""`.
- `termsForNew(db, {customerId?, leadId?})` → `{ text, lang }`, язык — `docLanguageFor` **без `personId`**: у сметы нет
  «человека», и сервер (`app.estimate_doc_language`, `20261105180000_portal_doc_language.sql:15`) считает так же: основной
  человек клиента → основной человек лида → `leads.language` → компания → en. Тест-пара unit + db на одних входах — иначе
  `/p/` и приложение покажут Terms на разных языках.
- `termsOnClientChange(current, oldLang, newLang, co)` — п.2.5: не трогали → умолчание нового языка, правили → как есть.
- `termsForClient(doc, co, lang)` — что видит клиент: `doc.terms` есть → он (пусто → блока нет); нет → `termsDefault(co, lang)`.
  Выбирает **страница** этой же функцией (`PortalData.terms`, `cloud/portal.ts`: и с сервера `fromRaw`, и с телефона
  `portalFromEstimate`) — сервер только отдаёт снимок и умолчания, поэтому разойтись приложению и `/p/` нечем.
- `syncCompanyTerms(prev, next)` — то же правило, что триггер t08, в `saveCompany` стора: экран, который ещё правит старое
  `estimate.terms`, не теряет правку за `termsByLang.en`.

## 5. Сервер: `/p/` и PDF

- `app.client_doc`: в список пропускаемых полей добавить `terms` (рядом с `note`) — клиент читает снимок из версии.
- Язык страницы: `doc_language` добавляет обёртка `public.portal_estimate` (`app.estimate_doc_language`), не
  `portal_estimate_base`. Подстановка по языку — в обёртке (новая редакция, та же сигнатура).
- `portal_estimate` (правило 16, та же сигнатура): добавляет `company.terms_by_lang` (`app.estimate_terms_by_lang`: только
  en/es/ru, непустые строки). `company.terms` остаётся (старый вид страницы в кэше браузера, старый сервер → старый текст).
  Выбор — на странице `termsForClient` (§4).
- PDF (`estimatePdf.ts`), `/p/` и подпись на месте (общий `EstimateView`, проп `terms`): «Notes» = `doc.note`,
  «Terms & conditions» = `PortalData.terms` / `termsForClient(...)`; заголовки — `tFor(lang)`
  (ключи `est.doc.notes`, `est.doc.terms`, RU/EN/ES); Terms выше подписи, шрифтом не меньше 10 pt (основной шрифт
  стилей classic 9.5 и compact 8.5 — тоже мал, это В4).
  - **Notes на `/p/` сейчас не выводятся вовсе** (в `p/[token].tsx` нет `note`) — это новая отрисовка.
  - **Подпись на месте** (`EstimateCard.tsx:315`, `SignBlock`): то же правило — клиент видит Notes и Terms выше подписи.
  - **Демо и PDF с телефона** идут не через сервер, а через `portalFromEstimate` / `companyForPortal` (`portal.ts:209`,
    `EstimateCard.tsx:76`): в `PortalData` добавить `terms` = `termsForClient(doc, co, lang)` — одна функция с сервером.
- Сметы без ключа `terms` (созданы до #1304; ещё старая операция `estimate.add` / `store.addEstimate`, `store.tsx:2017`,
  `ops.ts:812` — смета без `doc`, в интерфейсе не вызывается, но может прийти из очереди старого телефона; и черновик, впервые
  пересохранённый новым телефоном — подстановки нет, `prev` есть) показывают умолчание компании на языке клиента.
- Старые **отправленные** сметы без `terms` показывают умолчание компании (как сегодня) — восстановить, что было при подписи,
  нечем. Записано как известное ограничение.

## 6. API стора для «Экранов» (#1307 д)

- Компания: `Company.estimate.termsByLang` — через существующий `company.save` (новой операции нет). Сохранять умолчания может
  owner/admin — экран уже показывает раздел только для чтения, когда `store.role !== "director"` (роль приложения для owner/admin, `company/[section].tsx:39`) — то же для новых полей.
- Смета: `doc.terms` — через существующее сохранение сметы.
- `useStore().estimateTerms({ customerId?, leadId? })` → `{ text, lang }` — для подстановки в новую смету в редакторе.
- `estimateTermsOnClientChange(...)` — обёртка `termsOnClientChange` для редактора.
- Страховка в `saveEstimate`: первая версия без ключа `terms` → стор подставит `termsForNew`.
- Экран (не наш): два поля «Notes» / «Terms & conditions» в редакторе; раздел компании — Terms en + «Добавить испанский /
  русский»; подпись «Уходит клиенту на его языке».
- Правило для экрана: повторный выбор в «С чего начать?» (`estimate/new.tsx:138`) сбрасывает `doc` — `terms` при этом
