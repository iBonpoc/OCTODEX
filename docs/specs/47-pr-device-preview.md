## 0. Итог

**Делаем — вариант А (канал на PR + переключатель канала), за ~2 рабочих дня, без новой нативной сборки.** Расходов сверх нынешних нет (§4).

1. **Сменить канал в уже установленной сборке можно, и это штатная функция**, а не обход: `Updates.setUpdateRequestHeadersOverride({'expo-channel-name': '<канал>'})`, в Expo SDK 54 / expo-updates ≥ 0.29.0 и новее; у нас SDK 58, expo-updates `~58.0.22` [док: docs.expo.dev/eas-update/channel-surfing, /override; код: `apps/mobile/package.json`]. Назад — `setUpdateRequestHeadersOverride(null)`. Новая сборка в TestFlight не нужна, если в нативной сборке уже есть заголовок `expo-channel-name`: он есть, у профиля `testflight` в `eas.json` задан `channel: preview` [док + код].
2. **Сборка не станет «кирпичом»** при варианте А: защита от кирпича (anti-bricking) остаётся включённой. Её выключает только вариант Б (URL конкретного обновления), и его мы отвергаем (§3) [док: /override].
3. **Опасность реальна, но с другой стороны**: не «приложение не запустится», а «телефон застрянет на канале PR» (в документации прямо сказано: сломанное обновление может закрыть дорогу к экрану, который снимает подмену [док: /preview]) и «PR-код пишет в боевую базу» (§5). Оба закрываются условиями на PR и серверным выключателем (§5, §7).
4. **Правило 27 закрывается частично**: появляется канал проверки «до влития» (п. «в» правила), но проверяет по-прежнему человек на устройстве. Модульные тесты математики и строка «Натив:» остаются обязательными (§8).
5. **Открытый вопрос основателю — один** (§9): уточнение его решения 05.11 «видит только влитое». Подпись кода — нет (§5а п. 6). Условия аудита №2 — §5а.

## 3. Варианты

### А. Канал на каждый PR + переключатель канала в скрытом меню (**рекомендуем**)

- **Публикация.** Новый workflow `.github/workflows/pr-device-preview.yml`, запускается только когда на PR висит метка `на-устройстве` (её ставит руководитель или автор по запросу): `eas update --channel pr-<N> --branch pr-<N> --platform ios --message "PR #<N> @<sha7>"`. Повторный пуш в PR → новое обновление в той же ветке.
- **Переключатель.** В Настройках, в скрытом месте (семь нажатий на строку версии) — поле «номер PR» и две кнопки: «Открыть PR #N» и «Вернуться на main». Под ним — какой канал сейчас и когда опубликовано обновление (`Updates.createdAt`, как у `version.tsx`). Код работает только когда `EXPO_PUBLIC_APP_ENV === "preview"` (§5).
- **Вернуться на `preview`:** `setUpdateRequestHeadersOverride(null)` + `fetch` + `reload` [док].
- **Плюсы:** без новой нативной сборки; защита от кирпича включена; официальный API; возврат одним нажатием; серверный выключатель (§5); один и тот же TestFlight-сборочный номер у основателя.
- **Минусы:** API помечен Experimental [док]; сломанный PR-пакет может закрыть переключатель (§5, смягчаем); общая боевая база (§5); нативные изменения в PR так не проверить (§5).
- **Цена:** §4.

### Б. Загрузка конкретного обновления по URL (`setUpdateURLAndRequestHeadersOverride`)

- Нужна **новая нативная сборка** с `disableAntiBrickingMeasures: true` [док: /override].
- **Плюсы:** не нужны каналы на PR; можно загрузить любое обновление по id.
- **Минусы:** флаг живёт в бинарнике, а из TestFlight-сборки со временем получается магазинная (тот же профиль `production`) — документация прямо говорит «не включать в продуктовых»; без защиты от кирпича сломанный PR лечится только переустановкой; сотрудник с правом публикации мог бы направить установки на свой сервер (риск «компрометации сотрудника» из документации) [док: /override]. **Отвергаем.**

### В. Отдельное приложение «GoRix PR» (другой bundle id, свой канал `pr`)

- **Плюсы:** в магазинной сборке нет никакого переключателя вообще; PR-приложение можно держать на телефоне рядом.
- **Минусы:** второе приложение в App Store Connect и TestFlight, свои сертификаты и ключ пушей, свои адреса возврата Supabase Auth и ссылки `gorix://`; отдельная сборка при каждом нативном изменении; на устройстве другая локальная база и другая сессия — вход заново. [вывод] Это недели настройки против двух дней, и вариант А уже закрывает риск через `APP_ENV`.
- **Когда вернуться:** если аудит решит, что переключатель в бинарнике TestFlight неприемлем.

### Г. Не делать (как сейчас)

Правило 27: строка «Натив:» в PR + основатель проверяет после влития в TestFlight + откат по правилу 24. Нулевая цена, но каждая плохая правка жеста доходит до `main` (цепочка #1278 → #1405 → откат #1443 из текста задачи).

## 4. Цена [док, 15.11.2026]

- **Expo Update: обновлений безлимитно** на всех тарифах. Платится по **уникальным установкам, скачавшим хотя бы одно обновление за месяц (MAU)**, и по трафику: Free — 1 000 MAU, 100 ГиБ трафика, 20 ГиБ хранилища; Starter ($19/мес) — 3 000 MAU; дальше — по факту ($0,005 за пользователя, $0,10 за ГиБ трафика, $0,05 за ГиБ хранилища). Источники: expo.dev/pricing; docs.expo.dev/billing/usage-based-pricing.
- **[вывод]** PR-обновления весят как обычное (ориентир из справки: 5 МиБ на обновление). Пока обновления качают 1–3 устройства (основатель и аудит), MAU не растёт — установка считается один раз в месяц, сколько бы обновлений она ни скачала [док: тот же раздел]. Трафик: десятки PR в день × 5 МиБ × 2–3 устройства — единицы ГиБ в месяц, **[допущение]** без замера.
- **Хранилище.** Каждый PR-канал — своя ветка с обновлениями; без чистки копятся. Нужен второй шаг: при закрытии PR — `eas branch:delete pr-<N>` (образец чистки: docs.expo.dev/eas/workflows/examples/branch-cleanup). Без него 20 ГиБ Free не кончатся быстро, но чистим всё равно.
- **Минуты CI.** Один запуск = установка зависимостей + `eas update`, примерно как `release.yml` без миграций [допущение: 3–5 мин на GitHub, оплаты GitHub не добавляет, пока в лимите].
- **Подпись кода** (end-to-end code signing) в списке тарифов Expo есть только у Production и Enterprise [док: expo.dev/pricing]. На Free/Starter её нет — решение: не берём, §5а п. 6. Какой тариф у нашего проекта — **[не проверено]**, в документах репозитория не нашёл.

## 5а. Дополнения по аудиту №2 (15.11.2026) — условия «да» на код

Аудит №2 согласен с вариантом А; ниже семь условий. Они **сильнее** строк Р1–Р8 выше, где есть расхождение.

**1. Кто может включить PR-канал.** Только заранее названные учётные записи, не любой тестировщик TestFlight.
- Механизм: меню открывается, если одновременно (а) `EXPO_PUBLIC_APP_ENV === "preview"`, (б) `id` вошедшего пользователя (`auth.uid`, UUID, не почта и не имя) входит в список `EXPO_PUBLIC_PR_CHANNEL_USERS` и (в) выполнен жест (семь нажатий на строку версии). Список лежит не в git (но публичен, см. §5б В), а в переменной окружения EAS и попадает в бандл `main` при выпуске; смена списка — обычное обновление `main`. Для этого `release.yml` должен передать переменную при `eas update` — это правка `release.yml`, **только после «да»**.
- Что это защищает: чужой тестировщик TestFlight не увидит меню и не загрузит PR-код в **свою** сессию с боевой базой. Что не защищает: манифест канала открыт по имени (Р2); вход закрыт самим клиентом, а не сервером.
- Тесты: модульные — пользователь вне списка, пустой список, не `preview`, без жеста → меню закрыто; пользователь из списка → открыто.

**2. Сторож в CI файлом.** `pr-device-preview.yml` перед публикацией сверяет `git diff --name-only base...head` с запретным списком: `supabase/**`, `src/cloud/**`, `src/data/**`, `apps/mobile/package.json`, корневой `package.json`, `package-lock.json`, `app.json`, `app.config.ts`, `eas.json`, `src/config/version.ts`, а также любое изменение в `expo-*` и нативных зависимостях и `runtimeVersion`. Список — отдельный файл `.github/pr-device-preview-denylist.txt` (одна маска в строке); отказ — красный шаг с названием файла, обновление **не публикуется** и метка снимается. Тест сторожа: `apps/mobile/test/prDevicePreviewDenylist.test.ts` — таблица «путь → публикуется / нет», включая `supabase/migrations/x.sql`, `src/cloud/ops.ts`, `package.json`, `src/features/foo.tsx` (проходит). Образец — сторож `migrationGuard.test.ts`.

**3. Видимый признак, возврат, данные.**
- На каждом экране строка версии (`version.tsx`) получает в конце `· PR #N`, когда `Updates.channel` равен `pr-<N>` (канал виден после перезапуска [док: channel-surfing]). Строка уже стоит в шапке каждого экрана [код].
- Возврат: в меню кнопка «Вернуться на main» — одно нажатие; сама подмена снимается через **24 ч** (при старте, в первом модуле, по записанному времени включения).
- **Очередь офлайн и локальные данные при переключении туда и обратно.** Локальная база, ключи хранилища и очередь `useStore().queue` — **те же** до и после переключения: канал меняет только пакет JS, не данные приложения [вывод из документации: подмена заголовка не трогает хранилище; **[не проверено]** — проверяет проба]. Поэтому: (а) переключение (включить, снять, истечение) **разрешено только при пустой очереди** — иначе кнопка отказывает: «Сначала дождитесь отправки»; при истечении 24 ч с непустой очередью подмена снимается при **первом запуске с пустой очередью**, сначала очередь уходит; (б) PR с изменением `src/data/**` в канал не идёт (п. 2), значит форма данных у `pr-N` и `preview` одна. Тест: модульный — очередь непуста → переключение отказывает, пуста → разрешает; в e2e на вебе — меню нет.

**4. Вырезание переключателя из магазинной сборки — тестом сборки.** Сторож `apps/mobile/test/prChannelStrip.test.ts` (в CI): `EXPO_PUBLIC_APP_ENV=production expo export --platform ios` → в готовых файлах нет ни `setUpdateRequestHeadersOverride`, ни метки `__PR_CHANNEL_SWITCHER__`; тот же экспорт с `preview` — **обе есть** (контрольная проверка, иначе тест проходил бы вхолостую). Если Metro не уберёт мёртвую ветку, запасной ход: `metro.config.js` подменяет модуль `channelSwitcher` пустой заглушкой при `production`. Это «доказательство тестом сборки», а не проба на телефоне. Стоимость: два экспорта, порядка 1–2 мин **[допущение]**, только в CI.

## 5б. Правки по независимой проверке (16.11.2026) — сильнее §5 и §5а

Два независимых агента (Plan — архитектура; security-check — безопасность) получили только спеку и workflow, без выводов автора. Найдено 7 блокирующих пунктов, все приняты. Где §5б расходится с §5 и §5а, **верно §5б**.

**А. Публикация — только руками руководителя на проверенный коммит** (было: по метке и `synchronize`; закрывает Б1 и Б2).
- Workflow `pr-device-preview.yml` запускается **только** `workflow_dispatch` из `main`, входы: номер PR и **полный sha**, который руководитель просмотрел. Событий `pull_request`/`synchronize` и метки как спускового крючка нет: файл workflow, список запретов и скрипт сверки всегда берутся из `main`, правкой PR их не изменить.
- Сборка и публикация **двумя заданиями**. Задание 1 без секретов: checkout sha PR, `npm ci`, `expo export` (тут исполняется код PR — metro/babel/скрипты установки) → папка `dist` как артефакт. Задание 2 с секретом из GitHub Environment `device-preview` (обязательное подтверждение руководителя, только ветка `main`): checkout `main`, скачать `dist`, `eas update --skip-bundler` (инструменты и конфиг — из `main`). **[не проверено]** — работает ли `--skip-bundler` в eas-cli 27.4.1 и берёт ли он `dist` как есть; проверяет проба. Если нет — запасной вариант: одно задание, но токен только в Environment с подтверждением, запуск только `workflow_dispatch`, sha просмотрен руководителем. Тогда остаточный риск (код PR видит токен) записывается основателю одной строкой.
- Токен — **отдельный** `EXPO_TOKEN_PR` (имя секрета, значения нигде нет), только в Environment. Закрытие PR (чистка ветки `eas branch:delete`) — отдельное задание с тем же Environment.
- Входы workflow (номер, sha) в `run` не подставляются, идут через `env` и проверяются: номер `^[0-9]+$`, sha `^[0-9a-f]{40}$`, и sha должен быть головой этого PR.
- Список файлов — `git diff --name-only --no-renames <база>...<sha>`: переименование запретного файла не обходит маску.

**Б. Что запрещено в PR на устройство** (закрывает п. 4 безопасности; пути с префиксом `apps/mobile/`, где нужно). Автоотказ при изменении: `supabase/**`, `apps/mobile/src/cloud/**`, `apps/mobile/src/data/**`, `apps/mobile/src/config/**` (там адрес и ключ базы), `apps/mobile/package.json`, `package.json`, `package-lock.json`, `apps/mobile/app.json`, `apps/mobile/app.config.ts`, `apps/mobile/eas.json`, `apps/mobile/metro.config.js`, `babel.config.js`, `apps/mobile/scripts/**`, `.npmrc`, `patches/**`, `.github/**`, `.env*`, `packages/**`. Слова «`expo-*` и нативные зависимости» из §5а п.2 убраны: их ловят `package.json` и `package-lock.json`. **Честная граница:** PR из `src/features/**` и `src/auth/**` (то есть именно экраны и жесты) путь не защищает: такой код может вызвать боевую базу под сессией основателя. Закрывается **ручным просмотром кода перед запуском** (руководитель, п. А) и тем, что запускать может только он; отдельная тестовая база для канала PR — вопрос на будущее (§9).

**В. Меню не открывается в магазинной сборке — решает нативный канал, а не переменная** (закрывает Б3 безопасности; уточняет §5 Р1 и §5а п.1, п.4).
- Бандл OTA собирается командой `eas update` без профиля `eas.json`, поэтому `EXPO_PUBLIC_APP_ENV` в нём **не доказывает** тип сборки. Условие входа меняется на: `Updates.channel` (заводской канал сборки; для магазинной — `production`) равен `preview` **или** совпадает с `^pr-[0-9]+-[0-9a-f]{8}$` **и** `auth.uid` в списке **и** жест. Проверка делается при показе меню, в момент подмены и при старте.
- Поэтому даже если код переключателя окажется в OTA-бандле `production`, в магазинной сборке (`Updates.channel === "production"`) он **не включится**. Это сильнее, чем «пробой».

Тест `prChannelStrip.test.ts`: (а) экспорт с `APP_ENV=production` не содержит ни `setUpdateRequestHeadersOverride`, ни метки `__PR_CHANNEL_SWITCHER__`, экспорт с `preview` — обе (контроль); (б) модульно: `Updates.channel = "production"` → меню закрыто при любых остальных условиях. Публикация OTA-бандла с переключателем в канал `production` — запрещена правилом, которое проверяет (а) для OTA-экспорта `production`.
- `EXPO_PUBLIC_PR_CHANNEL_USERS` попадает в бандл, список UUID виден через манифест канала `preview`. UUID — не секрет, но и не «не в git»: формулировка §5а п.1 исправлена: список не в git, но **публичен**; вход закрыт клиентом, не сервером. **Г. Имя канала со случайным суффиксом** (п. 7 безопасности, бесплатно): `pr-<N>-<8 hex>`, суффикс виден только руководителю (в сводке задания), основатель вводит его целиком. Номера подряд уже не угадываются.

**Д. Сломанный пакет и возврат — что гарантируется, что нет** (закрывает блокирующие 1–4 архитектуры).
- **Гарантированный путь один — серверный:** `eas channel:edit pr-<N>-<hex> --branch preview`. После него устройство, которое ещё запускается, получает обновление `main` (в нём есть меню «Вернуться на main»). Из документации Expo (error-recovery): после падения до первого экрана приложение откатится на прежнее обновление само; после падения **после** экрана, если с первого рендера прошло не больше 10 с, приложение 5 с проверяет канал и скачивает обновление; дальше 10 с перехвата нет, но проверка обновления при запуске выполняется нативно, до JS [док + вывод; **[не проверено]** на устройстве].

Оно **не ждёт пустой очереди**: очередь лежит в локальном хранилище и от снятия подмены не страдает, уйдёт уже кодом `main`. Это снимает расхождение §5 Р3(2) и §5а п.3 (второе заменяется на: **переключение внутрь** — только при пустой очереди; **наружу и истечение** — всегда).
- Последний случай — переустановка из TestFlight. **Неотправленная очередь при этом теряется** (облако хранит только отправленное). Поэтому перед пробой: основатель убеждается, что «ждёт отправки» пусто (шаг 0 инструкции).
- Проба (§6) обязана включать **ломаные пакеты**: (а) падение до первого экрана; (б) через 1–3 с после первого экрана; (в) через >10 с. Для каждого — проверить, вернул ли серверный выключатель устройство на `main`, и сколько это заняло. Только после (а)–(в) и счастливого пути «туда-обратно» (два прохода) канал считается рабочим. Пробные пакеты — отдельные тестовые PR-ветки, не в `main`, без изменений данных.

**Е. Остальное из «желательно».**
- Канал и ветку создаём явно: `eas channel:create pr-<N>-<hex>` (если нет), затем `eas update --branch pr-<N>-<hex>` и `eas channel:edit pr-<N>-<hex> --branch pr-<N>-<hex>` — расхождение команд между §3 А и §6 п.1 снято.
