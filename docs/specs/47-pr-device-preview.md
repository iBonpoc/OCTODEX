## 0. Итог

**Делаем — вариант А (канал на PR + переключатель канала), за ~2 рабочих дня, без новой нативной сборки.** Расходов сверх нынешних нет (§4).

1. **Сменить канал в уже установленной сборке можно, и это штатная функция**, а не обход: `Updates.setUpdateRequestHeadersOverride({'expo-channel-name': '<канал>'})`, в Expo SDK 54 / expo-updates ≥ 0.29.0 и новее; у нас SDK 58, expo-updates `~58.0.22` [док: docs.expo.dev/eas-update/channel-surfing, /override; код: `apps/mobile/package.json`]. Назад — `setUpdateRequestHeadersOverride(null)`. Новая сборка в TestFlight не нужна, если в нативной сборке уже есть заголовок `expo-channel-name`: он есть, у профиля `testflight` в `eas.json` задан `channel: preview` [док + код].
2. **Сборка не станет «кирпичом»** при варианте А: защита от кирпича (anti-bricking) остаётся включённой. Её выключает только вариант Б (URL конкретного обновления), и его мы отвергаем (§3) [док: /override].
3. **Опасность реальна, но с другой стороны**: не «приложение не запустится», а «телефон застрянет на канале PR» (в документации прямо сказано: сломанное обновление может закрыть дорогу к экрану, который снимает подмену [док: /preview]) и «PR-код пишет в боевую базу» (§5). Оба закрываются условиями на PR и серверным выключателем (§5, §7).
4. **Правило 27 закрывается частично**: появляется канал проверки «до влития» (п. «в» правила), но проверяет по-прежнему человек на устройстве. Модульные тесты математики и строка «Натив:» остаются обязательными (§8).
5. **Вопросы основателю — два** (§9): отмена его решения 05.11 «видит только влитое» (для PR-каналов) и тариф Expo для подписи кода.

Ветку удаляют `eas branch:delete`. | /eas-cli, /getting-started |
| Откат на стороне сервера? | `eas update:rollback` и `eas update:republish` публикуют прежнее обновление заново: клиенты получают его как новейшее. | /rollbacks, /eas-cli |

## 2. Как у нас сейчас [код]

- Сборка TestFlight (`com.gorix.app`): профиль `testflight` = `production` + `channel: preview` + `EXPO_PUBLIC_APP_ENV=preview`. Магазинная сборка — профиль `production`, канал `production`, `EXPO_PUBLIC_APP_ENV=production` [код `eas.json`]. Это разделение — основа безопасности (§5).
- `runtimeVersion: { policy: "sdkVersion" }` → у всех сборок и обновлений SDK 58 одна среда выполнения `exposdk:58.0.0` (её же проверяет `release.yml`) [код `app.json`, `release.yml:168`]. **Следствие:** PR, добавивший нативный модуль, совместим по метке, но упадёт при запуске.
- `release.yml` публикует в канал `preview` только после слияния в `main`; `preview.yml` на PR собирает **веб-копию** и намеренно **не** публикует OTA: «Expo Go показывает все обновления проекта, основатель должен видеть только влитое» (решение основателя 05.11.2026) [код `preview.yml:1–5`].
- Проверка «Expo отдаёт новое обновление» в `release.yml` читает `https://u.expo.dev/<projectId>` без ключа: манифест канала открыт любому, кто знает id проекта (он лежит в `app.json`) и имя канала [код `release.yml:168`].
- Приложение и боевая база одна: `SUPABASE_URL` по умолчанию — боевой проект [код `src/config/backend.ts`]. Миграции PR на базу не попадают до влития (`preview.yml:5–6`).
- Версия в шапке показывает номер PR для превью-сборки сайта (`setBuild.cjs`) [код `src/features/version.tsx`, `preview.yml`].

## 3. Варианты

### А. Канал на каждый PR + переключатель канала в скрытом меню (**рекомендуем**)

- **Публикация.** Новый workflow `.github/workflows/pr-device-preview.yml`, запускается только когда на PR висит метка `на-устройстве` (её ставит руководитель или автор по запросу): `eas update --channel pr-<N> --branch pr-<N> --platform ios --message "PR #<N> @<sha7>"`. Повторный пуш в PR → новое обновление в той же ветке.
- **Переключатель.** В Настройках, в скрытом месте (семь нажатий на строку версии) — поле «номер PR» и две кнопки: «Открыть PR #N» и «Вернуться на main». Под ним — какой канал сейчас и когда опубликовано обновление (`Updates.createdAt`, как у `version.tsx`). Код работает только когда `EXPO_PUBLIC_APP_ENV === "preview"` (§5).
- **Вернуться на `preview`:** `setUpdateRequestHeadersOverride(null)` + `fetch` + `reload` [док].
- **Плюсы:** без новой нативной сборки; защита от кирпича включена; официальный API; возврат одним нажатием; серверный выключатель (§5); один и тот же TestFlight-сборочный номер у основателя.
- **Минусы:** API помечен Experimental [док]; сломанный PR-пакет может закрыть переключатель (§5, смягчаем); общая боевая база (§5); нативные изменения в PR так не проверить (§5).
- **Цена:** §4.

### Б. Загрузка конкретного обновления по URL (`setUpdateURLAndRequestHeadersOverride`)

- Нужна **новая нативная сборка** с `disableAntiBrickingMeasures: true` [док: /override].
- **Плюсы:** не нужны каналы на PR; можно загрузить любое обновление по id.
- **Минусы:** флаг живёт в бинарнике, а из TestFlight-сборки со временем получается магазинная (тот же профиль `production`) — документация прямо говорит «не включать в продуктовых»; без защиты от кирпича сломанный PR лечится только переустановкой; сотрудник с правом публикации мог бы направить установки на свой сервер (риск «компрометации сотрудника» из документации) [док: /override]. **Отвергаем.**

### В. Отдельное приложение «GoRix PR» (другой bundle id, свой канал `pr`)

- **Плюсы:** в магазинной сборке нет никакого переключателя вообще; PR-приложение можно держать на телефоне рядом.
- **Минусы:** второе приложение в App Store Connect и TestFlight, свои сертификаты и ключ пушей, свои адреса возврата Supabase Auth и ссылки `gorix://`; отдельная сборка при каждом нативном изменении; на устройстве другая локальная база и другая сессия — вход заново. [вывод] Это недели настройки против двух дней, и вариант А уже закрывает риск через `APP_ENV`.
- **Когда вернуться:** если аудит решит, что переключатель в бинарнике TestFlight неприемлем.

### Г. Не делать (как сейчас)

Правило 27: строка «Натив:» в PR + основатель проверяет после влития в TestFlight + откат по правилу 24. Нулевая цена, но каждая плохая правка жеста доходит до `main` (цепочка #1278 → #1405 → откат #1443 из текста задачи).

## 4. Цена [док, 15.11.2026]

- **Expo Update: обновлений безлимитно** на всех тарифах. Платится по **уникальным установкам, скачавшим хотя бы одно обновление за месяц (MAU)**, и по трафику: Free — 1 000 MAU, 100 ГиБ трафика, 20 ГиБ хранилища; Starter ($19/мес) — 3 000 MAU; дальше — по факту ($0,005 за пользователя, $0,10 за ГиБ трафика, $0,05 за ГиБ хранилища). Источники: expo.dev/pricing; docs.expo.dev/billing/usage-based-pricing.
- **[вывод]** PR-обновления весят как обычное (ориентир из справки: 5 МиБ на обновление). Пока обновления качают 1–3 устройства (основатель и аудит), MAU не растёт — установка считается один раз в месяц, сколько бы обновлений она ни скачала [док: тот же раздел]. Трафик: десятки PR в день × 5 МиБ × 2–3 устройства — единицы ГиБ в месяц, **[допущение]** без замера.
- **Хранилище.** Каждый PR-канал — своя ветка с обновлениями; без чистки копятся. Нужен второй шаг: при закрытии PR — `eas branch:delete pr-<N>` (образец чистки: docs.expo.dev/eas/workflows/examples/branch-cleanup). Без него 20 ГиБ Free не кончатся быстро, но чистим всё равно.
- **Минуты CI.** Один запуск = установка зависимостей + `eas update`, примерно как `release.yml` без миграций [допущение: 3–5 мин на GitHub, оплаты GitHub не добавляет, пока в лимите].
- **Подпись кода** (end-to-end code signing) в списке тарифов Expo есть только у Production и Enterprise [док: expo.dev/pricing]. На Free/Starter её нет — см. вопрос §9. Какой тариф у нашего проекта — **[не проверено]**, в документах репозитория не нашёл.

| (а) модульные тесты математики | Не заменяет и не отменяется. |
| (б) строка «Натив: как проверено на iPhone» | Становится содержательной: «PR-канал `pr-N`, устройство, версия iOS». |
| (в) проверка на устройстве **до** влития | **Это и есть решение #1449**: руководитель вливает PR, когда в нём указан проверенный канал `pr-N`. До появления канала действует прежнее условие «основатель готов проверить в тот же час». |

Не закрывает: жесты и клавиатура **не** проверяются автоматически; PR с нативными или данными-изменениями (Р4, Р5) идёт прежним путём (проверка после влития, откат по правилу 24).
