## 0. Итог

1. **Одно место — три правки.** Подпись компании (#1532, README §9 п.11), снимок издателя (45 §7) и фото с реквизитами оплаты (46 §0 п.4, §11 Р1–Р2, §11а п.2) меняют одно и то же: что попадает в документ в тот момент, когда он уходит клиенту. Делаем это **одной серверной функцией отправки** и **одним отпечатком** (`content_hash`) на версию.
2. **Момент отправки — это момент, когда сервер запирает версию** (`locked_at`). В той же транзакции сервер сам собирает снимок издателя, проверяет фото, считает отпечаток и, если отправитель это подтвердил, ставит подпись компании. Телефон ничего из этого не присылает: ни снимок, ни отпечаток, ни имя подписавшего.
3. **Подпись компании ставит человек, который нажал «Отправить»:** его сохранённой подписью, его именем и должностью из профиля, «for {компания}» (решение основателя 15.11, В1). Нужно право `can_sign_contracts` и **указанная должность** (у каждого сотрудника она обязательна, §4.3). На экране отправки видна строка «Подписано вами: …» — это и есть действие человека. Нет сохранённой подписи — приложение просит нарисовать её тут же, при отправке (В3). Нет права — смета уходит по старому пути: подпись компании ставится после клиента (S8b).
4. **После подписи клиента договор исполнен сразу:** работа «назначить дату», счёт на депозит, лид `won`, клиент `active`. Второго шага нет. Новых статусов нет.
5. **Отправленная и подписанная версия неизменна**, и PDF через год собирается из неё же: строки, фото, условия, язык, шапка, подписи, отпечаток. Для счёта — то же при выпуске, для квитанции — при записи платежа.
6. **Старые версии приложения (правило 16)** продолжают звать старую `send_estimate`. Снимок и отпечаток сервер пишет и для них. Подпись компании за них сервер **не ставит**: на старом экране человек не видел строки «Подписано вами».
7. **Ссылка уходит клиенту только после ответа сервера.** С сетью приложение ждёт ответа («отправлено», «отправлено без подписи компании» или отказ) и только потом открывает «Сообщения». Без сети смета ставится в очередь «отправить, когда будет сеть»: подпись компании не показывается как поставленная, ссылки у клиента нет, пока сервер не принял (§4.7).
8. **Вопросы В1–В5 сняты ответами основателя 15.11 (§12).** Подписать смету клиент может, только когда загружены все её данные вместе с фото (В5, §4.1 п.3).

## 4. Решение

### 4.1. Что входит в отправленную версию

Сервер пишет всё ниже **до `locked_at`, в одной транзакции** с запиранием. После запирания версию не меняет никто: это держит замок `tg_estimate_version_lock`, в него вносятся новые колонки.

1. **Содержание** — `calc_inputs`, как сейчас: строки, варианты, налог, скидка, задаток, заметка, условия (#1304), страницы-вложения. По спеке 46 сюда добавляются фото строк и блок «Фото» — ссылками (`fileId`, `sha256`).
2. **Снимок издателя** — новая колонка `issuer_snapshot jsonb` (45 §7). Собирает одна серверная функция `app.issuer_snapshot(company_id, lang)`, общая для сметы, счёта и квитанции:
   - название (`dba`, иначе `name`), юр. имя, адрес, телефон, почта, сайт;
   - лицензии и контакты «на документах»;
   - логотип и цвет. Логотип хранится один раз по `sha256` в таблице файлов документов (`app.document_assets`), в снимке — только хеш. Сейчас логотип — `data:`-строка в `companies.brand` (`app/company/[section].tsx:441`) [код];
   - часовой пояс компании;
   - язык документа (`app.estimate_doc_language` на момент отправки);
   - обязательные юридические фразы на этом языке (сейчас — `est.rescission` из словаря приложения) — текстом;
   - реквизиты и включённые способы оплаты (46 §11а п.2) — Zelle, «чек на имя», Venmo, Cash App, PayPal, перевод;
   - имя клиента, его телефон и почта, адрес объекта, название сметы, «действует до» (D2 §2: всё это сейчас живое);
   - `render_version` — версия вёрстки PDF; `taken_at` — время сервера; `source`: `send` / `backfill` (§7).
3. **Фото.** Сервер проверяет каждую ссылку на фото в версии: файл этой же компании и этого же клиента (иначе отказ отправки — подмена чужого фото, security-check §6 п.9); не удалён; `sha256` — тот, что заявлен. Фото, ещё не загруженное с телефона, остаётся в версии с заявленным `sha256`. На `/p/` и в PDF с сервера на его месте — «Фото скоро появится». Когда файл загрузится, сервер сам пересчитывает его `sha256`. Не совпало — фото не показывается никогда («Photo unavailable»), подпись клиента закрыта, подрядчику — карточка «Фото в смете № … отличается от отправленного — отправьте новую версию». **Подпись клиента (В5, решение основателя 15.11):** сервер принимает подпись по ссылке `/p/` (функция `portal_accept`; `estimate_client_accept` в `main` нет — имя в §4.3 и §5 условное, [не проверено]), только когда у каждого фото версии `sha256` пересчитан и совпал, а страница отдала клиенту всё содержимое; иначе отказ с кодом «ждём фото». На `/p/` кнопка «Подписать» неактивна и под ней — «Загружаем фото ({N} из {M}) — подпись откроется, когда всё будет готово»; страница сама перепроверяет состояние (опрос, пока открыта), клиент ничего не перезагружает. Подрядчику на смете — «Клиент ждёт ваши фото: N» (пункт «Требует внимания», пока фото не загрузятся). На месте (§4.4) клиент видит фото с самого телефона, поэтому подпись открыта сразу. **До отправки подрядчик видит два разных случая** (К26, решение руководителя 15.11): (а) «Фото ещё на телефоне: N. Клиент увидит их, когда они загрузятся» — «Подождать» / «Отправить» (46 §8.2), такие фото входят в документ; (б) «Не войдут в документ: N — не хватает места в облаке» — такие фото в версию не попадают, отправка идёт без них; чтобы они вошли — освободить место и отправить новую версию. Тест — e2e 401.
4. **Подпись компании** (если подтверждена, §4.3) — строка `estimate_approvals` с `party = 'contractor'`, `version_id = sent_version_id`, `document_hash = content_hash`, новым каналом `'send'`.

### 4.2. Один отпечаток

- `content_hash = sha256` от канонического JSON `{"v":1, "version_id", "calc_inputs", "issuer_snapshot"}`. Считает только сервер (`jsonb::text` в Postgres детерминирован) [вывод]. Пишется в версию вместе со снимком.
- Обе подписи — клиента и компании — пишут в `document_hash` этот же `content_hash`. Так подпись компании при отправке и подпись клиента позже стоят на одном отпечатке. Подпись компании, поставленная на другую версию, договор не исполняет: `execute` сверяет `version_id = sent_version_id` (map-keeper (б) п.5).
- Старые подписи (до миграции) оставляют свой отпечаток (`sha256(calc_inputs ‖ version_id)`). Признак старого — у версии нет `content_hash`. Функция проверки знает обе формулы.
- В PDF и на `/p/`, в «Журнале подписи», — «Контрольная сумма документа: первые 16 знаков» (45 §7 п.5). PDF, созданный на телефоне **до** ответа сервера (без сети), печатает вместо неё «Ждёт отправки» (значок и слово, правило 2).
- Для счёта и квитанции — свой `content_hash` от `{"v":1, id, суммы, blocks, issuer_snapshot}`. Его пишет тот же триггер, что и снимок (§4.6).

### 4.4. Подпись на месте (мастер или офис на объекте)

- Клиент подписывает на телефоне сотрудника. **Подпись компании ставится до того, как клиенту показывают экран подписи:** экран показывает смету с уже стоящей подписью держателя телефона («Подписано: Alex Kim, Technician, for Acme»). Нет права или подписи — экран, как сейчас: компания подписывает после клиента.
- Если смета уже отправлена офисом с подписью компании, экран показывает ту подпись, второй не нужно.
- **Без сети на месте.** Клиент подписывает сразу (подпись на месте — главный случай, мастер на объекте). Подпись компании на экране показана как «Будет подписано: Alex Kim — при отправке на сервер», не как поставленная; копия PDF, которую клиент получает до ответа сервера, несёт пустое место подписи компании с той же надписью. Сервер, когда операция дошла: право есть — подпись компании, затем подпись клиента, `approved`; права нет (снято, уволен, подпись заменена) — подпись клиента записывается, смета `awaiting_countersign`, подрядчику — карточка «Клиент подписал, подпись компании не поставлена — подпишите». Тест T223, e2e 401.
- **Имя держателя телефона** (`device_user`) копируется текстом в строку подписи клиента (`device_user_name`, 45 §7 п.4): после удаления аккаунта договор не показывает «Deleted user». Тест T221.
- Сервер: одна операция `estimate.approve` (канал `on_site`) несёт `memberSignatureId` держателя. Сервер в одной транзакции: отправляет черновик (если вправе: офис, директор, продажи — из `draft`; мастер — только из `sent`, `canSignDraftOnSite`), подписывает за компанию, записывает подпись клиента и исполняет договор. Сейчас `sign_estimate_on_site` всегда ставит `awaiting_countersign` (`rights_and_limits.sql:279,333`), а приложение ждёт `approved` (`estimateStatus.ts:6,15`) — это расхождение снимается (map-keeper (б) п.2).

### 4.5. Неизменность

- Версия: замок `tg_estimate_version_lock` уже запрещает любую правку запертой версии. Новые колонки (`issuer_snapshot`, `content_hash`) пишутся **только** до запирания, внутри серверной функции отправки.
- Перевести смету в `sent`, сменить `sent_version_id` или выставить `locked_at` может только функция отправки (security-check §6 п.6). Отправленная версия обязана быть версией **этой** сметы. Тесты T224, T223.
- Счёт: в защищённые поля `tg_invoice_guard` вносятся `issuer_snapshot`, `content_hash`, `blocks` (46 Р1), `title`, `due_date` (45 §7 п.3; решение автора — «под защиту», технический вопрос руководителю; срок оплаты меняется только новым счётом).
- Платёж: `issuer_snapshot`, `balance_after_cents`, `content_hash` — неизменны после `succeeded`.
- Удалённое подрядчиком фото, вошедшее в отправленный документ, выдаётся на `/p/`, пока жив документ (46 §5.4). Срок хранения — общая таблица спеки 50 (К15, К19).

### 4.6. Счёт и квитанция

- **Счёт.** Функции отправки нет: телефон вставляет строку сразу `sent` (`ops.ts:933–938`) [код]. Значит снимок пишет **триггер базы при вставке**: `issuer_snapshot := app.issuer_snapshot(company_id, язык клиента)`, значение от телефона игнорируется. Туда же — «сумма договора» и строки «минус счёт №…» на момент выпуска (`statement`: D2 §3, сейчас считается от текущей суммы работы), `blocks` (фото, 46 Р1) и `content_hash`. Старые сборки вставляют без этих полей — триггер заполняет их всё равно (правило 16 соблюдено).
- **Квитанция.** При переходе платежа в `succeeded` (там же, где сейчас ставится `receipt_number`, `core.sql:1102`) триггер пишет `issuer_snapshot`, `balance_after_cents` (остаток счёта на этот момент, 45 §7 п.2) и `content_hash`. Квитанция печатает **принятую** сумму (`amount_cents`), а возврат — отдельной строкой: сейчас печатается нетто после возврата (D2 §4) [код].
- Остаток считается в целых центах. На телефоне — только через `@octo/estimating-engine` (правило 8); на сервере — та же формула, паритет движок ↔ база проверяется тестом (§10).
- Реквизиты оплаты в счёте — из снимка. Банковские реквизиты на `/p/` скрыты до «Показать реквизиты» (46 §11а, условие 1).

### 4.7. Когда ссылка уходит клиенту; без сети (правило 6)

Сейчас ссылку создаёт телефон (`EstimateCard.tsx:432`), операция отправки встаёт в очередь (`:433`), и сразу открываются «Сообщения» [код]. Если сервер потом откажет, ссылка уже у клиента. С подписью компании так нельзя: клиент получил бы «подписанную» смету, которой на сервере нет (проверка аудита №2, Б1). Поэтому:

**(а) С сетью — ссылка только после ответа сервера.**
1. «Отправить» → приложение зовёт `send_estimate_signed` и ждёт ответа (индикатор на кнопке, до 15 с).
2. Ответ `sent` или `sent_unsigned` несёт **токен от сервера** → открываются «Сообщения» / почта / «Копировать» с этой ссылкой. У `sent_unsigned` перед этим — строка «Отправится без вашей подписи: {причина}» (нет права, нет должности, подпись заменена) и кнопки «Отправить» / «Подписать сначала». Клиент видит смету без подписи компании и прежнюю строку «Компания подпишет после вас» (ответ на В3, §12).
3. Отказ (версия изменилась, чужое фото, «только чтение», нет права отправлять) → «Сообщения» не открываются, ссылки нет, понятная строка «что сделать» (правило голоса: без «не удалось»).
4. Ответа нет 15 с (плохая сеть) → то же, что без сети (б).

**(б) Без сети — «Отправить, когда будет сеть».**
1. Кнопка «Отправить» без сети называется «Отправить, когда будет сеть». Нажатие ставит **одну** операцию `estimate.send` в очередь: `versionId` (что человек видел), `memberSignatureId` (что подтвердил), `deviceSentAt`. Токена у клиента нет: «Сообщения» не открываются.
2. На телефоне смета «Ждёт сети — отправится сама» (значок и слово), строка подписи — «Будет подписано вами при отправке». PDF, созданный в это время, — **без подписи компании**, на её месте «Подпись компании — после отправки», без контрольной суммы.
3. «Отменить» (правило 5) — 5 секунд и дальше, пока операция в очереди: снимает её, смета остаётся черновиком.
4. Сеть появилась, сервер принял → уведомление на телефоне «Смета № … готова — отправьте ссылку клиенту» и на смете кнопка «Отправить ссылку» (одно нажатие открывает «Сообщения» с токеном сервера). Без этого нажатия клиент ничего не получает: открыть «Сообщения» за человека приложение не может [вывод].
5. Сервер отказал → карточка и пункт «Требует внимания» по спеке 23 («Смета изменилась, пока вы были без сети — проверьте и отправьте снова»); ссылки у клиента нет, токена нет.

Так соблюдается и правило 6 (действие не теряется), и карта пути: «каждый стык работает офлайн, если в нём не участвует клиент» (`15-story-map.md` §4, строка «S7, S8, S12 — только при сети»).

**(в) Судьба токена.** Токен ссылки для новой сборки выдаёт сервер в ответе `send_estimate_signed`; при отказе токена нет. Старые сборки по-прежнему создают токен на телефоне и шлют SMS сразу; при отказе сервера их токен не регистрируется, и клиент по ссылке видит «Ссылка недействительна — свяжитесь с подрядчиком» (`/p/` отдаёт только `not_found`, без данных сметы). Тест T222.

**(г) Сервер, когда операция дошла:**
- `versionId` не совпадает с `current_version_id` (коллега поправил смету) — **отказ**, ничего не отправлено (security-check §6 п.2);
- право снято, человек уволен или подпись заменена — ответ `sent_unsigned`. С сетью человек видит это до открытия «Сообщений» (а). Без сети смета **не** отправляется сама без подписи: ставится «Готова к отправке без вашей подписи — отправить?» и ждёт решения человека [решение автора: подпись была частью того, что он подтвердил];
- всё совпало — снимок, отпечаток, подпись, `sent_at = now()` сервера.

**(д) Момент отправки — время сервера.** Время нажатия на телефоне — `device_sent_at`, в журнале подписи: «Нажато 10:02 (без сети), принято 10:47».

**(е) Шапка.** Снимок собирает сервер из своих данных на момент выполнения. Если владелец, пока телефон был без сети, поменял логотип — в документ уйдёт новый. Это осознанный риск [вывод]: подделать шапку с телефона опаснее.

**(ж) Совместимость.** Старая операция в очереди (записана старой сборкой, без `versionId` и подписи) выполняется по-старому. Сервер ещё без новой функции (`PGRST202`) — новая сборка падает на старую `send_estimate`, как это сделано для `accept_on_site` (`ops.ts:880`) [код].

**(з) Связь с #1108 (В1-6, «Сообщение ушло?»).** В `main` этого экрана нет. Если его сделают, порядок такой: ответ сервера → «Сообщения» → вопрос «Сообщение ушло?». Ответ «Нет» уже ничего не отпирает (версия заперта и подписана на сервере); он только ставит отметку «Ссылку клиенту не отправили» и предлагает «Отправить ссылку» ещё раз. Спеку В1-6 нужно поправить так (§11). PR 49-3 от #1108 не зависит.

### 4.8. Неоплаченная компания (спека 44 §7.2, S93б)

- Новые отправки и ссылки закрыты (44). Подпись клиента по старой ссылке в окне 14 дней записывается.
- Если компания подписала при отправке, а сейчас не записываема: смета остаётся `awaiting_countersign` с признаком «исполнение отложено» (`estimates.execution_deferred_at`); работа, счёт на депозит, `won` и `active` **не создаются**. Подрядчик видит «Подписано обеими сторонами — работа и счёт появятся после оплаты тарифа», без кнопки «Подписать за компанию».
- При возврате в записываемую (`company_writable`) сервер проходит отложенные сметы и вызывает `app.execute_estimate` **ровно один раз** на смету (повторная оплата и повторный вход — без дублей; опора — одна работа на смету и проверка депозита, map-keeper (б) п.10). В журнале — «создано после оплаты тарифа».
- **Ровно один раз** держится и на побочных действиях: `execute_estimate` сейчас при каждом вызове пишет уведомление `estimate.approved` и письмо (`20261105350000_email_outbox.sql`) [код]. Новый порядок: смета берётся `for update`, и если она уже `approved` — выход без уведомления и письма; уведомление и письмо пишутся только в той ветке, которая перевела статус. Тест T225: два прохода — одна работа, один счёт, одно уведомление, одно письмо.
- **Кто запускает проход:** функция спеки 44, которая возвращает компанию в записываемую (очищает `read_only_since`: вебхук оплаты Stripe, ручная смена тарифа в панели, StoreKit), в той же транзакции зовёт `app.run_deferred_executions(company_id)`. Страховка — ночной проход (спека 21) по компаниям, которые записываемы и у которых есть `execution_deferred_at`. Спеке 44 — строка об этом (§11).
- **Сбросить в черновик нельзя:** `reopen_estimate` отказывает, если на отправленной версии есть подпись компании (§4.3).
- Почему не `approved`: правило «`approved` ⇒ есть работа и счёт» держат код и тесты (`estimateSign.ts:5`, `countersign.sql:315–360`); `approved` без работы его сломал бы (map-keeper (а) п.4).

## 6. Права и подмена (`security-check`)

Что уже держит [код, по отчёту security-check]: подпись только своя и только действующая (`countersign_estimate`); право проверяется в момент выполнения (`app.can_sign_contracts`: активен, не удалён, право есть, не субподрядчик); удаление аккаунта отзывает подписи; подписи только добавляются; замок версии; повтор отправки и подписи ничего не удваивает; байты загруженного файла неизменны; суммы отправленного счёта заморожены.

Требования спеки:
1. **Снимок, отпечаток, имя подписавшего собирает только сервер** внутри функции отправки. От телефона сервер берёт только id сметы, ожидаемую версию, id своей подписи и время нажатия.
2. **Ожидаемая версия** в операции отправки; не совпала — отказ, никогда не «тихо другую».
3. Подпись отправителя — в той же транзакции, что и запирание, строго `auth.uid()`, право и `revoked_at is null` на момент выполнения; в одной функции держать **обе** проверки (право и «не субподрядчик»), не полагаться на порядок вызовов.
4. Имя и должность на договоре — только из профиля на сервере (§4.3).
5. `status = 'sent'`, `sent_version_id` и `locked_at` меняет только функция отправки; отправленная версия принадлежит этой смете.
6. **`/p/` показывает меньше, чем хранит снимок:** банковские реквизиты — только на счёте, по живой ссылке и после «Показать реквизиты»; не показываются почта и телефон сотрудника, `signer_user_id`, хеши файлов, ключи хранилища, внутренние id; номер HIS — только если компания печатает его на документах; логотип — из снимка; фото — только вошедшие в документ, по подписанной короткой ссылке.
7. Фото — только своей компании и своего клиента (проверка внутри функции отправки); `sha256` — пересчитанный сервером.
8. Новые функции — `revoke all … from public, anon`, затем `grant execute … to authenticated` (правило 18, T52).

Находки security-check о текущем коде переданы руководителю лично (закрытые задачи #1599–#1601) и в этот документ не входят.

## 10. Тесты (красные до правки)

Номера выдал руководитель 15.11: база T220–T229 (несколько проверок под одним номером), e2e 400 и 401.

**База (`core_rls.sql`):**
- **T220** снимок и отпечаток: отправка пишет `issuer_snapshot` и `content_hash` до `locked_at`; после — изменить их нельзя (42501); `content_hash` пересчитывается из сохранённых полей и совпадает; подписи клиента и компании несут его же.
- **T221** подпись компании: `send_estimate_signed` пишет строку на `sent_version_id`, `channel = send`, `option_id = null`; отозванная или чужая подпись, снятое право — `sent_unsigned`, строки нет; имя и должность — из профиля, даже если сохранённая подпись несёт другие; у отправителя пустая `memberships.title` — `sent_unsigned`, причина `no_title`; картинка, имя, должность скопированы в строку — после `delete_account` сотрудника и отзыва подписи договор не меняется, `device_user_name` на месте — прежний; повторная отправка `sent`/`viewed` — вторая строка не появляется (индекс).
- **T222** версия и токен: `versionId` не текущий — отказ, версия не заперта, статус не меняется, токена нет; токен старой сборки при отказе сервера не регистрируется, `/p/` по нему — `not_found` без данных.
- **T223** исполнение: подпись клиента при подписи компании → `approved`, работа и сумма договора — по варианту и допам клиента, один счёт на депозит; без подписи компании → `awaiting_countersign`, `countersign_estimate` как раньше (T18, T23 не ломаются); `countersign_estimate` на `sent` до клиента; правка → новая версия, подпись компании на версии 1 не исполняет версию 2; на месте без права у держателя — подпись клиента записана, `awaiting_countersign`.
- **T224** отправку меняет только функция: `status = 'sent'`, `sent_version_id`, `locked_at` напрямую — отказ; версия другой сметы в `sent_version_id` — отказ.
- **T225** «только чтение» и «ровно один раз»: подпись клиента записана, работы и счёта нет, `execution_deferred_at`; `reopen_estimate` такой сметы — отказ (и любой сметы с подписью компании на отправленной версии); `run_deferred_executions` дважды — одна работа, один счёт, одно уведомление `estimate.approved`, одно письмо.
- **T226** счёт: снимок и `statement` от триггера при вставке, значение телефона игнорируется; `title`, `due_date`, `blocks`, снимок после отправки — отказ; вставка старой сборкой без полей — снимок есть.
- **T227** платёж и перенос: `balance_after_cents` на момент `succeeded`; квитанция после частичного возврата — принятая сумма; backfill (В4 = (а)) заполняет только пустое и не трогает заполненное.
- **T228** фото и `/p/`: фото чужой компании или чужого клиента — отказ отправки; подпись клиента по `/p/` при фото без пересчитанного `sha256` — отказ «ждём фото», при всех совпавших — принята (В5); `sha256` не совпал — подпись закрыта; `sha256` не совпал — фото не выдаётся; `/p/` не отдаёт банковские реквизиты, почту/телефон сотрудника, хеши, ключи; логотип — из снимка после смены логотипа компании.
- **T229** старые: вызов `send_estimate(id, token)` — снимок есть, подписи компании нет; смета, отправленная до миграции и подписанная после, — отпечаток по старой формуле, `awaiting_countersign`; права новых функций (T52), `anon` не исполняет.

**Движок:** остаток после платежа и «сумма договора минус счета» — функция движка; паритет с базой на тех же примерах (`18-money-test-cases.md` — новый пример).

**Модульные (приложение):** `estimateSign` (`clientSigned` → `approved` при подписи компании; `canCountersign`; признак «Подписана вами»); отправка с сетью ждёт ответа и открывает «Сообщения» только при `sent`/`sent_unsigned` с токеном сервера, при отказе — не открывает; без сети — одна запись очереди, «Отменить» снимает её, PDF без подписи компании; после принятия — уведомление «готова — отправьте ссылку»; старая запись — по-старому; `PGRST202` → старая функция; `estimatePdf` / `docPdf` из снимка не меняются после смены названия, логотипа, лицензий, языка клиента; `estimateStatus` на месте; `storyMap` паритет; `pushPrefs` («открыл» по умолчанию).
