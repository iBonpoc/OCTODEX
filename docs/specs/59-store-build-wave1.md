## 2. Признак «сборка магазина» (п. 49)

Сейчас `EXPO_PUBLIC_APP_ENV` задан в `apps/mobile/eas.json` и в `src/` не читается.

**Решение.** Два файла.

1. `src/config/appEnv.ts` — **чистая функция без нативных импортов**: `resolveAppEnv({ channel, envVar }): "store" | "preview" | "dev"`. Правила: `channel` проверяется через `if (channel)` (пустая строка и `null` — «не задан»); `production` → `store`, `preview` → `preview`; затем `envVar` с тем же отображением (в `eas.json` значения `production` и `preview`, не `store`); иначе `dev`. Любая неопределённость даёт «не магазин». Также `isStoreBuild()` и подмена для тестов `setAppEnvForTest`.
2. `src/config/appEnvNative.ts` — тонкий слой: читает `Updates.channel` через `require` в `try/catch` (по образцу `pushNative.ts`) и `process.env.EXPO_PUBLIC_APP_ENV` **литералом** (Metro подставляет только литерал, не деструктуризацию и не динамический доступ).

Почему так: `expo-updates` нельзя импортировать в vitest (разбор падает), поэтому тестируется только чистая функция. Канал берётся из нативной части (`Updates.channel`, константа, доступна синхронно; у встроенной сборки и после обновления по воздуху одинаковый), а переменная `EXPO_PUBLIC_*` вшивается в JS при сборке и при `eas update` не попадает без `--environment`. Поэтому канал первичен, переменная — запас.

Веб, Expo Go и dev client дают пустой канал или `null`, переменной нет — итог `dev`, как сегодня. Все e2e идут на веб-сборке без переменной, то есть в `dev`; ветки «магазин» в них не пройдут, нужна отдельная веб-сборка с `EXPO_PUBLIC_APP_ENV=production` и своя e2e-спека магазина.

**Сторож:** `process.env.EXPO_PUBLIC_APP_ENV` и `Updates.channel` читаются только в этих двух файлах; существующие `version.tsx` и `boot.tsx` (читают `Updates` по другим поводам) разрешены поимённо. Профили: `testflight` и `preview` → `preview`; `production` → `store`.

## 5. Риски

1. **Признак и обновления по воздуху** — закрыт разделом 2 (канал первичен). Остаётся проверить на настоящей сборке, что канал не пуст (задача 3 и первая сборка магазина).
2. **`NSLocationAlways*` и Apple.** Библиотека собирает вызов запроса постоянной геопозиции так, что статический сканер Apple его не видит; при удалении ключей отказ ITMS-90683 маловероятен, но по исходникам не доказать — проверка загрузкой в TestFlight, откат — вернуть тексты.
3. **Срок хранения.** Вся работа по данным — серия 50-x с её таблицей сроков §6 и тестами T230–T242, зарезервированными спекой; «следующий свободный» номер теста в `core_rls.sql` брать с руководителем. Тесты, которых в задаче нужно не забыть: стирающие функции вызывает только `service_role` (правило 18, образец T52); миграция на чистой и текущей базе; старая версия приложения получает понятный отказ, не зависает в `stuck`; «удаление проходит всегда», даже если Storage недоступен; объекты Storage удаляются только через Storage API.
4. **Старые сборки** (правило 16): ничего не удалять одной миграцией; `runtimeVersion` не менять без новой нативной сборки.
5. **Заморозка на время ревью Apple** — решение руководителя, не код: сейчас `release.yml` катит миграции на каждое влитие и публикует веб, остановить их без правки workflow нельзя.

## 7. Политика и условия: когда менять версию (решение аудита 17.11.2026)

1. Сейчас политика — «Draft», приложение не выпущено. **Правка 6а — правка черновика: без бампа `LEGAL_VERSIONS`, без миграции, без повторного согласия.** Вливать можно.
2. **Один бамп до 1.0** — когда текст станет окончательным после юриста: версия 1.0, все учётные записи принимают при первом входе. Это PR 50-6 + финальный текст, «Draft» снимается тем же PR.
3. **Правило после выпуска.** Существенное изменение — бамп, уведомление и согласие при следующем входе: меняется, что собираем, зачем, кому передаём, сколько храним или права человека. Опечатки, адреса, уточнения без смены смысла и удобный путь (удаление в приложении) — без бампа, с датой «обновлено».
4. **Получатели данных в 6а** называются по факту из кода на сегодня. ИИ в 1.0 нет, в списке его нет.
5. Всё это входит в чек-лист юристу (#1790, #1940).
