# Спека 57. Сборка магазина: план волны 1 (эпик #1940)

Статус: **план на проверку двумя независимыми проверяющими**, кода нет. Основа — `docs/16-appstore-readiness.md` (пункты там названы «п. N»). Класс задач: К1 там, где данные, деньги, права; остальное К2/К3. Этап 6 (контейнеры #1882, эпик #1940).

## 1. Зачем и границы

Сборка для магазина должна отличаться от сборки для TestFlight: без служебных экранов, цен без покупок Apple, слов о незавершённости, со своим каналом обновлений. Для этого нужен **один признак «сборка магазина»**, на который опираются все остальные правки (п. 49).

Границы этого плана:

- Основатель ещё не ответил на решения (а)–(м) из раздела 3 `docs/16-appstore-readiness.md`. Работы делятся на **бесспорные** (нужны при любом ответе) и **зависящие от решений**. Зависящие не начинаются до ответа.
- Подписку (а), цену Gutters (б), витрину, строку версии (л), Stripe (и), демо-режим (к) не трогаем до ответа.
- Миграции — по правилам 16 и 18; каждый PR отдельный, без стопок, от свежего `main`.

## 2. Признак «сборка магазина» (п. 49)

Сейчас `EXPO_PUBLIC_APP_ENV` задан в `apps/mobile/eas.json` (профили `preview`, `production`, `testflight`), но в `src/` не читается.

**Предложение.** Один файл `src/config/appEnv.ts`, единственное место чтения:

- `appEnv(): "store" | "preview" | "dev"`.
- Порядок источников: канал обновлений времени выполнения (`Updates.channel`: `production` → store, `preview` → preview), затем `process.env.EXPO_PUBLIC_APP_ENV`, иначе `dev` (веб, локальный запуск, e2e).
- `isStoreBuild()` истинно только для `store`. Любая неопределённость даёт «не магазин»: тесты и разработка идут как раньше.
- Тестам даётся подмена (`setAppEnvForTest`), по образцу `src/config/version.ts`.

**Почему канал, а не только переменная.** Переменная `EXPO_PUBLIC_*` вшивается в JS при сборке. Обновление по воздуху собирается заново на сервере выпуска: если его опубликовать без переменной, сборка магазина «потеряет» признак и покажет служебные экраны. Канал берётся из нативной части сборки и не зависит от того, чем собран JS. Переменная остаётся запасом для первого запуска.

**Вопросы проверяющим:** (1) верно ли, что `Updates.channel` доступен синхронно при старте и не `null` в сборке магазина; (2) нужен ли запрет публикации в канал `production` из `release.yml` без явного ручного запуска (п. 53); (3) не ломает ли порядок источников веб-сборку и e2e.

## 5. Риски, на которые просим посмотреть

1. **Признак и обновления по воздуху.** См. раздел 2. Если признак окажется неверным, сборка магазина покажет служебное, а сборка TestFlight скроет нужное основателю.
2. **Сторож итогового конфига.** `app.json` не равен итоговому Info.plist (плагины Expo дописывают ключи). Сторож должен читать результат `expo prebuild` без установки новых зависимостей; нужно решить, где он живёт: локальный прогон `npx expo prebuild --no-install` или проверка `.ipa` в `eas-build.yml`. Правило 17: ничего нового не ставить.
3. **Срок хранения 30 дней (п. 7).** Затрагивает данные и деньги: что именно удаляется, а что обязан хранить закон (счета). Нужны два независимых ревью К1 и тесты базы на чистой и текущей базе.
4. **Совместимость старых сборок** (правило 16): ничего не удалять одной миграцией.
5. **Канал `production` и миграции.** Каждое влитие в `main` катит миграции в единственную боевую базу; на время ревью Apple нужна заморозка (п. 47, 55) — правило для руководителя, не код.

## 6. Что должны сделать проверяющие

Двое независимых, каждый читает этот план и `docs/16-appstore-readiness.md`, смотрит код по указанным файлам и отвечает списком: **блокирует / желательно / мелочь**. Особенно: раздел 2 (признак), задачи 2, 3, 7, 8 и порядок раздела 4. Выводов автора плана им не передаётся.

После двух ответов автор сводит замечания, правит план и отправляет итог руководителю на решение. Код начинается только после слова руководителя и, для задач «Р», после ответа основателя.
