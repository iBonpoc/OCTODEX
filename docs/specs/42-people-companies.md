### 2.3 Решения по пунктам

| Пункт | Варианты | Решение и почему |
|---|---|---|
| Где хранить активную компанию | а) только телефон; б) только сервер; в) телефон, затем сервер | **в)**. Телефон работает без сети (правило 6), сервер помнит компанию на новом устройстве. Порядок фиксирован, `memberships[0]` убираем — сейчас компания выбирается случайно |
| Запись `last_active_company_id` | а) как сейчас (любой id); б) триггер: только компания, где у человека `active`-членство, или `null` | **б)**. Пока колонку никто не читает, вреда нет. Как только мы начнём её читать, чужой id станет ловушкой для логики. Триггер ничего не переименовывает и не удаляет (правило 16) |
| Неотправленное при смене компании | а) запретить смену, пока есть неотправленное; б) пустить и держать в очереди; в) пустить и отправлять в фоне все компании | **б) в волне 1, в) — волной 1b.** Сейчас очередь уже хранит владельца, и ничего не теряется. Но офис компании A не видит правки, пока человек не вернётся в A. Поэтому: (1) перед сменой — попытка отправить (до 10 с при сети); (2) осталось неотправленное — шторка «В «A» N изменений не отправлены. Отправятся, когда вы вернётесь в «A»» с кнопками «Перейти» / «Остаться»; (3) в переключателе у компании — «не отправлено N». Вариант в) (`flush` по всем владельцам этого же человека, `applyOp(op, owner.companyId, …)`) — отдельной волной: отказы сервера для неактивной компании нужно показывать с её именем |
| Пуш из другой компании | а) открывать как есть; б) `company` в `data` + переключение | **б)**. Старые версии лишнее поле не читают (совместимо). Сейчас нажатие открывает маршрут в активной компании, где этой записи нет |
| Субподрядчик: как дать доступ | а) расширить `visits_select` / `customers_select` и др. на роль `subcontractor`; б) узкие функции `security definer`: `sub_visits()`, `respond_visit()`, `sub_visit_step()` | **б)**. Таблицы клиентов, работ, смет и денег для него остаются закрытыми целиком. Узкий набор полей задаёт одна функция, её проще проверить тестом. С вариантом а) каждая новая колонка таблицы будет открываться субподрядчику сама |
| Субподрядчик: что видит до «принять» | а) всё; б) дату, время, длительность, город + ZIP, «что сделать»; адрес, код ворот и телефон — после «принять» | **б)** [вывод]. Чтобы решить, хватает места и времени. Адрес клиента не уходит к тому, кто отказался. Мелкое решение — основателю «было/стало» |
| Субподрядчик: сколько видит после работы | а) всегда; б) полностью — пока выезд не закрыт и 14 дней после; потом только «дата · что сделано · мои фото» | **б)**. Своя история работ ему нужна (чтобы выставить счёт генподрядчику вне приложения), а контакты чужого клиента — нет |
| Документы субподрядчика | а) нет; б) `member_documents`: файл, вид, дата окончания, заметка; без проверок | **б)**, по README §4.3 п.5. Видят owner/admin/office. Сам субподрядчик видит **список** того, что компания о нём хранит (прозрачность), но не правит. Напоминаний и блокировок по дате нет |
| Выход: новый статус или `deleted` | а) `left`; б) `deleted` | **б)**. Для компании результат тот же. Повторное приглашение уже работает. Нового статуса в §5 и в `statusMap` нет, а кто ушёл сам — видно в `audit_log` (`actor = сам человек`) |
| Пауза: как закрыть доступ | а) Supabase `ban_duration`; б) `memberships.status`; в) `users.paused_at` + выход на всех устройствах; права (`is_member`) не трогаем | **в)**. а) — человек не сможет сам войти и включиться, а поведение бана для уже выданных сессий [не проверено]. б) — пауза смешается с отключением админом: при включении нельзя будет понять, кто что выключил. **Пауза — не граница безопасности.** Человек сам решил отдохнуть. Если он войдёт и прочтёт данные своих компаний, он имеет на это право. Поэтому трогать `is_member` / `has_role` (их зовёт каждая политика) не нужно. Меняются только «кому слать пуши», «кого можно назначить» и «кому выдать лид» |
| Пауза последнего владельца | а) запретить; б) разрешить с предупреждением | **б)**. Главный случай — одиночка в межсезонье. Компания работает дальше: страница `/p/` и приём заявок не останавливаются. Предупреждение: «Пока вы на паузе, владельцем компании «A» никто не управляет: подписка, права, передача компании» |
| Удаление | — | без изменений механики S22. Добавляется только список компаний на экране удаления и «Удалить» на экране паузы. Apple требует удаления, а пауза — дополнительная возможность и удаление не заменяет (цитата §2.2) |
| Вторая своя компания | а) без предела; б) предел 5 на человека | **б)**. Защита от мусора. Платность — направление Е, здесь не решается |

### 2.4 Оспорено: «чужая компания видит только «занят»» (README §4.3 п.7)

[вывод] Это **первый канал данных между компаниями**: компания A узнаёт что-то о расписании человека в компании B. Сейчас сервер нигде не пересекает границу `company_id`. README §4.2 сам отмечает: такого не найдено ни у кого. Это новая функция с правовым смыслом (знание компании о чужой занятости близко к «контролю расписания» из IRS 15-A — README §4.4). А основатель велел не брать такие решения на себя.
**Предложение:** в этапе 4 — только свой вид (S33): человек видит свои выезды во всех компаниях. Это чтение по правам каждой компании, без пересечения границы. «Занят» для чужих глаз — не делать. Если основатель всё же захочет — отдельной К1-спекой, с согласием самого человека. Вопрос — §10 В1.

### 2.5 Оспорено: нужна ли пауза вообще

[вывод] Для одной компании паузу закрывают выход (S30) и отключение админом. Пауза нужна человеку, у которого есть учётная запись, но он сейчас нигде не работает: межсезонье, отпуск. Слово основателя — «всё должно быть». Поэтому делаем, но в самом узком виде: без автоудаления, без срока, без отдельного состояния данных.

## 4. Статусы и переходы

### 4.1 Membership (сверка с §5)
`active → deleted`: сам (`leave_company`; удаление аккаунта), Д (закрытие компании последним владельцем). Запреты: последний активный owner не выходит (`42501 'transfer the company first'`), а `disabled` не выходит сам — ему и так закрыт доступ, это не нужно. `deleted → active` — только новым приглашением.

### 4.2 User
`работает → на паузе` (сам). `на паузе → работает` (сам, после входа). `на паузе → удалён` (S22, свежий вход как сейчас). Автопереходов нет.

### 4.3 VisitAssignee.sub_response
`offered → accepted | declined` (субподрядчик, пока выезд `scheduled` / `en_route`). `accepted → declined` (субподрядчик, до `on_site`; офису — карточка). Снять предложение может офис (`assign_visit` без него, как сейчас — `deleted_at`). После `on_site` ответ не меняется.

## 5. Как приходит / как уходит

- **Вход:** почта (код или пароль) — как сейчас, [код] `cloud/auth.tsx:228,236`. Без компании: демо и две кнопки «Создать компанию» / «У меня есть приглашение». Вторая кнопка открывает «Мои приглашения», а если их нет — поле «Вставьте ссылку приглашения».
- **Приглашение:** ссылка (как сейчас) + `my_invitations()`: возвращает ожидающие приглашения, где `email` = подтверждённая почта входа из `auth.users`, а не `public.users.email` (так же, как `accept_invitation`, [код] `team_invitations.sql:190-197`). Поля: имя компании, роль, кто пригласил, срок. `accept_invitation_for_me(id)` повторяет все проверки `accept_invitation`, кроме токена. Почта уже подтверждена, и приглашение адресовано ей. [вывод] Это не слабее ссылки: ссылку может переслать кто угодно, а почту всё равно сверяют. Письмо с приглашением — после почты П1b (`docs/specs/07-email.md`), здесь не решается.
- **Пуш:** `data = {route, company}`. Заголовок при ≥2 активных компаниях у получателя — «<компания>: <текст>».
- **Выход, пауза, удаление:** экран «Настройки → Мои настройки → Учётная запись» (§7.3).
- **Уходит клиенту:** ничего нового. Пуши субподрядчику — на языке приложения (это не клиент, правило 7).

### 7.1 Шапка и переключатель (S26, S32)

### 7.2 «Вас добавили в «B»» (S28)
Окно после принятия, если у человека уже была компания: «Вас добавили в «B» как <роль>». Кнопки: «Перейти» (акцент) / «Остаться в «A»».

### 7.3 «Учётная запись» (S30, S31, S22)
Порядок: почта входа → «Мои компании» (карточки `ListCard density="compact"`: имя, роль; «⋯» → «Выйти из компании») → «Поставить на паузу» → «Удалить учётную запись» (`bad`).
- «Выйти из компании «A»» — подтверждение (правило 5): «Вы перестанете видеть данные «A». Ваши записи останутся у компании. Вернуться можно только по новому приглашению». Неотправленное в «A» — сначала «Отправить» (кнопка ждёт сети), выйти с неотправленным нельзя. [вывод] Иначе правки потеряются молча — главная жалоба в отзывах (README §3). Последний владелец — вместо кнопки строка «Сначала передайте компанию» → `transfer_ownership`.
- «Поставить на паузу» — подтверждение со списком последствий: выход на всех устройствах, нет уведомлений, нельзя назначить. Для последнего владельца — предупреждение §2.3.
- Экран после входа на паузе: «Учётная запись на паузе с <дата>» → «Включить» (акцент) / «Удалить учётную запись».

### 7.4 Субподрядчик (S29)
Своя Главная с одной вкладкой «Выезды» и «Мои настройки». Кнопки «＋», денег, лидов, клиентов, каталога, команды у него нет.
- «Предложено» сверху: карточки `ListCard` — дата и время · город, ZIP · «что сделать» · компания. Кнопки «Принять» (акцент) / «Отклонить» (с полем причины, необязательно).
- «Мои выезды»: принятые, по дате. Экран выезда — адрес (карта), код ворот, контакт на месте, «что сделать», фото, шаги «Еду / На месте / Готово», заметка. Чек-лист, если есть, — по желанию, без запрета на «Готово».
- «История»: после 14 дней — только «дата · что сделано · мои фото».
- Пустые состояния: «Пока нет предложенных выездов».

### 7.5 Офис
- «Назначить» на выезде: у субподрядчика пометка «предложить». В строке исполнителя — «предложено» (`neutral`) / «принял» (`ok`) / «отклонил» (`warn`).
- «Требует внимания»: «Субподрядчик отклонил выезд», «Выезд без исполнителя (человек ушёл из компании)».
- Карточка человека в «Команде»: «на паузе с <дата>» (`neutral`); у субподрядчика — блок «Документы» (файл, вид, «до <дата>», без цвета и без предупреждений — мы ничего не проверяем).

## 8. Права, офлайн, уведомления

### 8.1 Права (сервер — источник правды)
| Действие | Кто | Проверка |
|---|---|---|
| `set_active_company` / запись `last_active_company_id` | сам | членство `active` в этой компании |
| `leave_company(c)` | только сам (параметра «кого» нет) | членство `active`; не последний активный owner; блокировка owner-строк `for update`, как в `set_member_status` (гонка двух владельцев, [код] `team_invitations.sql:252-258`) |
| `pause_account` / `resume_account` | только сам | `account_alive()`; включение — только своё |
| `my_invitations` / `accept_invitation_for_me` | сам | подтверждённая почта входа; все проверки `accept_invitation`, кроме токена |
| `sub_visits(c)` | субподрядчик `c` | только строки `visit_assignees` с его `user_id`, `deleted_at is null`, `sub_response in (offered, accepted)`; поля до «принять» — по §2.3 |
| `respond_visit` | субподрядчик | своя строка; выезд до `on_site` |
| `sub_visit_step` | субподрядчик | `accepted`; шаги только вперёд (как у `tech`); денег, цен и подписи клиента нет |
| `member_documents` select | owner, admin, office этой компании; сам человек — свои строки (кроме `note`) | RLS |
| `member_documents` insert/update/delete | owner, admin, office | RLS + `company_id_immutable` |
| Цены, себестоимость, клиенты, сметы, счета, оплаты, лиды, каталог | субподрядчик — **никогда** | существующие политики не меняются |

Субподрядчик в двух компаниях (у одной он работник, у другой — субподрядчик) видит в каждой своё — права считаются по `company_id`, а не по человеку.

### 8.2 Офлайн (правило 6)
- Переключение работает без сети на компании, которая уже в кэше. Ключ кэша — `cloudCacheKey(company, user)` (уже так).
- Очередь: операции несут владельца. Смена компании их не трогает (§2.3).
- `respond_visit` и `sub_visit_step` — операции очереди (`Op`), как шаги выезда у мастера.
- `leave_company`, `pause_account`, `resume_account`, `accept_invitation_for_me` — **только при сети** (кнопка «Нужна сеть»). Они меняют доступ, а повтор в очереди после чужих изменений опасен.
- После выхода: кэш этой компании и её копии удаляются с телефона. Свои неотправленные операции этой компании — до выхода (§7.3).

### 8.3 Уведомления
- Субподрядчику: «предложен выезд», «выезд перенесён / отменён», «вас сняли с выезда». Ни денег, ни лидов, ни подписей (`pushPrefs.ts` сейчас — «ничего», [код] `features/pushPrefs.ts:7`).
- Офису: «Субподрядчик принял / отклонил выезд».
- На паузе — ничего. После выхода — ничего из этой компании (уже так: `push_member` проверяет `active`).
