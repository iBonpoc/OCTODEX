## 0. Итог (для аудита №2 и руководителя)

1. **Сейчас в документах клиенту фото нет нигде** [код]: ни в PDF сметы, ни в PDF счёта, ни на `/p/`. «Страницы-вложения» (`EstimateDoc.pages`, `features/docPages.ts`) — только векторные листы модуля (линии, круги, текст), растровых картинок там нет и быть не может — так задумано ради безопасности `/p/` (`docPages.ts:5–10`).
2. **Фото в документе = новый вид данных — «блоки документа»** (`DocBlock`): галерея, «до/после», фотоотчёт, оплата. В смете блоки живут **в версии документа** (`calc_inputs`), то есть входят в то, что клиент подписывает; в счёте — новое поле счёта. Файлы не копируются: блок ссылается на `files.id` (§3).
3. **Главный риск — `/p/` открыта без входа.** Фото уходят туда только через новую серверную функцию, которая проверяет ссылку `/p/` и выдаёт короткие подписанные ссылки **только на файлы, названные в блоках этого документа** (§5). До неё — блокер Ф-0 из G: в файле не должно остаться GPS, а запасной путь `shrinkPhoto` сейчас **сохраняет оригинал со всеми EXIF** (`photoShrink.ts:63–67`) [код].
4. **«Шаблон фото по направлению» (фото моих работ ко всем сметам по электрике) показывает новому клиенту дом прежнего клиента.** Поэтому фото для шаблонов — отдельная «папка работ компании», куда фото попадает только явным действием владельца, без адреса и подписи прежнего клиента (§3.5, §5.3).
5. **PDF собирается из HTML** (`expo-print` на телефоне, печать браузера на `/p/` и в вебе) [код]. Лист — Letter 612×792 pt по умолчанию `expo-print` [док]. Правил переноса для строк таблицы нет; переносы есть только у подписей (`.sigs`, `.signoff`) и у листов-вложений (`break-before: page`) [код]. Для фото задаём правила переноса по рядам (§4.3).
6. **Блок оплат** — только из настроек компании (`Company.payment`: Zelle, чек; онлайн-оплата Stripe — на `/p/`) [код]. QR — только на счёте с остатком и только на ссылку оплаты; карт не храним, сумма считается движком (§6).
7. Волны Д-1…Д-7 после Ф-0/Ф-1/Ф-2 из G (§10). Вопросы основателю — три (§10.2).

## 3. Сущности и поля

### 3.1. Варианты модели

| Вариант | Как | Плюсы | Минусы |
|---|---|---|---|
| **А. Блоки в документе** (выбор) | `EstimateDoc.blocks: DocBlock[]` в версии сметы; у счёта — `invoices.blocks jsonb` (новая колонка). Блок ссылается на `files.id` | подписанная смета = подписанные фото (снимок, #1105); порядок и вид — часть документа; сервер чистит блоки так же, как `app.doc_pages` | у счёта своя колонка; проверку надо писать дважды (телефон и база), как у `docPages` |
| Б. Связи у файла | `files.estimate_id / invoice_id / position` | просто, без JSON | порядок, обрезка, подписи — вне версии: после подписи их можно поменять; «до/после» — пара, а не файл |
| В. Таблица `document_blocks` | общая таблица для сметы и счёта | одна схема | версия сметы замораживается копированием строк — новый механизм; лишняя таблица для офлайн-очереди |

Решение — **А** [вывод]: то, что клиент подписал, не меняется, и это уже так устроено для строк и Terms (`EstimateDoc.terms`, #1304).

### 3.2. Тип (ядро, `features/docBlocks.ts`, рядом с `docPages.ts`)

```ts
type DocPhotoRef = { fileId: ID; caption?: string /* ≤ 120 */; crop?: { x: number; y: number; w: number; h: number } /* 0..1 */ };
type DocBlock =
  | { id: ID; t: "gallery"; title?: string; layout: "auto" | "g4" | "g6" | "g7" | "g8"; photos: DocPhotoRef[] }
  | { id: ID; t: "beforeAfter"; title?: string; aspect: "4:3" | "1:1" | "3:4" | "16:9"; pairs: { before: DocPhotoRef; after: DocPhotoRef; caption?: string }[] }
  | { id: ID; t: "report"; title?: string; from: string; to: string; jobId?: ID; photos: (DocPhotoRef & { stage?: FileStage; at: string })[] }
  | { id: ID; t: "payment" /* без своих данных: всё из настроек компании в момент печати */ };
```
- Только скаляры, текст через `esc()`; сервер — функция `app.doc_blocks(jsonb)` (как `app.doc_pages`): что непонятно — выбрасывается; запись сверх пределов — **отказ, не обрезка** (клиент подписывает целое, `docPages.ts:9–10`).
- Пределы [вывод, уточнить на Д-1]: блоков ≤ 20, фото в документе ≤ 200, подпись ≤ 120 символов, заголовок ≤ 80.
- `fileId` блока — только файл **той же компании**, `kind='photo'`, `client_visible=true`, не удалён. Проверяет триггер версии сметы и счёта (как `app.doc_pages_problem`).

### 3.3. Обрезка «до/после»
- Оригинал не меняется. Блок задаёт формат кадра (`aspect`), у каждого снимка — своя рамка `crop` этого формата (доли 0..1). Так оба снимка пары **одного размера** и стоят рядом; подрядчик двигает и масштабирует каждый снимок в рамке.
- Рамка по умолчанию — по центру, наибольшая [вывод]. Для печати рамка применяется на телефоне при сборке PDF (§4.4), на экране — `overflow: hidden` + сдвиг картинки.
- Чистая математика рамки (пределы, формат, щипок без скачка) — модульные тесты; жест — правило 27 (§9).

### 3.4. Фото выезда → документ
- Меню «Фото» в смете и счёте: «Снять», «Из фото клиента», «Из галереи телефона», «Из работ компании» (§3.5). «Из фото клиента» — сетка `files` этого клиента (замеры, выезды, работы), сгруппированная по выезду и стадии (`before/during/after`).
- Фотоотчёт к счёту: промежуток `from..to` по умолчанию — от первого выезда работы до сегодня; предлагаются фото работы с `taken_at` в промежутке; подрядчик снимает лишнее галочкой. В блоке фиксируется **список** фото (не правило), иначе счёт менялся бы сам после отправки.
- «Скрытые работы» и «для инспекции» — сейчас стадий таких нет (`before/during/after/other`). Вариант: подпись к фото + стадия `during`; новая стадия — расширение `check` (правило 16, шаг 1) — **вопрос В3** (§10.2).

### 3.5. Работы компании и шаблон по направлению
- **Папка работ компании**: те же `files`, новая колонка `files.portfolio boolean default false` (правило 16, шаг 1). В неё фото попадает только действием owner/admin «Добавить в работы компании» — **копией** без `customerId/visitId/jobId` и без подписи прежнего клиента (§5.3).
- **Шаблон фото по направлению**: в `companies.estimate_settings` — `photoTemplates: { serviceCategoryId, docType: "estimate" | "invoice", block: DocBlock }[]` (≤ 20). Новая смета с `serviceCategoryId` (`types.ts:663`, уже есть) получает блок шаблона **копией** при создании; его можно убрать. Смена шаблона уже созданные сметы не трогает. Меняют owner/admin.
- Чего не заводим: отдельной таблицы альбомов, тегов, ИИ-подбора фото.

## 4. Вёрстка

### 4.1. Как сейчас [код]
- Один каркас `docPage()` для сметы, счёта, квитанции (`docPdf.ts:66–119`): шапка (логотип `data:image/…` + реквизиты), тело, подвал `position: fixed` на каждой странице. Три вида (`print.styles`: classic / modern / compact), смета поднимается до 10 pt (`print.contract`, спека 41).
- Порядок сметы: «Для кого» (имя, **адрес объекта**, телефон, почта) → по каждому варианту таблица строк и итоги → Notes → Terms → «одобрено» → право отказа + подписи (`.signoff`, `break-inside: avoid`) → запись подписи → листы-вложения (`break-before: page`) (`estimatePdf.ts:120–132`).
- Перенос: таблицы рвутся браузером где угодно; у `tr` нет `break-inside: avoid`, у заголовка раздела нет `break-after: avoid` — заголовок может остаться внизу страницы без строк [код; на устройстве **не проверено**].
- Телефон: `Print.printToFileAsync({ html })` без размеров → Letter 612×792 [док: docs.expo.dev/versions/latest/sdk/print `FilePrintOptions`]; поля — `@page { margin: 14mm }`. Веб и `/p/`: `iframe` + `print()` через **250 мс** (`estimatePdf.ts:144–162`): картинки, не успевшие загрузиться, в PDF не попадут [вывод] — для фото нужно ждать `img.decode()`.
- ~50 размеров CSS мимо токенов (DS §19.2, Н-34) — фото-CSS добавляем **только на токенах** (§4.5).

### 4.2. Место блоков в документе
- Смета: блоки — **после итогов вариантов, до Notes** (их можно переставить в редакторе, перетаскиванием `SortableList`). Подпись и право отказа остаются рядом (`.signoff`), блоки их не разрывают.
- Счёт: после таблицы сумм; блок оплат — **последним перед подвалом**, `break-inside: avoid`.
- Листы-вложения модуля (`pages`) — как сейчас, в конце.

### 4.3. Сетка и переносы (PDF Letter)
Ширина текста: 8,5″ − 2×14 мм ≈ **532 pt** [вывод, расчёт].

| Блок | Раскладка | Ячейка ≈ (зазор 8 pt) |
|---|---|---|
| g4 | 2×2 | 262 pt |
| g6 | 3×2 | 172 pt |
| g7 | 1 широкое (2/3 ширины) + 3 сбоку, затем ряд из 3 | 352 / 172 pt |
| g8 | 4×2 | 127 pt |
| auto (любое число) | по 3 в ряд, последний ряд по левому краю | 172 pt |
| до/после | 2 в ряд, пара = ряд | 262 pt |
| фотоотчёт | 3 в ряд, над фото — дата и время съёмки компании (`docTime`) | 172 pt |

Правила переноса:
- ряд фото с подписями — `break-inside: avoid` (ряд не рвётся; рвётся блок между рядами);
- заголовок блока — `break-after: avoid` (не остаётся один внизу листа);
- пара «до/после» — один ряд, не рвётся никогда;
- блок оплат и `.signoff` — целиком;
- для таблицы строк (не только фото) добавляем `tr { break-inside: avoid }` и `h2 { break-after: avoid }` — это правка поведения всех документов, отдельный пункт DS (§4.5).

### 4.4. Картинка для печати и размер PDF
- В PDF фото идут **встроенными** (`data:image/jpeg;base64`, как логотип сейчас): `expo-print` с удалёнными адресами — ждёт ли загрузки, **[не проверено]**; встроенные — надёжны.
- Копия для печати делается при сборке PDF: применить рамку (`crop`), длинная сторона 1200 px при ≤ 12 фото, 900 px при 13–40, 700 px дальше; JPEG 0,7 [вывод, цифры проверить на Д-1]. Ориентир: ~150–250 КБ на фото при 1200 px [вывод, не измерено].
- Сторож: модульный тест — 40 фото → PDF-HTML ≤ 10 МБ (порог проверить: почтовые вложения обычно до 20–25 МБ [не проверено]).
- На `/p/` — подписанные ссылки (§5), в браузерном PDF — та же копия через `canvas` или ожидание `decode()` (решить на Д-2).

### 4.5. Телефон, `/p/`, новое правило DS
**Телефон, редактор сметы и счёта (390 / 820 / 1280):** блоки — карточками `Card` в порядке документа, внутри — плитки фото (как `PhotoStrip`), подпись под плиткой одной строкой. Кнопка «Добавить блок» → шторка: «Галерея», «До и после», «Фотоотчёт» (только счёт), «Оплата». Плитка: нажатие — просмотр крупно, долгое — меню «Подпись», «Обрезка», «Убрать из документа». Фото ещё на телефоне — нейтральная метка «ждёт отправки» (значок + слово, правило 2; G §7.4).

**`/p/`:** блоки после вариантов, сетка по ширине листа: 390 — 2 в ряд (до/после — 2 в ряд всегда), ≥ 820 — как в PDF. Нажатие — просмотр на весь экран, листание, закрытие жестом вниз; на вебе — клавиши ← →, Esc. Подпись под фото — `print.mut`, не мельче 10 pt в смете (спека 41).

**Новое правило DS — отдельным пунктом (§2.3, до кода, Д-1):** «§19.5. Фото в документах клиенту» — токены `print.photo = { gapPt: 8, captionPt: 10, cellMinPt: 120, aspects: ["4:3","1:1","3:4","16:9"], printLongPx: [1200, 900, 700] }` (зеркало в `print.css`, `mirror.test.ts`); правила переноса §4.3 (в том числе `tr`/`h2` для всех документов); вид плитки и метки «ждёт отправки»; просмотрщик на `/p/`. QR в PDF **сметы** ведёт на `/p/`, где можно **подписать** договор. Бумагу видят не только клиент (соседи, вторые владельцы). У счёта подпись уже позади (счёт появляется после подписи обеих сторон, S8b), поэтому QR там безопаснее [вывод; подтвердить у security-check].
