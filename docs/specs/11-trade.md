# 11. Направление бизнеса у лида, сметы и работы

Решение основателя 05.11.2026: у лида, сметы и работы есть «направление бизнеса». Нужно для статистики: где больше денег, какие направления работают, откуда приходят лиды по каждому направлению.
Решение руководителя 05.11: направление хранится **ссылкой на запись** (id), а не строкой: строка ломает статистику при переименовании и опечатках.

**Это уже задуманная сущность ServiceCategory** (`docs/04-domain-model.md` §3: «направление и вид работ… ставится на Lead и наследуется в Estimate → Job (`service_category_id`)»). В базе уже есть пустые колонки `estimates.service_category_id` и `jobs.service_category_id` (`20261104000000_core.sql:571, 795`). Поэтому вторую сущность не заводим: таблица `service_categories`, поля `service_category_id`. В этой волне — только верхний уровень (направление); второй уровень («вид работ», `parent_id`) — позже. Отличия от модели данных — в §3.

Ядро от ниши не зависит: логика ядра ни одно направление не различает и работает только с `service_category_id` — записью из списка компании. Названия ниш в ядре есть только как переводимые заготовки (`TRADES` в `features/companySetup.ts`, `seed_key`); модуль (Gutters и следующие) может узнать «своё» направление по `seed_key`, ядро этим ключом не пользуется.

Владелец: чат «Лиды и клиенты» (в `CLAUDE.md` — «Leads tab implementation»): данные, лид, работа, настройки, стык, функции. Экран сметы — чат смет. Чип на карточках списков — чат дизайна карточек (§7).

## 1. Стыки

Новый стык **S16 «Направление: лид → смета → работа»** (`docs/15-story-map.md` §4).

| Откуда | Куда | Что передаётся | Правило |
|---|---|---|---|
| Компания (настройки) | Лид (S1) | список направлений | при создании лида без направления — единственное активное направление компании, иначе пусто. Так же для лида, пришедшего не из приложения (форма сайта L4) |
| Лид | Смета (S5) | направление лида | смета по лиду получает направление лида; без лида — направление последней сметы или работы клиента, иначе единственное направление компании, иначе пусто |
| Смета | Работа (S8, S8b) | направление сметы | работа из сметы получает направление сметы. Пути создания работы: `public.portal_accept` (подпись клиента), операция приложения `estimate.approve` (`cloud/ops.ts`), работа после подписи компании S8b (волна E2, ещё не собрана). Правило базы стоит на вставке в `jobs`, поэтому покрывает все три пути без правки функций чата смет |
| Лид, смета, работа | Отчёт (S14), «Сегодня» (S15) | направление | только чтение |

Осмотр по лиду — это визит с `lead_id`, работы у него нет (`docs/specs/03` §2). Направление у визита не храним: оно берётся из лида визита или из работы визита.

Правила стыка:
- Направление **по умолчанию берётся с предыдущего шага** и только при создании. Человек может поменять его на любом шаге.
- Изменение **не идёт назад и не идёт вперёд**: поменяли направление сметы — лид и уже созданная работа не меняются. Вторая смета того же лида снова берёт направление лида.
- Одна функция наследования в приложении (`inheritCategory`, `src/features/serviceCategories.ts`) и то же правило в базе: триггер «при вставке, если поле пустое» на `leads`, `estimates`, `jobs`. Повторный вызов ничего не портит: заполненное поле не трогается.
- Офлайн: стык полностью локальный, без сервера.

## 3. Сущности и поля

**Таблица `service_categories`** (ServiceCategory из модели данных; в этой волне — только направления).

| Поле | Тип | Смысл |
|---|---|---|
| `id`, `company_id` | uuid | `unique (company_id, id)` для составного ключа |
| `seed_key` | text, null | ключ заготовки из `TRADES` (handyman, plumbing, …, other), если направление выбрано из заготовок; для своего — пусто. По ключу берётся перевод `trade.<seed_key>`; модуль по нему узнаёт своё направление |
| `name` | text, null | своё название или переименование. Пусто у заготовки — показывается перевод на языке интерфейса. Хотя бы одно из `seed_key`, `name` заполнено (check) |
| `parent_id` | uuid, null | в этой волне всегда пусто (check); «вид работ» — позже |
| `position` | int | порядок в списке выбора |
| `archived_at` | timestamptz, null | в архиве: не предлагается для новых записей, старые его сохраняют |
| стандартные поля | | `created_at/by`, `updated_at/by`, `row_version`; `deleted_at` не используется |

Отличия от `docs/04-domain-model.md` (модель обновить в кодовом PR): `is_active` → `archived_at` (видно, когда убрали); `is_user_modified` не нужен (переименование хранится в `name`); `color` не заводим (правило 2: цвет только для статуса); `module`, `show_on_public_page`, `price_from_cents` — позже, с модулями и витриной. `CatalogItem.category_id` — позже, с фильтром каталога.

Ограничения: в компании `seed_key` не повторяется среди неархивных; `name` не повторяется без учёта регистра среди неархивных.

**Поля**: `leads.service_category_id` — новое; `estimates.service_category_id`, `jobs.service_category_id` — уже есть, пустые, получают внешний ключ. У всех трёх: `(company_id, service_category_id) → service_categories (company_id, id)` — направление только своей компании.

**Переименование** меняет только `name`; записи хранят id, история и статистика не ломаются. В отчёте — текущее название.

**Удаления нет**: ни `delete`, ни `deleted_at`. Только «в архив» и «вернуть». Архивное направление остаётся у записей, где уже стоит (при правке не сбрасывается), но выбрать его заново нельзя — проверяет триггер.

**Чего не заводим**: несколько направлений у одной записи; направление у строки сметы, у клиента (у клиента бывают работы разных направлений — «последнее» вычисляется, §1) и у визита (§1); включение модуля — отдельная настройка компании, не направление.

**Перенос `companies.trades[]`.** Миграция создаёт по записи `service_categories` на каждую строку массива, в его порядке (`seed_key` = строка, если она из списка заготовок; иначе `name` = строка). Проверка на текущей базе — `supabase/tests/upgrade/<миграция>.before.sql` / `.after.sql`. После переноса приложение массив не читает и не пишет; колонки `companies.trades` и `companies.primary_trade` (core.sql:91, ограничение gutters/roofing/other; приложение не читает) удаляет отдельная миграция после выпуска. До неё тест базы `core_rls.sql:583`, который пишет `trades`, переводится на новую таблицу в том же кодовом PR.

**Кто читает `trades` сейчас** (проверено по коду 05.11) — всё переводится в кодовом PR:

## 4. Статусы и переходы

Новых статусов нет (§5 карты не меняется). У направления два состояния, «активно» и «в архиве» (`archived_at`). «В архив» и «вернуть» — владелец и админ; при возврате проверяется уникальность названия.

## 5. Как приходит / как уходит

Приходит: из настроек (список), в лид — по §1, из приёма заявок L4 позже (форма сайта может передать направление; без него сработает правило «единственное направление»). Уходит: в смету и работу по §1, в отчёт S14, чипом на карточках списков.

## 6. Настройки

«Настройки → Направления и модули → Направления работ» (`docs/specs/05` §5). Список с порядком, «+ Направление» (заготовка или своё), переименовать, в архив, вернуть. Меняют владелец и админ. После переноса — направления из `trades[]`. Пустое состояние: «Добавьте, чем занимается компания».

## 7. Экраны

- **Лид** (наш чат): в блоке «Заявка» строка «Направление» с выбором в шторке (строками: активные направления + «Без направления»). Если у компании одно направление — строка только показывает его.

- **Настройки** — §6.

## 8. Права, офлайн, уведомления

- `service_categories`: читают все участники компании; добавляют, переименовывают, архивируют владелец и админ; `delete` не выдаётся никому. Новая миграция: сначала `revoke all … from anon, authenticated`, потом `grant select, insert, update … to authenticated`.
- Направление у лида, сметы, работы меняет тот, кто может менять саму запись (их RLS не меняется). Чужое не поставить — составной ключ; архивное заново не поставить — триггер.
- Офлайн: выбор направления и правка списка — в очередь (`useStore().queue`).
- Уведомлений нет.
