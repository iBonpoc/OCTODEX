## 2. Решения (варианты → выбор)
1. **«Чем занимаетесь?»** — отдельный шаг после создания компании (`auth/trade`), выбор направлений существующим `ServiceCategoryPicker` + «Другое»; пропустить можно. Примеры каталога — только с пометкой «тестовые» (правило 9). Шаг `trades` мастера компании засчитывается.
2. **«Первые шаги»** на Главной владельца — по 13 §3.11: профиль компании, первая работа (`/job/new`), пригласить команду (`/team`), установить на телефон (только веб, PWA). «Импорт клиентов» и «Оплаты онлайн» — **нет**, пока нет экранов (Apple 2.1). Скрыть — владелец (13 §5а). Старые пункты (каталог, лид, смета) уходят; `CompanySetupCard` остаётся в «Настройках компании».
3. **Статусы Membership:** `invited → active → disabled`, `invited → deleted` (отменено), `active/disabled → deleted` (удалил аккаунт). В базе: `suspended` переименовать в `disabled` новой миграцией; `deleted` — статус + `deleted_at`. Сначала строка в карте §5 (руководитель).
4. **Приглашение (S21):** приглашение по email (телефон — позже, когда SMS): строка `memberships` нельзя без `user_id` → отдельная таблица `invitations` (company, email, role, can_sign, token_hash, expires_at, status). RPC `invite_member` (owner/admin), `accept_invitation(token)` — SECURITY DEFINER, проверяет токен и email входящего → создаёт `memberships(active)`; `revoke_invitation`, `set_member_disabled`. Письма пока нет (домен, П1b): ссылку приглашения можно **скопировать / отправить системным «Поделиться»**; письмо — когда заработает почта. **Подтверждение почты в Supabase обязательно** (Authentication → Providers → Email → Confirm email; `supabase/config.toml` `[auth.email] enable_confirmations = true`): `accept_invitation` берёт email из `auth.users` и требует `email_confirmed_at`. Вход по коду из письма (OTP) сам подтверждает почту; вход по паролю — только после письма-подтверждения при регистрации (`auth.checkEmail`), неподтверждённого пароля не бывает.
5. **Clickwrap (legal/01 §8 п.13):** при регистрации галочка «Принимаю Условия и Политику» (кнопка неактивна без неё) → `legal_acceptance(user_id, doc, version, accepted_at)`; новая версия документа — экран согласия при входе. Компанию создать без записи нельзя (тест базы).
6. **Ссылки и помощь:** «Политика конфиденциальности», «Условия», «Помощь и поддержка» (адрес поддержки, «Сообщить о проблеме» письмом) — на входе, в «Моих настройках», «Помощь» — плиткой в «Ещё». Пояснения к разрешениям — EN/RU/ES.
7. **Удаление аккаунта (S22):** «Мои настройки» внизу → экран «что удалится, что останется» → подтверждение кодом / вводом слова → RPC `delete_account`: личные данные обезличены, членства `deleted`, вход закрыт; записи компании остаются. Единственный владелец — по умолчанию из 15-flows §4 в.1 (передать админу; нет админа — «Удалить компанию»). **Ждёт ответа основателя.**

## 5. 7а-1 подробно: согласие с условиями, документы, помощь, разрешения (этап 0 «Каркаса» №4, 06.11.2026)
> Источники: `docs/legal/01-founder-protection.md` §3.1–§3.5, §8 п.13; `14-app-store.md` §1 п.3–4, §4; `15-flows.md` §1.8. Клетка карты: S0 (регистрация, первый шаг 1.8). Новой сущности в §5 карты нет: `LegalAcceptance` — журнал, без статусов (строка для §1 модели данных — руководителю).

### 5.1 Инспекция
- Компания создаётся прямой вставкой `companies` (`cloud/auth.tsx createCompany`), политика `companies_insert` — только «вошёл». Фикстуры тестов базы вставляют компании суперпользователем, поэтому политика их не затрагивает.
- Вход необязателен: приложение работает в демо, вход — из «Мои настройки». Общего «шлюза входа» нет.
- Флажка (checkbox) в `src/ui` нет, есть только `Toggle` (переключатель, `role=switch`). Для clickwrap нужен флажок.
- «wave N» в пользовательских строках есть только в `est.sendNote` («Сметы») и `help.money` («Деньги»). Слов compliant / guaranteed / «гарантируем» нет.
- `app.json`: камера и фото только по-русски, в `infoPlist` и в плагине `expo-image-picker`.

### 5.2 Варианты
**Где записывать согласие.**
- **А. RPC `accept_legal` после входа (выбрано).** Время ставит сервер, IP берётся из заголовков запроса, версию сверяет сервер. Работает и для кода из письма, и для пароля, и для приглашённого.
- Б. Метаданные при регистрации (`options.data`) и триггер на `auth.users`. Вход по коду не различает «новый» и «старый» человек. Новая версия документа так не записывается. Отклонено.
- В. Прямая вставка в таблицу по RLS. Клиент мог бы поставить своё время и версию. Отклонено.

**Где спрашивать.**
- **А. Флажок на экране входа во всех трёх режимах (код, пароль, регистрация) и шлюз «Условия изменились» для вошедших без текущей версии (выбрано).**
- Б. Флажок только при регистрации. Вход по коду создаёт аккаунт без «регистрации», поэтому согласие бы терялось. Отклонено.

**Как закрыть компанию без согласия.**
- **Политика `companies_insert`: «вошёл» и `app.has_current_legal()` (выбрано).** То же условие добавляется в `accept_invitation`: приглашённый принимает Условия и Политику (DPA принимает владелец, legal §3.5).

### 5.3 Решение
**База, миграция `20261106140000_legal_acceptance.sql`.**
- `public.legal_acceptance`: `id`, `user_id` (`auth.uid()`), `company_id` (null при регистрации), `doc` (`terms` | `privacy` | `dpa`), `version` (дата `YYYY-MM-DD`), `accepted_at` (время сервера), `platform` (`ios` | `android` | `web`), `app_version` (≤ 40 символов), `ip` (inet из `x-forwarded-for`, если есть).
- Журнал только дописывается. Строки нельзя менять и удалять. Человек видит только свои строки. Вставка — только через RPC.
- `app.legal_current_version(doc)` — текущие версии (`terms` и `privacy` = `2026-11-06`). Новая редакция документа = новая миграция с `create or replace` и правкой `LEGAL_VERSIONS` в приложении.
- `public.accept_legal(p_versions jsonb, p_platform text, p_app_version text)` — security definer. Отказывает, если версия не текущая (`legal version outdated`): старое приложение показывало старый текст. Повтор той же версии не создаёт дубль.
- `public.legal_status()` — что текущее и что принято (для шлюза).
- `app.has_current_legal()` — приняты текущие `terms` и `privacy`.
- Правило 18: у всех новых функций `revoke all … from public, anon`, у `accept_legal` и `legal_status` — `grant execute … to authenticated`. Таблица: `revoke all … from anon, authenticated`, `grant select` своим.
- Старые сборки без флажка: новый человек на старой сборке компанию не создаст (ошибка прав). В магазинах приложения ещё нет, Expo Go обновляется `release.yml`, поэтому риск принят. Схема не переименовывается, правило 16 не затронуто.

**Приложение.**
- `features/legal.ts`: `LEGAL_VERSIONS`, `LEGAL_DOCS`. Флажок `LegalAgree` (Press + Icon, только токены, `accessibilityRole="checkbox"`, `aria-checked`) — пока локально в `features/legal.tsx`. В общий `src/ui` — отдельным PR, если руководитель решит.
- `auth/sign-in.tsx`: пустой флажок перед кнопками: «I agree to the Terms of Service and Privacy Policy», ссылки видимые и подчёркнутые. Без флажка все кнопки входа и регистрации неактивны. После входа — `accept_legal`, затем дальше по прежнему пути.
- `auth/terms.tsx`: шлюз «Условия изменились». Что поменялось (до 3 строк), флажок, «Принять», «Выйти». Шлюз в корневом `_layout` (одна строка, общий файл): в облаке, с сессией, если `legal_status` говорит «не принято». Не срабатывает на `/auth/*`, `/legal/*`, `/help`, `/p/*`. **Офлайн не блокирует** (решение руководителя 06.11). Шлюз показывается, только если `legal_status` ответил «не принято». Нет сети или ошибка — работа идёт дальше, проверка повторяется при появлении сети. **В демо шлюза нет**: демо считается «принято», поэтому e2e и сид не затронуты.
- `legal/[doc].tsx`: `/legal/terms`, `/legal/privacy` — черновик «Draft · edition 2026-11-06» по legal §3.2–§3.3, коротко, через i18n. В ES и RU — пометка «обязательный текст — английский». Доступны без входа.
- `help.tsx`: «Помощь и поддержка». Адрес поддержки (`config/support.ts`, плейсхолдер `support@octodex.example` до ответа основателя). «Написать в поддержку» и «Сообщить о проблеме» — письмом (mailto, тема с версией и сборкой). Ссылки на документы. Строка «Мы не даём юридических и налоговых советов» (legal §3.2а).
- «Ещё»: плитка «Помощь и поддержка» (`sections.ts`, группа bottom). «Мои настройки»: раздел «О приложении» — Условия, Политика (с версией), Помощь.
- `app.json`: базовые тексты разрешений на EN, `CFBundleAllowMixedLocalizations`, `locales` → `locales/{en,ru,es}.json` (iOS InfoPlist). У Android системного текста разрешения нет.

### 5.6 Находки помощников (map-keeper, security-check, 06.11) → что меняется в решении
**База.**
- `app.has_current_legal()` — security definer, `stable`, `search_path = ''`, без аргументов. Права: `revoke all … from public, anon` и `grant execute … to authenticated`. Без этого гранта политика `companies_insert` падает у всех.
- `app.legal_current_version(text)` — `stable`, а не `immutable`: иначе план кэшируется со старой версией. Исполнять её не может никто, кроме функций definer.
- Политику меняем через `alter policy companies_insert … with check ((select auth.uid()) is not null and (select app.has_current_legal()))`. Плюс триггер `before insert` на `companies`: если не принято — `legal not accepted` (42501). Так приложение узнаёт причину по коду, а не по тексту RLS.
- `accept_invitation` пересоздаётся целиком (`create or replace`, тело из 110000 без изменений). Проверка `legal not accepted` ставится сразу после `v_me is null`. `set_member_status` возвращает отключённого без нового согласия — так и задумано.
- `accept_legal(p_versions jsonb, p_platform, p_app_version)`:
  - объект строго с двумя ключами `terms` и `privacy`, значения — строки, сравнение через `is distinct from` с текущей версией, иначе `legal version outdated`;
  - `user_id = auth.uid()`, при null — 42501; анонимный вход (`is_anonymous`) — отказ;
  - `accepted_at = now()`;
  - `app_version` по шаблону `^[0-9A-Za-z.+ _-]{1,40}$`, `platform` из списка;
  - `company_id` не принимает, всегда null. DPA — позже, отдельной функцией только для owner.
- Таблица:
  - `check (doc <> 'dpa' or company_id is not null)`, `version` — `date`;
  - уникальный индекс `(user_id, doc, version) where company_id is null` + `on conflict do nothing`: повтор и двойное нажатие не дают дубля;
  - RLS `enable` + `force`, только select своих строк.
- IP (ревью #206 M3): только `cf-connecting-ip` — его ставит Cloudflare. Какой адрес в `x-forwarded-for` клиентский, зависит от прокси (на staging не проверено), поэтому оттуда IP не берётся. Нет заголовка или он битый → `ip = null`. Оба заголовка сырыми — в `ip_raw` (`cf=… | xff=…`, ≤ 200). IP — вспомогательное доказательство; `platform` и `app_version` сообщает клиент. Несуществующая дата (`2026-02-30`) → та же ошибка `legal version outdated` (M4).
- Удаление аккаунта: `user_id references public.users on delete cascade`. Триггер «только дописывать» пропускает только каскад (`pg_trigger_depth() > 1`: внутри самого триггера глубина ≥ 1, каскад от `public.users` даёт 2) и системное стирание. Сколько хранить доказательство согласия после удаления (обезличить или удалить) — решаем в 7а-2 (S22).
- Тесты базы:
  - **T48:** перед каждым успешным `accept_invitation` — `accept_legal` под JWT принимающего.
  - **T49:** без согласия — отказ; повтор даёт ровно 2 строки; anon не исполняет функции; у всех definer-функций в public/app задан `search_path`; удаление auth-пользователя с согласием проходит.
  - **Upgrade-тест** `upgrade/20261106140000_legal_acceptance.{before,after}.sql`: старые членства работают, задним числом согласие не создаётся, новую компанию без согласия не создать.
- Отметка галочки на устройстве (security-check финала): с email и временем, действует 30 минут и только для сессии того же email; стирается при неудачном входе и при выходе (общий планшет бригады).
- Проверить на staging, какие заголовки приходят в `request.headers` (`cf-connecting-ip` / XFF), — `docs/specs/19` §5.6, находка 5.
- **Повтор принятой ссылки** (ревью #206 M5): `accept_invitation` проверяет согласие раньше ветки «repeat». Повторно открыть уже принятую ссылку без текущего согласия нельзя — придёт `legal not accepted`, приложение попросит согласие.
- **Старая сборка у приглашённого** (M6): без галочки сервер ответит `legal not accepted`. Старая сборка считает это мёртвой ссылкой и стирает её. Владельцу нужно «Отправить ещё раз», человеку — обновить приложение.
- Ответы не по порядку (M1): проверки и «Принять» берут билеты, применяется только ответ последнего. Без сети проверка повторяется при возврате в приложение, по `online` и раз в минуту (M2). Логика приглашения — чистые функции `features/inviteFlow.ts` (V1, `test/inviteFlow.test.ts`).
- Уже вошедших сервер к принятию не заставляет: для обычной работы это делает только шлюз в приложении.

**Приложение.**
- **Гонка на приглашении** (`auth/invite.tsx` вызывает `acceptInvitation`, как только есть сессия):
  - Флажок на входе кладёт «принято, версии» в AsyncStorage (`pendingLegalKey`).
  - `AuthProvider` при появлении сессии сначала отправляет `accept_legal`, потом `reloadMemberships`, и выставляет `legal: "ok" | "missing" | "unknown"`.
  - `invite.tsx` ждёт `legal !== "unknown"`. При `missing` или `legal not accepted` ссылку **не стирает** и показывает флажок прямо на экране, затем снова принимает приглашение.
  - `invite.tsx` и `features/team.ts` (`team.err.legal`) — в списке файлов.
- То же покрывает подтверждение почты по ссылке из письма: отметка лежит на том же устройстве. Если устройство другое — шлюз с текстом **первого раза** («Примите Условия и Политику»), а не «Условия изменились».
- `legal version outdated` → `legal.err.outdated`: «Обновите приложение».
- `createCompany` больше не показывает сырой текст базы: `legal not accepted` → шлюз.
