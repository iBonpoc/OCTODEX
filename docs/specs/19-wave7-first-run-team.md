## 2. Решения (варианты → выбор)
1. **«Чем занимаетесь?»** — отдельный шаг после создания компании (`auth/trade`), выбор направлений существующим `ServiceCategoryPicker` + «Другое»; пропустить можно. Примеры каталога — только с пометкой «тестовые» (правило 9). Шаг `trades` мастера компании засчитывается.
2. **«Первые шаги»** на Главной владельца — по 13 §3.11: профиль компании, первая работа (`/job/new`), пригласить команду (`/team`), установить на телефон (только веб, PWA). «Импорт клиентов» и «Оплаты онлайн» — **нет**, пока нет экранов (Apple 2.1). Скрыть — владелец (13 §5а). Старые пункты (каталог, лид, смета) уходят; `CompanySetupCard` остаётся в «Настройках компании».
3. **Статусы Membership:** `invited → active → disabled`, `invited → deleted` (отменено), `active/disabled → deleted` (удалил аккаунт). В базе: `suspended` переименовать в `disabled` новой миграцией; `deleted` — статус + `deleted_at`. Сначала строка в карте §5 (руководитель).
4. **Приглашение (S21):** приглашение по email (телефон — позже, когда SMS): строка `memberships` нельзя без `user_id` → отдельная таблица `invitations` (company, email, role, can_sign, token_hash, expires_at, status). RPC `invite_member` (owner/admin), `accept_invitation(token)` — SECURITY DEFINER, проверяет токен и email входящего → создаёт `memberships(active)`; `revoke_invitation`, `set_member_disabled`. Письма пока нет (домен, П1b): ссылку приглашения можно **скопировать / отправить системным «Поделиться»**; письмо — когда заработает почта. **Подтверждение почты в Supabase обязательно** (Authentication → Providers → Email → Confirm email; `supabase/config.toml` `[auth.email] enable_confirmations = true`): `accept_invitation` берёт email из `auth.users` и требует `email_confirmed_at`. Вход по коду из письма (OTP) сам подтверждает почту; вход по паролю — только после письма-подтверждения при регистрации (`auth.checkEmail`), неподтверждённого пароля не бывает.
5. **Clickwrap (legal/01 §8 п.13):** при регистрации галочка «Принимаю Условия и Политику» (кнопка неактивна без неё) → `legal_acceptance(user_id, doc, version, accepted_at)`; новая версия документа — экран согласия при входе. Компанию создать без записи нельзя (тест базы).
6. **Ссылки и помощь:** «Политика конфиденциальности», «Условия», «Помощь и поддержка» (адрес поддержки, «Сообщить о проблеме» письмом) — на входе, в «Моих настройках», «Помощь» — плиткой в «Ещё». Пояснения к разрешениям — EN/RU/ES.
7. **Удаление аккаунта (S22):** «Мои настройки» внизу → экран «что удалится, что останется» → подтверждение кодом / вводом слова → RPC `delete_account`: личные данные обезличены, членства `deleted`, вход закрыт; записи компании остаются. Единственный владелец — по умолчанию из 15-flows §4 в.1 (передать админу; нет админа — «Удалить компанию»). **Ждёт ответа основателя.**

## 5. 7а-1 подробно: согласие с условиями, документы, помощь, разрешения (этап 0 «Каркаса» №4, 06.11.2026)
> Источники: `docs/legal/01-founder-protection.md` §3.1–§3.5, §8 п.13; `14-app-store.md` §1 п.3–4, §4; `15-flows.md` §1.8. Клетка карты: S0 (регистрация, первый шаг 1.8). Новой сущности в §5 карты нет: `LegalAcceptance` — журнал, без статусов (строка для §1 модели данных — руководителю).

### 5.1 Инспекция
- Компания создаётся прямой вставкой `companies` (`cloud/auth.tsx createCompany`), политика `companies_insert` — только «вошёл». Фикстуры тестов базы вставляют компании суперпользователем, поэтому политика их не затрагивает.
- Вход необязателен: приложение работает в демо, вход — из «Мои настройки». Общего «шлюза входа» нет.
- Флажка (checkbox) в `src/ui` нет, есть только `Toggle` (переключатель, `role=switch`). Для clickwrap нужен флажок.
- «wave N» в пользовательских строках есть только в `est.sendNote` («Сметы») и `help.money` («Деньги»). Слов compliant / guaranteed / «гарантируем» нет.
- `app.json`: камера и фото только по-русски, в `infoPlist` и в плагине `expo-image-picker`.

### 5.2 Варианты
**Где записывать согласие.**
- **А. RPC `accept_legal` после входа (выбрано).** Время ставит сервер, IP берётся из заголовков запроса, версию сверяет сервер. Работает и для кода из письма, и для пароля, и для приглашённого.
- Б. Метаданные при регистрации (`options.data`) и триггер на `auth.users`. Вход по коду не различает «новый» и «старый» человек. Новая версия документа так не записывается. Отклонено.
- В. Прямая вставка в таблицу по RLS. Клиент мог бы поставить своё время и версию. Отклонено.

**Где спрашивать.**
- **А. Флажок на экране входа во всех трёх режимах (код, пароль, регистрация) и шлюз «Условия изменились» для вошедших без текущей версии (выбрано).**
- Б. Флажок только при регистрации. Вход по коду создаёт аккаунт без «регистрации», поэтому согласие бы терялось. Отклонено.

**Как закрыть компанию без согласия.**
- **Политика `companies_insert`: «вошёл» и `app.has_current_legal()` (выбрано).** То же условие добавляется в `accept_invitation`: приглашённый принимает Условия и Политику (DPA принимает владелец, legal §3.5).

### 5.3 Решение
**База, миграция `20261106140000_legal_acceptance.sql`.**
- `public.legal_acceptance`: `id`, `user_id` (`auth.uid()`), `company_id` (null при регистрации), `doc` (`terms` | `privacy` | `dpa`), `version` (дата `YYYY-MM-DD`), `accepted_at` (время сервера), `platform` (`ios` | `android` | `web`), `app_version` (≤ 40 символов), `ip` (inet из `x-forwarded-for`, если есть).
- Журнал только дописывается. Строки нельзя менять и удалять. Человек видит только свои строки. Вставка — только через RPC.
- `app.legal_current_version(doc)` — текущие версии (`terms` и `privacy` = `2026-11-06`). Новая редакция документа = новая миграция с `create or replace` и правкой `LEGAL_VERSIONS` в приложении.
- `public.accept_legal(p_versions jsonb, p_platform text, p_app_version text)` — security definer. Отказывает, если версия не текущая (`legal version outdated`): старое приложение показывало старый текст. Повтор той же версии не создаёт дубль.
- `public.legal_status()` — что текущее и что принято (для шлюза).
- `app.has_current_legal()` — приняты текущие `terms` и `privacy`.
- Правило 18: у всех новых функций `revoke all … from public, anon`, у `accept_legal` и `legal_status` — `grant execute … to authenticated`. Таблица: `revoke all … from anon, authenticated`, `grant select` своим.
- Старые сборки без флажка: новый человек на старой сборке компанию не создаст (ошибка прав). В магазинах приложения ещё нет, Expo Go обновляется `release.yml`, поэтому риск принят. Схема не переименовывается, правило 16 не затронуто.

**Приложение.**
- `features/legal.ts`: `LEGAL_VERSIONS`, `LEGAL_DOCS`. Флажок `LegalAgree` (Press + Icon, только токены, `accessibilityRole="checkbox"`, `aria-checked`) — пока локально в `features/legal.tsx`. В общий `src/ui` — отдельным PR, если руководитель решит.
- `auth/sign-in.tsx`: пустой флажок перед кнопками: «I agree to the Terms of Service and Privacy Policy», ссылки видимые и подчёркнутые. Без флажка все кнопки входа и регистрации неактивны. После входа — `accept_legal`, затем дальше по прежнему пути.
- `auth/terms.tsx`: шлюз «Условия изменились». Что поменялось (до 3 строк), флажок, «Принять», «Выйти». Шлюз в корневом `_layout` (одна строка, общий файл): в облаке, с сессией, если `legal_status` говорит «не принято». Не срабатывает на `/auth/*`, `/legal/*`, `/help`, `/p/*`. **Офлайн не блокирует** (решение руководителя 06.11). Шлюз показывается, только если `legal_status` ответил «не принято». Нет сети или ошибка — работа идёт дальше, проверка повторяется при появлении сети. **В демо шлюза нет**: демо считается «принято», поэтому e2e и сид не затронуты.
- `legal/[doc].tsx`: `/legal/terms`, `/legal/privacy` — черновик «Draft · edition 2026-11-06» по legal §3.2–§3.3, коротко, через i18n. В ES и RU — пометка «обязательный текст — английский». Доступны без входа.
- `help.tsx`: «Помощь и поддержка». Адрес поддержки (`config/support.ts`, плейсхолдер `support@octodex.example` до ответа основателя). «Написать в поддержку» и «Сообщить о проблеме» — письмом (mailto, тема с версией и сборкой). Ссылки на документы. Строка «Мы не даём юридических и налоговых советов» (legal §3.2а).
- «Ещё»: плитка «Помощь и поддержка» (`sections.ts`, группа bottom). «Мои настройки»: раздел «О приложении» — Условия, Политика (с версией), Помощь.
- `app.json`: базовые тексты разрешений на EN, `CFBundleAllowMixedLocalizations`, `locales` → `locales/{en,ru,es}.json` (iOS InfoPlist). У Android системного текста разрешения нет.

### 5.6 Находки помощников (map-keeper, security-check, 06.11) → что меняется в решении
**База.**
- `app.has_current_legal()` — security definer, `stable`, `search_path = ''`, без аргументов. Права: `revoke all … from public, anon` и `grant execute … to authenticated`. Без этого гранта политика `companies_insert` падает у всех.
- `app.legal_current_version(text)` — `stable`, а не `immutable`: иначе план кэшируется со старой версией. Исполнять её не может никто, кроме функций definer.
- Политику меняем через `alter policy companies_insert … with check ((select auth.uid()) is not null and (select app.has_current_legal()))`. Плюс триггер `before insert` на `companies`: если не принято — `legal not accepted` (42501). Так приложение узнаёт причину по коду, а не по тексту RLS.
- `accept_invitation` пересоздаётся целиком (`create or replace`, тело из 110000 без изменений). Проверка `legal not accepted` ставится сразу после `v_me is null`. `set_member_status` возвращает отключённого без нового согласия — так и задумано.
- `accept_legal(p_versions jsonb, p_platform, p_app_version)`:
  - объект строго с двумя ключами `terms` и `privacy`, значения — строки, сравнение через `is distinct from` с текущей версией, иначе `legal version outdated`;
  - `user_id = auth.uid()`, при null — 42501; анонимный вход (`is_anonymous`) — отказ;
  - `accepted_at = now()`;
  - `app_version` по шаблону `^[0-9A-Za-z.+ _-]{1,40}$`, `platform` из списка;
  - `company_id` не принимает, всегда null. DPA — позже, отдельной функцией только для owner.
- Таблица:
  - `check (doc <> 'dpa' or company_id is not null)`, `version` — `date`;
  - уникальный индекс `(user_id, doc, version) where company_id is null` + `on conflict do nothing`: повтор и двойное нажатие не дают дубля;
  - RLS `enable` + `force`, только select своих строк.
- IP (ревью #206 M3): только `cf-connecting-ip` — его ставит Cloudflare. Какой адрес в `x-forwarded-for` клиентский, зависит от прокси (на staging не проверено), поэтому оттуда IP не берётся. Нет заголовка или он битый → `ip = null`. Оба заголовка сырыми — в `ip_raw` (`cf=… | xff=…`, ≤ 200). IP — вспомогательное доказательство; `platform` и `app_version` сообщает клиент. Несуществующая дата (`2026-02-30`) → та же ошибка `legal version outdated` (M4).
- Удаление аккаунта: `user_id references public.users on delete cascade`. Триггер «только дописывать» пропускает только каскад (`pg_trigger_depth() > 1`: внутри самого триггера глубина ≥ 1, каскад от `public.users` даёт 2) и системное стирание. Сколько хранить доказательство согласия после удаления (обезличить или удалить) — решаем в 7а-2 (S22).
- Тесты базы:
  - **T48:** перед каждым успешным `accept_invitation` — `accept_legal` под JWT принимающего.
  - **T49:** без согласия — отказ; повтор даёт ровно 2 строки; anon не исполняет функции; у всех definer-функций в public/app задан `search_path`; удаление auth-пользователя с согласием проходит.
  - **Upgrade-тест** `upgrade/20261106140000_legal_acceptance.{before,after}.sql`: старые членства работают, задним числом согласие не создаётся, новую компанию без согласия не создать.
- Отметка галочки на устройстве (security-check финала): с email и временем, действует 30 минут и только для сессии того же email; стирается при неудачном входе и при выходе (общий планшет бригады).
- Проверить на staging, какие заголовки приходят в `request.headers` (`cf-connecting-ip` / XFF), — `docs/specs/19` §5.6, находка 5.
- **Повтор принятой ссылки** (ревью #206 M5): `accept_invitation` проверяет согласие раньше ветки «repeat». Повторно открыть уже принятую ссылку без текущего согласия нельзя — придёт `legal not accepted`, приложение попросит согласие.
- **Старая сборка у приглашённого** (M6): без галочки сервер ответит `legal not accepted`. Старая сборка считает это мёртвой ссылкой и стирает её. Владельцу нужно «Отправить ещё раз», человеку — обновить приложение.

## 6. 7а-2: удаление аккаунта, S22 (этап 0 «Каркаса» №4, 06.11.2026)
> Источники: `15-flows.md` §1.12, §4 в.1; `14-app-store.md` §2 п.1 (Apple 5.1.1(v): «удаление, а не пометка»); `docs/legal/01` §3.3, §8; `CHECKS.md` §7. Клетка карты: **S22**, Membership `→ deleted`. Миграция `20261106200000_delete_account.sql`, тест базы T50, e2e 97.

### 6.1 Инспекция
- **Членство.** `memberships.status` уже допускает `deleted`, есть `deleted_at`. Статус меняется только в definer-функциях с флагом `app.accepting_invite` (guard из 110000). `is_member` = только `active`: удалённый сразу теряет доступ к данным компании.
- **Ссылки на `public.users`** (17 FK, все без каскада). Делятся на три группы:
  - деловые записи компании, остаются: `assigned_to`, `owner_user_id`, `voided_by`, `received_by`, `invited_by`, `accepted_by`, `requested_by`, `assignee_id`, `visit_assignees.user_id`, `calendar_events.user_id`, `member_signatures.user_id`, `estimate_approvals.signer_user_id`;
  - связь контакта компании с аккаунтом: `company_contacts.user_id`;
  - личное: `legal_acceptance` (каскад), `member_prefs` (с #203, FK на `memberships` с каскадом — но членство мягкое, поэтому удалять явно), `user_locations` (появится в 7б-2).
- **Удалить строку `auth.users` нельзя.** Каскад в `public.users` упрётся в 17 FK без каскада. Поэтому человек обезличивается, а вход закрывается без удаления строки.
- **Дыра в правах.** `companies_select` пускает `created_by = auth.uid()` без членства. Удалённый владелец, пока жив его токен (до часа), видел бы строку своей компании.
- **Компания с одним владельцем.** Функции передачи владения нет. `set_member_role` в долгах «Каркаса».
- Edge-функций в репозитории нет (`supabase/functions` пусто).

### 6.2 Варианты
**Как закрыть вход.**
- **А. Всё в одной RPC `delete_account` (security definer) — рекомендую.** Обезличить `public.users`. Членства перевести в `deleted`. Удалить личные строки. В `auth`: email заменить на `deleted+<id>@deleted.invalid`, телефон убрать, `banned_until = 'infinity'`, удалить `auth.sessions`, `auth.refresh_tokens`, `auth.identities`, `auth.mfa_factors`.
  - Плюсы: одна транзакция, ничего нового в инфраструктуре, тест базы проверяет всё целиком. Email освобождается — по нему можно зарегистрироваться заново как новый человек.
  - Минусы: пишем во внутренние таблицы `auth`. Колонки проверяются через `to_regclass` / `information_schema`, в заглушке тестов они добавлены. На staging — проверить один раз.
- Б. RPC для данных + edge-функция с service role → `auth.admin.deleteUser(uid, shouldSoftDelete = true)`. Это официальный путь Supabase. Но нужна инфраструктура функций и деплой (их нет), две части не в одной транзакции, а тест базы не видит вторую. Предлагаю позже, если staging покажет, что А не закрывает вход.

**Подтверждение.**
- **Заново ввести код из письма (как в 15-flows §1.12) + ввести слово «УДАЛИТЬ» / DELETE / ELIMINAR (рекомендую).** Сервер требует свежий вход: `auth.users.last_sign_in_at` не старше 10 минут. Иначе `sign in again first`. Чужой забытый телефон с открытой сессией аккаунт не удалит.
- Только слово — слабо: любой, у кого телефон, удалит аккаунт. Отклонено.

**Единственный владелец** (вопрос основателю 1, по умолчанию 15-flows §4).
- **В 7а-2 (рекомендую).**
  - `delete_account` отказывает, если человек — последний активный owner хотя бы одной компании (`the company keeps at least one active owner`).
  - Экран показывает, у какой компании.
  - Если в компании есть активный admin — кнопка «Передать компанию»: новая RPC `transfer_ownership(company, to_user)`. Admin становится owner, сам владелец — admin. После этого удаление проходит.
  - Если admin нет — «Удаление компании — через поддержку» (письмо из «Помощи»).
- «Удалить компанию» с выгрузкой и сроками хранения — отдельная задача **7а-3**: нужно решение основателя и правового чата о сроках (`legal-research` §8.3). Для Apple достаточно, чтобы удаление можно было начать в приложении (5.1.1(v): «initiate deletion»). Путь через поддержку для крайнего случая это допускает. Пишу как риск.

### 6.3 Решение (при «да» на варианты А и «код + слово»)
**Миграция `20261106200000_delete_account.sql`.**
- **`public.delete_account(p_confirm text)`** — security definer, `search_path = ''`.
  - Проверки: вошёл (не anon, не `is_anonymous`); свежий вход ≤ 10 мин; `p_confirm` в (`DELETE`, `УДАЛИТЬ`, `ELIMINAR`).
  - Блокирует свои членства `for update`, затем всех owner этих компаний `for update`. Не последний активный owner ни одной компании — иначе ошибка с `company_id`.
  - Под `app.accepting_invite = on`:
    - `memberships`: `status = 'deleted'`, `deleted_at = now()`, `share_location = false`, `title`, `his_registration_number`, `color` → null;
    - его `invitations` в статусе `pending` → `revoked` (как при отключении);
    - удалить `member_prefs`;
    - `company_contacts.user_id` → null (контакт компании остаётся данными компании);
    - вызвать `app.erase_personal_rows(uid)` — точка расширения: 7б-2 добавит туда `user_locations`, а T50 проверит.
  - `public.users`: `full_name = 'Deleted user'`, `email = deleted+<id>@deleted.invalid`, `phone`, `avatar_file_id`, `last_active_company_id` → null, `deleted_at = now()`.
  - `legal_acceptance`: строки остаются как доказательство согласия, `ip`, `ip_raw` → null (`app.erasing_user = on`, guard из 140000 это пропускает только для `update ip/ip_raw`; правлю guard в 200000). Срок хранения — вопрос основателю.
  - `auth`: email и телефон обезличены, `banned_until = infinity`, сессии, токены, identities и MFA удалены.
  - Возвращает `{deleted: true}`.
- **`public.transfer_ownership(p_company_id, p_to_user)`** — только активный owner. Цель — активный admin этой компании (не он сам). Под флагом: цель → owner + `can_sign_contracts`, сам → admin. Блокировки — как в `set_member_status`.
- **`companies_select`** — `alter policy`: `created_by = auth.uid()` действует, только пока у человека нет никакого членства в этой компании (момент создания). Удалённый владелец строку больше не видит.
- **`app.tg_membership_guard`** не меняется. Флаг тот же.
- **Правило 18:** `revoke all … from public, anon`, `grant execute … to authenticated` на `delete_account` и `transfer_ownership`. `erase_personal_rows` — никому.
- Правило 16: колонки и функции не переименовываются. Политика — `alter`.

**Приложение.**
- «Мои настройки» → в самом низу «Удалить аккаунт» (видно только в облаке; в демо — строка «В демо аккаунта нет»).
- Экран `/settings/delete-account`:
  1. Что удалится: имя, email, телефон, вход, личные настройки, местоположение. Что останется у компании: работы, сметы, счета, квитанции, подписанные договоры, история — с подписью «Удалённый пользователь».
  2. Если последний owner: компания и «Передать компанию» (выбор admin) или «Через поддержку».
  3. «Получить код» → код из письма (`verifyOtp`).
  4. Ввести слово.
  5. «Удалить навсегда» (`bad`, подтверждение в шторке).
  6. → выход, экран входа, тост «Аккаунт удалён».
- **Офлайн:** кнопка неактивна, текст «нужна сеть». В очередь не ставится — необратимо, сервер должен ответить сразу.
- Ошибки RPC → `acct.err.*` (последний владелец, вход устарел, слово).
- Файлы: `settings/delete-account.tsx`, `settings/index.tsx`, `features/deleteAccount.ts` (чистая логика: слово по языку, ошибки, блок «последний владелец»), `cloud/account.ts`, i18n `acct.*`, e2e 97, SCREENS в 08-layouts.

### 6.7 Решение руководителя (06.11) и итоговая схема

### 6.8 Ручной проход перед выпуском (CHECKS §7; облачного e2e в CI нет — запись в `14-app-store`)
На staging или проде, тестовые аккаунты, телефон и веб:
1. Владелец A с компанией, где есть admin B. Сотрудник C (tech) с назначенным выездом и одной оплатой «принял».
2. C: «Мои настройки» → «Удалить аккаунт». Видно «что удалится / что останется». Без кода кнопка неактивна.
3. C получает код, вводит его и слово → «Удалить навсегда». Выход, экран входа, тост «Аккаунт удалён».
4. C пробует войти тем же email по коду → новый пустой аккаунт без компании A. Старых данных не видно.
5. На втором устройстве C (открытая сессия) обновление токена не проходит, данные компании не грузятся.
6. A: «Команда» — C нет. Выезд C — «Удалённый пользователь», в «Требует внимания» «не назначен». Оплата — «Принял: Удалённый пользователь».
7. A пробует удалиться — «последний владелец» нет, есть B → «Передать компанию» B → удаление проходит. B — owner.
8. Компания с одним владельцем без admin: «Закрыть компанию и удалить аккаунт» → компания недоступна всем её людям.
9. В Supabase Dashboard: `auth.users` C — мягко удалён. `public.users` C обезличен. `legal_acceptance` C без IP.
10. Скриншоты шагов 2, 3, 6, 8 — в PR выпуска.
11. После шага 3: в Dashboard у C в `auth.users` — пустые `raw_user_meta_data` (имя, email, телефон, `sub`, `*_verified`) и `auth.identities.identity_data` (если GoTrue их оставил — записать и решить, ревью #214 №3).
12. Функция: `deno check supabase/functions/delete-account/index.ts` (в CI deno нет). Вызов без токена → 401; с токеном нового (асимметричного) ключа подписи `verify_jwt` пускает; `OPTIONS` из браузера (веб-приложение) → 204 с CORS `POST, OPTIONS`.
13. Не проверено тестами: ответ «try again» при конфликте блокировок в `delete_account` и `transfer_ownership` (нужна вторая сессия). На staging — два одновременных удаления двух owner одной компании: один проходит, второй — «try again» или «последний owner».

### 6.12 Решения руководителя по 7а-2b (06.11)
- **Два PR.** (а) `liveAssignees` + `memberName` + `deleted` в repo/types/statusMap/демо, unit, e2e на назначение; (б) экран, `cloud/account.ts`, повтор, e2e 97.
- **Передача компании** — сразу в шаге 3, с подтверждением в шторке «Передать компанию X пользователю Y? Отменить нельзя» (правило 5).
- **Повтор при потерянном ответе** (ревью #214): сервер может ответить 500, хотя данные уже стёрты, или `pending` при уже сделанном soft delete. Приложение после «Удалить навсегда» при 500 / сетевой ошибке / 401 / `auth: "pending"` повторяет `delete-account` (до 3 раз, пауза 1–2–4 с): RPC отвечает `repeat`, функция закрывает вход. Успех — любой ответ `deleted: true`. 401 после первой попытки = вход уже закрыт → тоже успех, если прежде был 500/pending. Не вышло — тост `acct.err.retry` и кнопка «Повторить», не «ошибка навсегда»; при следующем входе — повтор §6.11 п.4. Unit: последовательности ответов (500→repeat, pending→done, 500→401, 400 OD001 — без повтора).
- **Есть активный admin — только передача** (сервер после ревью #214 №2: `transfer the company first`): у такой компании на экране нет «Закрыть компанию», только «Передать компанию»; закрыть можно только компанию без admin. Ошибка → `acct.err.transferFirst`, компания из `detail` подсвечена.
- **Проверка «удалён ли» на старте и при входе (ревью #220).** Только без активных членств (`goneChecker`): с членствами профиль жив, запроса нет. Один вопрос за раз на человека; ответ «да/нет» запоминается, «нет ответа» (сеть, таймаут 8 с) — нет: вопрос повторяется вместе с повтором согласия (возврат в приложение, «online», раз в минуту), согласие спрашивается только после «жив». «Удалён» → сессия скрыта сразу, доудаление и очистка — фоном, приложение не ждёт. Все запросы удаления — с таймаутом (функция 20 с, `users` 8/20 с). Лимит частоты Supabase → `acct.err.rateLimit`. Не стёртое устройство (ошибка хранилища) — в журнал и метка `octo.wipe.pending.v1`, повтор при следующем старте.
- **Испорченная очередь при удалении аккаунта (решение руководителя 11.11.2026, #1014).** Запись `octo.outbox.v1` или `octo.cloud.v1.rejected`, которая не читается как список («broken»), при удалении остаётся на месте, как есть. В ней могут быть операции удаляемого, но разобрать её по владельцу нельзя: стереть целиком — потерять неотправленное другого человека на этом телефоне (правило 6). Такая запись никуда не отправляется и нигде не показывается; следующий вошедший видит экран ошибки хранилища, а «Сохранить копию и продолжить» кладёт её в `octo.broken.*` — этот ключ стирается при следующем удалении аккаунта на телефоне (`DEVICE_PREFIXES`). Это осознанное исключение из «ничего от удалённого не остаётся». Тест: `accountCloud.test.ts` «#1014».
- **Долг владельцу стора (`store.tsx`, `persist.ts`), не 7а-2b:** после очистки и выхода стор в памяти не сбрасывается; `persist.ts` не отменяет 250-мс таймер записи старого ключа при смене ключа; `refresh` не проверяет режим после `await` — в редкой гонке данные компании могут записаться в `octo.db.v5` после выхода.
- **Сделано (#231, #240):** поколение «устройство стёрто» (`deviceGeneration`): отправка, перезагрузка и точка, начатые до стирания, после него ничего не пишут; память сбрасывается до `wipeDevice`; при смене ключа ожидающая запись старого ключа пишется сразу. **Очередь по владельцу:** ключ `octo.outbox.v1` один на телефон, у операции — `owner {userId, companyId}`; отправляет, считает («не отправлено») и отменяет только свои; чужие ждут владельца. **Удаление аккаунта на общем телефоне** убирает из очереди только операции удаляемого (и старые без владельца — как «его»); неотправленное другого человека остаётся в памяти и на телефоне и уходит, когда он войдёт (правило 6; `othersOf`, `src/data/outboxOwner.ts`). По ревью #240: отправка выбирает владельца один раз и шлёт ему же, сменился вошедший — цикл останавливается; операции старых версий получают владельца при первой загрузке очереди (вошедший в тот момент); id удаляемого идёт в сброс памяти и в метку `octo.wipe.pending.v1` (повтор без сессии знает, чьи операции убрать); «не отправлено» на экране удаления — по человеку во всех компаниях (`unsentAll`). Операции старых версий без владельца уходят один раз от того, кто вошёл после обновления (узнать точнее неоткуда; риск — только у телефона, где осталась очередь и сменился человек). Тесты: `persistHook`, `storeSync`, `accountCloud`.
