> Этап 0 принят руководителем 08.11.2026 (вариант Б, 2 PR; T155–T159, e2e 198 и 205, миграция 20261110090000). SUP2-а собран «Лиды и клиенты» №16. ## 2. Брейншторм: что нужно подрядчику
Утром перед работой: «что купить и у кого». Нажал в работе «Заказ поставщику» → черновики по поставщикам, количества уже в упаковках → поправил → «Отправить» (PDF/текст на email или в мессенджер, как удобнее поставщику) → по приезду материалов мастер отмечает «получено».

| Вариант | Плюсы | Минусы |
|---|---|---|
| А. Полный PRD 11: авто-PO при одобрении, RFQ, confirmed, обязательства в job costing, email с нашего домена | всё сразу | почтовый провайдер не настроен (gorix.app только куплен), RFQ — шаг «ИИ»; 4–5 PR |
| **Б. Ручной заказ из работы и без работы, PDF «Поделиться», получение (рекомендация)** | закрывает утро подрядчика; 2 PR; ничего внешнего | авто и RFQ — позже |
| В. Только список «что купить» без сущности | 1 PR | нет статуса «отправлен/получен», нет истории, тупик для job costing |

**Решение — Б.**

## 3. Ядро и модуль (S11b, S11g)
| Что | Где |
|---|---|
| Сущность, статусы, номер `PO-0001`, строки, себестоимость строк (скрытая), получение, PDF на английском, экраны | **ядро** |
| Откуда строки: материалы (`kind = material`) из утверждённого варианта сметы работы (+ выбранные дополнения) или из строк работы без сметы; по `catalog_item_id`, сложено по позиции | **ядро** |
| Пересчёт в упаковки: `⌈кол-во ÷ pack_size⌉` в `purchase_unit`; нет `pack_size` → 1 и пометка «проверьте упаковку» | **ядро**, функция движка `purchasePacks` в общей части (`packages/estimating-engine/src/purchase.ts`, файл «Смет» — согласовать) |
| Группировка по `catalog_items.supplier_id`; без поставщика — черновик «Без поставщика» (выбрать в заказе) | **ядро** |
| Детали «только для закупки» (не в смете клиента) и своё округление модуля | **модуль** через слот |
| **Слот S11g:** `ModuleDef.purchaseLines?: (job: Job, db: DB, data: unknown) => { catalogItemId: ID; qty: string; packed?: boolean; note?: string }[]` (по образцу `checklistTemplates`, `estimateNotes`). Ядро вызывает его у активных модулей при «Заказ поставщику»; строку модуля с той же позицией **заменяет** строку ядра (модуль знает точнее); `packed: true` — модуль уже посчитал упаковки, ядро не делит; `note` — подпись (цвет, ширина) в строку заказа | **ядро** — только тип и вызов |

**Что сделать модулю Gutters (чат «Правки Gutters», не здесь):** реализовать `purchaseLines` (детали `use = purchase` из замера: рулон, заклёпки, крепёж; количества из движка), решить, отдаёт ли он упаковки сам (`packed`) через свой `purchaseQty` или оставляет делить ядру; перенести/переиспользовать `purchaseQty` — его решение. Тест модуля: e2e «замер → заказ поставщику: строки модуля без цен».

## 5. Сущности (SUP2-а, база)
- `purchase_orders`: `id`, `company_id`, `number` (сервер, `PO-NNNN`), `supplier_id` (null = не выбран; отправить нельзя), `job_id` (null = на склад), `status`, `revision`, `fulfillment` (`delivery`/`pickup`), `deliver_to` (текст, по умолчанию адрес работы), `needed_on` (дата), `note`, `print_prices bool`, `sent_at`, `received_at`, стандартные колонки. Снимок поставщика при отправке (`supplier_name`, `supplier_email`, `supplier_phone`, `supplier_address`) — мастер видит, у кого забирать, не читая `suppliers`.
- `purchase_order_lines`: `id`, `company_id`, `po_id`, `position`, `catalog_item_id`, `name`, `supplier_sku`, `note`, `bom_qty` (в единицах расчёта, текст-десятичное), `qty` (упаковки), `unit`, `received_qty`, `check_pack bool`.
- `purchase_order_line_costs`: `line_id`, `company_id`, `unit_cost_cents` (за упаковку, без налога) — только `can_view_costs`.
- Строку убирают через `deleted_at` (у приложения нет DELETE — сторож T52); строки заказа `partially_received` / `received` / `cancelled` не правятся (`t25_po_line_lock`), `received_qty` меняет только `po_receive`. `id` заказа, строки и строки себестоимости не меняются (`t12`).
- Страж `t26_po_guard` (проверка безопасности SUP2-а): новый заказ — всегда `draft`; `received`/`partially_received` ставит только `po_receive`; закрытый заказ (`received`, `cancelled`) не меняется; недопустимый переход из очереди оставляет прежний статус (не отказ — очередь не встаёт). Строки и себестоимость закрытого заказа так же остаются как есть. Снятые все отметки → снова `sent` (переходы `partially_received`/`received` → `sent` только у `po_receive`) — так работает «Отменить» получения. Себестоимость строк читают только owner/admin/office с `can_view_costs`.
- По проверке руководителя #461: номер — своя функция `tg_po_number` (повторное «вставить, если нет» не берёт номер из счётчика), уникальный индекс `(company_id, number)`; охрана отличает приложение от `po_receive` по `current_user`, а не по настройке сеанса; правки строк принимаемого или отменённого заказа — понятный отказ (`hint po_receiving / po_cancelled` → карточка «Сервер отказал»), а не молчание; `po_receive(p_po_id, p_lines, p_row_version)`: получено ≤ заказано (излишек — позже), пустой список — ошибка, устаревшая офлайн-отметка — отказ `po_stale`; **полученный заказ возвращает только офис** (решение руководителя 08.11), мастеру — `po_received_office`. Телефон ведёт `rowVersion` заказа (+1 на сохранение и отметку).
- Номер: `app.next_document_number(…, 'purchase_order', 'PO')` из `tg_po_number` (без правки общего файла). Переходы — строки `app.status_transitions` (`entity_type = 'purchase_order'`), страж — как у других сущностей.
- RLS: чтение — owner/admin/office всех; мастер — заказы своих работ (`app.is_job_assignee`), без цен; sales — нет (В3). Запись — owner/admin/office; мастер — только `public.po_receive(po_id, lines jsonb)` (security definer: мастер работы или офис; `received_qty` 0..∞, статус `partially_received`/`received` по строкам).

## 6. Экраны (SUP2-б)
- **Работа → «Заказ поставщику»** (офис): шторка «Что заказать» — строки-материалы работы по поставщикам с упаковками; «Создать N заказов» → черновики (или открыть существующий черновик этого поставщика по работе).
- **Заказы** (☰ Документы → «Заказы поставщикам», owner/admin/office): `ListCard` — номер, поставщик, работа, статус (draft `neutral`, sent `info`, partially_received `warn`, received `ok`, cancelled `neutral` + слово), «нужно к»; фильтр «Открытые / Закрытые» (`FilterBar`; по каждому статусу — лишнее на телефоне, статус и так на карточке). «Новый заказ» ничего не создаёт до первого «Сохранить» / «Отправить».
- **`/purchase-order/[id]`**: поставщик (выбор, если нет), работа, доставка/самовывоз, адрес, дата; строки (`ListRow` внутри одной карточки: имя, SKU, qty × unit, пометка «проверьте упаковку»; себестоимость — только `costsVisible`); «Добавить позицию» (каталог); «Отправить» (PDF «Поделиться» + статус `sent`, `revision`); «Отменить заказ» (подтверждение); «Получено…» (шторка: по строкам, «Всё получено»).
- **Работа (мастер)**: блок «Материалы» — заказы работы (`ListCard compact`: поставщик, статус, адрес самовывоза), «Отметить получение». Без цен.
- PDF (новый файл `features/poPdf.ts`, раскладка из `docPdf.ts` только чтением): английский; компания, «PURCHASE ORDER PO-0012», дата, поставщик, аккаунт компании у поставщика, работа №, доставка/самовывоз и адрес, строки (SKU, описание, qty, unit), цены — только при `print_prices`.

## 7. Права, офлайн, уведомления
Офлайн: черновик и правки — в очередь; номер — после синхронизации («PO — номер после отправки в базу»). «Отправить» без сети — PDF собирается локально, статус в очереди. «Отменить» 5 с на удаление строки и отмену заказа (правило 5). Уведомлений нет (позже: «материалы получены» офису).
