## 0. Слова основателя (11.11)
«Продумать, как удалять: я не понимаю, как удалять черновики, как удалять сметы и тому подобное. Массовое удаление, отдельное удаление — всё это сделать. И вообще во всём приложении придумать, как удалять карточки по отдельности или все вместе».

Принято основателем 11.11:
1. **Три слова.** «Удалить» — в Корзину, «Отменить» 5 с, вернуть 30 дней. «В архив» — вернуть в любой момент. «Аннулировать» — деньги и подписанное; вернуть нельзя, только новый документ.
2. **Корзина 30 дней**: «Настройки → Корзина», кнопка «Вернуть»; потом скрыто насовсем, а в базе хранится по сроку хранения (#628; 7 лет не подтверждено — значение в одной функции `app.retention_years()`).
3. **Кто**: каждый — свои черновики; чужое и массовое — владелец, админ, офис.
4. **По одной**: «⋯» в карточке объекта → «Удалить»; в списке на телефоне — смахнуть влево (открывается кнопка, удаление только по нажатию + «Отменить»); на компьютере — значок при наведении.
5. **Массово**: «Выбрать» в шапке списка или долгое нажатие → галочки на `ListCard` → полоса «Выбрано N» (Удалить / В архив / Выбрать все); что нельзя — пропускается с объяснением («Удалено 4. 1 нельзя: смета подписана»); «Отменить» 5 с на всю пачку.
6. Причины «нельзя» — простыми словами на языке приложения.

## 3. Брейншторм

### 3.1 Где хранить «что лежит в Корзине»
| Вариант | Плюсы | Минусы |
|---|---|---|
| **А. Только `deleted_at` в каждой таблице**, Корзина читает таблицы по очереди | ничего нового в схеме | 8+ запросов; мастер не видит свои удалённые строки (политики прячут `deleted_at`); нет «кто удалил»; модульные таблицы ядро должно знать по имени |
| **Б. Запись Корзины `trash_entries`** (одна строка на удаление) + `deleted_at` в таблице как сейчас | один список, одна политика доступа, «кто и когда удалил», пачка (`batch_id`), модуль добавляет свой вид строкой реестра; старые телефоны, пишущие `deleted_at`, попадают в Корзину через триггер | новая таблица, триггер на каждой таблице Корзины |
| В. Перенос строки в отдельную таблицу-архив | чистые рабочие таблицы | ломает внешние ключи, ленты, отчёты, старые телефоны; против правила 16 |

**Решение: Б.** `deleted_at` в таблице остаётся единственным признаком «удалено» для всех чтений (старые версии приложения продолжают его понимать); `trash_entries` — журнал для Корзины и прав на «Вернуть». Общий реестр с динамическим SQL по имени таблицы **не делаем** (проверка security-check: внутри `security definer` RLS не работает, у каждого вида свой предикат видимости — `can_read_estimate`, ветки задач, `gutter_sees`, лиды по `assigned_to`; общий код легко пропустит один): у каждого вида свои функции, написанные руками.

### 3.2 Как удаляет приложение
| Вариант | Плюсы | Минусы |
|---|---|---|
| Прямой `update … set deleted_at` из приложения (как сейчас у каталога, фото) | просто | права «свои черновики» и причины «нельзя» придётся дублировать в политиках каждой таблицы; пачка — N запросов |
| **Функция удаления на вид (`public.trash_estimates(ids[])` и т. п.)** → ответ по каждой строке `{id, ok, reason}` | одна проверка прав и причин на сервере; пачка одним вызовом; повтор без вреда; тот же ответ «Удалено 4. 1 нельзя: …» и от сервера | новая функция с `security definer` — тщательный тест прав |

**Решение: функция + страж на таблице.** Сейчас прямой `update deleted_at` обходит любые правила: персонал (и продажи) может «удалить» подписанную смету и вернуть любого клиента, мастер — вернуть свой удалённый лид, расход, чужой замер (security-check, §6.2). Поэтому правила живут **в страже таблицы** (`before update of deleted_at`), а функция — удобный вход для пачки и ответа по строкам. Старые прямые записи `deleted_at` (каталог, фото, замер) продолжают работать и проходят тот же страж (правило 16).

### 3.3 «Выбрать» в списке
| Вариант | Плюсы | Минусы |
|---|---|---|
| **Режим выбора у `ListCard`** (новый проп `picked`, галочка слева, нажатие = отметить) + общая полоса `SelectBar` + хук `useListSelection` | одно правило на все списки; правило 12 соблюдено | правка общего компонента карточек (держит чат «Дизайн системы карточек списков», согласовать) |
| Отдельный экран «Выбрать из списка» | не трогает карточку | ещё один экран, другие фильтры — против «одно правило» |

**Решение: режим у `ListCard`.**

### 3.4 Смахивание на телефоне
| Вариант | Плюсы | Минусы |
|---|---|---|
| **Смахнуть влево → открывается кнопка «Удалить»/«В архив», действие только по нажатию** (как решил основатель) | нет случайных удалений; «Отменить» 5 с | два движения |

## 4. Решение: одно правило на все объекты

### 4.2 Правило «кто» — одно в приложении и на сервере
`canTrash(role, me, kind, obj)` (чистая, `src/features/trash.ts`, модульный тест) и на сервере — функции **по виду**, написанные руками (§6.1):
- Д/Дп — любой объект, для которого слово разрешено таблицей §4.1;
- П/М/С — только **свои черновики** и только то, что видят сейчас (тот же предикат, что в `select`-политике вида);
- «Выбрать» и действия над пачкой — только Д/Дп («массовое — владелец, админ, офис»);
- аннулирование — по таблице (счёт и оплата — только Д).

### 4.3 Причины «нельзя»
Чистая функция `trashBlock(db, kind, id) → reason | null` в приложении и та же проверка в серверной функции вида; коды одинаковые: `signed`, `sentOnce`, `paid`, `card`, `hasDocs`, `done`, `invoiceOpen`, `notYours`, `expired` (в Корзине больше 30 дней), `parentDeleted` («Сначала верните клиента»), `doNotService` («Клиент отмечен „не обслуживаем“» — страж `t44`), `noRight`. «Нет такой строки», «чужая компания» и «нет права» — один ответ `noRight` (не выдаём, что строка есть). Тексты — `trash.why.<код>` в RU/EN/ES простыми словами. Приложение проверяет первым (офлайн), сервер — всегда (старые версии и чужие очереди). Отказ сервера — постоянная ошибка со своим кодом: очередь не встаёт (`CHECKS.md` §9).

## 6. База

### 6.1 Новое (шаг 1 правила 16 — только добавление и сужение)
- **Таблица `public.trash_entries`**: `id`, `company_id`, `kind` (`estimate`, `task`, `expense`, `catalog_item`, `customer`, `lead`; модуль — `gutters.measurement`), `object_id`, `batch_id`, `parent_entry_id` (дети пачки: объекты и люди клиента — в Корзине не показываются, возвращаются с родителем), `deleted_by` (может быть пусто — сервер), `deleted_at`, `restored_by`, `restored_at`. RLS + FORCE; `revoke all … from anon, authenticated`, затем только `grant select`; `select`: Д/Дп — вся компания, остальные — `deleted_by = я`; запись — только функциями и триггером. Уникальный частичный индекс `(company_id, kind, object_id) where restored_at is null` (гонка двух удалений — одна запись). Индекс `(company_id, deleted_at desc)`.
- **Страж `app.tg_trash_guard_<вид>`** (`before update of deleted_at`, и `before insert` со сразу заполненным `deleted_at`), только когда `old.deleted_at is distinct from new.deleted_at` и `current_user = 'authenticated'` (прямая запись с телефона; функции сервера — отмена импорта, склейка, `delete_account`, бэкфиллы — идут мимо): удаление — `can_trash` + `trash_block` вида; возврат — то же + `expired` (запись Корзины старше `app.trash_days()` = 30) + `parentDeleted`. Исключение: каталог — «добавить снова» (`ops.ts:1063`) Д/Дп разрешено и после 30 дней. Флаг через `set_config` не используем — его может поставить любой (`20261109150000_advances_refund_fix.sql`).
- **Запись в Корзину `app.tg_trash_stamp`** (`after update of deleted_at` / `after insert`, `security definer`, `set search_path = ''`, правило 18): то же условие `current_user = 'authenticated'` и `old is distinct from new`; `null → время` — вставить запись (если её нет), `время → null` — отметить `restored_at`. Так в Корзину попадают и старые телефоны, пишущие `deleted_at` напрямую; отмена импорта, склейка и удаление аккаунта — не попадают (их «Вернуть» обошло бы `ImportJob undone`).
- **Сужение политик** (шаг 1 разрешает — старые телефоны удалённое и так не читают, `repo.ts:123`): ветки мастера/автора в `select` лидов, расходов, задач, замера (`gutter_sees`) и каталога для не-персонала — `and deleted_at is null`. Свои удалённые им показывает только `trash_list`.
- **Функции по виду** (`security definer`, `set search_path = ''`, `auth.uid()` обязателен — без пользователя отказ, роль и компания внутри, id только через параметры): `public.trash_estimates(ids uuid[])`, `trash_tasks`, `trash_expenses`, `trash_catalog_items`, `trash_customers`, `trash_leads` → `table(id uuid, ok bool, reason text)`; повтор без вреда (уже удалённое → `ok`); `ids` не больше 500. `batch_id` делает **сервер** (одна на вызов), клиент его не присылает. Модуль — своя `public.gutters_trash_measurements` в своей миграции (ядро имени таблицы модуля не знает) и проверка `module_active`.
- **`public.trash_restore(entry_ids uuid[])`** → `table(id, ok, reason)`: каждая запись проверяется отдельно (компания, право, `deleted_by` для не-Д/Дп, 30 дней, родитель); дети возвращаются только свои (`parent_entry_id` этой записи), не всё, что удалено в то же время. Возврат вида модуля — через его функцию.
- **`public.trash_list(company uuid, kind text default null)`** — `is_member` и роль; записи ≤ 30 дней без `parent_entry_id`; имя объекта (клиент, номер сметы) читается из таблицы в момент запроса и отдаётся **только если предикат видимости вида верен сейчас** (мастер, снятый с работы, имени не видит); имена не копируются в Корзину — нет второй копии личных данных (CCPA). Виды модулей отдаются, только если модуль включён.
- **Архив**: `estimates.archived_at` (новое), лиды — `archived_at` (есть); `public.archive_estimates/leads(ids, on bool)`.
- **Аннулирование**: `public.void_invoice(id, reason)`, `public.void_payment(id, reason)` — обёртки над стражами `tg_invoice_guard`/`tg_payment_guard` (без пользователя стражи роль не проверяют — обёртка отказывает при `auth.uid() is null`); `public.cancel_job(id, reason)`; `public.withdraw_estimate(id, reason)` (статус `voided`: check `estimates_status_check`, переходы `sent/viewed/expired → voided`, `portal_estimate`/`portal_accept`).
- **Страж на `jobs → cancelled`**: сейчас продажи отменяют работу прямым `update status` без проверки оплат (`core.sql:1625`, grant `20261107040000_jobs_write_rights.sql:86`). Новый страж: только Д/Дп, без оплат, Дп — без счёта. Старые телефоны работу не отменяют — ничего не ломается.
- Правило 18: каждая новая функция — `revoke all … from public, anon`, `grant execute … to authenticated`; функции стражей — `revoke all … from public, anon, authenticated` (T52).

### 6.2 Права (сервер — главный)
- Д/Дп — любой объект вида; П/М/С — только свои черновики и только видимое сейчас.
- Восстановить может тот, кто мог удалить; П/М/С — только записи `deleted_by = я`.
- Чужая компания, нет строки, нет права — один ответ `noRight`.
- Счёт и оплата: `DELETE` по-прежнему запрещён `tg_forbid_delete`; в Корзину не попадают никогда.
- Возврат клиента «не обслуживаем» — страж `t44_no_service_guard` (`20261106050000_do_not_service.sql:63`) считает возврат новым: функция ловит отказ и отвечает причиной `doNotService`, не падает.
- Отправленная смета в Корзину не попадает (только черновик без отправки) — живой ссылки `/p/` у удалённого нет.
- Долг: step-up `aal2` для void (`08-security.md` §3) — когда появится MFA; записать задачей.

### 6.3 Офлайн и очередь
- Удаление: стор сразу ставит `deletedAt` у объекта (объект исчезает из списков), кладёт операцию `trash.items {kind, ids}` в очередь; «Отменить» в 5 с вынимает её (как сейчас, `outboxTiming.ts`). Ответ сервера с `ok=false` по строке — объект возвращается в список, тост «1 нельзя: …» (не «Ошибка синхронизации»).
- Восстановление: операция `trash.restore {entryIds}`; объект возвращается локально сразу, если он есть в сторе, иначе — после ответа и подтягивания строки.
- Повтор операции без вреда.
- Старые телефоны: читают `deleted_at is null` — восстановленный объект у них появляется при следующем обновлении, удалённый — пропадает. Новых операций они не шлют; их прямые записи `deleted_at` проходят страж. Старая версия, увидев новый статус сметы `voided`, должна не упасть — тест «неизвестный статус» (как `paymentShown`).

### 6.4 Срок хранения
- 30 дней — `app.trash_days()` (одна функция, как `retention_years`).
- После 30 дней — только скрыто; стирание строк по `app.retention_years()` — задача 7а-3 / #628, **не в этой спеке** (нужно слово юриста о сроке).
