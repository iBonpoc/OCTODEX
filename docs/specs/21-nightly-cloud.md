# 21. Ночные сценарии против настоящего Supabase и контракт по живому каталогу

«Каркас приложения» №6, 06.11.2026. Задача руководителя: `docs/ai/CHECKS.md` §3а «Осталось». Клетка карты: `docs/15-story-map.md` §8 (тесты), стыки S0, S22. Статус: этап 0 принят руководителем №4 (07.11); PR-1 — дамп каталога, T64, serverCatalog.

## 1. Стыки
- **S0** (компания → документы): сценарий «лид → смета → счёт → оплата» идёт в облачном режиме, номера `EST-/INV-/RCT-` ставит настоящий сервер.
- **S22** (удаление аккаунта): настоящая edge-функция `delete-account` (verify_jwt) → `public.delete_account` → вход закрыт. Сейчас это проверяют только db T50/T57, модульные тесты и ручной проход 19 §6.8. Сценарий закрывает автоматическую часть §6.8, ручной проход на staging остаётся.
- Связка «приложение ↔ сервер» (`serverContract`). Сейчас её сверяют с текстом миграций. Нужно сверять с тем, что реально лежит в базе.

## 5. serverContract по pg_proc
- `run.sh`: если задан `CATALOG_OUT` (запрос — `supabase/tests/catalog.sql`), после миграций пишем JSON, отсортированный, чтобы дамп был стабильным. Для каждой функции `public.*`: имя, входные аргументы (`proargnames`/`proargmodes`), `pronargdefaults`, `has_function_privilege('anon'|'authenticated', oid, 'EXECUTE')`. Для таблиц и видов `public.*`: права anon и authenticated (select/insert/update — `has_any_column_privilege`: `has_table_privilege` не видит грантов на колонки, например `grant select (id, …) on invitations`; первый прогон дал ложную тревогу именно на нём), RLS.
- Новый `apps/mobile/test/serverCatalog.test.ts` берёт вызовы приложения через `appCalls` из `serverContract.test.ts` и сверяет их с JSON: функция есть, ключи подходят к одной из сигнатур, у authenticated есть EXECUTE, а anon не получил лишнего. Отдельно проверяется список «намеренно для anon» (`portal_*`).
- Нет JSON: локально тест пропускается (остаётся статический). В CI при `CATALOG_REQUIRED=1` тест **падает**: сторож не должен молча пропускаться.
- Фикстура, которая падает: `test/fixtures/catalog.bad.json` с 4 ошибками (опечатка в параметре, пропущен обязательный, нет EXECUTE у authenticated, лишний EXECUTE у anon). Тест ждёт ровно эти 4.
- **T64** (core_rls): функция без grant → `has_function_privilege('authenticated')` = false. Заглушка не раздаёт прав, которых нет в Supabase.
- Статический `serverContract.test.ts` остаётся: он быстрый и работает локально без Postgres.

## 7. Права, офлайн
Ключи локального стека публичные (те же для всех, кто запускает `supabase start`), секретов в CI нет. Job ничего не пишет в боевой проект. `config.toml`: добавляются только локальные секции (`[auth] site_url`, `[edge_runtime]`). `release.yml` делает `db push`, а не `config push`, поэтому боевые настройки auth не меняются. Это проверю перед PR.

## 8. Ночной job и сигнал
Job `cloud` в `checks.yml`: `if: schedule || workflow_dispatch`, `timeout-minutes: 30`. Шаги: setup-cli → `supabase start` → seed → прогрев функции (401 без JWT) → cat → api-1, api-2 → сборка `dist-cloud` → 102–104. Если упало, в артефакт идут скриншоты и `docker logs` auth/rest/edge. `nightly-alert` получает `needs: [checks, cloud]`, условие `failure()`, текст issue называет упавший job. Job `checks`: `cloud` = skipped допустимо, кроме ночного запуска.

## 9. Тесты
e2e 102, 103, 104 (cloud); api-1, api-2; cat; unit `serverCatalog.test.ts` + фикстура, которая падает; db T64. Проверка на ветке: `workflow_dispatch` по ветке. Полный ночной прогон считается зелёным после первой ночи на `main`.
