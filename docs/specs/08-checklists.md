# 08. Шаблоны чек-листов — спецификация OCTODEX

> v1, 05.11.2026, **одобрено основателем 05.11** (жёлтая карточка в «Требует внимания» до «Просмотрено» — §8). Шаг хребта 7 «Выполнить» (`docs/15-story-map.md` §3, строка 7; `10-build-plan.md` §0 п. 14). Шаблон — §7 карты.
> Запрос основателя 05.11 (памятка чата клиентов 05.11 §3.4; памятка удалена 07.11, открытое перенесено в `docs/ai/LOG.md`): «зашёл в выезд, там чек-лист… как это устроено и где это настраивается директором или диспетчером?». Сейчас чек-лист тестовый и одинаковый у всех (`seed.ts` `jobChecklist`), новые выезды создаются с пустым (`store.tsx`: `checklist: []`).
> Источники: код сборки 52 (`app/visit/[id].tsx`, `features/visits.tsx`, `techDay.ts`, `types.ts` `ChecklistItem`, `Photo`), база (`visits.checklist_template_id` — колонка есть, таблицы шаблонов нет), PRD `03-prd/07-jobs-schedule.md` (JOB-US-08, MVP: «1–3 шаблона от модуля Gutters»).
> Estixa не разбиралась: в ней нет чек-листов выезда.

Что входит: директор настраивает шаблоны; шаблон сам попадает в выезд по услуге или виду выезда; обязательные пункты; фото «до» и «после»; диспетчер правит пункты конкретной работы; мастер отмечает.
Что не входит: числовые и текстовые ответы, подпись под пунктом, условия «если — то» (позже); чек-лист AB5 у субподрядчика (другая сущность, PRD 07 JOB-US-23).

## 1. Стыки

| Стык (§4 карты) | Что приходит / уходит | Что делает чек-лист |
|---|---|---|
| **S4** лид → осмотр | создаётся `Visit` осмотра | получает шаблоны вида «Осмотр» (снимок) |
| **S9** работа → расписание | создаётся `Visit` работы | получает шаблоны «Каждый выезд» + шаблоны услуг из выбранного варианта сметы (снимок, без дублей) |
| **S10** визит выполнен | шаги визита; работа → `done` | обязательные пункты и фото не закрыты → предупреждение со списком, «Заполнить» / «Пропустить»; пропущенные остаются в ленте |
| Каталог → шаблон | позиция каталога (услуга) | шаблон привязан к услугам каталога |
| Визит → история клиента и объекта | — | фото «до/после» и отметки (кто, когда) видны в ленте работы и объекта |

Правило снимка: в выезд копируются пункты шаблона на момент создания выезда. Правка шаблона потом **не меняет** прошлые и уже созданные выезды (только новые). Так история честная: видно, что именно мастер должен был сделать в тот день.

## 2. Сравнение и решения

| Тема | Сейчас у нас | Jobber / HCP / ServiceTitan | Решение | Почему |

| Обязательные пункты | все пункты блокируют подпись (код сейчас) | у всех есть «required» | Пункт обязательный или нет — отметка у пункта. Новый пункт по умолчанию **обязательный**. | Пункт-фото | нет | есть | Вид пункта: **отметка** или **фото** (пункт закрывается, когда к нему приложено фото) | «Сфотографировать уклон» нельзя проверить галочкой |
| Язык пунктов | английский тестовый | Jobber: один текст | Один текст, как написал директор. Перевод для мастера — позже (вопрос В3) | Директор пишет на языке своей бригады |

## 3. Сущности и поля (✚ — новое)

### 3.1 ✚ `ChecklistTemplate` (база ✚ `checklist_templates`)
`id`, `companyId`, `name`, `items: TemplateItem[]`, `appliesTo: { everyVisit: boolean; visitKinds: ("estimate" | "work")[]; catalogItemIds: ID[] }`, `minPhotosBefore?`, `minPhotosAfter?` (поднимают минимум компании), `module?` (стартовый модуля), `archivedAt?`, служебные поля.
`TemplateItem`: `id`, `label`, `kind: "check" | "photo"`, `required: boolean`, `hint?` (подсказка мастеру).

### 3.2 `ChecklistItem` в выезде (изменение `types.ts`)
Сейчас `{ id, label, done }`. ✚ `kind`, ✚ `required`, ✚ `templateId?`, ✚ `hint?`, ✚ `doneBy?`, ✚ `doneAt?`, ✚ `na?: { reason: NaReason; text?: string }`, ✚ `photoIds?: ID[]` (для пункта-фото).
`NaReason` (необязательна при пропуске): `not_on_site` (этого нет на объекте) · `client_refused` (клиент отказался) · `unsafe` (небезопасно) · `other`. Поле `na` = «пропущен».
База: ✚ `visit_checklist_items` (строки, а не json в выезде — чтобы отметку мастера и правку офиса можно было синхронизировать по одной строке без конфликтов) + существующая `visits.checklist_template_id` не используется (у выезда может быть несколько шаблонов; поле `template_id` у строки).

### 3.3 ✚ `Company.visits`
`photosBeforeRequired: boolean` (вкл.), `photosAfterRequired: boolean` (вкл.), `minPhotosBefore: 1`, `minPhotosAfter: 1` (раздельно для «до» и «после», 1..20). База: ✚ `companies.visit_settings jsonb`.

### Не заводим
- Числовые / текстовые ответы, выбор из списка, подпись под пунктом — позже (PRD 07 `kind` check/photo/text/number: начинаем с двух).
- Версии шаблона — вместо них снимок в выезде (§1).
- Отдельный шаблон на мастера.

## 4. Статусы и переходы

Новых статусов нет (§5 карты не меняется). Вычисляемое правило — одна чистая функция:

`checklistGate(visit, companySettings) → { canStartWork, canSign, missing: { items: ID[]; photosBefore: number; photosAfter: number } }`

| Шаг визита | Условие перехода | Подсказка, если нельзя |
|---|---|---|
| `on_site → working` | фото «до» ≥ минимума (если обязательно) — иначе предупреждение «Нет фото до работы» + «Сделать фото» / «Пропустить» | — |
| `working → signed` (подпись клиента) | все обязательные пункты отмечены или сфотографированы; фото «после» ≥ минимума — иначе шторка «Не заполнено: N» со списком (нажатие — к пункту) и кнопками «Заполнить» / «Пропустить» | «Пропустить» помечает незаполненные как пропущенные и пускает дальше |
| работа → `done` (S10) | все выезды работы дошли до подписи (пропуски не мешают, видны в ленте) | — |

Ничего не запирается: правило только решает, показать ли предупреждение (решение основателя 05.11). Выполнен = `done`. Пропущенный (`na`) — **не выполнен**: мастер прошёл дальше, но пункт остаётся «не сделан» в истории, на карточке и в «Требует внимания». Фото «до» и «после» — так же (решение основателя 05.11). Снять отметку можно до подписи клиента; после подписи пункты только для чтения (отметка — в ленте).

## 5. Как приходит / как уходит

**Шаблон приходит:** «+ Новый шаблон» в настройках; копия существующего; модуль (стартовые при включении модуля).
**В выезд приходит:** при создании выезда (S4, S9) — одна функция `checklistFor(visit, job, estimate, templates)`: «Каждый выезд» → по виду → по услугам выбранного варианта сметы (по `catalogItemId` строк) → без дублей по `id` пункта шаблона; порядок — как в этом списке. Уже созданные выезды без пунктов — кнопка «Добавить из шаблона» в карточке выезда (офис, директор).
**Уходит:** отметки и фото — в ленту работы и объекта; фото «до/после» — на страницу клиента (если включено, шаг «После работы»).

## 7. Экраны

### 7.1 «Чек-листы» (список шаблонов)
Карточки (`CardList` + `ItemCard`): имя, «N пунктов · M обязательных», к чему привязан («Каждый выезд» / «Осмотр» / «Услуги: Установка guards, +2»), метка модуля. «+ Новый шаблон» — акцент. Архив вместо удаления (+ «Отменить» 5 с). Пусто: «Создайте список того, что мастер делает на каждом выезде».

### 7.2 Шаблон
Сверху вниз: имя · «Когда добавлять» (Каждый выезд — переключатель; Вид выезда — Осмотр / Работа; Услуги — выбор из каталога шторкой, строками) · пункты (строка: текст, вид «отметка/фото», переключатель «Обязательный», перетаскивание порядка; «+ пункт») · минимум фото до/после (если выше компании).

### 7.3 Выезд мастера (`/visit/[id]`, изменение)
Пункт: значок вида, текст, подсказка, «Обязательный» (слово + значок `warn`, пока не закрыт). Нажатие — отметить (зона 44). Долгое нажатие / «…» — «Пропустить» (причина по желанию). Пункт-фото открывает камеру, фото прикрепляется к пункту и попадает в «до» или «после» по шагу визита. Сверху счётчик «Осталось обязательных: N». Кнопка следующего шага всегда активна; если что-то не заполнено — шторка «Не заполнено: N» со списком и кнопками «Заполнить» / «Пропустить».

### 7.4 Карточка работы / выезда (офис, директор)
Блок «Чек-лист»: пункты, откуда пришли (имя шаблона мелко), «+ пункт», «Добавить из шаблона», убрать необязательный (обязательный — только директор). Только до начала выезда (`scheduled`, `en_route`).

390 — один столбец; 820/1280 — пункты в две колонки в выезде мастера не нужны (один столбец по центру), шаблон — список слева, редактор справа. Цвета — только статусы: warn «не закрыт обязательный», ok «всё закрыто», neutral — необязательные.

## 8. Права, офлайн, уведомления

| Действие | Директор | Офис | Мастер |
|---|---|---|---|
| Шаблоны: создать, изменить, архив | ✓ | ✓ (решение основателя 05.11) | — |
| Настройки фото | ✓ | — | — |
| Пункты конкретной работы: добавить, убрать необязательный | ✓ | ✓ | — |
| Убрать обязательный пункт у работы | ✓ | — | — |
| Отметить, пропустить, фото | ✓ | ✓ | ✓ (свои выезды) |

База: `checklist_templates` — писать `owner/admin/office`; `visit_checklist_items` — вставка и удаление `owner/admin/office`; изменение отметки — назначенный мастер (`app.is_visit_assignee`) или офис; мастер не может менять `label`, `required`, удалять (триггер). Миграция начинает с `revoke all … from anon, authenticated`.
Офлайн: всё, кроме правки шаблонов, работает без сети; снимок шаблонов лежит на телефоне мастера вместе с выездом.
Уведомления и «Требует внимания» (решение основателя 05.11):
- Выезд закончен, а обязательные пункты или фото не сделаны → **одна карточка на выезд** в «Требует внимания»: «{Клиент} · выезд {дата}: не сделано 2 обязательных, нет фото после».
- Цвет **warn** (жёлтый, значок + слово «Не сделано»), не красный: красный остаётся за деньгами и просрочкой.
- Карточка висит, пока директор или офис не нажмёт **«Просмотрено»** (с «Отменить» 5 с) или пока пункты не доделают (мастер может доделать позже, например дослать фото).
- После «Просмотрено» карточка уходит из «Требует внимания»; в истории работы и на карточке выезда пункты остаются «не сделаны».
- Само по времени не исчезает: пропуск должен увидеть человек.
- `attention.ts` — файл общий: правку делаю отдельным маленьким PR после сообщения руководителю.

### 10.1 Интерфейс для экрана выезда

Экран выезда только **читает** и **вызывает мутации**; правила считают чистые функции из `src/features/checklist.ts` (мой файл).

Что читает:
```ts
// src/data/types.ts (изменение — моим маленьким PR после сообщения ведущему чату)
type ChecklistItemKind = "check" | "photo";
type NaReason = "not_on_site" | "client_refused" | "unsafe" | "other";
interface ChecklistItem {
  id: ID; label: string; done: boolean;           // как сейчас
  kind: ChecklistItemKind;                         // старые пункты читаются как "check"
  required: boolean;                               // старые пункты читаются как true (как ведёт себя код сейчас)
  hint?: string; templateId?: ID; templateName?: string;
  doneBy?: ID; doneAt?: string;
  na?: { reason: NaReason; text?: string; by: ID; at: string };
  photoIds?: ID[];                                 // id из visit.photos (пункт-фото)
}
// Visit.checklist: ChecklistItem[] — без изменений по имени

// src/features/checklist.ts
function checklistGate(visit: Visit, settings: VisitSettings): {
  warnBeforeWork: boolean;                         // on_site → working: показать предупреждение (не запрет)
  warnBeforeSign: boolean;                         // working → signed: показать предупреждение (не запрет)
  missing: { items: ID[]; photosBefore: number; photosAfter: number };
};
function itemDone(item: ChecklistItem): boolean;   // только done; пропущенный (na) — не сделан
function visitMissed(visit: Visit): { items: ID[]; photosBefore: number; photosAfter: number }; // для карточки выезда и «Требует внимания»
// мутация офиса: reviewVisitMissed(visitId: ID): Undo — «Просмотрено», убирает карточку из «Требует внимания»
function visitSettings(db: DB): VisitSettings;     // настройки компании с умолчаниями
```

Какие мутации стора вызывает (`store.tsx`, все возвращают `undo`, работают офлайн):
```ts
checkItem(visitId: ID, itemId: ID, done: boolean): Undo;
skipItems(visitId: ID, itemIds: ID[], reason?: NaReason, text?: string): Undo; // «Пропустить» в предупреждении (все незаполненные) или у одного пункта
attachItemPhoto(visitId: ID, itemId: ID, uri: string): Undo; // кладёт фото в visit.photos (kind по шагу визита) и id в item.photoIds
// офис/директор, до начала выезда:
```
