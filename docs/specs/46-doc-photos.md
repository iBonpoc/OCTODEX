## 0. Итог

1. **Сейчас фото нет ни в одном документе клиенту** [код]: ни в PDF сметы и счёта, ни на `/p/`. Листы-вложения (`EstimateDoc.pages`, `features/docPages.ts`) — только векторные примитивы, без картинок. Это сделано намеренно, ради безопасности `/p/` (`docPages.ts:5–10`).
2. **Ядро (волны сейчас)** — две вещи:
   - **фото к строке сметы** (до 4 на строку, как у Joist, §2);
   - **блок «Фото» уровня документа** (галерея «до/после» без жестовой обрезки).
   Предложить фото замера или выезда **этого** клиента. Фото видны в PDF и на `/p/`.
3. **Расширения Р1–Р6** (фотоотчёт к счёту, блок оплат и QR, шаблоны фото по направлению, обрезка «до/после» жестом, свои стили PDF, сетки) — **решение основателя 15.11** (цитата §1а; руководитель подтвердил аудиту №2). Они идут волнами после ядра; порядок волн определяет общий план (§11).
4. **Фото в смете — часть подписанного**: фото строк и блоки лежат в `calc_inputs` версии. Значит, они входят в отпечаток версии — `content_hash` версии (спека 49 §4.2; было `document_hash = sha256(calc_inputs || version_id)`) (`20261105240000_estimate_countersign.sql:298`) и под замок `tg_estimate_version_lock` (`20261104000000_core.sql:739`) [код]. Правка после отправки — новая версия и новая подпись (README §9 п.11).
5. **Главные риски `/p/`** (security-check, §5):
   - офис может перезаписать уже загруженный объект [код];
   - чужое фото можно вписать по `fileId`;
   - запасной путь `shrinkPhoto` оставляет в файле EXIF/GPS [код].
   Все три закрываются до показа фото на `/p/`.
6. **Порядок с направлением Г — построчно** (§10): PR-0 (`taken_at`) → Ф-0 (EXIF) → Ф-1 (постоянная папка) → Ф-2 (показ из облака) → Д-1…

## 3. Сущности и поля (ядро)

### 3.1. Варианты модели
| Вариант | Как | Плюсы | Минусы |
|---|---|---|---|
| **А. В версии документа** (выбор) | `EstimateDoc.linePhotos: Record<lineId, DocPhotoRef[]>` и `EstimateDoc.blocks: DocBlock[]` в `calc_inputs` | входит в `content_hash` версии (спека 49 §4.2) и под замок версии без новых механизмов [код]; движок денег (`CustomLine`) не трогаем | проверка дважды — на телефоне и в базе (как у `docPages`) |
| Б. Связи у файла (`files.estimate_id/line_id`) | колонки файла | просто | вне версии: после подписи можно поменять; старые сборки не знают |
| В. Поле в `CustomLine` (движок) | `line.photos` | рядом со строкой | лезет в денежный пакет, `templateLine` и фильтр строк `/p/` (`20261113020000_estimate_terms.sql:153`) копировали бы фото клиента в шаблоны |

Решение — **А** [вывод]. Фото строки не копируются в шаблон сметы: id строк шаблона новые (`estimateTemplate.ts` `templateLine`, `uid()`) [код], значит фото клиента в шаблон не попадут.

### 3.2. Тип (ядро, `features/docPhotos.ts` — рядом с `docPages.ts`)
```ts
type DocPhotoRef = { fileId: ID; sha256: string; caption?: string /* ≤ 120 */ };
type DocBlock = { id: ID; t: "photos"; title?: string; layout: "auto" | "pairs"; photos: DocPhotoRef[] };
// EstimateDoc: linePhotos?: Record<lineId, DocPhotoRef[]> (≤ 4 на строку); blocks?: DocBlock[]
```
- Только скаляры; текст — через `esc()`. Сервер чистит функцией `app.doc_photos(jsonb)`, как `app.doc_pages`. Запись сверх пределов — **отказ, а не обрезка** (`docPages.ts:9–10`).
- Пределы [допущение, уточнить на Д-1]:
  - на строку — 4 фото (как у Joist);
  - на документ — 100 фото; число основателя «любое» здесь ограничено размером PDF (§4.4);
  - блоков — 10;
  - подпись — 120 символов.
- **`sha256`** — отпечаток байтов файла. Его считает телефон перед отправкой; сервер **пересчитывает** его сам при `uploaded` (значению телефона не верит — спека 49 §4.2) и хранит в `files.sha256` (новая колонка, правило 16, шаг 1). Подпись клиента покрывает и сами байты.
- Что проверяет триггер версии (`app.doc_photos_problem`, как `app.doc_pages_problem`):
  - тот же `company_id`, `kind='photo'`, не удалён на момент записи;
  - `reencoded = true` (§5.3);
  - файл того же клиента, объекта или работы, что и смета;
  - автор правки может читать файл (`app.can_read_file_object`).
  Иначе — отказ.
- «До/после» в ядре — раскладка `pairs`: фото идут парами, обе ячейки одного формата 4:3, кадр — по центру (`object-fit: cover`), без ручной рамки. Рамка жестом — расширение Р3.

## 4. Вёрстка

### 4.1. Как сейчас [код]
- Один каркас `docPage()` для сметы, счёта и квитанции (`docPdf.ts:66–119`):
  - шапка: логотип `data:image/…` и реквизиты компании;
  - тело;
  - подвал `position: fixed`.
- Три вида документа: `print.styles` classic / modern / compact. В смете шрифт не мельче 10 pt (`print.contract`, спека 41).
- Порядок сметы (`estimatePdf.ts:120–132`):
  1. «Для кого»: имя, **адрес объекта**, телефон, почта;
  2. варианты: таблица строк и итоги;
  3. Notes, затем Terms;
  4. «одобрено»;
  5. право отказа и подписи (`.signoff`, `break-inside: avoid`);
  6. запись подписи;
  7. листы-вложения (`break-before: page`).
- **Перенос:** у `tr` нет `break-inside: avoid`, у `h2` нет `break-after: avoid`. Строки рвутся где угодно, и заголовок может остаться внизу листа один [код; на устройстве не проверено].
- Телефон: `Print.printToFileAsync({ html })` без размера листа → Letter 612×792 [док: docs.expo.dev/versions/latest/sdk/print, `FilePrintOptions`]; поля — `@page { margin: 14mm }`.
- Веб и `/p/`: `iframe`, затем `print()` через **250 мс** (`estimatePdf.ts:144–162`). Незагруженная картинка в PDF не попадёт [вывод], поэтому перед печатью ждём `img.decode()` всех фото.
- Рабочие чертежи Gutters печатаются своим путём (`savePdf.ts:13`: свой лист и нулевые поля) — спеку они не затрагивают [код].

### 4.2. Место в документе
- **Фото строки** — под названием и описанием строки: ряд до 4 миниатюр с подписями. Строка с фото — `tr { break-inside: avoid }`: она короче листа всегда, потому что 4 миниатюры занимают один ряд.
- **Блок «Фото»** — после итогов вариантов, до Notes. Блоки переставляются через «⋯ → Переместить выше / ниже» (DS §14.6). В отправленной версии блоки не двигаются.
- `.signoff` остаётся целым, фото его не разрывают.

### 4.3. Сетка и переносы (PDF Letter)
Ширина текста: 8,5″ − 2×14 мм ≈ **532 pt** [вывод, расчёт].

| Что | Раскладка | Ячейка ≈ (зазор 8 pt) |
|---|---|---|
| фото строки | до 4 в ряд, 4:3 | 72 pt |
| блок `auto` | по 3 в ряд, 4:3; последний ряд — по левому краю | 172 pt |
| блок `pairs` | 2 в ряд, пара = ряд, 4:3 | 262 pt |

Правила переноса:
- ряд фото с подписями не рвётся (`break-inside: avoid`); блок рвётся только между рядами;
- заголовок блока не остаётся один внизу листа (`break-after: avoid`);
- пара «до/после» никогда не рвётся.

`tr`/`h2` во **всех** документах (не только с фото) меняются отдельным PR DS со снимками «было/стало» трёх видов (design-reviewer №6).

### 4.4. Картинка для печати и размер PDF
- В PDF фото **встроены** (`data:image/jpeg;base64`, как логотип). Ждёт ли `expo-print` удалённые картинки — **[не проверено]**.
- Копию для печати делает телефон при сборке PDF:
  - длинная сторона: 1200 px для блока, 400 px для фото строки, 800 px, если в документе больше 24 фото [допущение];
  - JPEG 0,7.
- **Размер** [допущение, не измерено]:
  - фото блока 1200 px ≈ 150–250 КБ, фото строки 400 px ≈ 25–40 КБ;
  - base64 добавляет ~33 %;
  - 40 фото × 200 КБ × 1,33 ≈ 10,6 МБ — уже у порога 10 МБ.
- **Правило при превышении:**
  - собираем HTML и меряем его (`jsonbTextBytes`-подобно);
  - если больше `PDF_MAX` (10 МБ [допущение]), копии пересжимаются ступенями 800 → 600 px;
  - если и так не влезло — шторка «PDF большой (N МБ). Отправить ссылкой на страницу клиента?» с кнопками «Ссылка» / «Всё равно PDF».
  Тест ТД7.
- **Порог приёмки на iPhone (правило 27)**, проверка до влития Д-1:
  - PDF с 8 фото собирается ≤ 5 с и весит ≤ 3 МБ;
  - PDF с 40 фото собирается ≤ 15 с и весит ≤ PDF_MAX.
  Числа [допущение] — замерить и записать в PR.

### 5.3а. Сжатие: способы по порядку, оригинал не уходит (#1558, вариант В)
Решение основателя 15.11: вариант В с условиями (README §12 п.21). Фото загружается всегда, «не с первого, так со второго раза». Оригинал с EXIF и GPS из телефона в облако **не уходит никогда**. Человек видит, что происходит и что сделать, без слов «не удалось», «ошибка», «сбой».

**Сейчас [код].** `shrinkPhoto` (`data/photoShrink.ts:58–62`) при любом сбое возвращает `img.uri`, то есть оригинал. Он попадает в стор, в очередь и в облако.

**Где вызывается.** Одна функция `prepareForCloud` в `data/photoShrink.ts` (бывшая `shrinkPhoto`). Её зовут:
- `features/PhotoStrip.tsx` — фото выезда и замера Gutters;
- `nav/Fab.tsx` — «＋ → Фото»;
- `app/expense/new.tsx` — чек расхода (#1538).

**Исключение — фото замера Gutters** (решение руководителя 15.11, вариант А). У фото замера своё хранилище и своя операция модуля. В #1558 `PhotoStrip.onAdd` принимает только перекодированный файл, а фото «готовится» идёт отдельным `onAddPreparing`. У Gutters `onAddPreparing` нет. Поэтому фото замера при сбое не добавляется, а человек видит тост «Фото не добавилось — добавьте его снова» (`photoUp.prep.notAdded`). «Готовится» для фото замера — задача #1698.

**Сделано в #1558 и что осталось.**
- «Повторить» (#1431) тоже сначала заново собирает файл (`retryPhoto` → «готовится» → раунд → `photo.retry`). Фото, которое старая сборка сохранила как есть, уходит только перекодированным.
- Раунды повтора: при запуске и раз в минуту, пока приложение открыто. Каждое фото — не чаще раза в 10 минут, после 5 раундов — раз в 2 часа (`data/photoPrepare.ts`).
- Экран выезда (`app/visit/[id].tsx`, v2) подключён: «＋ → Фото» (лист камеры), ленты «до» и «после», «не на месте» — фото «готовится» остаётся на телефоне. Фото пункта чек-листа и чек нового расхода тоже подключены.
- Осталось: «Подготовить снова» для чека «не открывается» (в «Деньгах» его пока нет); фото замера Gutters при сбое не добавляется (#1698), его «Повторить» файл заново не собирает; на вебе оригинал «готовится» живёт до перезагрузки страницы.

**Способы по порядку.** Каждый способ собирает файл заново, и метаданные не переносятся. Подтверждается проверкой Ф-0 на iPhone, правило 27. Если GPS останется — вырезать явно, отдельной правкой до влития.

| № | Способ | Где | Попыток | Почему поможет |
|---|---|---|---|---|
| С1 | `ImageManipulator`: длинная сторона до 2048, JPEG 0.7 — как сейчас | все | 2, вторая — сразу, новым контекстом | [допущение] на телефоне сбой чаще всего от памяти, и повтор через миг проходит. Причину каждого сбоя телефон записывает (см. ниже) |

| С3 | браузер: `createImageBitmap` → `canvas` (до 2048) → `toBlob("image/jpeg", 0.7)` | только веб | 1 | другой декодер; холст метаданных не несёт |

**Ни один не сработал — фото «готовится».**
- Фото не теряется. Оно остаётся на телефоне с локальным адресом оригинала, со своей плиткой и в счётчиках выезда или расхода.
- Отметка — та же `Photo.upload` из #1431: `failed: "preparing"`. Для чека — `Expense.receiptFailed: "preparing"`. Параллельной отметки нет.
- В облако идёт только строка `files` (`photo.add` без `uri`, `expense.add` без `receiptUri`). Байтов нет, оригинал не отправляется.
- **Повтор сам.** При каждом запуске приложения и каждом проходе очереди с сетью телефон снова проходит С1–С3 для фото с «готовится».
  - Получилось: новый файл заменяет локальный адрес, отметка снимается. В очередь встаёт загрузка байтов: `photo.retry` для фото; для чека — новая операция `file.send {id, uri}`, той же `uploadPhoto`.

### 5.4. Неизменность и удаление
- **Подмена байтов** [код, блокер]. Новая миграция запрещает запись объекта **всем**, когда строка уже `uploaded` (сейчас офис может, `files_measurement.sql:138`). Плюс `sha256` в ссылке на фото (§3.2).
  - **Старые сборки (правило 16):** старое приложение повторяет загрузку только у фото, которое у него ещё не `uploaded` (`ops.ts:488–513`, повтор при `failed` и сетевых ошибках). На уже загруженное оно upsert не шлёт, кроме обрыва между `storage.upload` и записью `uploaded` (G §8 п.0). Тот случай — тот же файл и те же байты: сервер ставит `uploaded`, если объект уже есть с тем же `sha256`. Тест: повтор старой сборки после обрыва не падает и не меняет байты.
- Файл, на который ссылается **отправленный или подписанный** документ, выдаётся на `/p/`, пока жив документ (спека 50 §6 С6), даже если подрядчик его удалил. Исключение — удаление по CCPA (`docs/specs/38`): тогда «Photo unavailable» (§4.4).

  - файл не из версии — не выдаётся;
  - неотправленный черновик не выдаётся;
  - после подписи — фото подписанной версии;
  - закрытая компания — пусто;
  - удалённая смета — пусто;
  - предел частоты срабатывает;
- `content_hash` версии (спека 49 §4.2) меняется при смене фото в версии;
- запертая версия с фото не правится;
- новые функции — `revoke … from public, anon` (правило 18, T52).

**e2e (6 видов):** новая спека «фото в смете»:
- смета клиента с выездом → строка → «Фото» → 1 фото за ≤ 2 нажатия, 3 фото за ≤ 4 (счёт в спеке);
- в HTML PDF есть картинки;
- `/p/`: миниатюры под строкой, блок, просмотр;
- без сети: метка и проверка перед отправкой.

Новых экранов нет (шторка «Фото» и просмотр — не маршруты). Если появится маршрут просмотра — добавить его в `SCREENS` `e2e/specs/08-layouts.cjs`.

Облачная e2e (после Ф-2): `/p/` и второе устройство видят фото.

**Натив (правило 27)** — строка «Натив: как проверено на iPhone» в PR Д-1 и Д-2:
- PDF с 8 и 40 фото: время и размер (§4.4);
