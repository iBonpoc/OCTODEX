# Инструкция для агентов: как вести работу до выпуска 1.0 — черновик (11.11.2026)

Дополняет `CLAUDE.md` и `docs/ai/*`. Там, где этот файл расходится с ними, действует `CLAUDE.md`, пока основатель не сказал «да», а руководитель не внёс правки (список — §8). План работ — `2026-11-11-release-plan.md`; находки — `2026-11-11-full-audit.md`.

## 1. Команда

| Роль | Сколько | Модель | Что делает |
|---|---|---|---|
| Чат аудита (контроль) | 1 | самая сильная | Проверяет этапы по вызову руководителя. Код и задачи не ведёт |
| Руководитель | 1 | `claude-opus-5-5` | Ставит задачи, принимает PR, вливает, ведёт очередь. Код не пишет |
| Исполнитель «Данные и деньги» | 1 | `claude-opus-5-5` | Дорожка А: хранение, очередь, база, платежи |
| Исполнитель «Gutters» | 1 | `claude-sonnet-5-5` | Дорожка Б |
| Исполнитель «Проверки → вид → магазин» | 1 | `claude-sonnet-5-5` | Дорожка В |
| Помощники внутри чата | по одному | `sonnet` или `haiku` | Поиск по коду, ревью, сверка с картой |

Правила состава:
- Одновременно не больше трёх исполнителей. Больше — растёт число конфликтов и расход лимита подписки.
- Модель исполнителю задаёт руководитель при создании чата (`create_session`, поле `model`). Основателю ничего переключать не нужно.
- Сильная модель — там, где ошибка стоит данных или денег: `src/data/**`, `src/cloud/**`, `supabase/**`. Экраны, тесты, тексты, документы — на `sonnet`.
- Чат живёт одну-две задачи этапа, сдаёт и уходит в архив. Памятка — номера задач.

## 2. Откуда берётся работа

1. Работа берётся только из GitHub Issues с меткой `до-1.0`, в порядке `release-plan.md` §4.
2. Задачи без метки и с меткой `после-1.0` не берутся. Новая просьба основателя — задача; метку ставит руководитель по правилу: ошибка в пути выпуска, требование магазина или Gutters — `до-1.0`, остальное — `после-1.0`.
3. Одна задача — одна ветка — один PR с `Closes #N`.
4. Нашёл по ходу другую ошибку — завёл задачу, в свой PR не добавляешь.

## 3. Три класса задач и порядок действий

Класс определяет руководитель в задании.

| Класс | Что это | До кода | Кто смотрит PR |
|---|---|---|---|
| **К1. Данные, деньги, права** | `src/data/**`, `src/cloud/**`, `supabase/**`, платежи, роли, новая сущность или статус | Полный этап 0 по `PLANNING.md` + короткая спецификация + «да» руководителя | Руководитель + `code-reviewer`; база — ещё `security-check` |
| **К2. Обычная задача** | Экран, правило, компонент, находка аудита размера M | Десять строк руководителю: что есть сейчас, что меняю, какие тесты, какие файлы | Руководитель |
| **К3. Мелкая правка** | Одна ошибка, до ~30 строк, без новых сущностей | Ничего, кроме заявки на файлы | Руководитель по диффу |

Порядок для любой задачи:

1. **Прочитать.** `CLAUDE.md`, первые строки `BOARD.md`, задачу, находку аудита и спецификацию своего шага. Больше ничего читать не нужно.
2. **Заявить файлы** руководителю и дождаться ответа.
3. **Воспроизвести.** Для ошибки — написать тест, который падает. Не падает — сообщить руководителю, а не чинить вслепую.
4. **Исправить** наименьшей правкой. Рефакторинг «заодно» запрещён.
5. **Проверить** по §4.
6. **Сдать** одним пушем; отчёт по шаблону `WORKER.md` + строка «тест падал до правки: да, <имя теста>».

## 4. Тесты

**Какой тест нужен:**

| Что меняется | Тест |
|---|---|
| Правило, расчёт, переход статуса, работа очереди | модульный (`apps/mobile/test`) |
| Деньги | движок и база |
| Права и политики | тест базы под каждой ролью, которой касается |
| Хранение на устройстве | модульный с подменой хранилища: ошибка чтения, ошибка записи, переполнение |
| Экран | e2e на 6 видах, поиск по `testID` |
| Клиент ↔ сервер | облачная спека |
| Поведение, которое есть только на телефоне | сценарий Maestro (когда появится, этап 3.5) |

**Как писать:**
- Тест проверяет сохранённые данные, а не только надпись на экране.
- Нет `if (await x.count())` без `else throw`, нет `expect(true)`, нет `.catch(() => {})` на ожидании, нет новых `waitForTimeout`.
- Ждать то, что проверяешь. Время — только через `companyTime.cjs`.
- Ошибка считается исправленной, когда её тест был красным до правки и стал зелёным после.

**Что запускать перед сдачей** — `CHECKS.md` §10 без изменений: `git merge origin/main` последним шагом, `npm run check`, свои и затронутые спеки на всех видах, новые спеки три раза подряд, один пуш.

## 5. Приёмка и вливание

Руководитель принимает PR по чек-листу `DIRECTOR.md` и дополнительно:
- у находки аудита есть тест с её ID в названии или комментарии;
- PR не шире своей задачи;
- для К1 — отчёт `code-reviewer` приложен.

Вливает по одному. Пока `main` красный, не вливает ничего, кроме починки.

## 6. Проверка этапа чатом аудита

Когда закрыты все задачи этапа, руководитель пишет в `session_015CqH65zYaCaecNrBxcPr1v`:

```
Этап <N> готов.
Закрыто: #… (находки A-01, A-02, …)
PR: #…
Не сделано и почему: …
Замеры (если были): …
```

Чат аудита отвечает «принято» или списком правок. Следующий этап той же дорожки не начинается до «принято». Другие дорожки не ждут.

Чтобы проверка была дешёвой: чат аудита читает отчёт, выборочно проверяет тесты и код самых опасных правок, остальное сверяет помощниками на дешёвой модели.

## 9. Экономия лимита подписки

- Три исполнителя, не больше; чаты короткие.
- Сильная модель — только руководитель, дорожка А и контроль.
- Полный прогон e2e делает GitHub, не чат.
- Помощников звать по одному и на дешёвой модели.
- Новый чат читает только то, что названо в §3 п.1.
- Этап 3.2 сокращает ожидание проверок с ~20 до ~8 минут.
