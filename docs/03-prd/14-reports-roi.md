# PRD 14. Отчёты, ROI по источникам, сводка дня

> Статус: черновик v0.1, ноябрь 2026. Читает: `Lead`, `LeadSource`, `MarketingSpend`, `Estimate`/`EstimateVersion`/`EstimateOption`/`EstimateApproval`, `Job`, `Invoice`, `Payment`, `Refund`, `Expense`, `TimeEntry`/`LaborRate`, `SubcontractorAssignment`, `SubcontractorPayment`, `Subcontractor`, `Referral`, `Visit`, `Task` (`../04-domain-model.md`). Своих бизнес-сущностей модуль почти не создаёт — только вводит `MarketingSpend`.
> Колонки: **MVP** = бета на компании основателя · **Запуск** = до первых платящих · **Позже**.

## 1. Назначение
Каждое утро за 30 секунд показать владельцу, где лежат деньги, которые требуют действия сегодня, и раз в месяц честно ответить: какой канал (Thumbtack, Yelp, Google, сарафан) приносит прибыль, а какой её съедает.

## 2. Как это приносит деньги подрядчику (`money_impact`)
| Отчёт | Деньги |
|---|---|
| **Сводка «Сегодня»**: неотвеченные лиды, горячие сметы, неотправленные инвойсы, просрочка | Владелец без офиса не забывает про $: «работа у Петрова сделана 3 дня назад, инвойс на $2,850 не выставлен» |
| **ROI по источникам** с затратами на **все** лиды (вкл. мусор и lost) и с **валовой прибылью**, а не «выручкой» | Решение «урезать Thumbtack на $600/мес и вложить в рефералки» на цифрах, а не на ощущении. Пример: Yelp — $400, 18 лидов, 11 мусор, 1 работа на $900 → GP $350 < затрат |
| **Скорость ответа vs конверсия** | Видно, сколько денег стоит ответ через 2 часа вместо 5 минут |
| **Конверсия смет** и выбор G/B/B | Понятно, дорого ли считаем и работает ли «Better» как рекомендованный |
| **AR aging** (дебиторка по срокам) | Деньги 60+ дней собираются до того, как станут безнадёжными |
| **Субподрядчики и 1099** | Видно, сколько стоит каждый субподрядчик и какая маржа на его работах; в январе готов итог выплат по каждому для 1099-NEC (бухгалтер не берёт часы на раскопки) |
| Объединённый отчёт группы (v1.1) | Владелец двух компаний видит общий результат без Excel |

## 3. Пользователи и роли
- **Owner/Admin** — все отчёты, ввод затрат на рекламу.
- **Office** — сводка «Сегодня», AR aging; ROI и маржа — по override (PRD 01).
- **Tech** — отчётов нет; его «Сегодня» = визиты и задачи (PRD 07), без денег.
- **Владелец группы** — консолидированные отчёты (v1.1).

## 5. Критерии приёмки
- **RPT-US-01.** Given owner открывает главную, Then блок «Нужно действие» показывает до 7 карточек, отсортированных по сумме под риском, из списка: (а) лиды без ответа — число, самый старый таймер, сумма `cost_cents`; (б) горячие сметы (открыта за 48 ч, не решена) — сумма рекомендованных вариантов; (в) сметы, истекающие ≤ 3 дн; (г) работы `completed` без финального инвойса — сумма одобренного варианта минус выставленное; (д) одобренные сметы с несобранным депозитом; (е) просроченные инвойсы — `balance`; (ж) задачи на сегодня/просроченные; (з) наряды субподрядчиков `completed`, ждущие одобрения, и долг к выплате; (и) COI/лицензия субподрядчика истекает ≤ 7 дн при назначенных нарядах. Каждая карточка открывает список с действием в 1 тап (позвонить / выставить / напомнить). Given всё пусто, Then «Всё под контролем» и ссылка на ROI. Данные ≤ 5 мин давности (метка «обновлено 08:12»).
- **RPT-US-02.** Given главная, Then плитки: «Получено сегодня / неделя / месяц» (cash collected) с сравнением с прошлым периодом, «Ждём оплату» (сумма открытых балансов), «Продано за месяц» (estimate value одобренных). Подписи терминов — по §7 (иконка «i» с определением).
- **RPT-US-03.** Given экран «Затраты на рекламу», When «+» → канал, месяц (по умолчанию текущий), сумма, заметка, Then создаётся `MarketingSpend(period_start=1-е, period_end=последний день)`; кнопка «Скопировать прошлый месяц» создаёт черновики по всем каналам с прошлыми суммами для подтверждения. Для `paid_per_lead` подсказка «цены лидов уже учтены на лидах; вводите только подписки, возвраты (со знаком −), бонусы».
- **RPT-US-04.** Given период (месяц по умолчанию, неделя, квартал, произвольный), Then строка на каждый `LeadSource` с лидами или затратами + строка «Без источника» + «Итого»; столбцы по §7; сумма строк = итогу (сверка автотестом). Given источник с затратами и 0 работ, Then строка красная «$X без результата». Сортировка по любому столбцу; tap по строке — список лидов канала.
- **RPT-US-05.** Given режим «Когорта» (по умолчанию для ROI), Then лиды выбираются по `created_at` в периоде, а результаты (сметы, работы, выручка, GP) — за всё время до сегодня; в строке «ещё в работе: N смет на $X». Given режим «Период», Then затраты и результаты — по датам самих событий в периоде. Режим виден в заголовке.
- **RPT-US-06.** Given воронка, Then шаги: лиды (без `duplicate`) → с ответом → с отправленной сметой → одобрено → работа completed → оплачено полностью; для каждого шага число, % от предыдущего и сумма; фильтр по источнику и назначенному. В MVP воронка — столбцы таблицы ROI, отдельный экран-график — Запуск.
- **RPT-US-07.** Given период, Then по каждому источнику медиана `response_time`, % ответов < 5 мин, и таблица корзин: число лидов, % won, средняя выручка на лид. Лиды без ответа — отдельная корзина «нет ответа». Корзины считаются только по лидам, у которых есть `first_response_at` или которые закрыты.
- **RPT-US-08.** Given период, Then: отправлено смет (шт., $ рекомендованного варианта); решено (approved + declined + expired); close rate по шт. и по $; средний чек одобренной; медиана дней sent → approved; распределение выбранного варианта по `EstimateOption.position` (Good/Better/Best) и доля `is_recommended`; число и $ смет, одобренных после касания дожима №2+ (PRD 13). Фильтр по `owner_user_id`.
- **RPT-US-09.** Given AR aging на дату (сегодня), Then корзины по дням после `due_date`: «не наступил срок», 1–30, 31–60, 61–90, 90+; итог = Σ `balance` всех `sent`, не `void` инвойсов с `payment_status ∈ {unpaid, partially_paid}`; список с клиентом, номером, суммой, днями просрочки, последним напоминанием, кнопками «Напомнить» (шаблон №4) и «Позвонить». Отдельно строка «Депозиты/платежи без инвойса».
- **RPT-US-10.** Given любой денежный показатель, Then он относится ровно к одному из типов §7 и подписан им; в одной таблице не смешиваются «estimate value» и «revenue» без подписи столбца.
- **RPT-US-11.** (v1.1) Given режим «Все компании», Then каждый отчёт имеет переключатель «по компаниям / вместе», строки с бейджем компании, итог «A / B / всего»; затраты и источники не объединяются между компаниями автоматически (у каждой свои `LeadSource`), объединение по совпадающему имени — опция.
- **RPT-US-13.** Given период, Then строка на каждого `Subcontractor`: наряды (шт.), Σ `agreed_amount`, Σ `approved_amount` (дата `approved_at` в периоде), Σ выплат (`paid_at` в периоде), долг (одобрено − выплачено, на сегодня), средняя валовая маржа его работ, бейджи COI/лицензии/W-9 (`compliance_status`); tap → список нарядов. Видно только owner/admin (office — без выплат).
- **RPT-US-14.** Given календарный год (по умолчанию прошлый), Then по каждому субподрядчику Σ `SubcontractorPayment.amount_cents` с `paid_at` в году (по `Company.timezone`), `tax_classification`, последние 4 цифры TIN, флаги «нужна 1099» (Σ ≥ `form_1099_threshold_cents` и не корпорация) и «нет W-9»; CSV (имя, адрес, TIN полностью — только owner, с AuditLog) и ZIP с W-9. Порог по умолчанию $2,000 за 2026 год (до 2025 — $600) — подтвердить у бухгалтера. Сам бланк 1099 Octo не подаёт (MVP).
- **RPT-US-12.** Given вопрос AI о деньгах, Then ответ строится вызовом того же отчётного запроса (инструмент), не вычисляется моделью; в ответе указан тип показателя и период: «Thumbtack, октябрь, когорта: затраты $1,240, выручка $8,600, валовая прибыль $4,100, ROI 2.3×. Открыть отчёт?».

## 7. Бизнес-правила и расчёты
**Четыре денежных понятия (не смешивать):**
| Термин | Определение | Дата события |
|---|---|---|
| **Estimate value** («продано») | Σ total выбранного варианта (`EstimateApproval.option_id`) + выбранных optional, без налога | `signed_at` |
| **Revenue** («выставлено») | Σ subtotal без налога по инвойсам `sent`, не `void`, всех видов, минус возвраты-кредиты; депозитный инвойс входит, финальный содержит только остаток (правило PRD 09) — двойного счёта нет | дата отправки инвойса |
| **Cash collected** («получено») | Σ `Payment.succeeded.amount` − Σ `Refund.amount`, включая налог (показываем отдельно «из них налог») | дата платежа/возврата |
| **Gross profit** | Revenue работы − прямые затраты работы (`Job.actual_cost_cents` по правилу PRD 10 §7: материалы (Expense, PO — только через счёт поставщика), труд (TimeEntry × LaborRate), субподряд (одобренные наряды), прочее, комиссии платежей). Если ставки труда не заданы — подпись «GP без учёта труда» | дата `completed` работы |

**Атрибуция работы к источнику:** Job → `estimate_id` → `Estimate.lead_id` → `Lead.source_id`. Нет лида → `Customer.lead_source_id`, если это первая работа клиента; иначе «Повторный клиент». Отдельный столбец **LTV по первому источнику**: вся выручка клиента за всё время по `Customer.lead_source_id` (показывает, что сарафанный клиент приносит повторные чистки).

**Затраты канала за период P:**
`spend = Σ Lead.cost_cents (лиды, созданные в P, ВСЕ статусы, включая lost, junk_spam, duplicate) + Σ MarketingSpend × (дни пересечения с P / дни периода затрат) + Σ Referral.reward (выданные в P, канал «Реферал»)`.

**Показатели строки:**
- `leads` — без `duplicate`; `junk_rate = junk_spam / leads`.
- `CPL = spend / leads`; `cost_per_estimate = spend / лиды с отправленной сметой`; `CAC_job = spend / won jobs` (главная цифра «сколько стоит заказ»).
- `close_rate = won / leads`.
- `ROAS = revenue / spend`; `ROI = (GP − spend) / spend` (показываем как «2.3×» и цветом: < 0 красный, 0–1 жёлтый, > 1 зелёный). При `spend = 0` — «бесплатный канал», ROI не считается.
- Выручка и GP в когорте включают только завершённые работы; открытые сметы — отдельно «в работе».

**Сводка «Сегодня»:** порядок карточек — по `amount_at_risk` (cost лидов без ответа считается как риск, сметы — по рекомендованному варианту, инвойсы — по `balance`). Не больше 7 карточек; задачи всегда последние.

**Временные границы:** день/месяц по `Company.timezone` (`America/Los_Angeles`).

**Сверка:** Σ строк = «Итого» во всех столбцах; revenue и cash за месяц сверяются с модулем инвойсов (автотест на эталонном наборе данных основателя).

**Права:** ROI, GP и затраты не отдаются API роли tech и office без override; Сводка для office — без столбцов маржи.

## 8. AI-помощник
| Команда | Подтверждение |
|---|---|
| «Сколько я заработал на Thumbtack в октябре» / «какой канал самый выгодный» | нет (чтение) |
| «Кто мне должен больше 30 дней» | нет |
| «Добавь расходы на Yelp $400 за ноябрь» → `MarketingSpend` | да |
| «Напомни всем, кто должен больше 60 дней» | да, список получателей в предпросмотре |
AI получает агрегаты через инструмент отчётов с правами пользователя; если вопрос двусмысленный («заработал»), отвечает с явным типом (GP) и предлагает другие (revenue, cash). Цифры AI не придумывает и не вычисляет.

## 9. Офлайн
- Сводка «Сегодня» и последние открытые отчёты кэшируются со временем снимка («данные на 08:12, нет сети»); карточки действий работают офлайн (звонок, создание инвойса в черновик).
- Ввод `MarketingSpend` офлайн — в outbox.
- Пересчёт отчётов — только на сервере.

## 11. Ошибки и крайние случаи
- **Нет затрат по платному каналу** — строка с пометкой «затраты не введены», ROI не показывается (а не «∞»).
- **Возврат платежа в следующем месяце** — уменьшает cash месяца возврата; revenue работы корректируется кредитом в периоде кредита; GP в когорте пересчитывается.
- **Лид переназначен на другой источник задним числом** — отчёты пересчитываются, изменение в `AuditLog`; закрытые месяцы не «замораживаются» (MVP), снимков нет.
- **Смета без лида, клиент без источника** — «Без источника»; карточка «12 работ без источника: заполнить?» (влияет на точность ROI).
- **Работа из повторяющегося плана** — источник «Повторный клиент» в прямом виде, первый источник в LTV.
- **Отрицательный MarketingSpend** (возврат Thumbtack за плохой лид) — допускается, уменьшает spend.
- **Дубли лидов** — не входят в `leads`, но их `cost_cents` входит в `spend` (заплатили).
- **Большие объёмы** — отчёт по году < 3 с на вебе (материализованные агрегаты по дням, обновление по событиям).
- **Нет прав** — tech по прямой ссылке получает «нет доступа».
- **Смена часового пояса компании** — исторические границы пересчитываются по новому поясу, предупреждение перед сменой.

## 13. Метрики
- Доля дней, когда owner открыл «Сегодня» (цель: ежедневно в рабочие дни), и доля карточек, закрытых в тот же день.
- Время от `Job.completed` до отправки финального инвойса (до/после сводки).
- Доля платных каналов с введёнными затратами за месяц (цель 100%).
- Доля работ с известным источником (цель ≥ 95%).
- Изменение маркетингового бюджета основателя по каналам через 2–3 месяца (решения, принятые по ROI) и доля бесплатных каналов в выручке.
- Сумма AR 60+ (до/после).
- Расхождение отчёта с ручной сверкой основателя — 0.

## 14. Изменения модели данных
- `MarketingSpend`: + `company_id` (явно), `kind` (`subscription/ads/per_lead_adjustment/other`), `expense_id` (→ Expense, если затрата заведена как расход `category=marketing`, чтобы не было двойного ввода), `created_by`.
- `Expense`: при `category=marketing` — + `lead_source_id`; сохранение создаёт связанный `MarketingSpend`.
- `Job`: + `completed_at` (если не выводится из `StatusEvent`), `attributed_source_id` (денормализация для быстрых отчётов, пересчитывается при смене источника лида).
- Служебные (не бизнес-сущности): материализованные дневные агрегаты `daily_company_metrics`, `daily_source_metrics` — проектируются в архитектуре (Фаза 3).
- `Company.subcontractor_settings.form_1099_threshold_cents`, `Subcontractor.tax_classification`, `tin_encrypted` (для RPT-US-14).

✅ Внесено в 04-domain-model v0.2: MarketingSpend (company_id, kind, expense_id, created_by), Expense.lead_source_id, Job.attributed_source_id, поля 1099. `Job.completed_at` — дубль с PRD 07. Дневные агрегаты не внесены — это служебные таблицы архитектуры Фазы 3.
