# 16. Офлайн-режим и синхронизация

> Статус: черновик v0.1, ноябрь 2026. Основа: `../02-product-vision.md` §6, `../04-domain-model.md` §0 (`row_version`, UUID v7, `idempotency_key`) и §11. Движок синхронизации (PowerSync / ElectricSQL / свой) выбирается в ADR Фазы 3; этот документ задаёт **поведение**, которое должен обеспечить любой выбор.
> Связанные модули: `05-estimates.md`, `06-gutters-module.md` (чертёж), `07-jobs-schedule.md`, `09-invoices-payments.md`, `10-expenses-job-costing.md`, `15-ai-assistant.md`.

## 1. Назначение
Полевой цикл работает без сети: открыть объект, нарисовать гаттеры на заранее скачанном спутнике, посчитать смету на устройстве, сделать фото, получить подпись, отметить статусы и время. Когда сеть появляется, всё уходит на сервер само, без потерь и дублей, а деньги остаются под контролем сервера.

## 2. Как это приносит деньги подрядчику (`money_impact`)
| Механизм | Оценка |
|---|---|
| **Смета и подпись прямо у клиента** в зоне без связи (каньоны LA: Topanga, Malibu, холмы Glendale/La Crescenta, подвалы, металлические крыши) | Same-day close вместо «пришлю вечером»; каждая потерянная подпись ≈ $2.5k смета × 30–40% шанс |
| Нет повторных выездов из-за «не загрузилось» | Каждый лишний выезд ≈ $80–150 (время + топливо) |
| Фото/время/чек-лист не теряются | Доказательства для споров и гарантий; точная себестоимость |
| Надёжность как отличие от рынка | Jobber/HCP офлайн почти не работают (`01` §4 п. 8) → аргумент продаж и удержания |

## 3. Пользователи и роли
Все полевые роли (owner, tech, subcontractor с входом; sales — позже) — основные пользователи. Набор кэшируемых данных ограничен правами роли (tech кэширует только свои визиты и связанные объекты; subcontractor — только свои наряды, без цен клиента; cost-поля не попадают на устройство без права их видеть). Субподрядчик без входа работает по ссылке наряда — это онлайн-веб, офлайна у него нет. Офис/веб — онлайн (веб без офлайна в MVP).

## 5. Критерии приёмки
- **OFF-US-01.** Given последняя синхронизация была сегодня утром, When включён авиарежим, Then открываются: визиты пользователя от −7 до +14 дней, их Job, Customer, Property, Contact, чертежи (последняя версия), BOM/cut list, чек-листы, каталог и сборки; время открытия экрана ≤ 300 мс (локальная БД).
- **OFF-US-02.** Given нет сети, When создан клиент «Ким», объект, чертёж из 4 runs и нажато «Рассчитать», Then движок на устройстве даёт тот же результат в центах, что и сервер для тех же входов (контрольные тест-кейсы движка, разница = 0), смета сохраняется как `draft` с UUID v7, в списке значок «не синхронизировано».
- **OFF-US-03.** Given смета `sent` закэширована (клиенту ранее отправлена ссылка) **или** черновик, который подрядчик показывает на месте, When клиент подписывает офлайн, Then локально создаётся `EstimateApproval(channel=in_person, offline=true)` с подписью (файл), временем устройства и геометкой; смета локально показывается «Подписано · ожидает подтверждения сервера»; при синхронизации сервер (a) фиксирует черновик как новую версию `sent` с той же подписью и переводит в `approved`, или (b) отклоняет, если версия заменена/истекла/цена изменилась — тогда подпись сохраняется как Activity, владельцу Task «Подпись Ким требует решения», клиенту ничего не отправляется автоматически. Job и депозитный инвойс создаются только сервером после (a).
- **OFF-US-04.** Given нет сети, When tech проходит `scheduled → on_site → completed`, Then статусы и TimeEntry сохраняются с временем устройства; после синхронизации `StatusEvent.at` = время действия (не время синхронизации), `synced_at` отдельно.
- **OFF-US-05.** Given нет сети, When записан чек на $2,188, Then Payment создаётся локально `pending_sync` с `idempotency_key`; баланс инвойса на устройстве показан «≈ $0 (ожидает подтверждения)»; сервер при приёме проверяет баланс: переплата → `needs_review` (модуль 09).
- **OFF-US-06.** Given 3 записи в очереди, Then в шапке индикатор «3 ждут отправки», в карточке записи значок; When сеть появилась и очередь ушла, Then «Всё сохранено · 10:42»; ошибка отправки → красный индикатор с текстом причины и «Повторить».
- **OFF-US-07.** Given у пользователя визиты на 14 дней вперёд и включён Wi-Fi, When фоновая задача сработала, Then для каждого Property без актуального снимка скачивается base image чертежа и тайлы вокруг (радиус ~100 м) в пределах бюджета памяти; в карточке визита значок «доступен офлайн».
- **OFF-US-08.** Given черновик сметы правили офлайн на телефоне и параллельно на вебе, When синхронизация, Then поля без пересечения сливаются; для изменённых обеими сторонами строк показывается экран «Две версии»: слева «На этом телефоне», справа «На сервере (Анна, 10:15)», выбор по каждой строке или целиком; до выбора смету нельзя отправить.
- **OFF-US-09.** Given нет сети, When «Отправить клиенту» по смете, Then действие встаёт в outbox; при появлении сети, если прошло < 2 ч и версия не изменилась — отправляется автоматически; если > 2 ч — push «Отправить смету Ким сейчас?» (защита от неожиданных отправок «из прошлого»).
- **OFF-US-10.** Given membership сотрудника `suspended`, When устройство выходит в сеть, Then при первой синхронизации локальные данные этой компании удаляются (несинхронизированные записи сначала отправляются, если токен ещё действителен; иначе уничтожаются), пользователь видит экран «Доступ к компании закрыт».
- **OFF-US-12.** Given авиарежим, When команда навигации введена текстом («открой клиентов», «календарь на завтра»), Then выполняется на устройстве ≤ 200 мс; Given голос и iOS поддерживает on-device распознавание для языка, Then так же; иначе подсказка «Без сети — введите текстом» (`15` AI-US-02).
- **OFF-US-14.** Given субподрядчик с ролью `subcontractor` и наряды на 14 дней, When авиарежим, Then открываются его наряды, адрес, доступ (gate code — день работ и накануне), чертёж, cut list, количества — **без цен клиента** (поля не синхронизируются на устройство); «Начал», «Готово» и фото сохраняются в outbox и применяются сервером по state machine наряда.
- **OFF-US-11.** Given объект в списке, When «Скачать для офлайн», Then объект, клиент, последние сметы, чертёж и снимок скачиваются, прогресс-бар, итог «12 МБ».

## 6. Экраны
| Элемент | Описание |
|---|---|
| Индикатор синхронизации | В шапке (стеклянная пилюля): ✓ «Сохранено», ↻ «Отправка N», ⚠ «Ошибка», ☁︎✕ «Офлайн · последняя синхр. 10:42». Тап → экран «Синхронизация» |
| Экран «Синхронизация» | Очередь (что, когда создано, попытки, причина ошибки), «Повторить всё», размер кэша, «Скачанные объекты», «Скачать на завтра» |
| Бейдж записи | «Не отправлено» / «Ожидает подтверждения сервера» / «Конфликт» на карточках и в списках |
| Экран конфликта | Две версии рядом (телефон / сервер, автор и время), выбор по полю/строке или целиком |
| Блокировки онлайн-действий | Кнопки «Оплатить картой», AI-команды сложного типа — неактивны с подписью «Нужна сеть», без модальных ошибок |
| Предупреждение при выходе | «3 записи не отправлены. Выйти всё равно?» (выход стирает кэш) |
Тон: спокойный, без тревожных красных экранов, пока данные в безопасности на устройстве.

## 7. Бизнес-правила и расчёты
**Что кэшируется (scope по пользователю и роли, для каждой компании, где у пользователя активный Membership):**
| Данные | Объём | Правило |
|---|---|---|
| Visits + Jobs | от −7 до +14 дней (+ все `in_progress`) | tech — только назначенные |
| SubcontractorAssignments (наряды) | по кэшированным Job | owner/office — все; subcontractor — только свои, без цен клиента, баланса, себестоимости |
| Customers, Properties, Contacts | все компании (owner/admin/office/sales); tech — связанные с его визитами | Без cost-полей для ролей без права |
| Leads | статусы `new…estimate_sent`, последние 90 дней | Не для tech |
| Estimates | `draft` все свои; `sent/viewed/approved` за 90 дней; версии и строки | Себестоимость только по праву |
| Drawings | последняя версия для кэшированных Property | — |
| Catalog, Assemblies, AssemblyComponents | целиком | Движок смет на устройстве |
| Invoices, Payments | по кэшированным Job/Customer, read-only | Сервер авторитетен |
| ChecklistTemplates, RecurringPlans (чтение) | целиком | — |
| Files | миниатюры всегда; оригиналы фото — свои за 14 дней и объекты визитов | Бюджет памяти |
| Спутник | base image чертежей + тайлы объектов визитов на 14 дней | Только Wi-Fi по умолчанию |
Бюджет памяти по умолчанию 1 ГБ (настройка 0.5–5 ГБ), вытеснение LRU, никогда не вытесняются несинхронизированные данные и визиты на ближайшие 3 дня.

**Работает офлайн / требует сети:**
| Офлайн ✅ | Требует сети ⛔ (очередь или недоступно) |
|---|---|
| Создание/правка клиентов, объектов, контактов, лидов, заметок, задач | Отправка клиенту (SMS/email/портал) — **очередь** с правилами TTL |
| Чертёж, расчёт сметы (тот же движок, детерминированный), черновики смет, change order черновик | Оплата картой/ACH/tap-to-pay — **недоступно** |
| Подпись клиента на устройстве (approval «ожидает подтверждения») | Refund, void, правка `sent` инвойса — **недоступно** |
| Статусы визитов, чек-листы, фото, TimeEntry; статусы и фото нарядов субподрядчика | Сложные команды AI-помощника, OCR чеков — **очередь** |
| Навигация по приложению текстом/тапом (словарь команд); голосом — где iOS распознаёт на устройстве | Голосовая навигация офлайн для языков без on-device распознавания — позже |
| Запись наличных/чека/Zelle | Онлайн-запись, генерация повторяющихся визитов, геокодинг новых адресов — **сервер** |
| Расход с фото (OCR позже) | Скачивание новых спутниковых снимков |
| Перенос своих визитов (07) | Отчёты по компании (кэш последнего снимка — только чтение) |

**Outbox (очередь изменений):**
- Каждое локальное изменение = операция `{op_id (UUID v7), entity, entity_id, kind (create/update/delete/action), payload (изменённые поля), base_row_version, idempotency_key, created_at_device}`.
- Порядок: FIFO в пределах сущности и её зависимостей (Customer → Property → Drawing → Estimate → Approval); независимые цепочки идут параллельно.
- Файлы — отдельная очередь с возобновляемой загрузкой (resumable / chunked), запись ссылается на `file_id`, который создаётся на устройстве; запись допускается на сервер раньше файла со статусом файла `uploading`.
- Повторы: экспоненциальная задержка 2 с → 5 мин, бесконечно для сетевых ошибок; для ошибок валидации (4xx) — стоп, запись в «Ошибки» с понятной причиной и действиями («Исправить», «Удалить локальное изменение» — только для не-денежных).
- Сервер идемпотентен по `idempotency_key`/`op_id`: повтор после обрыва не создаёт дубль.
- Фон: iOS BGAppRefresh/BGProcessing + отправка при каждом выходе в foreground и при смене сети; гарантий по времени фона нет — UI это честно показывает.
- Действия с TTL: «В пути» — 30 мин (07 §11); «Отправить смету/инвойс» — 2 ч до авто-отправки, позже — переспросить; напоминания клиенту, просроченные по времени, — отбрасываются.

**Правила конфликтов:**
| Класс данных | Правило |
|---|---|
| Денежные документы: `sent/viewed/approved` Estimate и их версии, Invoice (кроме `draft`), Payment, Refund, ChangeOrder `approved` | **Сервер авторитетен.** На устройстве read-only; офлайн-действия (подпись, ручной платёж) приходят как *заявки*, сервер их валидирует и принимает или отклоняет с Task владельцу |
| Черновики: Estimate `draft`, Drawing, Invoice `draft`, ChangeOrder `draft` | Слияние по полям/строкам; при пересечении изменений — **показываем обе версии**, выбор пользователя; до выбора отправка заблокирована |
| Простые записи (Customer, Property, Contact, Lead, Task, notes) | Слияние по полям; одно поле изменено обеими сторонами → побеждает последнее по серверному времени приёма, проигравшее значение сохраняется в AuditLog и в Activity «значение заменено», с возможностью вернуть |
| Статусы (Visit, Job, Lead, SubcontractorAssignment) | Применяются по state machine в порядке `created_at_device`; недопустимый переход (визит отменён в офисе, а tech его завершил) → полевой результат **не теряется** (фото, время, чек-лист сохраняются), статус помечается «Конфликт статуса», Task владельцу |
| Только-добавление (File, TimeEntry, ChecklistResponse, Activity, StatusEvent) | Конфликтов нет, всегда принимаются |
| Удаление vs правка | Правка удалённой записи → запись восстанавливается с пометкой и уведомлением удалившему |
`row_version` — серверный счётчик; устройство отправляет `base_row_version`, сервер сравнивает по полям (хранит версии полей или делает diff с AuditLog — решение ADR).

**Время.** Действия несут `created_at_device`; сервер хранит и `synced_at`. Если часы устройства расходятся с сервером > 5 мин (по ответу сервера), время корректируется на смещение и помечается.

**Идентификаторы и номера.** UUID v7 создаются на устройстве. Человеческие номера (`EST-0148`, `INV-0093`) присваивает **только сервер** при синхронизации; офлайн показывается «EST-черновик». Клиенту никогда не уходит документ без номера.

**Спутниковые снимки — лицензия.** Условия Google Maps Platform ограничивают предзагрузку и кэширование контента; Mapbox допускает офлайн через SDK-пакеты в лимитах. Для чертежа сохраняется base image, сделанный при создании чертежа онлайн; заранее скачиваются снимки **только у провайдера, условия которого это разрешают** (решение ADR Фазы 3, §15). Если нельзя — офлайн-чертёж для новых объектов только по своему фото с калибровкой («эта линия = 20 ft», `06`).

**Безопасность устройства.** Локальная БД зашифрована (SQLCipher или iOS Data Protection `complete until first unlock`), ключ в Keychain; кэш разделён по `company_id`; выход из аккаунта и потеря доступа стирают кэш; биометрическая блокировка приложения — настройка компании. RLS проверяется сервером для каждой операции outbox (устройство не доверенное).

## 8. AI-помощник
Офлайн доступна только on-device навигация по приложению (MVP): текстом и тапом всегда, голосом — где iOS распознаёт речь на устройстве (согласовано с модулем 15 §9). Сложные команды AI офлайн недоступны. Команда, сказанная офлайн, сохраняется как черновик «Выполнить, когда появится сеть?» и **не выполняется автоматически** — при появлении сети пользователь подтверждает (контекст мог измениться). OCR чеков — в очереди (модуль 10).

## 10. Уведомления и автоматизации
- Очередь не отправлена > 4 ч при наличии сети (ошибка) → push пользователю + индикатор.
- Офлайн-подпись или платёж отклонены сервером → push автору и владельцу + Task.
- Конфликт черновика → бейдж и push автору.
- Перед выездом: вечером (19:00) push «Скачать данные на завтра? 3 визита, 1 без офлайн-снимка» если есть неготовые объекты.
- Хранилище > 90% бюджета → предупреждение и предложение очистить старые фото (только синхронизированные).

## 11. Ошибки и крайние случаи
- **Приложение убито / телефон сел в середине записи** → запись в локальную БД транзакционна, outbox переживает перезапуск.
- **Двойное нажатие «Сохранить» офлайн** → один `op_id`, одна запись.
- **Сеть «мигает»** (1 полоска LTE) → запросы с таймаутом, частичная загрузка файлов возобновляется, UI не дёргается между состояниями чаще раза в 3 с.
- **Две офлайн-подписи одной сметы** (два устройства) → сервер принимает первую по `created_at_device`, вторая — Activity + Task.
- **Каталог изменился, пока смета считалась офлайн** → цены в смете — снимок на момент добавления (`04` §4); при синхронизации баннер «Цены каталога изменились с 10:00 — пересчитать?», без авто-пересчёта.
- **Версия схемы/приложения устарела** → сервер принимает старые операции через версионированный API ≥ 2 версий назад; иначе «Обновите приложение», очередь сохраняется.
- **Мульти-компания офлайн** → создание требует выбора компании, как онлайн; кэш раздельный.
- **Потеря телефона** → owner отзывает сессию устройства; данные стираются при следующем выходе в сеть; локально данные зашифрованы.

**Обязательные failure-тесты (E2E на устройстве/симуляторе с управлением сетью):**
| # | Сценарий | Ожидание |
|---|---|---|
| T1 | Авиарежим → клиент, объект, чертёж, смета, подпись → сеть | Всё на сервере, номера присвоены, Job создан один, депозит-инвойс один |
| T2 | Обрыв сети на середине загрузки 30 фото | Все 30 загружены, без дублей |
| T3 | Повтор каждой операции outbox дважды (имитация потерянного ответа) | Нет дублей ни в одной таблице |
| T4 | Параллельная правка черновика сметы (телефон офлайн + веб) | Экран двух версий, ничего не потеряно |
| T5 | Офис отменил визит, tech офлайн завершил его с фото | Фото/время сохранены, статус «Конфликт», Task |
| T6 | Офлайн-запись наличных + онлайн-оплата картой того же инвойса | Переплата `needs_review`, без потери данных |
| T7 | Убийство приложения во время записи и во время отправки | Ни одна операция не потеряна и не задублирована |
| T8 | Смена часов устройства на +1 день | Время скорректировано и помечено |
| T9 | Membership отозван, устройство офлайн 3 дня, затем сеть | Несинхронизированное отправлено (если разрешено) или стёрто, кэш удалён |
| T10 | Кэш 14 дней для компании с 5,000 клиентов на iPhone 12 | Первая загрузка ≤ 2 мин на Wi-Fi, БД ≤ 300 МБ без фото |
| T11 | «В пути» офлайн, сеть через 40 мин | SMS клиенту не отправлено (TTL) |
| T12 | Отправка сметы офлайн, сеть через 3 ч | Не отправлено автоматически, push-подтверждение |

## 12. MVP / позже
**MVP:** локальная зашифрованная БД, кэш по таблице §7, outbox с идемпотентностью и зависимостями, очередь файлов, правила конфликтов (сервер для денег, две версии для черновиков, поля для простых), офлайн-подпись как заявка, офлайн ручные платежи, TTL для отправок, индикатор и экран синхронизации, «Скачать на завтра», предзагрузка снимков (при допустимой лицензии), удалённое стирание, тесты T1–T12 в CI на симуляторе.
**MVP (дополнительно):** on-device навигация текстом/тапом офлайн, голосом — где iOS распознаёт на устройстве; офлайн-наряды субподрядчика с входом.
**Позже:** офлайн на вебе/PWA, офлайн голосовая навигация для языков без on-device распознавания iOS, офлайн tap-to-pay (Stripe Terminal offline), P2P-синхронизация внутри бригады без сети, умный префетч по маршруту, дельта-синхронизация больших фото.

## 15. Открытые вопросы

1. **Лицензия спутника для офлайн-кэша** (Google vs Mapbox vs Nearmap): какой провайдер разрешает предзагрузку для полевого использования — блокер для OFF-US-07, решить в ADR Фазы 3.
