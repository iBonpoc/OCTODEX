# 09. Инвойсы и платежи

> Статус: черновик v0.1, ноябрь 2026. Сущности: `Invoice`, `InvoiceLineItem`, `Payment`, `PaymentAttempt`, `Refund`, `TaxRate`, `WebhookEvent`, `EstimateVersion.deposit_rule`, `EstimateApproval.deposit_payment_id`, `ChangeOrder`, `RecurringPlan`, `Company.stripe_account_id`, `Company.tax_settings`, `StatusEvent`, `AuditLog`, `ExternalRef` (`../04-domain-model.md` §6, §9).
> Связанные модули: `05-estimates.md` (депозит при одобрении), `07-jobs-schedule.md` (промпт финального инвойса), `10-expenses-job-costing.md` (billable расходы), `12-portal-public-page.md` (оплата клиентом), `13-communications-automations.md`, `16-offline-sync.md`.
> **Юридические оговорки:** правила по надбавкам и скидкам в CA и раскрытие комиссий — проверить у юриста до запуска (см. §15).

## 1. Назначение
Выставить счёт в 2 тапа из работы или сметы, получить деньги быстро и дёшево (ACH, карта, tap-to-pay, наличные/чек/Zelle) и всегда точно знать, кто сколько должен. Статус документа и статус оплаты ведутся раздельно.

## 2. Как это приносит деньги подрядчику (`money_impact`)
| Механизм | Оценка |
|---|---|
| **Депозит при подписи сметы** | 30–50% вперёд на материалы: кэш не замораживается (монтаж $3k → $1–1.5k сразу), меньше отказов после подписи |
| **ACH-first** для крупных чеков | Карта на $5,000 ≈ $145 + 30¢ Stripe; ACH ≈ $5 (cap) → **экономия ~$140 на чеке**; при $20k/мес через нас и 50% в ACH ≈ **$250–300/мес** |
| Оплата на месте (tap-to-pay / QR) при завершении | Деньги в день работы вместо «вышлите счёт» → DSO −7…14 дней, меньше просрочки |
| Автонапоминания о просрочке | Возврат 5–10% «зависшей» дебиторки без звонков владельца |
| Частичные оплаты и учёт наличных/Zelle | Нет потерянных платежей вне системы, точный баланс клиента |
| Прозрачная комиссия платформы | Доверие → больше оборота через продукт (наш основной доход: +0.5% к Stripe [черновик], `02a` §5) |

## 5. Критерии приёмки
- **INV-US-01.** Given у компании нет `stripe_account_id`, When owner нажал «Подключить платежи», Then открывается Stripe Connect onboarding (Express, hosted), по возврату статус `charges_enabled/payouts_enabled` виден в настройках; до `charges_enabled` кнопки онлайн-оплаты в портале скрыты, доступна запись ручных платежей.
- **INV-US-02.** Given `deposit_rule = 40%` и итог выбранного варианта $3,000, When клиент подписал в портале, Then идемпотентно создаётся Invoice `kind=deposit` на $1,200 (`sent`), экран подписи переходит к оплате; при успешной оплате `EstimateApproval.deposit_payment_id` заполнен. Given клиент закрыл страницу, Then инвойс остаётся `sent/unpaid`, ссылка в письме-подтверждении.
- **INV-US-03.** Given работа: вариант $3,000 + CO $250 + billable расход $120 (+15% = $138), депозит $1,200 оплачен, When «Создать финальный», Then инвойс `final` содержит строки сметы и CO, строку расхода $138 и строку «Депозит INV-0091 −$1,200»; итог к оплате $2,188 (+налог, только если он включён на инвойсе). Повторное нажатие не создаёт второй финальный (на Job ≤ 1 не-void `final`).
- **INV-US-05.** Given инвойс с балансом $2,188, When клиент выбирает ACH и вводит $1,000, Then создаётся Payment `pending` (ACH), `payment_status` остаётся `unpaid` до вебхука `succeeded` (ACH до 4 рабочих дней, в UI «Платёж в обработке»), затем `partially_paid`, баланс $1,188. Сумма > баланса не принимается.
- **INV-US-06.** Given iPhone с Tap to Pay и сеть, When tech нажал «Принять $2,188», Then Stripe Terminal собирает карту, Payment с `method=tap_to_pay`; Given entitlement не получен или нет NFC, Then показывается QR на портал инвойса.
- **INV-US-07.** Given инвойс $2,188, When записан чек #1043 на $2,188 с фото, Then Payment `method=check, status=succeeded, received_by=user, reference=1043`, инвойс `paid`; ошибочный ручной платёж аннулирует только owner/admin с причиной (`voided`), запись не удаляется.
- **INV-US-08.** Given карточный Payment $1,200 succeeded, When admin делает refund $500 с причиной, Then создаётся Refund и Stripe refund с `idempotency_key`; Payment → `partially_refunded`; инвойс → `partially_paid` (баланс +$500); у роли office кнопка отсутствует, а API отвечает 403.
- **INV-US-09.** Given платёж картой $1,000, Then в деталях: «Stripe $29.30 · Octo $5.00 · вам $965.70»; на дашборде «ACH сэкономил вам $X в этом месяце» = Σ(оценка карточной комиссии − фактическая ACH-комиссия) по ACH-платежам.
- **INV-US-10.** Given `due_date` прошла, payment_status ≠ `paid`, напоминания включены, Then письма уходят в день +1, +7, +14 (настройка), каждое с ссылкой оплаты; при `paid` или ручной паузе цепочка останавливается; клиент получает не больше 1 напоминания в сутки по всем его инвойсам.
- **INV-US-16.** Given финальный или депозитный инвойс из сметы, When создаётся, Then `tax_enabled`, `tax_rate_id` и флажки `taxable` строк берутся из одобренной версии сметы (снимок ставки `tax_rate_bps`); Given standalone или recurring, Then из `Company.tax_settings` (по умолчанию налог выкл.). Given `draft`, When owner/office переключает налог или ставку, Then итоги пересчитываются. Given инвойс `sent` без оплат, When меняется налог, Then создаётся новая ревизия (`revision + 1`, «обновлён», AuditLog), прежний PDF сохраняется; Given есть succeeded платёж, Then налог и строки заблокированы (исправление — новый standalone-инвойс или void после refund). Определения ставки по адресу/ZIP нет нигде.
- **INV-US-11.** Given RecurringPlan `auto_invoice=true, per_visit`, When визит `completed`, Then создаётся инвойс `recurring` с ценой плана; отправляется автоматически, только если в плане включено «отправлять сразу», иначе черновик владельцу.

## 7. Бизнес-правила и расчёты
**Статусы.** Документ: `draft → sent → void` (state machine `04` §9). Оплата `payment_status` вычисляется из Payment и Refund:
```
paid_net = Σ succeeded.amount − Σ refunds.amount   (pending не учитываются)
balance  = total − paid_net
payment_status = refunded        если были платежи и paid_net = 0 после возвратов
               = paid            если balance ≤ 0
               = partially_paid  если 0 < paid_net < total
               = unpaid          иначе
overdue (флаг) = sent ∧ balance > 0 ∧ today > due_date (в tz компании)
```
**Виды инвойсов.**
| kind | Откуда | Правило |
|---|---|---|
| deposit | Одобрение сметы с `deposit_rule` | % от итога выбранного варианта (с optional) или фикс. сумма; на Job ≤ 1 не-void deposit |
| progress | Вручную из работы | Сумма или % от договора; Σ (deposit+progress) ≤ договор |
| final | Промпт завершения (07) или вручную | `договор + Σ approved CO + Σ billable расходы с наценкой − Σ не-void deposit/progress` строками-кредитами |
| standalone | Без работы/сметы | Свободные строки или из каталога |
| recurring | RecurringPlan | Цена плана на момент вхождения |

**Договор** = `totals` выбранного варианта из `approved_version_id` + выбранные optional. Строки копируются снимком из EstimateLineItem (только `client_visible`), BOM-строки не попадают.

**Налог (ручной, никогда не автоматический — решение основателя).** На инвойсе переключатель `tax_enabled` и выбор `tax_rate_id` (снимок `tax_rate_bps`); облагаются строки с `taxable = true`; `tax = tax_enabled ? round((Σ taxable − доля скидки) × rate) : 0` — те же формулы, что `05` §7.2. Значения по умолчанию: для deposit/progress/final — из одобренной версии сметы и CO; для standalone/recurring — `Company.tax_settings`. Что облагать для монтажа гаттеров в CA, решает подрядчик с бухгалтером (`00-decisions-for-founder.md`). Депозит: налог в финальном (по умолчанию, `deposit_tax_mode = in_final`) или пропорционально — настройка.

**Редактирование после отправки.** `sent` и `payment_status=unpaid` → правка разрешена owner/admin/office как **новая ревизия** инвойса (`revision + 1`, старый PDF сохраняется), `AuditLog` + повторная отправка с пометкой «обновлён». Есть хотя бы один succeeded платёж → строки и итог заблокированы; исправление = новый standalone-инвойс или (позже) credit note. Void: owner/admin, только если `paid_net = 0` (иначе сначала refund); номер не переиспользуется.

**Нумерация.** `INV-xxxx` присваивается при создании по счётчику компании (multi-company: у каждой компании свой счётчик и свой Stripe-аккаунт). В режиме «Все компании» создание требует выбора компании.

**Платежи и комиссии.**
| Метод | Себестоимость Stripe | Платформа [черновик] | Где |
|---|---|---|---|
| card / tap_to_pay | 2.9% + 30¢ (tap 2.7% + 15¢ [проверить]) | +0.5% | Портал, Tap to Pay |
| ach | 0.8%, cap $5 | +0.5%, **cap $5** (чтобы ACH оставался выгодным) | Портал (Financial Connections) |
| cash / check / zelle / other | $0 | $0 | Ручная запись |
`platform_fee_cents` = Stripe `application_fee_amount` (Connect direct charges на аккаунт подрядчика). `fee_cents` берётся из balance transaction после вебхука. Комиссии показываются подрядчику до подтверждения и в каждом платеже; клиенту комиссии не добавляются.

**Калифорния: надбавки и скидки.**
- **Надбавка за оплату картой (surcharge) в CA запрещена** (Civil Code §1748.1), а SB 478 требует показывать полную цену без скрытых сборов. В MVP функции надбавки **нет ни для какого штата** (для других штатов — позже, INV-US-14).
- Скидка за наличные/ACH: §1748.1 допускает скидки за наличные; применимость к ACH и формулировки — **pending legal review**. Реализация: строка-скидка `kind=discount` «Скидка за оплату банковским переводом −X%», показывается клиенту до выбора метода и применяется только при оплате выбранным методом. По умолчанию выключено (фича-флаг `payment_method_discount`).
- **ACH-first nudge (разрешён без скидки):** в портале ACH стоит первым, если `balance ≥ $1,000` (настройка), с пометкой «Рекомендуем для крупных сумм»; карта всегда доступна; подрядчику — счётчик экономии.

**Идемпотентность (защита от двойного списания).**
1. Клиент/приложение при открытии экрана оплаты получает `payment_attempt` с `idempotency_key = hash(invoice_id, amount, attempt_no)`; тот же ключ передаётся в Stripe PaymentIntent.
2. Кнопка «Оплатить» блокируется после нажатия до ответа; повтор с тем же ключом возвращает тот же PaymentIntent.
3. Источник правды — вебхук Stripe; события обрабатываются один раз по `event.id` (таблица `WebhookEvent`).
4. Перед созданием нового PaymentIntent сервер проверяет: `balance − Σ pending ≥ amount`, иначе «Предыдущий платёж ещё обрабатывается».
5. Ручные платежи также имеют `idempotency_key` (создаётся на устройстве, офлайн-безопасно).

**Депозит до инвойса.** `Payment.invoice_id` может быть пуст только во время оформления; в MVP депозит всегда идёт через deposit-инвойс (проще учёт).

**Refund.** Только owner/admin (UI + серверная проверка роли + `AuditLog`). Сумма ≤ `amount − Σ refunds`. Card/ACH → Stripe refund; cash/check/zelle → запись «возвращено наличными/чеком» с причиной. Комиссия Stripe за карту при возврате не возвращается (показываем это до подтверждения); `application_fee` платформы возвращается пропорционально (`refund_application_fee=true`) — решение §15.

**Споры (chargeback).** Вебхук `charge.dispute.created` → `Payment.dispute_status=open`, Activity + Task владельцу с дедлайном ответа; доказательства (подпись, фото после, чек-лист) собираются в один PDF — позже, в MVP ссылка на работу.

**Payouts.** Стандартные выплаты Stripe (2 рабочих дня); instant payout — позже.

## 9. Офлайн
Без сети: просмотр инвойсов из кэша, создание **черновика** инвойса, запись наличных/чека/Zelle (outbox, статус «ожидает синхронизации», сервер проверяет баланс). Требует сети: отправка клиенту, оплата картой/ACH, tap-to-pay (офлайн-режим Stripe Terminal для Tap to Pay в MVP не используем), refund, void. Инвойсы и платежи на сервере — авторитетны (модуль 16).

## 11. Ошибки и крайние случаи
- **Двойной тап «Оплатить» / повтор запроса / возврат по кнопке «назад»** → тот же PaymentIntent (idempotency), одно списание.
- **Вебхук пришёл раньше ответа клиенту** или пришёл дважды → обработка по `event.id`, состояние монотонно.
- **ACH return** (недостаточно средств, закрытый счёт): до settlement Payment остаётся `pending` и при отказе → `failed`; return уже после `succeeded` в текущей state machine не выражается → предлагаем статус `returned` (§14, §15), баланс инвойса восстанавливается, клиенту письмо «оплата не прошла», владельцу push.
- **Клиент платит одновременно с двух устройств** → проверка `balance − pending` на сервере, второй получает «Платёж уже обрабатывается».
- **Офлайн-запись наличных, а клиент уже оплатил картой онлайн** → при синхронизации переплата: ручной платёж сохраняется с флагом `needs_review`, Task владельцу.
- **Смета изменена после депозита** (новая версия, change order) → депозит остаётся кредитом в финальном.
- **Отмена работы с оплаченным депозитом** → промпт refund (owner/admin) или удержание по условиям `terms_text`.
- **Stripe-аккаунт отключён/restricted** → онлайн-оплата скрыта, баннер владельцу, ручные платежи работают.
- **Нет прав** → кнопки скрыты и API 403; попытка пишется в AuditLog.
- **Мульти-компания:** инвойс компании A нельзя оплатить на Stripe компании B; платёж всегда на `stripe_account_id` компании документа.

## 12. MVP / позже
**MVP:** все 5 видов инвойсов (recurring — per_visit), раздельные статусы, ручной налог на инвойсе (вкл/выкл, ставка `TaxRate`, `taxable` по строкам), Stripe Connect Express (card + ACH), депозит при подписи, частичные оплаты, ручные платежи (cash/check/Zelle/other) с фото, refund owner/admin, idempotency + WebhookEvent, прозрачные комиссии и счётчик экономии ACH, ACH-first nudge, напоминания о просрочке (email; SMS при пакете), QR-оплата на месте, email-квитанции, aging, CSV-экспорт. **Tap to Pay** — MVP при своевременном одобрении Apple entitlement, иначе v1.1.
