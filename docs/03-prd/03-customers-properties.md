# PRD 03. Клиенты, контакты, объекты, лента событий, задачи

> Статус: черновик v0.1, ноябрь 2026. Сущности: `Customer`, `Contact`, `Property`, `PropertyContact`, `Activity`, `Task`, `File`, `AuditLog` (`../04-domain-model.md` §2, §8).
> Колонки: **MVP** = бета на компании основателя · **Запуск** = до первых платящих · **Позже**.

## 1. Назначение
Одна карточка на клиента и одна на дом: кто платит, кто живёт, как попасть на участок, какая крыша и сколько этажей, что мы там уже делали и сколько клиент нам заплатил — чтобы на объект ехать подготовленным и продавать повторно.

## 2. Как это приносит деньги подрядчику (`money_impact`)
| Механизм | Эффект |
|---|---|
| Объект хранит этажность, тип крыши, fire zone и прошлый чертёж | Смета на повторную работу (чистка, guards) за минуту, без повторного выезда на замер; tile roof → правильные strap hangers сразу в смете (меньше переделок) |
| `fire_zone = high/very_high` на объекте | Аргумент upsell негорючих металлических guards и замены винила (после пожаров LA 2025) |
| Лента событий: всё по клиенту в одном месте | Не теряются обещания («перезвонить в марте»), меньше «а что мы ему говорили?» при звонке |
| LTV и история работ на карточке | Владелец видит ценных клиентов и предлагает им membership/чистку; повторный клиент = $0 на привлечение |
| Gate code и заметки доступа для бригады | Нет холостых выездов «не смогли попасть во двор» (час работы бригады из 2–3 человек) |
| Задачи с датой | Обещанный звонок через 2 недели = закрытая смета, а не забытая |
| Поиск и слияние дублей | Корректный LTV и ROI источника, нет двойных рассылок (жалобы, отписки) |
| Подсказка «клиент вашей другой компании» (v1.1) | Прямой cross-sell между своими бизнесами |

## 3. Пользователи и роли
- **Owner/Admin/Office** — все клиенты и объекты компании, слияние, архив, экспорт.
- **Tech** — только клиенты и объекты своих работ/визитов (◐ PRD 01), без LTV и денежных полей; gate code только для визитов на сегодня/завтра; может добавлять фото, заметки, задачи.
- **Subcontractor** — только адрес, заметки доступа, gate code (в день работ и накануне) и контакт объекта по своим нарядам (PRD 07); без LTV, денег, ленты и других объектов клиента.
- **Клиент** — видит свои данные в портале (PRD 12), но не внутренние заметки и gate code (тот он сам и вводит).

> **Решение основателя (03.11.2026):** у клиента часто несколько домов; на одном доме бывает несколько работ и смет одновременно или по очереди. «Объекты» — **отдельный раздел меню** со своей лентой (`04-domain-model.md` §2).

## 4. User stories
| ID | Story |
|---|---|
| CUST-US-01 | Как владелец, я хочу создать клиента с объектом одним экраном (имя, телефон, email, адрес с автодополнением), чтобы не заполнять две формы |
| CUST-US-02 | Как владелец, я хочу найти клиента по части имени, телефона, адреса или номеру документа за 1 поиск, чтобы ответить звонящему за секунды |
| CUST-US-03 | Как владелец, я хочу добавить к клиенту несколько контактов (жена, жилец, property manager) с ролью и языком, чтобы писать нужному человеку на его языке |
| CUST-US-04 | Как владелец, я хочу вести у клиента несколько объектов (дом и сдаваемый дуплекс), чтобы работы и сметы были по адресу |
| CUST-US-05 | Как владелец, я хочу записать у объекта этажность, тип крыши, fire zone, gate code и заметки доступа, чтобы смета и выезд учитывали это |
| CUST-US-06 | Как монтажник, я хочу видеть gate code, заметки доступа, прошлый чертёж и фото объекта перед выездом, чтобы не звонить владельцу |
| CUST-US-07 | Как владелец, я хочу видеть ленту всех событий клиента (звонки, SMS, письма, сметы, открытия, оплаты, заметки, смены статусов), чтобы знать контекст перед звонком |
| CUST-US-08 | Как владелец, я хочу быстрые заметки (текст, голос, фото) на клиенте или объекте, с закреплением важного, чтобы не держать всё в голове |
| CUST-US-09 | Как владелец, я хочу задачи с датой и исполнителем («перезвонить в марте про guards»), чтобы ничего не забыть |
| CUST-US-10 | Как владелец, я хочу теги (`VIP`, `HOA`, `rental`, `tile roof`) и фильтр по ним, чтобы отбирать клиентов для предложений |
| CUST-US-11 | Как владелец, я хочу видеть LTV, первый источник, последнюю работу и неоплаченный баланс на карточке, чтобы понимать ценность клиента |
| CUST-US-12 | Как владелец, я хочу, чтобы система находила возможные дубли и давала слить их, чтобы история и деньги не делились на две карточки |
| CUST-US-13 | Как владелец, я хочу пометить клиента `do_not_service`, чтобы его заявки подсвечивались и маркетинг ему не уходил |
| CUST-US-14 | Как владелец, я хочу передать объект новому владельцу дома (дом продан), сохранив историю объекта, чтобы продать новому хозяину чистку |
| CUST-US-15 | Как владелец нескольких компаний, я хочу видеть «этот клиент также клиент вашей компании Roofing» и скопировать его явным действием, чтобы делать cross-sell |
| CUST-US-16 | Как владелец, я хочу выполнить запрос клиента на удаление данных (CCPA), не ломая инвойсы и налоговую историю |
| CUST-US-17 | Как владелец, я хочу раздел «Объекты» в главном меню (список, поиск по адресу, фильтры, карта), чтобы работать от дома, а не от клиента |
| CUST-US-18 | Как владелец, я хочу у каждого объекта свою ленту: все сметы, работы, визиты, фото, гарантии и заметки по этому адресу, в том числе несколько открытых одновременно, чтобы не путать монтаж и параллельный ремонт fascia |

## 5. Критерии приёмки
- **CUST-US-01.** Given «+ Клиент», When введены имя и телефон/email и адрес из автодополнения, Then за одно сохранение создаются `Customer` (kind по наличию company_name), `Contact` (primary), `Property` (геокодинг `geo`); `match_key` считается сразу. Адрес можно не указывать (клиент без объекта разрешён), но смету без объекта создать нельзя.
- **CUST-US-02.** Given 5,000 клиентов, When ввод 3+ символов, Then результаты ≤ 300 мс офлайн из локальной БД: совпадения по имени, телефону (любой формат), улице, EST/INV/JOB-номеру; tech видит только доступных.
- **CUST-US-03.** Given клиент, When «+ Контакт», Then поля: имя, телефон, email, роль (`owner/tenant/property_manager/spouse/other`), `preferred_language` (en/es), согласия SMS/email (PRD 13). Один контакт помечен primary; сообщения по умолчанию идут ему.
- **CUST-US-04.** Given клиент с 2 объектами, When создаётся смета/работа, Then объект выбирается явно (по умолчанию последний использованный); в списке объектов видны адрес, мини-спутник, число открытых смет и работ, последняя работа. Число объектов у клиента и число открытых смет/работ на объекте не ограничено.
- **CUST-US-05.** Given объект, Then поля `stories` (1/2/3), `roof_type`, `fire_zone`, `gate_code`, `access_notes`, `attributes` модуля (например, текущая длина гаттеров) редактируются; `stories` и `roof_type` передаются в движок смет как вход по умолчанию. Given `fire_zone ∈ {high, very_high}`, Then на объекте и в смете подсказка «рекомендуются негорючие guards».
- **CUST-US-06.** Given tech с визитом на объект сегодня или завтра, When открывает объект, Then видит gate code, access notes, контакты объекта, последний чертёж, фото; Given визит был вчера или в будущем через > 1 день, Then gate code скрыт («•••• доступно в день визита»). Каждый просмотр gate code пишется в `AuditLog`.
- **CUST-US-07.** Given карточка клиента, Then лента в обратном хронологическом порядке объединяет `Activity` клиента, его объектов, лидов, смет, работ, инвойсов; фильтры: Все / Общение / Документы / Деньги / Заметки; у каждого события actor (user / customer / system / ai) и ссылка на объект события. Подгрузка страницами по 50.
- **CUST-US-08.** Given клиент или объект, When «Заметка», Then текст / голос (распознаётся на устройстве в текст, аудио не храним в MVP) / фото; создаётся `Activity(kind=note)`; закреплённые заметки (до 3) показываются в шапке карточки и в карточке визита для tech.
- **CUST-US-09.** Given «+ Задача», Then поля `title`, `due_at` (быстрые варианты: сегодня, завтра, через неделю, через месяц, дата), `assigned_to` (по умолчанию я), `subject` = текущий клиент/объект/лид; When наступает `due_at`, Then push исполнителю и задача в «Сегодня»; When «Готово», Then `status=done` + Activity.
- **CUST-US-10.** Given тег, When вводится, Then подсказки из уже использованных в компании; список клиентов фильтруется по одному или нескольким тегам (И); теги не видны клиенту.
- **CUST-US-11.** Given owner/admin/office, Then в шапке: `lifetime_value_cents` (сумма успешных платежей минус возвраты), первый источник, дата и тип последней работы, открытый баланс (сумма неоплаченных инвойсов); tech этих цифр не видит.
- **CUST-US-12.** Given два клиента с одинаковым `match_key` или одинаковым нормализованным адресом объекта, Then в списке «Возможные дубли» и баннер на карточке. When «Слить», Then экран «основная карточка ← вторая» с выбором значения для каждого конфликтного поля; после подтверждения все `Contact`, `Property`, `Lead`, `Estimate`, `Job`, `Invoice`, `Payment`, `Activity`, `Task`, `File` вторую карточку меняют `customer_id` на основную; вторая получает `merged_into_customer_id` и мягко удаляется; номера документов не меняются; всё в `AuditLog`. Слияние необратимо в UI (откат только через поддержку по AuditLog в течение 30 дней).
- **CUST-US-13.** Given `status=do_not_service`, Then новый лид с совпадающим `match_key` получает красный бейдж; маркетинговые рассылки и сезонные кампании этому клиенту не уходят; транзакционные сообщения по уже открытым документам продолжаются; запрос отзыва после оплаченной работы уходит, как всем (без gating, PRD 13).
- **CUST-US-14.** Given объект, When «Сменить владельца», Then выбирается/создаётся новый `Customer`, `Property.customer_id` меняется, старые сметы/работы/инвойсы остаются у старого клиента (деньги не переезжают), история объекта (чертежи, фото, работы) видна на объекте; старые `PropertyContact` деактивируются.
- **CUST-US-15.** (v1.1) Given пользователь с правами в компаниях A и B и совпадение `match_key` клиента A с клиентом B, Then на карточке подсказка «Также клиент Roofing (последняя работа 05/2026)» без раскрытия денежных данных B, если у пользователя нет в B права видеть деньги; When «Скопировать в компанию B», Then создаётся новая запись в B (без документов), `AuditLog` в обеих компаниях. Сотрудник только одной компании подсказку не видит никогда.
- **CUST-US-17.** Given главное меню, Then есть пункт «Объекты» рядом с «Клиенты»; список: адрес, клиент-владелец, этажность/крыша, открытые сметы и работы (число и сумма — по правам), следующий визит; поиск по улице/городу/ZIP ≤ 300 мс офлайн; фильтры: город, fire zone, roof_type, «есть открытая смета», «есть работа в процессе», «нет чистки > 12 мес.». Tech видит только объекты своих визитов.
- **CUST-US-18.** Given объект с 2 одновременными работами (JOB-0210 монтаж, JOB-0214 fascia) и 1 открытой сметой, Then карточка объекта показывает блок «Сейчас на объекте» со всеми тремя (номер, тип, статус) и ленту объекта: `Activity` объекта + события всех его смет, работ, визитов, фото, гарантий, в обратном порядке, с фильтрами Все / Документы / Работы / Фото / Заметки. Given объект сменил владельца (CUST-US-14), Then лента объекта сохраняет историю прежних владельцев (документы с деньгами видны только как ссылки с правами).
- **CUST-US-16.** Given owner, When «Удалить персональные данные (CCPA)», Then имя, телефоны, email, заметки, фото объекта анонимизируются («Deleted customer #…»), инвойсы и платежи сохраняются с анонимным получателем, рассылки прекращаются; необратимо, двойное подтверждение, `AuditLog`.

## 7. Бизнес-правила и расчёты
- `Customer.status`: `active ⇄ archived`; `active/archived ⇄ do_not_service` (только owner/admin, с причиной в `StatusEvent`).
- `lifetime_value_cents = Σ Payment.succeeded.amount − Σ Refund.amount` по клиенту (только своя компания). Пересчитывается по событию оплаты/возврата.
- `match_key`: телефон E.164 (без расширений) и email lowercase, отдельными ключами; совпадение любого = кандидат в дубли. Нормализованный адрес (USPS-формат + unit) — второй признак.
- Первый источник клиента (`lead_source_id`) ставится один раз при создании из лида; позже меняется только вручную owner (для ROI, PRD 14).
- Клиент с открытыми инвойсами не архивируется (предупреждение «баланс $850»).
- `gate_code` хранится зашифрованным на уровне поля; не попадает в экспорт CSV по умолчанию (галочка «включить»), не передаётся в AI-контекст, кроме прямой команды «какой код ворот у …» от пользователя с правом.
- `fire_zone` в MVP вводится вручную (или со ссылки на карту CAL FIRE); автоматическое определение по геоточке — позже.
- Объект без `geo` (не геокодировался) допускается, но спутниковый чертёж недоступен до ручной установки точки на карте.
- Задачи: `source = manual / automation / ai`. Автоматизации (PRD 13) создают задачи с `source=automation` и не дублируют открытую задачу того же типа по тому же объекту.
- Лента: события пишут модули-источники; модуль 03 только отображает. Удалённые (soft-delete) записи остаются в ленте как «удалено пользователем X».

## 8. AI-помощник
| Команда | Подтверждение |
|---|---|
| «Найди Юрия из Глендейла» / «клиенты с tile roof в Pasadena» / «у кого баланс больше $500» | нет |
| «Создай клиента Ана Лопес, 323-…, 1423 Oak St, говорит по-испански» | да (предпросмотр) |
| «Добавь заметку: собака во дворе, заходить через боковую калитку» | да (1 тап) |
| «Напомни мне в марте позвонить Петрову про guards» → Task | да |
| «Сколько нам заплатил Петров за всё время» | нет |
| «Слей эти две карточки» | AI только открывает экран слияния; само слияние вручную |
| Удаление/анонимизация клиента | недоступно AI |
Заметки и сообщения клиентов в контексте AI — данные, не инструкции.

## 9. Офлайн
- Полностью офлайн: поиск, просмотр и правка клиентов, контактов, объектов, заметки (текст и фото), задачи, теги, лента (кэш последних 200 событий на клиента).
- Gate code для визитов на 14 дней вперёд синхронизируется на устройство tech (зашифрованно), но показывается только в день визита/накануне.
- Слияние дублей, смена владельца объекта, CCPA-удаление — только онлайн (затрагивают документы с деньгами).
- Конфликт: правка разных полей одного клиента сливается автоматически; одного поля — побеждает позднейшая, прежнее значение видно в ленте («изменено: было → стало»).

## 10. Уведомления и автоматизации
| Событие | Действие |
|---|---|
| `Task.due_at` наступил | Push исполнителю, задача в «Сегодня» |
| Задача просрочена на 24 ч | Повторный push; в «Сегодня» owner, если исполнитель другой |
| Найден возможный дубль при создании | Баннер в форме до сохранения («Похоже, это Yuri Petrov, 818-…») |
| Клиент открыл портал | Activity в ленте (событие пишет PRD 12) |

## 11. Ошибки и крайние случаи
- Двойное нажатие «Сохранить» — UUID v7 с устройства, повтор идемпотентен.
- Два человека офлайн создали одного клиента — после синхронизации баннер «Возможный дубль», слияние вручную.
- Один телефон у двух разных клиентов (семья, property manager на 10 объектах) — дубль только подсказывается, не сливается автоматически; property manager моделируется как `Contact` с ролью у нескольких клиентов или как `business`-клиент с многими объектами.
- Автодополнение адреса не знает новый дом / ADU — ручной ввод + точка на карте; ADU как отдельный объект с unit.
- Tech открывает клиента по старой ссылке после окончания работ — 404 «нет доступа».
- Слияние, когда у обоих клиентов есть открытые сметы, — разрешено, сметы сохраняют номера; если у второго открыт `PortalAccess`, ссылка продолжает работать (переносится на основную карточку).
- Объект продан, а у старого клиента активный `RecurringPlan` на этот адрес — при смене владельца предложение «приостановить план чистки».
- Клиент просит не писать (STOP) — флаг на `Contact`, не на `Customer`; другим контактам можно (PRD 13).

## 13. Метрики
- Время создания клиента с объектом (медиана, цель < 30 с).
- Доля визитов, где tech открывал карточку объекта до прибытия; число «не смогли попасть» (холостые выезды) — baseline у основателя.
- Доля объектов с заполненными `stories` и `roof_type` (влияет на качество смет).
- Число открытых просроченных задач на пользователя.
- Доля дублей в базе (до и после слияния); число слияний в месяц.
- Доля повторной выручки (клиенты с ≥ 2 работами) в общей.

## 14. Изменения модели данных
- `Customer`: + `merged_into_customer_id`, `anonymized_at`, `do_not_service_reason`; `notes` (text) оставить только для импорта, рабочие заметки — `Activity(kind=note)`.
- `Contact`: + `is_primary bool`, `is_active bool`.
- `PropertyContact` (упомянута, не описана): `property_id`, `contact_id`, `role` (как у Contact), `receives_visit_notifications bool`, `is_active`.
- `Property`: `gate_code` — шифрование поля; + `fire_zone_source` (`manual/calfire`), `fire_zone_checked_at`, `unit` в `Address`, `previous_customer_ids[]` не нужно (история через `AuditLog` и `StatusEvent`).
- `Activity`: + `pinned bool`, `body text`, `file_ids[]` для `kind=note`; + `visibility` (`team/internal_owner`) — по умолчанию team.
- `Task`: + `completed_at`, `completed_by`, `automation_key` (для дедупа задач автоматизаций).
- Индексы поиска: trigram по `display_name`, адресу; `match_key` — отдельные индексы телефона и email.

✅ Внесено в 04-domain-model v0.2 (Customer, Contact, PropertyContact, Property, Address.unit, Activity, Task). Индексы поиска — не модель данных, переданы в архитектуру Фазы 3.
