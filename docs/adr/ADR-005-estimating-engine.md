# ADR-005. Движок смет — общий детерминированный пакет с decimal-деньгами

- **Статус:** Proposed — needs founder/tech review
- **Дата:** 03.11.2026
- **Связано:** `02-product-vision.md` §4, `04-domain-model.md` §0, §3 (Assembly), PRD `05`, `06`, `18-money-test-cases.md`, ADR-002

## Контекст
- Смета считается **офлайн на телефоне** и должна совпасть с серверной **до цента** (`16` OFF-US-02: «разница = 0»).
- Правила денег: целые центы, ставки в bps, округление везде одно — round half up (`04` §0); длины `numeric(10,3)`.
- Формулы сборок редактирует компания (`ceil(gutter_lf / hanger_spacing_ft)`), значит нужен **безопасный** вычислитель выражений, а не `eval`.
- AI не считает и не придумывает цены (`15` §7.5) — он только передаёт входы.
- JS `number` (двоичная плавающая точка) даёт ошибки вида `0.1 + 0.2`; для денег недопустимо.

## Варианты
| Вариант | Плюсы | Минусы |
|---|---|---|
| **A. Один TS-пакет, decimal-библиотека + свой парсер формул** | Один код на Hermes, Node, Deno; детерминизм проверяется общими golden-тестами | Нужна дисциплина: никаких `number` в промежуточных расчётах |
| B. Расчёт только на сервере, телефон показывает «≈» | Проще | Нарушает офлайн-требование (смета у клиента без сети) |
| C. Расчёт в Postgres (PL/pgSQL), на телефоне — копия на TS | Источник правды в БД | Два реализации одной логики → расхождения |
| D. Rust/WASM общий модуль | Строгая арифметика | Сложность сборки под Hermes/Deno, мало пользы для нашего объёма |

## Решение
**Вариант A** [Совет]:
1. `packages/estimating-engine` — чистые функции без I/O: `calculate(inputs, assemblies, catalogSnapshot, taxContext, engineVersion) → {lines, options, totals, bom, cutList, coil, warnings, calcHash}`.
2. **Числа:** входы/выходы денег — целые центы (`bigint` в БД, `number` в безопасном диапазоне в TS); вся промежуточная арифметика — decimal (например, `decimal.js` с фиксированной конфигурацией: точность ≥ 34 знаков, `ROUND_HALF_UP`), версия библиотеки закреплена точно. Округление до центов — **только** в определённых точках (строка, скидка, налог, итог) по `05` §7.2; порядок операций описан в спецификации движка и покрыт тестами.
3. **Формулы:** собственный маленький парсер (Pratt) с whitelist: `+ - * / ( )`, сравнения, `and/or/not`, `ceil floor round min max if`, переменные только из `inputs`/`constants`. Нет доступа к объектам JS, нет `eval/Function`. Ошибка формулы → ошибка расчёта, без молчаливой подстановки (`04` AssemblyComponent).
4. **Геометрия** гаттеров (длины, углы, end caps) — в `packages/gutters`, тоже decimal на выходе (футы, 3 знака), вход — гео-координаты чертежа (ADR-004).
5. **Версионирование:** `engine_version` = semver пакета; хранится в `EstimateVersion`. Старые сметы не пересчитываются автоматически; пересчёт — явное действие «Пересчитать» с новой версией.
6. **Проверка сервером:** при синхронизации и перед отправкой клиенту сервер пересчитывает тем же пакетом и сравнивает `calcHash` (SHA-256 канонического JSON результата). Расхождение → версия не отправляется, ошибка в Sentry, Task владельцу.
7. **Тесты:** golden-кейсы в `packages/test-fixtures` (PRD 18 §I, прайс основателя Г1, правила замера Г2, `Assembly.test_cases`) прогоняются в CI в Node, Deno и Hermes; property-based тесты (fast-check) на инварианты (сумма строк = subtotal, налог ≥ 0, override виден).

## Последствия
- ✅ «Одинаково на телефоне и сервере» доказывается тестами, а не обещанием.
- ✅ AI-помощник вызывает тот же движок на dry-run (ADR-006) — предпросмотр совпадает с применённым результатом.
- ⚠️ Производительность: смета до ~200 строк × 3 варианта должна считаться ≤ 1 с офлайн на iPhone 12 (`06` §5); проверяем бенчмарком в Sprint 0 (decimal медленнее `number`, но объёмы маленькие).
- ⚠️ Изменение порядка округления = новая major-версия движка и запись в журнал изменений.
- Нужна короткая спецификация движка (порядок вычислений, точки округления) — часть Фазы 3 вместе со схемой БД.
