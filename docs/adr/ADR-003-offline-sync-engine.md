# ADR-003. Движок офлайн-синхронизации

- **Статус:** Proposed — needs founder/tech review
- **Дата:** 03.11.2026
- **Закрывает:** Д2 (`03-prd/00-decisions-for-founder.md`), `16` §15 п. 2
- **Связано:** `06-architecture.md` §6, PRD `16-offline-sync.md`

## Контекст
Требования PRD 16 (не зависят от выбора движка):
- частичная реплика **по пользователю и роли** (tech — только свои визиты; sub — только свои наряды без цен; cost-поля не уходят на устройство без права);
- офлайн-**запись** часами и днями (каньоны LA), outbox переживает убийство приложения;
- сервер авторитетен для денег; офлайн-подпись и ручной платёж — «заявки»;
- слияние по полям для черновиков и простых записей, «две версии» при пересечении, state machine для статусов в порядке `created_at_device`;
- идемпотентность каждой операции (`op_id`), зашифрованная локальная БД, удалённое стирание;
- Supabase Postgres как источник правды; RLS проверяется на каждой операции.

## Решение
**Вариант A — PowerSync для чтения и локальной очереди + наш endpoint `/sync/ops` для записи** [Совет]:
1. **Чтение:** Sync Streams, параметризованные `user_id`, компаниями членства и ролью. Таблицы с себестоимостью и закрытые проекции (ADR-001, `06` §4.3) в стримы ролей `tech`/`subcontractor` не входят. Окна данных — `16` §7.
2. **Запись:** клиент пишет в локальные таблицы транзакционно и добавляет запись в собственный журнал операций (`op_id`, `entity`, `kind`, `payload` изменённых полей, `base_row_version`, `idempotency_key`, `created_at_device`, зависимости). `uploadData` отправляет пачку на `POST /sync/ops` (Edge Function, JWT пользователя).
3. **Сервер** на каждую операцию: дедуп по `op_id` (`sync_operation`) → проверка RLS-контекстом пользователя → класс данных (`16` §7): деньги — заявка и валидация; черновики и простые записи — merge по полям через `field_versions jsonb`; статусы — state machine по `created_at_device`; append-only — принять. Ответ: `applied | merged | conflict | rejected` + серверные номера и `row_version`.
4. **Фатальные ошибки** (4xx) не блокируют очередь: операция уходит в «Ошибки» на экране синхронизации (`16` §6), для денежных — без кнопки «удалить».
5. **Безопасность:** SQLCipher, ключ в Keychain; `device.revoked_at`/`membership.suspended_at` → стирание при следующем контакте.
6. **Хостинг:** PowerSync Cloud (Free на разработке, Pro на бете). Self-host Open Edition — план Б при росте или требованиях к данным.
7. **Выходная стратегия:** локальная схема и протокол `/sync/ops` — наши; заменить нужно только поток чтения (на Electric shapes или свой delta-endpoint), без изменения модели данных и серверной логики записи.

## Последствия
- ✅ Не пишем самое трудное (поток изменений из WAL, частичную реплику, локальную реактивную БД).
- ✅ Деньги и статусы защищены сервером независимо от движка.
- ⚠️ Нужно добавить в модель (`04` v0.3): `field_versions jsonb` у черновиков и простых сущностей, `sync_operation.batch_id`, отдельные cost-таблицы.
- ⚠️ Тесты T1–T12 (`16` §11) — обязательный ночной прогон (Maestro + управление сетью) с первого среза.
- ⚠️ Стоимость: Pro от $49/мес и лимит 1,000 одновременных клиентов (до 3,000 с доплатой) — хватает на первые сотни компаний (F11).
- ⚠️ Веб в MVP онлайн (без офлайна, `16` OFF-US-13) — читает Supabase напрямую через RLS и пишет через API.
- 🔁 Пересмотреть, если: Sync Streams не покроют правило «tech видит только свои визиты» без сложных обходов (проверяем в Sprint 0 прототипом на 5,000 клиентов, T10).
