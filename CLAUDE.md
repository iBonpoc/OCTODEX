# OCTODEX — правила репозитория

Название продукта: **OCTODEX** (решение основателя 03.11.2026). «Наряд» — только имя дизайн-системы в `design/naryad-ds/`. Estixa — старый отдельный проект, его не трогать. **Estixa не копировать** (неудачный проект основателя): идею оттуда можно взять только после разбора — почему она нужна OCTODEX, — и с этим обоснованием в спецификации.

CRM/FSM для подрядчиков США **любых направлений** (клиенты, лиды, сметы, счета, оплаты, расписание). **Ядро общее и не привязано к нише**; специфика trade живёт в **модулях** (первый — Gutters: чертёж, формулы, каталог; затем Roofing и др.). Для ниш без модуля — универсальная смета из позиций каталога и шаблонов. Работа идёт **с телефона**; планшет и десктоп — то же приложение.

Правило планирования: ничего gutter-специфичного в ядре (экраны, сущности, тексты). Всё про гаттеры — внутри модуля Gutters и включается настройкой компании.

## Где что
- `apps/mobile` — единое приложение Expo Router (iOS, Android, планшет, веб). Экраны в `src/app/`, всё остальное вне `src/app/`.
- `packages/design-tokens` — токены «Наряда» в TS (зеркало `design/naryad-ds/tokens/*.css`).
- `packages/estimating-engine` — расчёт смет и денег (decimal, центы), 50+ тестов.
- `design/naryad-ds/` — дизайн-система основателя (источник правды по виду). Прочитать её `CLAUDE.md`, `HANDOFF.md`, `CHECKLIST.md`.
- `docs/` — продукт, PRD, модель данных, архитектура, ADR, юр. исследование; план сборки `docs/10-build-plan.md`.

Публикует в Expo Go (канал `preview`) только `release.yml` после слияния в `main`. Миграции базы — новым файлом с уникальным временем, слитые миграции не правим.

## Правила (не нарушать)
1. **Только токены.** Ни одного «своего» цвета, размера, радиуса, шрифта, длительности в компонентах. Нет токена — сначала добавить в `packages/design-tokens`. Новая выгрузка дизайн-системы кладётся в `design/naryad-ds/`, затем значения переносятся в `packages/design-tokens`, пока не позеленеет `mirror.test.ts`.
2. **Цвет только для статуса** (ok / info / warn / bad / neutral), всегда значок + слово. Один акцент `acc` для главного действия.
3. Кнопки видимые ≤ 36 (телефон 36, планшет/десктоп 28/32), зона нажатия 44 (`Press visibleHeight`). Поля 44 на телефоне.
4. Обе темы (тёмная и светлая) и три ширины (390 / 820 / 1280) проверяются на каждом экране.
5. Необратимое действие — подтверждение или тост «Отменить» на 5 секунд (мутации стора возвращают `undo`).
6. Офлайн с первого дня: изменения сразу локально, без сети — в очередь (`useStore().queue`).
7. Все строки через i18n (`src/i18n`: RU/EN/ES, ключи одинаковые — проверяет TypeScript). Деньги и даты всегда в формате США (`$`, en-US).
8. Деньги — целые центы, считать только через `@octo/estimating-engine`.
9. Тестовые цены только с пометкой «тестовые»; реальные цены в код не вносить.
10. Не коммитить в `main`; PR — только по просьбе.
11. **Номер сборки.** В каждом PR, который меняет приложение, ставить `BUILD` в `apps/mobile/src/config/version.ts` равным номеру этого PR. Он виден в шапке каждого экрана («OCTODEX v1.0.0 · 18 · дата публикации»), по нему основатель понимает, какая версия открыта.
12. **Списки — карточками.** Каждый объект в списке (клиент, лид, смета, счёт, квитанция, позиция каталога, пункт «Требует внимания», уведомление) — отдельная карточка: `CardList` + `ItemCard` из `src/ui/surfaces.tsx`. Строки внутри одной карточки — только детали одного объекта (итоги, суммы, строки сметы). Меню выбора в шторках (клиент, позиция каталога, мастер) — строками.
13. **Проверки перед каждым PR — обязательно.** `npm run check` (типы; тесты приложения со сторожем дизайн-системы `apps/mobile/test/designSystem.test.ts`; денежные сценарии движка; токены и контраст; тесты базы; сверка токенов приложения с CSS дизайн-системы `packages/design-tokens/test/mirror.test.ts`) и `npm run check:e2e` (сквозные прогоны в браузере `apps/mobile/e2e/specs/*`, 3 ширины × 2 темы). Новая функция = новый тест (денежная — в движке и в базе, экранная — e2e-спека). На GitHub то же самое запускает `.github/workflows/checks.yml`; вливать только при зелёных проверках.

14. **Карта пути — сначала.** Порядок сборки и все стыки между шагами — в `docs/15-story-map.md`. Новая функция сначала находит там свою клетку и стык; новый статус сначала вносится в её §5. Углубление шага — по шаблону §7 (образец `docs/14-leads-spec.md`).
15. **Тесты везде, без исключений.** Каждый стык из карты — e2e-спека; каждый переход статуса и вычисляемое правило — модульный тест; каждый денежный расчёт — тест движка и базы; каждое правило доступа — тест базы (RLS); каждая миграция — на чистой и текущей базе; каждая исправленная ошибка — тест, который падал до исправления. Функция без тестов не считается готовой, PR без них не вливается.

## Команды
```bash
npm install                                   # из корня (workspaces)
cd apps/mobile
npx expo start                                # разработка (Expo Go / dev build / web)
npx tsc --noEmit && npx vitest run            # типы и тесты приложения
npm run check        # (из корня) все быстрые проверки: типы, тесты, дизайн-сторож, база
npm run check:e2e    # (из корня) сборка сайта + сквозные прогоны в браузере
npm run preview:web                           # веб-сборка, открываемая по ссылке (.preview-web/)
cd ../../packages/estimating-engine && npx vitest run
```
Зависимости приложения ставить только `npx expo install <pkg>`.
