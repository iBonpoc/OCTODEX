## Миграции и права
- Функции схемы `app` не видны PostgREST: нужна обёртка в `public`, право — только `service_role` (A:131, 145).
- `create or replace` функции, которую меняет ещё не влитый PR, затирает его правки: тело брать из последней версии, включая открытые PR; чужую политику так же не перетирать без сверки (A:205, 634).
- `revoke` на колонку ломает `select *` у старых сборок и не отличает офис от мастера: скрытые данные (себестоимость) — в отдельную таблицу-спутник со своим RLS (A:84, 205).
- Перенос данных в миграции — напрямую, триггеры на время переноса выключить (A:84).
- Агент `security-check` — после каждой правки миграции, а не один раз (A:84, 145, 502, 662, 770).
- Триггерные функции: `revoke` от `public, anon, authenticated`, без `grant` (A:509). Вложенный вызов функции из триггера тоже проверяет `EXECUTE` (A:472). `alter default privileges` по схеме не снимает `EXECUTE` у `PUBLIC` (A:490).
- `has_table_privilege` проверяет одно право за вызов; права на колонки — `has_any_column_privilege` (A:490, 608).
- На новой таблице с `company_id` — триггер `t11_company_id_immutable`; сторожа T50 и T59 ловят новые таблицы с `user_id`/`company_id` (A:421, 641).
- Индекс на каждом внешнем ключе (сторож базы) (A:409). Частичный индекс помогает внешнему ключу, только если условие — «колонка IS NOT NULL» (A:527). `db push` сам выносит `create index concurrently` из транзакции (A:527).
- Сторож по каталогу базы (`pg_proc`, права) ловит то, чего не видит сверка по тексту миграций (A:527).

## upsert и триггеры
- `BEFORE INSERT` срабатывает до `ON CONFLICT`: в `EXCLUDED` уже строка, изменённая триггером. Проверки при upsert сравнивают с существующей строкой; надёжнее — insert с `ignoreDuplicates` плюс отдельный update (A:212, 344, 409).
- upsert всеми колонками требует `grant update` и на `id`, `company_id` (A:212). upsert с `ignoreDuplicates` без права `INSERT` даёт 42501 (A:479).
- upsert мастера проверяется политикой insert — отметки мастера слать как update одной строки (A:358).
- Мастеру закрыт `jobs_update`: переходы статуса работы — только триггером или серверной функцией (A:662).
- Системные UPDATE, которые задевает сторож владельца (миграция 110000), — под флагом `app.accepting_invite` (A:641).

## security definer
- В `security definer` `current_user` — владелец функции: страж прав — invoker, чтение служебных таблиц — definer (пример `app.po_move_ok`) (A:212, 509).
- `FOR SHARE` в триггере без definer требует прав у вызывающего — такой триггер делать definer (A:114). Триггер-definer первой строкой отказывает всем, кто не сотрудник (A:667).
- Тексты отказов одинаковые для «нет строки» и «нет прав» — иначе перебор чужих id (A:409). Внутренности SQL (`DETAIL`, текст запроса) в ошибке наружу не отдавать (L:28, 30).

## RLS и целостность
- Soft delete под RLS: строку с `deleted_at` должно быть видно по политике select, иначе update падает (A:358).
- Под `FORCE RLS` проверять постусловие (строка правда изменилась); `force RLS` плюс definer без `BYPASSRLS` — нужны политики select и delete (A:634, 641).
- «insert or nothing» молчит и при чужом id, и при своей удалённой строке — после вставки читать строку обратно (A:375).
- «Один раз на строку» — метка плюс `for update` (A:184). Сверка токена — под той же блокировкой, что и действие (L:33).

## plpgsql и данные
- Псевдоним таблицы совпал с переменной цикла — ошибка «record has no field» (A:190). `new.<поле>` в общей триггерной функции — разбирать по таблицам раздельно (A:509).
- `CHECK` с `like_regex` — с флагом `"s"` (A:413).
- `at time zone` принимает больше, чем `pg_timezone_names`; EST/MST без перехода часов — допустимые пояса своим списком (A:472).
- Текст перед записью чистить от `\n` и резать по длине (A:68). Почту человека брать только из `auth.users` (A:502). Статус участника — `'disabled'`, не `'suspended'` (A:521).
- Задача по расписанию не смотрит всю таблицу каждую минуту: отбор в SQL с лимитом на компанию, индексы concurrently; тайм-аут на самой функции не действует. Старые строки не должны закрывать новые — лимит и порядок отбора (L:83).

## Тесты базы
- Свои пользователи в каждом T-тесте, id явно (`gen_random_uuid()`) (A:413, 421, 705). Каждый оператор — своя транзакция, `now()` сравнивать с допуском (A:690).
- Помощники: `tst.set_token`, `tst.est_of`; отказы — `tst.fails_like` по тексту ошибки. «Падал до правки» подтверждать текстом ошибки, а не кодом (A:205, 490, 527, 634).
- Шаги функций `app.*` в тестах — от суперпользователя; `service_role` нужен grant на схему `tst` (A:184, 705).
- Плохие данные и фикстуры журнала заводить мимо триггеров (`session_replication_role`) (A:472, 634). Заготовки в `core_rls.sql` ломаются новыми проверками — триггер выключать в SEED и включать перед своим тестом (A:114). `t40_child_lock` действует и для суперпользователя — фикстуры до `locked_at` (A:126).
- Новая серверная проверка — сразу найти старые тесты, которые делают то же от имени участника, и починить (A:126).
- В `core_rls` с T38/T45 `office_a` уже admin — проверку «не owner/admin» делать на `sales_a` (A:657, 667).
- Тест «после обновления»: уборка детей по внешним ключам (A:472).
- Конфликт в `supabase/tests/core_rls.sql` при каждой новой миграции: брать оба блока, `\echo 'ALL TESTS PASSED'` — последней строкой (B:143).
- Supabase CLI оставляет `supabase/.temp` — удалять, не коммитить (A:620).
